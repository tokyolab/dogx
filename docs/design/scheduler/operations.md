Cron 输入遵守[固定六字段规则](behavior.md#cron-contract)，不提供 Job 时区选择。独立预览接口从调度进程当前时间计算未来最多 5 个时间点，不查库、不注册规则，以带偏移的 RFC 3339 返回；不能在浏览器改用 Quartz 解析器或按浏览器本地时区重新解释表达式。接口边界见[管理契约](data-contracts.md#job-management-proposal)，页面布局仍待设计。

第一版固定双端异步回报，执行器每次 RPC 上报一个结果，不提供同步／异步或网络合批切换开关。执行器回报组件默认保留 256 条结果（包含待首次发送、延迟重试和在途），回报 RPC 并发默认 16，二者属于部署参数；单次 RPC 2 秒、应用层最多 7 次总调用及带抖动的重试间隔使用独立内部常量，不消耗 Task 执行预算，详见[回报初值](execution.md#reporting-defaults)。执行器业务处理并发默认 32、业务等待队列默认 128，均为部署参数，见[业务初值](execution.md#executor-business-defaults)。调度端结果逐条 JOIN 核验、条件 UPDATE 并独立提交，默认保留 512 条、保存并发 8、一次处理 2 秒，均部署可调；详见[调度端保存初值](execution.md#scheduler-result-defaults)。不设置执行器网络合批窗口或批次数量参数；这些参数均不进入 Job 页面。

执行器回报组件内的结果从接纳到 ACK、永久错误或重试耗尽始终占原保留位置，发送中和等待重试的记录不移到容量之外；尚未完成交接的结果由有限业务处理者持有。调度端 512 条保留范围包含首次待处理、延迟重试和正在保存的记录，不另加 8 条在途额度；一次处理结束即释放保存并发，退避保留原位置但不占并发。各条保存独立提交，一条失败不回滚或重放其他已提交结果。报文大小复用 RPC 上限，不另建跨业务阶段统一计数，第一版不提供队列总内存 MB 配额或独立业务结果长度配置。调度端写库故障不设置次数耗尽或保留 TTL 清理，具体边界见[结果保留策略](execution.md#scheduler-result-retention)。

实现状态：2026-11-04 公共执行器 Runtime／reporter 已实现业务 32／等待 128 与结果保留 256／发送 16 的组件配置，包含活动防重、取消、结果交接、有限重传及安全丢弃诊断；2026-11-05 已接入 System 的 `JobExecutor.Runtime`，解码省略值使用默认值，显式非正值拒绝。当前尚无生产处理器，本轮验证与剩余链路见 [System 内嵌接线记录](ordinary-readiness-review.md#ordinary-system-executor-wiring-progress)，初值不代表压测结论。

2026-10-30 已通过[结果回报错误分类与无效结果处理](data-contracts.md#result-error-classification)。接收 ACK 正常结束执行器上报；队满 `ResourceExhausted`、未就绪／退出／认证依赖失败 `Unavailable` 及无法确定性质的通信故障、未知码或异常响应按既定预算有限重传。明确 `Unauthenticated`／`PermissionDenied`，或既有 `bizerror` 的 `common.invalid_request`，结束该条重传并记录诊断；不解析错误文案。通用 `ResourceExhausted` 不能据以判定报文超大，只有本地能够证明实际发送上限被超过或确定格式错误时才可直接释放。此分类只适用于结果回报，不改变派发、取消和管理接口的错误契约。

管理操作复用 DogX 菜单与 API 角色权限，不限定为超级管理员专属。第一版不提供重开历史 Instance 或手动选择失败分片重跑；新建一轮手动执行可能再次处理已成功业务，不应包装为等价操作。

Job 配置编辑采用完整可编辑配置提交，与启停入口分开；说明和参数省略／null／空串均清空，其他必需配置缺失拒绝。说明及参数统一去首尾空白，参数内部内容不改；零重试和 false 明确生效，不用创建默认值替代。该入口不做 PATCH，不增加编辑版本号，允许同时编辑停用 Job 时后提交覆盖前者。普通新增 Job 返回 Job ID，不增加请求防重，响应不明时不能盲目自动重建；这与下方手动触发的同请求号重试不同。数据库提交成功不等于 Leader 已应用配置，通知失败仍按分钟核对兜底。

手动停止按[停止状态协议](data-contracts.md#instance-termination-sql)及[终态规则](behavior.md#terminal-order)处理：父为 WAITING 或 RUNNING 时先保存 `STOPPING` 和人工停止原因，即使已过截止也不改判超时；已有 STOPPING 保留原原因，已有终态如实返回。成功反馈仅表示停止决定已经确认落库，不等待全部子 Task 状态结束、停止 RPC 成功或业务退出。后台有界取消未结束子 Task，全部子记录终态后才将父最终设为 CANCELED；超时入口则按冻结的超时原因最终设为 FAILED。

新 STOPPING 决定提交确认后，分别向数据库取消处理和[远端取消通知](execution.md#cancel-notification-capacity)交接，两条路径独立接纳、独立执行，一条路径接纳失败不阻止另一条尝试接纳。不因每批子 Task 更新、每 2 分钟 STOPPING 扫描，或重复停止请求读到既有决定就重新启动通知；数据库恢复责任不等于可靠补送 RPC。提交不明后确认结果可能造成重复通知，本地合并排队和处理中的重复提示，不增加永久通知记录或全局通知锁。

STOPPING 是非终态，页面单独显示“停止中”，不与运行阶段拼接；此时 `finished_at` 为空，`end_reason` 已保存本次停止决定。阻塞丢弃策略继续丢弃后续触发，直到 Instance 最终结束才解除阻塞；已丢弃触发不补跑。Job／组删除与历史保留也继续将 STOPPING 视为未结束。数据库处理积压会延后最终结束时间及解除阻塞，但不表示平台正在等待远端业务退出。

停止决定提交不明且有限处理仍无法确认时，返回未确认，由调用方查询或重试，不能显示为确定已接受。实际已落库的决定由 [STOPPING 恢复](execution.md#stopping-recovery)继续处理，实际未落库的人工意图不能凭空恢复；[最小停止管理契约](data-contracts.md#execution-management-contract)已通过：返回已确认观察到的 ID、状态和原因；提交不明按错误反馈，不伪装成已接受。停止管理协议、后台处理与恢复已接通，实际验证见[停止运行记录](ordinary-readiness-review.md#ordinary-stop-runtime-progress)；前端页面交互仍待落实。

### 手动执行反馈与重发 {#manual-trigger-ui}

手动执行默认沿用 Job 参数，可仅替换本轮业务参数；不临时改写组、处理器、重试、超时或节点地址，也不把当次输入保存回 Job。停用 Job 仍允许手动验证，定时进度不变，集群阻塞判断不能绕过。

一次操作使用同一 `request_id`，网络超时重发沿用原号和原内容；明确再执行一次才换新号。后端提交 Instance 与本轮配置成功后返回 ID，页面提示“已创建执行记录”，后续通过执行记录查看状态，不把提交成功提示成“执行成功”。Job 未删除、原实例已经失败或取消时，同号重发仍返回原 ID，不重开旧记录。

收到明确阻塞拒绝就结束本次操作，不在后台等待补跑。手动与自动入口共用本进程创建并发额度，没有空位时明确返回系统繁忙，不另排手动等待队列。重试沿用原请求号；本次繁忙不能证明此前同号请求没有创建成功。响应不明不等于未创建，不能自动换号再提交；相同请求号改参数返回冲突。拒绝结果不永久留痕，同号迟到重试可能在条件满足后创建；原请求重放仅在 Job 未删除且执行记录仍保留时适用。Job 删除后，旧手动创建请求返回不存在，但原 Instance 仍可按 ID 查询，不能据此认定原请求未执行；完整规则见[手动触发](behavior.md#manual-trigger)。页面布局、请求表达及重试交互在管理契约中细化。

Job 删除沿用 `deleted_at` 标记，不物理清除定义，也不同时清理 Instance／Task。普通管理页面不展示已删除 Job，第一版不提供恢复站；历史按 Instance 快照继续查询，不要求关联有效 Job。必要的只读关联可查看已删除 Job 的最后定义，但这不是每轮执行时的完整配置历史。删除前置条件、并发检查及子 Task 收敛边界见[Job 逻辑删除](behavior.md#job-deletion)。

新增、编辑保存、启用 Job 及手动新建 Instance 时，校验目标组存在且允许引用；已有同请求号成功记录按原查重规则处理，前提仍是 Job 未删除。组内暂无在线执行器不阻止这些管理操作；处理器名称只做必填和本地输入校验，不做远程探测。停用、删除 Job 不依赖组存在或在线，其他删除前置条件不变。该校验不增加到每次 Cron 触发或 Task 派发，完整边界见[组引用与离线配置](data-contracts.md#job-group-reference-proposal)。

基础组管理不要求运维人员逐台录入实例 IP，也不替代业务程序部署。新增组无需修改或重启调度服务来增加映射；业务执行器仍需配置正确的组名和注册范围。组配置采用[未命中回源与周期完整替换](#group-cache)，正常情况下首次使用新组不等待下一次周期刷新，但不承诺提交即全节点同步完成；[删除后的客户端清理](#group-client-cleanup)及[启动退出规则](#startup-readiness)已定，管理反馈、装配与具体连接创建流程仍须落实。

第一版组管理不设启停，只做[逻辑删除](data-contracts.md#executor-group-lifecycle)。组引用与删除采用已通过的[共同组行锁协议](data-contracts.md#group-reference-concurrency-proposal)，只串行协调同组的低频新增／编辑与删组，不给执行主路径加锁。未删除 Job（含停用）、原组快照的未结束 Instance 和未收敛 Task 均阻止删组；无恢复依赖的已完成历史不永久阻挡。删除仅标记组定义，不级联删除历史，不自动取消任务或关闭执行器进程。凭据随完整快照更新，[连接缓存按下节清理](#group-client-cleanup)；删除保护、取消恢复边界及清理规则仍须实现验证，未完成前不开放入口。

### 普通执行阶段的最小管理入口 {#minimal-management}

[组字段与管理契约](data-contracts.md#executor-group-management-contract)和[执行查询／停止契约](data-contracts.md#execution-management-contract)已于 2026-11-02 通过。先实现组创建、详情、分页列表与删除四个入口，不增加组编辑；列表可直接供 Job 选组，不另建选项接口。所有组记录必须具备完整字段，软删除保留原字段值；字段与约束按正式契约落实。

执行侧先提供 `GetInstance(id)`、`ListInstanceTasks(instanceId, page, pageSize)` 与 `StopInstance(id)`。详情读取本轮冻结事实，保留已删除 Job 的历史查询；Task 按 ID 稳定分页、每页最多 200 条，只读运行事实和摘要，不加载业务 Data 或追加整轮成功／失败统计。不存在 Instance 返回业务错误，存在但尚无 Task 返回空列表。最近摘要可能来自前次尝试，不能充当本次完成证据。

停止反馈已确认观察的 Instance ID、状态及原因：新人工决定为 STOPPING／manual_stop；已有 STOPPING 或终态如实返回、保留原原因，不因重复请求重发取消通知；数据库失败或提交不明返回错误。用户可查询或重试，不将响应成功解释为所有子状态已结束或业务已退出。

管理入口复用 System API 的登录／权限及 Job 管理 RPC，不增加独立鉴权机制；参数错误、业务错误与技术原因链沿现有风格。全局执行历史列表、Task 业务 Data 详情及完整页面留给后续管理模块。普通闭环先开发验收，完整执行能力待分片完成后正式发布，见[发布边界](progress.md#ordinary-integration-contract)。本节是已批准设计，不表示入口已经可用。

## 7.2 业务接入责任

业务团队编写并显式注册具名 Go 处理器，在 Job 配置中引用名称；平台不要求为每种业务任务新增 RPC 方法。业务代码解释参数、访问所属业务域数据，并为准备、分片与收尾可能产生的副作用设计幂等键。

幂等键需匹配业务操作，例如按商户和统计日期约束日报，不能仅依赖 Task ID 或尝试 ID，否则跨 Instance 重跑仍可能重复业务数据。处理器还需配合取消上下文；平台无法保证不响应取消的业务代码立即停止。

合理分片是业务接入规范的一部分，平台负责 RPC 报文上限、队列长度、处理并发和满载时的行为。[排队、并发与满载处理](execution.md#capacity-model)确认普通、准备、分片和收尾共用进程内的业务队列及处理并发；业务结束后交给有界回报组件，由独立有限并发的发送者逐条发送，每次 RPC 结束即释放发送并发，退避期间只保留结果。结果保留位置满时，当前业务处理者持有已完成结果等待交接，仍占业务处理并发，期间不领取下一项；活动防重仍在业务实际退出时清理。长业务不能被抢占，交接等待也可能增加排队时间，不保证短任务或 Pre／Post 立即执行。每执行器进程采用[业务并发 32、等待队列 128 的初值](execution.md#executor-business-defaults)，回报组件采用[独立初值](execution.md#reporting-defaults)；Go 内部组织结合完整执行、取消及停机需求落实。

第一版交付普通任务和分片任务接入示例及最小部署说明。平台不提供配置任意 HTTP／RPC 目标的执行方式；处理器可根据业务需要自行调用其他服务，但仍遵守数据所有权与幂等责任。

## 7.3 部署与内部安全

调度服务以 `job-rpc` 进程独立多副本部署，Leader 为其中一个副本额外承担的角色，不另建专用 Leader 部署。每个进程内分别运行管理与执行器通信两个 RPC Server，共用一套调度运行组件和数据库连接池，不增加内部 RPC 转发。System 第一版内嵌执行组件于 `system-rpc`，由组件创建执行器专用 Server，与原业务 Server 分开；暂不新增 Worker 进程，但组件、处理器和依赖注入保持可由后续同域 Worker 复用，不能将内嵌视为资源隔离。

[恢复资源分工](execution.md#recovery-resources)按职责复用已有派发、结果保存和 Instance 检查组件；恢复候选扫描、未知结算和子 Task 状态收敛不占派发协程，结果消费者不兼任扫描或清理。真实恢复派发仍与新任务共用派发容量，数据库连接池、CPU 与数据库 I/O 仍共享。RUNNING Instance 已确认由 Leader 每 2 分钟执行或继续有界扫描，开始时间门槛为本趟数据库时间减 4 分钟，每页 256 条，候选交本节点已有检查组件。正常提示与恢复候选共用[Instance 检查初值](execution.md#instance-check-defaults)：每节点 512 个唯一 ID（含合并等待、排队和处理中）、并发 8、单次处理 2 秒。[RUNNING 复核初值](execution.md#instance-recheck-defaults)已确定单次候选查询 1 秒、每周期扫描交接 5 秒；恢复仅在集合占用低于总量一半时接纳新 ID，达到水位或满时在剩余预算内等待释放再继续，已有 ID 仍可合并。不按来源计数或划分检查并发，也不保证持续正常负载下恢复仍有固定份额。STOPPING 的预算及满时退出规则独立，不能相互套用。[无绑定观察结算](#unbound-recovery-configuration)由每个调度节点独立执行一条不重叠的串行流程，每次实际结束后等待 10 秒并加 ±20% 抖动；不占上述业务组件的处理并发，也不新增长期候选队列或工作池。其他恢复类别的节点分工和周期不由本项一并确定。部署参数和压测需同时约束后台查询及处理量，不能以协程分开承诺彼此不影响，也不承诺一次扫完。

每个进程使用一份配置文件，分别配置两个入口的监听、服务发现及 RPC 中间件。新增执行通信的 Server 和 Client 使用 zrpc，注册发现沿用 etcd；既有管理及普通业务入口保留原有直连或发现配置。进程级配置由宿主提供同一来源，不同用途的地址不得混入同一发现 Key。管理 RPC 与普通业务 RPC 保留 go-zero 原生鉴权配置能力，由部署方决定是否启用及配置配套客户端凭据；Job 组件不增加管理权限机制，也不强制新增网络访问规则。组 Token 仅应用于执行协议入口，不能把分开 Server 解释为已经自动限制了所有调用方的访问权限。具体装配边界见[RPC 入口与鉴权装配](architecture.md#rpc-boundaries)。

配置布局采用[执行接入配置与来源](architecture.md#execution-configuration)：Job 保留顶层管理 RPC，新增 `ExecutionRPC`；System 保留顶层业务 RPC，新增 `JobExecutor`，包含作为接入身份的组名、组 Token、`Server` 与 `ReportClient`。调度端派发目标由部署的 etcd 连接信息和数据库中的组发现 Key 组成，不在配置文件中重复维护静态组映射；组 Token 不混入 go-zero 原生 `App/Token` 配置。两个新增入口使用 `Auth: false`、`Health: true`，不注册反射；`DispatchTask`、`CancelInstance`、`ReportTaskResult` 在业务适配入口共用请求体 `GroupAuth` 校验，标准 Health 不要求组凭据。启停遵守本章已定规则，[执行通信协议与装配](data-contracts.md#execution-rpc-contract)已通过。2026-11-04 已接入 Job 双 Server 和真实结果 Queue／Saver，示例回报端口为 9003；2026-11-05 已接入 System 内嵌执行器，原业务端口 9001、执行器端口 9004，组名及完整发现 Key 手工对应管理配置。Token 环境占位须保留 YAML 引号；ReportClient 使用 etcd 发现和非阻塞拨号，不使用原生 App／Token。当前未注册生产业务处理器，本轮验证与剩余项见 [System 内嵌接线记录](ordinary-readiness-review.md#ordinary-system-executor-wiring-progress)。

Job 的 `ExecutionRPC.Name` 仍须填写以满足原生解码；实际整个 ServiceConf 取自顶层宿主，不能借嵌套块设置另一套进程日志或退出预算。结果保存使用 `ResultPersistence` 的 512／8／2s 默认值，示例与填写方式见[README](../../../README.md#job-调度域执行模块开发中)。受版本控制的示例已更新，私有配置不自动改写；缺失新配置时明确报错，不增加旧配置回退。

一个执行器进程归属一个组，可注册多个处理器；同组多个实例使用相同组 Token，并必须兼容被调度的处理器及参数契约。新处理器先完成兼容部署再启用对应 Job；具体发布与存量任务兼容规则在详细设计中补齐。调度服务通过 etcd 发现执行器，不另建调度端注册接口或数据库心跳注册中心。

### 调度时钟与时区 {#scheduler-timezone}

所有调度副本使用相同的服务器／容器进程默认时区；承担规则校验、预览和启用计算的调度后端也遵守同一约定。没有 Job 独立时区字段，不要求执行器或用户浏览器使用同一时区，也不把数据库连接时区当作 Cron 的解释依据。

Job 的到期、错失与下一次时间计算使用调度后端进程时间，与 robfig 同源，不另取数据库当前时间判断到点。相关服务器须通过 NTP 等系统机制校时；时区一致不代表时钟同步，也不承诺各节点毫秒级绝对一致。校时由部署保障，调度框架不自行探测时钟偏差、修正系统时间或自动隔离节点。适用范围见[Job 触发时间来源](behavior.md#trigger-clock)，Instance／Task 的数据库时间规则不变。

#### 时间跳变

下一次实际检查 Job 时，仍按持久化进度和本次判定时间应用既有规则：

- 时间向前跳：已迟到则按固定 5 秒容忍与错失策略处理，不逐轮补跑；跳变本身不触发额外检查。
- 时间向后调：对持续启用的 Job，不倒退已保存的 `next_trigger_at`。本机时间尚未到该时刻时不触发，也不重新生成已消费的旧轮次。

不承诺异常校时期间准点或不漏跑，也不认为系统时间一改变，robfig 已设置的 Timer 就立即重排。明显的时钟故障由运维处理，必要时校正后重启相关调度进程；不新增应用层时钟补偿机制或扫描。显式停用后重新启用仍遵守原启用重算规则，不属于持续启用的进度保护；重算后若再次到达已保留的同一 Job、同一完整计划时间，按[触发持久化协议](data-contracts.md#trigger-transaction-proposal)保留旧 Instance、推进当前 Job，不覆盖参数或重新执行旧轮次。需要再次执行时使用新的手动请求号；历史记录已清理时，不承诺仍能识别旧身份。

#### 部署时区变更

时区由部署环境统一管理，不写死 `Asia/Shanghai`。它是部署固定项，第一版不支持运行中直接切换；变更会改变“每天零点”等表达式含义，须在维护窗口按以下顺序处理：

1. 停用受影响的 Job，安排在途执行结束或按既有停止流程处理。
2. 退出旧时区的调度与管理计算进程，确认在途规则计算和事务已经结束，不让新旧时区同时进行启用或触发计算。
3. 统一修改所有相关进程的部署时区并重启。
4. 重新启用 Job，按新时区计算未来的下一次时间，不补停用期间尚未创建的轮次。

不改写已有 Instance 的历史计划时间或已保存的绝对截止时间，不迁移历史执行记录，也不增加热切换、集群自动校时或数据库进度自动迁移功能。停止与进程重启仍受既有执行、回报及故障边界约束，不保证业务代码的副作用立即停止。相关测试见[时钟与时区运维验收](verification.md#clock-operations-checks)。

### 组身份与发现标识 {#group-identity}

`job_executor_group.id` 是数据库技术主键，供 Job、Instance 等持久化关联使用；`name` 是业务执行器配置的组名，也是执行协议中的组接入身份，不只是管理页面的展示文字。etcd Key 是创建组时手动填写的服务发现标识，不由组名自动生成；处理器名称则用于选择业务代码，三者职责不同。

**组名和 etcd Key 创建后均不可修改。** 管理入口与后端写入契约均须遵守，不提供组更名或发现 Key 热切换，也不增加另一套组编码／展示名。该限制不阻止同一 Key 下执行器地址随扩缩容、重启而变化，地址集合仍由原生服务发现更新。

组仍可新增，并在满足既定引用与恢复保护后逻辑删除。组名 `VARCHAR(128)` 和 Key `VARCHAR(255)` 分别全表唯一，包含软删除记录，删除后不复用；非空、拒绝首尾空白、按大小写精确匹配，不自动改写 Key。所有组记录的 name／Key／Token 均为非空完整字段，软删除保留原字段值，见[正式字段与持久化约定](data-contracts.md#executor-group-management-contract)。这避免旧注册节点或未刷新缓存混入新组，代价是重新接入要用新组名和 Key；不提供原身份恢复。字段及约束已随阶段 2 增量迁移实现，并通过隔离 PostgreSQL 测试；未迁移共享业务库。

### 组凭据管理 {#group-credentials}

组 Token 与管理后台登录凭据分离。创建组时由后端使用安全随机源生成 UUIDv4，去掉连字符后保存为 32 个小写十六进制字符。组表明文保存完整 Token，调度端取得原值用于派发、取消及回报认证；不做应用层加密，不只存哈希，也不增加凭据加密密钥配置。执行器通过配置文件、环境变量或部署 Secret 注入相同值，同组扩容复用组配置。不提供公开固定默认 Token，也不以空值关闭认证。

明文存储是受控内网部署下减少密钥管理的取舍，接受组表或数据库备份泄露会暴露 Token 的风险；不据此取消调用认证、日志保护或传输保护。SnailJob 的明文存取可作为参考，但不照搬其 Token 格式、前端生成方式或公开默认值，见[凭据参考](references.md#group-token-evidence)。

**第一版不提供 Token 重置或更换功能。** Token 仅在创建组时生成，组无编辑入口，后端不得更新已有 Token，也不增加重置按钮、管理 API／RPC 或自动轮换机制。凭据轮换不再作为第一版的待设计或开工前置项；以后确有需求时另行评审，不把手工改库视为已支持的管理能力。

**组详情接口返回完整 Token，普通组列表不返回 Token。** 详情页面默认遮挡，支持主动显示和复制，不采用仅创建时展示一次的方式。组不提供编辑入口，管理请求不得更新已有 Token。

生成和查看沿用既有 API／RBAC 授权；有组详情权限即允许读取 Token，不另建查看密钥 API 或独立查看权限。页面遮挡只减少直接展示，不改变详情响应包含完整 Token 的事实。凭据不得写入日志，包括请求、响应及错误诊断日志；采用下文已确认的[Token 日志保护](#token-log-protection)，具体实现仍须审计并验证，不以页面遮挡代替日志保护。

调度服务复用组凭据缓存，命中时不额外查询组表，未命中时按下节查询单个组；无法取得可用凭据时拒绝调用，不能降级为免认证。格式、明文存储、查看方式、不支持重置、[组配置缓存](#group-cache)、[删除后的客户端清理](#group-client-cleanup)及[启动退出规则](#startup-readiness)已定，不承诺组配置提交后所有节点立即应用；连接创建的具体并发和故障处理随实现契约闭合。

etcd 连接凭据与读写范围由部署管理，不复用组 Token。实例注册、任务调用和管理操作的认证责任见[内部信任边界](architecture.md#internal-trust)；执行协议不得因请求来自内网而跳过组 Token 校验，管理 RPC 是否启用原生服务鉴权由部署方配置。跨不可信网络需保护传输。

### 组配置缓存 {#group-cache}

实现状态：2026-11-04 已实现缓存、回报认证适配和各节点启动／退出接线，见[阶段 2 记录](ordinary-readiness-review.md#ordinary-stage2-progress)。真实结果队列已随[Job 生产接线](ordinary-readiness-review.md#ordinary-result-wiring-progress)接入；派发客户端尚未装配，缓存就绪仍不能视为完整执行链路已就绪。

各调度节点启动时加载未逻辑删除的组，之后每 **60 秒**串行读取一次全部未删除组的执行字段，包括数据库 ID、组名、发现 Key 和 Token。读取完整成功后原子替换整份配置快照，失败保留旧快照；不先计算新增／删除差异再逐条同步，也不增加 etcd 组变更通知。回报可到任意调度节点，因此不只由 Leader 加载。

两次完整刷新之间，缓存未命中时按当前请求所需的组查询数据库。查到未删除的有效组，补入本节点缓存并继续本次处理，不要求新组先等到下一次周期刷新；同一组并发未命中时合并回源查询。回源成功只提供组配置，认证及原有派发、回报校验仍须继续执行。

| 环节 | 已确认行为 |
| --- | --- |
| 派发与回报认证 | 优先读取本节点缓存，命中不查库 |
| 完整加载成功 | 原子替换完整快照，请求不读取半份新配置；新增组自然进入、已删组自然移出，不做增删差异同步 |
| 刷新失败 | 保留上一份完整快照并记录错误，不用失败或部分结果覆盖 |
| 请求的组未在缓存中 | 合并同组并发查询；查到有效组后缓存并继续本次处理，不仅凭本地缺失判定永久错误 |
| 回源查无组或组已删除 | 不写入有效组缓存，不绕过认证、不确认接收；结果回报按[已定分类](data-contracts.md#result-error-classification)作为明确认证失败，不能仅凭缓存未命中直接这样处理；其他接口编码仍按各自契约落实 |
| 回源数据库查询失败 | 不写入有效组缓存，不绕过认证、不确认接收；结果回报返回 `Unavailable` 并由执行器有限重传，不把依赖失败转为 Token 错误 |
| 冷启动没有可用配置 | 不免认证放行；单组回源只解决该组配置，不替代队列、消费者及必要依赖等[接入就绪条件](#startup-readiness) |
| RPC 客户端 | 配置快照替换不等于重建全部连接；保留有效组客户端，已删组按[清理规则](#group-client-cleanup)移除并关闭；进程退出按[统一停机规则](#process-shutdown)释放 |

A 节点已加载新组并派发时，结果可能负载均衡到尚未刷新的 B 节点。B 查询到组后即可继续认证和接收，不必先拒收并等待 60 秒刷新。数据库故障等暂时不可接收情形仍按独立有限预算重传，不承诺故障期间无限保留；取得组配置本身不构成接收 ACK，已定回报入队及后台持久化边界不变。回源仅解决组认证，入口仍不读取 Task；任务归属、尝试及状态由后台既有 JOIN 与条件写入核验。

数据库故障期间沿用旧快照，也接受组删除继续滞后；60 秒是完整刷新周期，不是条目 TTL、全节点同步或强制撤销时限。快照内存随实际有效组数量增长，不宣称固定内存上限；查无组或查询失败不缓存为有效组。同组查询合并不等于不同未知组请求的总容量控制，具体并发与故障保护随运行参数设计，不在此承诺任意请求洪峰均无数据库开销。

SnailJob 的 `CacheToken` 同样在未命中时查库，但其 60 秒是写入后过期；DogX 保留 60 秒完整快照替换，并补充未命中回源，不将两者描述成同一种刷新机制，见[缓存依据](references.md#group-cache-evidence)。这是组元数据同步，不是 Job／Instance／Task 扫描或执行器地址目录；实例地址仍由 etcd 与原生发现维护。组名、Key 与已有 Token 均固定，周期同步不承担热切换或凭据轮换。启动退出规则及组删除保护仍须实现验证，不能因缓存设计已明确就提前开放删除入口。验收见[组配置缓存检查](verification.md#group-cache-checks)。

### 组删除后的客户端清理 {#group-client-cleanup}

**各节点复用 60 秒完整刷新时机，移除并关闭已删除组的本地 RPC 客户端。** 这项规则针对正常派发复用的组客户端；[定向取消客户端](execution.md#cancel-routing)仍按单次通知创建、有限重试内复用、结束后关闭，不跨通知缓存。

一次完整查询成功并原子替换组配置后，检查本节点已经创建的组客户端：所属组仍在新快照中则原样复用；不在新快照中则先从客户端缓存移除，再调用 `client.Conn().Close()`。完整查询失败时保留原配置和客户端，不把数据库故障当成组已删除。

检查使用新的组快照和本地客户端集合，不额外查询数据库，也不增加独立清理线程。组配置仍是全量替换，不改成新增／删除差异同步；连接持有运行资源，必须显式关闭，不能只丢弃缓存引用。清理不因整轮历史保留而延期，也不等待远端业务结束，不增加引用计数、排空队列或等待所有在途 RPC 结束的机制。

清理以[组删除保护](data-contracts.md#group-reference-concurrency-proposal)已满足为前提，但删除保护不证明零在途通信。关闭连接可能中断已发出的 RPC，已取出旧客户端的调用也可能失败；仍按既有通信结果不明规则处理，不能据此推断执行器未接单、业务已取消或允许无条件重派。删除组不替代停止业务，原有父终态和当前尝试核验不变。

缓存回源、客户端创建与清理须做本地并发协调：旧查询结果不能覆盖已观察到的删除事实；迟到创建结果不得把已移除组的客户端重新挂回，未采用的新建连接须关闭。不为此增加分布式锁；具体同步实现及竞态测试随编码落实。

接受各节点在下一次成功刷新前仍持有旧配置和连接，也接受清理对少量在途通信的影响，不承诺 60 秒强制释放。调用 Close 不等于依赖框架的共享状态全部回收，连接、发现订阅及相关资源须按[清理验收](verification.md#group-client-cleanup-checks)验证。SnailJob 的组删除与实例过期清理是两条路径，且 Java `shutdown()` 与 Go `ClientConn.Close()` 的在途调用语义不同，见[对照依据](references.md#group-client-cleanup-evidence)。本项不包括完整启动退出协议，也不表示清理功能已经实现。

### 依赖故障与恢复边界 {#dependency-boundaries}

| 故障场景 | 服务边界 |
| --- | --- |
| PostgreSQL 不可用 | 不能创建新 Instance、取得新派发授权或推进持久化状态；前置步骤未提交不能凭内存继续派发。认证与基础校验有效且结果保存组件可接纳时，接纳并确认接收；数据库技术错误、原因不明或提交不明时保留对应原结果并退避，不回滚或重放其他已明确提交的结果，不按次数或 TTL 丢弃。默认 512 条包含首次待处理、退避及在途，满时拒收；一次处理结束释放并发，退避不占并发，全部记录退避时允许保存者空闲。按到期最早处理，恢复后也不承诺立即排空或结果已经落库 |
| 仍有效结果需要的平台快照损坏、配置版本未知或 SQL 缺陷 | 保留原结果、退避并告警，排查平台数据或实现，不认定为业务方永久无效。512 条占满后继续背压，不按失败次数或 TTL 丢弃腾空；后台先用已有 JOIN 排除旧尝试、终态等无效结果，再解析仍需使用的快照 |
| 普通首次启动或已有 Task 新尝试登记时父行被占用 | 按父主键尝试 `FOR UPDATE NOWAIT`；冲突即回滚，不登记尝试、不占执行次数、不发送 RPC。跳过本次同一 Instance 的候选组并处理其他 Instance，不连续重争、不立即重新排队，也不利用旧合并提示立即再抢；后续查询重新发现仍符合条件的工作。不能因争锁失败反复查询第一页，也不能永久跳过该 Instance，见[派发竞争](execution.md#dispatch-contention) |
| 自动触发队列满或创建事务变慢 | 队满时拒绝新的 Job 提示并记录指标及限频日志，不因此推进触发进度；事务变慢时受数据库操作超时约束，不因变慢就拒绝仍有容量可接纳的提示。后续 Cron 或分钟恢复按事实补查，仍适用 5 秒错失策略，不承诺补跑每轮。手动没有创建额度时返回繁忙；见[触发容量与过载](execution.md#trigger-capacity) |
| Job 恢复查询失败、队满或头部候选持续失败 | 每次只从主库读最早到期的一批，查询失败或投递队满即结束，下一分钟重新查；不分页、不保留跨分钟游标，也不叠加补试。头部大量持续失败、反复队满可能使后续候选长期未获恢复检查，不保证严格公平或一分钟恢复完成；不自动改写异常 Job 的进度或启停状态 |
| Job 配置读取失败或单条 Cron 无效 | 整次读取失败保留原内存规则；首次失败则 Cron 暂不启动，后续核对及独立触发恢复继续。原规则的触发不能绕过数据库检查。单条 Cron 解析无效则移除其残留规则并记录错误，其他规则继续，不自动停用数据库中的 Job；见[配置重载流程](execution.md#job-config-reload) |
| 自动触发时 Cron 解析失败或求不出下一次时间 | 本次不创建 Instance、不推进原进度，记录含 Job ID 与原因的限频错误；不自动停用或新增异常状态。Job 可能仍显示启用但无法自动触发，需管理员修正，必要时修正后重启相关调度进程；不提供专门的内存规则自动修复，见[Cron 异常处理](behavior.md#cron-errors) |
| Job 保存已提交，但 etcd 通知失败 | 请求内通知最多 1 秒且服从上游期限，不另建重试队列；记录日志和指标，不主动将已提交保存改报失败，分钟核对补发现，不保证客户端断线后仍收到成功响应 |
| Job 配置 Watch 中断或历史已压缩 | 可恢复连接故障交给客户端；需要重建时退出旧监听，按 1 秒至最多 30 秒带抖动退避，重新核对。不叠加活跃监听，分钟核对不等待 Watch 恢复；仅在 Leader 资格仍有效时运行 |
| 发现 Leader 租约失效或无法确认有效性 | 关闭任期入口并取消独立上下文，停止自动触发、配置同步、Job 恢复及 RUNNING／STOPPING 候选发现，丢弃旧任期 Job 提示和各分支临时游标、等待任期工作退出；接受按最新 Job 合法记账的在途事务仍可能提交。已经交给进程级检查或后台处理组件的候选仍可按数据库协议完成，不清空这些组件，不停止正常对等推进和回报，见[任期生命周期](execution.md#leader-runtime-lifecycle) |
| 暂无有效 Leader | 自动触发与 Leader 的周期恢复发现暂停，包括 RUNNING 中的超时发现及 STOPPING 补漏；各节点正常结果保存、本地推进与停止决定提交后的处理不因此停止。新 Leader 就绪后分别从头开始有界检查，RUNNING 仍遵守 4 分钟门槛，STOPPING 不套该门槛；不转交旧游标或队列，允许换主交界重复处理 |
| 正常 Instance 检查提示队满或检查失败 | 已存在的 ID 仍合并；新的正常提示非阻塞放弃，不回滚已经保存的 Task 结果。检查中收到新提示时保留一次后续检查，技术错误不能抹掉该提示；没有新提示时，NotReady 或技术错误结束本地条目，不因错误自行无限重查，后续正常提示或既定 Leader 复核补漏 |
| RUNNING 复核查询失败、达到交接水位或本地集合已满 | 查询失败结束本周期扫描并保留本趟位置。集合占用达到总量一半或已满时，暂停新增查询及新 ID 交接，在本周期剩余 5 秒预算内等待本地空间释放再继续，不立即退出；已有 ID 仍可合并。等待不持有数据库连接或事务，不忙循环，不创建无界等待协程。接纳或合并后才推进游标，不越过首个未接纳候选；预算用尽或失主停止新发现，已接纳检查不随扫描取消。持续占用不低于水位可能使恢复长期无进展，不保证固定份额或恢复时限 |
| 无绑定观察结算读取失败、写入失败或提交不明 | 批量读取失败或尚未处理的候选不能被游标越过；某条 Task 写入技术失败或提交不明时，允许游标越过该已尝试项，但立即结束本次执行，下一次从其后继续，之后新一趟从头补查仍符合条件的失败项。游标前移不证明写入成功或回滚，也可能延迟重查该项；只有更新且明确提交才提示 Instance 检查，不直接重派，见[扫描与结算初值](#unbound-recovery-configuration) |
| STOPPING 父行正在被其他处理占用 | 每批先按父主键尝试 `FOR UPDATE NOWAIT`，拿不到即回滚并跳过本 Instance，不先读其子 Task、不立即重新排队，也不让已合并的旧重复提示立即再次抢锁；后续恢复重新发现，不在当前候选上忙等 |
| STOPPING 处理失败、提交不明、节点退出或本地后台容量已满 | 已保存的停止决定和原因保留，不授权新工作；Leader 每 2 分钟的独立有界候选分支重新发现并继续子状态处理及父最终结束。数据库操作失败或提交不明按既定事实核对与恢复处理，不能假定已取消或一定回滚；逐轮有界处理并公平轮转，不永久耗尽数据库处理重试。父锁 NOWAIT 不消除子 Task UPDATE 与回报之间的锁等待；远端取消失败或耗尽不阻止数据库完成 |
| 远端取消通知容量不足、地址查询失败或通知进程退出 | Instance 通知总量满时拒收并记录；目标总量满时暂停地址读取，不继续无界生产。地址查询失败不再枚举本次剩余地址，已经入队的目标仍在原期限内继续；宕机可能丢失通知，不扫描历史补送。通知失败、耗尽或丢失不阻止数据库取消和父最终结束，具体期限见[通知容量](#cancel-notification-operations) |
| 本地旧任期清理异常卡住 | 本机不重新参选或叠加新任期，记录错误，必要时运维重启；其他机器可接任，不等待旧机或业务执行完成。进程创建额度不得在实际操作结束前提前归还 |
| etcd 服务发现不可用 | 实例注册、地址更新和新节点发现受影响；已有连接在认证、任务执行权及所需数据库操作有效的前提下可以继续使用，不要求每次 RPC 实时访问 etcd |
| 某组没有可用执行器或派发 RPC 失败 | 影响该组相关 Task，不使其他组整体不可用；按已定的失败、重试与超时规则处理，不增加无限重派额度，具体无节点分类留待派发与恢复协议确定 |
| 执行器明确返回 BUSY | 仅容量满且未接单、未入队、未执行时可条件返还并延期，零重试同样适用；记账失败或提交不明只做有界有限重试，原响应释放或失效后不猜测补返。复用既有检查并退避，不延长整轮截止、不保证换节点；通用通信错误不免费返还 |
| 执行器暂时联系不到调度服务 | 已接收业务可以继续；回报组件有界保留结果，发送失败后释放 RPC 并发，原记录等待到期后重试。保留位置满时由有限业务处理者等待交接，将压力传回业务队列；业务队列无法接纳时才按既定契约返回 BUSY，不增加独立拥塞开关。重试耗尽释放结果并记录错误及丢弃指标；全部记录都在退避时，发送者可空闲而新结果仍等待交接，服务恢复后也须等待剩余退避；取消请求可能无法送达 |
| 业务数据库或外部服务故障 | 由处理器按契约返回失败等结果，平台按 Task 规则处理；不把所有业务依赖加入调度服务的全局健康检查 |

控制面故障不保证正在运行的业务立即停止，也不能撤回所有已发出的 RPC。两侧内存结果均不是可靠存储：执行器回报重试耗尽后释放、未报出就退出，或调度端 ACK 已被收到但落库前退出，都可能丢失原结果。ACK 只确认接收，不承诺持久化；不使用本地回报文件或持久卷进行结果补偿，节点替换不依赖原机文件。调度端对数据库技术错误、原因不明、提交不明及仍需使用的平台坏快照有界保留对应结果、退避并告警，不套用执行器的有限回报耗尽释放；正常完成、无错误零行或已确定无效才结束保留，零行不证明此前已保存，也不补查猜测原因。按[已定错误分类](data-contracts.md#result-error-classification)实施，Protobuf 与具体驱动行为仍须验证。[停机期间有限善后](#process-shutdown)不改变正常运行时的结果保留规则。数量、并发及 RPC 报文上限不等于整个进程内存的硬配额。

业务幂等覆盖后续重跑可能重复的副作用，但不能重建已经丢失的执行结果。已有持久化执行器绑定但无有效结果时，保持当前尝试执行中，等待有效结果、人工停止或整轮截止；失联、重启、回报耗尽及 ACK 后丢失都不能单独授权提前重跑，第一版不新增 Task 活动查询、心跳或独立失联提前重派。明确成功正常推进，明确失败仍按原 Task 预算重试；etcd 注册存活不证明结果能够找回。

整轮超时必须有限、不允许 `0`；新增表单预填 900 秒，用户按业务调整，API 仍必填。接受执行器宕机后等待剩余整轮时间，也接受单个分片丢失结果拖至整轮超时且无法进入正常 Post。自动超时先尝试根据已保存的完整最终结果结束本轮；仅明确 `NotReady` 才进入父单行短事务，锁后读取父状态和当前数据库时间，仍为 RUNNING 且已到期才尝试保存 STOPPING 及超时原因。父锁内不重新汇总 Task，接受该期间最后结果到达而超时停止决定先提交的竞争窗口；正常完成 UPDATE 零行、技术错误或提交不明均不能当成结果不齐。停止决定确认后，未结束 Task 按统一取消规则处理，全部子状态终态后父最终失败；不再新增 Task 或登记新尝试，也不把所有 Task 判为业务失败。无绑定的有限观察规则及业务预算不变，权威边界见[已绑定结果等待](execution.md#bound-result-wait)与[终态竞争](behavior.md#terminal-order)。

平台页面和诊断须区分“已过截止”“已保存超时停止决定”和“已经最终结束”：父仍 RUNNING 且已具备完整最终结果时，可以在截止后按成功或失败结果结束，也接受当前有效迟到结果赶在 STOPPING 决定前完成收尾。它不表示业务获得了追加时间，不允许截止后创建分片、Post 或新尝试；已有 STOPPING 及其原因、超时、取消和其他父终态不可覆盖。不新增时间轮、延迟恢复队列或固定超时宽限期，也不保留独立短周期 deadline 扫描，不承诺精确在截止时刻保存停止决定或最终状态。

没有积压且周期扫描正常运行时，RUNNING Instance 首次周期复核通常在开始后约 4～6 分钟；超时短于 4 分钟也仍受此门槛约束。扫描压力、交接水位、队满、数据库故障和切主可使终态保存更晚；若每个扫描窗口内集合占用始终不低于总量一半，恢复可以长期无法接纳新 ID，4～6 分钟不是恢复 SLA。已超过门槛的正常长任务仍可能在后续扫描中被再次检查，接受其读取成本及少量与正常路径的竞争。平台晚结算不会延长执行器原业务 Context 或授权期限；阻塞丢弃可能继续跳过后续触发，并行策略可能积累更多未结束 Instance，遗漏阶段推进恢复时也可能已无剩余预算，不能为补救而延长原截止。

依赖恢复后仍遵守停止、整轮超时、重试预算和已提交状态，错失触发沿用既定策略；恢复不等于所有工作重新执行。父 Instance 为 STOPPING 时，子状态未完成或父尚未最终结束均属于恢复范围，包括与停止决定交错写入的重试候选；新增 Task 和新尝试被父行授权检查禁止，已授权在途 RPC 或业务仅能尽力取消。旧 Leader 迟到触发只能按最新 Job 进入短事务记账，停止本地 Cron 不是数据库硬隔离；切主处允许的在途提交见[切主边界](execution.md#leader-config-boundary)。重连与重传契约继续按模块设计。

Instance／Task 的有界数据库恢复独立于 Job 定时触发：遗漏阶段推进、最终结果齐备但父未结束及到期未结束的 RUNNING Instance 由 [Leader 统一复核](execution.md#instance-recheck-direction)发现；STOPPING 由[同一 2 分钟驱动中的独立候选分支](execution.md#stopping-recovery)恢复，不混入 RUNNING 查询或套其 4 分钟门槛。两者均不等待该 Job 的下一次 Cron，也不因 Job 停用或删除跳过旧轮次。不重新执行已有有效结果的业务，不新增全历史 Task 扫描、恢复分桶、下次检查字段或固定负责人。WAITING 首次启动、待派发／到期重试及[无绑定观察结算](#unbound-recovery-configuration)继续各自协议，不在这两类查询里顺带处理，也不据此将其集中到 Leader。

### 启动与能力就绪 {#startup-readiness}

**配置、处理器、队列、消费者及对应能力所需依赖准备好后，才开放该能力的新工作接收。** 处理器注册表在启动时校验并固定；执行器不能先 ACK 接单再初始化执行与回报能力，调度端不能在结果消费与容量控制尚未准备好时确认回报接收。

基础配置缺失或非法时明确报错；短暂依赖故障允许进程保持存活、等待恢复，但相关能力不得假装就绪。进程存活、回报接收容量、数据库推进能力和 Leader 触发资格分别判断；非 Leader 是正常副本状态，不能因此把可接收回报的节点全部摘除。接收 ACK 可用不表示后台落库能力正常，具体探针与背压反馈在详细设计落实。

调度服务就绪不等待所有执行器组上线，某个动态组异常不导致整个调度集群启动失败。嵌入业务 RPC 的执行组件不应仅因调度服务暂不可达就拖垮原业务接口；业务本身对数据库、etcd 等依赖的要求仍然成立。

这些是已通过、待实现验证的启动规则，不是框架现成保证。当前依赖的 go-zero v1.10.3 在原生 etcd 注册路径上先注册、再启动 RPC 服务，首次发现读取也依赖 etcd；两个新增 Server 保留标准 Health，但其健康状态不检查 DogX 队列或组配置，也不能代替业务接收开关。标准 Health 与全部执行业务入口的共用组认证分别装配，不增加方法跳过白名单。启动编排、重连和探针须遵守原生组件的实际约束，不能把“已有连接可继续”外推成“etcd 故障时新进程也能正常启动服务”，也不以已注册或端口已监听代替接入就绪。

etcd 需要按可用性目标部署和运维，单节点部署不自动具备高可用；注册地址不代表业务健康、剩余容量或 Task 存活。具体验证见[第 8 章](verification.md#trust-dependency-checks)。

选主使用官方 Session＋Election，TTL 部署初值 15 秒且须为正值；此值不是切主 SLA，不保证在 5 秒错失窗口内接任。统一集群前缀必须按环境及逻辑调度集群隔离，选主范围与持久通知标记分开，执行器不得访问这两类范围。短 etcd 请求、配置读取及通知分别采用已定 5／5／1 秒预算，长期竞选、续租与 Watch 使用生命周期上下文，见[etcd 接入约定](execution.md#etcd-integration)。

### 进程停机与有限善后 {#process-shutdown}

**每个进程默认共用 30 秒停机宽限，可通过部署配置调整。** 从进入停机开始计时，两套 RPC Server、后台组件、结果处理和依赖清理使用同一个截止时间，不逐组件重新计时；它不是 Task 执行超时、RPC 超时或切主期限。无需用满宽限即可结束的进程可以提前退出；到期结束等待，接受未完成业务和未持久化结果，由宿主进程负责最终退出。

调度端按以下顺序停止：

1. 关闭新工作入口，停止新增触发、派发及恢复生产，停止接纳新的结果回报；若持有 Leader 任期，同时结束任期。入口关闭与接纳须协调，已明确接收的结果计入善后，未接收的请求不能回复成功 ACK。
2. 在剩余宽限内尽力处理已接收结果并提交数据库，保存结果遵守[Task 条件更新](data-contracts.md#task-result-persistence)，不给每条结果另加父状态或截止硬条件。后续按完整结果结束仍服从父终态不可逆；新工作继续受原截止与父状态约束，停机不新增派发。数据库持续不可用或预算用尽时结束等待，不为排空结果而无限延长停机。
3. 正常完成时先结束使用依赖的本地工作，再关闭本进程拥有的客户端、etcd 和数据库等资源。取消请求或 RPC 返回不证明所有业务工作已结束；不能提前关闭仍被使用的依赖，再把善后声明为完成。

执行器按以下顺序停止：

1. 拒绝新的 Task 接纳。停机拒绝不是队满 `BUSY`，不因此免费返还执行机会；明确未接纳的新工作使用 `job.executor.dispatch_rejected` 表达退出拒收，调度端按[非 BUSY 拒绝结算](data-contracts.md#dispatch-rejection-settlement)处理；已经接纳或接纳结果不确定时不能改报此拒绝，活动中的重复尝试继续按既有防重契约响应。通信中断或通用不可用错误仍按结果不明处理，不能据此推断拒绝。
2. 已接纳的排队和运行任务可以在剩余宽限内继续，仍受既有整轮截止、取消和处理并发限制；结果交接和独立回报继续进行。业务已退出但尚在等待交接时，不再保留活动防重记录；不重置每条结果的有限重传预算，也不延长业务执行期限。每次回报 RPC 取单次 2 秒上限与剩余停机宽限中的较小值，不为等待重试另开宽限。
3. 宽限到期后不再启动排队任务，对仍运行的业务 Context 发出取消信号，取消在途回报 RPC，结束结果交接、未来重试及其他组件等待，由宿主结束进程。未获 ACK 的结果可能丢失，不为用完 7 次调用或等待全部退避而延长停机。不能仅凭取消信号认定业务已经退出；公共执行组件不调用 `os.Exit`，也不能强杀 Go goroutine。

结果提交、队列接纳与关闭必须处理并发交界：业务晚返回不能向已关闭通道发送而 panic、永久阻塞，或另外启动无界后台协程保存结果。停止接单、摘除服务发现地址或关闭连接均不证明远端业务已经停止；停机也不直接将 Instance 判失败／取消，不退款执行机会，不成为立即换节点重派的依据。有绑定无结果仍等待有效结果、人工停止或整轮截止；能够确认未接纳的拒绝按已定条件结算，未取得有效拒绝结算且仍完全未绑定的才按既有有限观察规则处理。

正常运行中的调度端结果保留没有新增 30 秒 TTL；只有进入进程停机才适用本宽限。骤停不保证有善后机会，正常停机也不保证所有结果落库。内嵌执行组件与 System 共用进程总预算及宿主依赖，不能各自再增加一轮 30 秒等待；若业务忽略取消，宿主最终退出前不能声称业务已经结束。

普通失主不是进程停机：仍按[任期规则](execution.md#leader-runtime-lifecycle)关闭任期资源，旧任期清理完成前本机不重新参选；RUNNING／STOPPING 新候选发现停止，但已经接纳的检查或后台处理仍按原数据库协议完成，不因此停止正常对等执行与回报能力。30 秒不用于允许本机带着未清理的旧任期开新任期。

#### zrpc 进程装配 {#zrpc-process-assembly}

停机由宿主的统一协调者负责，不要求执行组件独立热启停。第一次进入停机即确定共享截止时间，框架的 wrap-up／shutdown 阶段包含在默认 30 秒之内；进入后续阶段不重新获得完整宽限。两个 Server 的 `ServiceConf` 必须使用宿主同一来源的日志、监控、模式及退出配置，不能由各自的 `SetUp` 覆盖，也不能依赖初始化先后选择配置。

wrap-up 开始时先关闭本章规定的新工作入口；shutdown 阶段允许框架并行停服与宿主有限善后。已接纳的后台业务及出站回报独立于入站 RPC 的生命周期，继续使用剩余预算；宿主确认实际 RPC 和本地工作完成后再释放仍被使用的客户端、数据库等依赖。到期按上文结束等待并由宿主最终退出，不将取消信号等同于业务已经结束。

go-zero v1.10.3 的 `ServiceGroup` 并行启动／停止成员，不能靠 `Add` 顺序表达依赖释放顺序；`RpcServer.Stop()` 只关闭全局日志，不是 gRPC 停服屏障。宿主必须使用实际停服及工作完成信号，不把两套 Server 的 `Stop` 直接用作善后屏障或提前关闭日志的步骤；日志在正常善后结束或最终退出前由宿主统一关闭，不能被某个 Server 的停止抢先关闭。可在 zrpc 注册回调取得底层 gRPC Server 来协调真实停服，但具体 Go 并发组织留到实现时确定。

宿主的 shutdown 回调不得等待 `zrpc.Start()` 或 `ServiceGroup.Start()` 返回：zrpc 的返回路径本身会等待全局 shutdown 回调，反向等待会形成循环。两套 Server、后台组件和依赖清理均服从同一截止时间；Unix 原生钩子与 Windows 宿主退出路径必须分别验证，不能假定 Windows 的 proc 行为与 Unix 相同。

2026-11-04 已实现共享宿主协调：两域 Main 使用 `rpchost.Run`，Job 分离 Stop／Wait／Close，取消后的在途操作、Cron 回调及 Session 清理仍按实际完成信号等待，但整个宿主共用 `Shutdown.WaitTime` 默认 30 秒预算（包含 `Shutdown.WrapUpTime` 默认 1 秒）。Windows 与 Unix 的真实信号、初始化期间停止及超时退出已有子进程测试，详见[阶段 1 实施记录](ordinary-readiness-review.md#ordinary-stage1-progress)。后续已完成 Job 双入口及真实结果队列的生产接线，实际验证见[生产接线记录](ordinary-readiness-review.md#ordinary-result-wiring-progress)。此前公共执行器 Runtime／reporter 已落实共享 Drain 截止与 Wait 实际完成边界，见[执行器运行记录](ordinary-readiness-review.md#ordinary-executor-runtime-progress)；2026-11-05 System 接线已实现：Stop 关接单，Drain 立即传递共享截止，Wait 观察业务和回报实际退出，Close 随后关闭回报连接、安全刷新、策略发布与数据库，初始化注册失败或 panic 也负责释放已有依赖。本轮实际验证见 [System 内嵌接线记录](ordinary-readiness-review.md#ordinary-system-executor-wiring-progress)，完整生产进程 E2E 仍待完成；操作系统强制结束、骤停和忽略取消的业务仍遵守上述有限善后边界。依据见[启动与停机对照](references.md#process-lifecycle-evidence)，验收见[生命周期检查](verification.md#process-lifecycle-checks)和[执行通信检查](verification.md#execution-rpc-checks)。

Job 当前实现中，`Stop` 关闭派发、结果与完成提示接纳，再取消调度与组刷新；已开始派发、接收结果和已接纳检查保留独立处理 Context。`Drain(ctx)` 立即把同一宿主期限并发传给三类消费者，并与原运行组件退出共同等待。`Wait(ctx)` 观察实际完成，`Close` 先 Stop、再等实际退出后才释放组客户端、etcd 和数据库。正常宿主流程须先经过双 Server 入站屏障和有界 Drain；超时不提前释放依赖，Close 不能当作有界停机接口。关闭提示接纳后才保存的结果仍持久化，但可能失去本次本地检查提示；阶段 5 的复核尚未实现，不能据此宣称当前已能恢复所有遗漏。详见[最新实现记录](ordinary-readiness-review.md#ordinary-completion-progress)。

初始化阶段尚未把宿主 Context 传入所有数据库连接和初始快照 I/O。宿主在取消时限制等待，初始化未实际结束前不启动监听或并发清理仍在构造的依赖；不承诺收到停止信号后相关 I/O 立即中断。

etcd 与仓库当前跨进程协调规范的适用边界已由 [ADR-0009](../../adr/0009-scheduler-domain-and-etcd.md)确认，待用户明确要求开始实现后同步生效规范；其他数据分层、短事务和 Redis 键管理约束继续生效。

## 7.4 日志与可观测性

### Token 日志保护 {#token-log-protection}

日志默认只记录组、Job、Instance、Task 等定位信息，不主动记录 Token，也不直接输出包含凭据的完整请求、响应、配置或认证错误。日志保护不改变已授权组详情返回完整 Token 的契约。

框架自动日志与手写日志分别控制：

- RPC 涉及凭据的接口使用原生配置关闭正文记录：服务端采用 `StatConf.IgnoreContentMethods`，客户端采用 `zrpc.DontLogClientContentForMethod`；不关闭方法、耗时及不含凭据的错误诊断，尤其要检查组详情响应的客户端慢调用日志。
- HTTP 请求／响应转储、启动配置和错误字符串不得带出 Token；认证错误不包含收到值或期望值。页面遮挡或关闭普通访问日志正文，都不替代对实际错误、慢调用和详细日志路径的检查。

不为本项新增公共 `rpclog` 包或通用脱敏框架。方案已确认，日志控制代码和测试尚未完成；使用测试 Token 覆盖正常、慢调用、认证失败及数据库失败路径，验证日志不泄露且正常详情响应不受影响。原生日志行为见[日志保护依据](references.md#token-log-evidence)，验收见[Token 日志保护检查](verification.md#token-log-checks)。

### 并发、队列与批次配置 {#capacity-configuration}

[排队、并发与满载处理](execution.md#capacity-model)的六条原则和[执行器处理流程](execution.md#executor-processing-flow)于 2026-10-28 通过并修订。配置直接描述处理并发、队列长度及适用的读取批量，不把“容量控制”设为独立模块，也不增加接单到回报结束的统一总量配置。主要并发、队列长度及派发补查间隔使用部署配置；调度端结果保存于 2026-10-29 明确为每条一次 JOIN、条件 UPDATE、独立提交，不设置后台写库事务批量参数，也不强制组织批量预读。分页、轮转等采用集中默认值，不为每个内部步骤配置独立份额。

| 执行器参数含义 | 说明 |
| --- | --- |
| 业务等待队列长度 | 每执行器进程默认 **128 条**，部署可调；仅包含尚未被处理者领取的 Task，不含已领取的 32 个处理中工作。队列不能接纳的新请求返回 BUSY，活动重复请求和停机拒绝仍按原契约处理 |
| 业务处理并发 | 每执行器进程默认 **32**，部署可调；从领取开始处理到完成结果交接均计入，包含业务已结束但等待交接的处理者。交接后才领取下一项，不另起业务绕过限制；业务实际运行与交接等待应分别观察 |
| 回报结果保留上限 | 默认 **256 条**，部署可调；包含待首次发送、延迟重试和在途结果，一条结果从接纳到释放始终占原位置，满时业务处理者等待交接 |
| 回报 RPC 并发 | 默认 **16**，部署可调；仅约束同时进行的单次 RPC，完成一次即释放发送并发；等待下次重试不占用发送者 |

**业务并发 32 与等待队列 128 已通过，公共 Runtime 与 System 配置接线已实现，本轮所列接线验证已通过；压测尚未完成。** 普通、准备、分片和收尾在进程内共用这两项配置，不按 Job、Instance 或阶段各建一份额度；此前解释中的 64／100 不作为默认值。若当前 20 个处理者正在执行业务、12 个已经结束业务但等待结果交接，32 个处理位置仍全部占用，不能再领取新工作。业务实际退出即清理活动防重，不能等到交接或回报 ACK 后才清理；仅发出取消信号则不证明业务已退出，不能提前归还处理位置。完整规则见[执行器业务初值](execution.md#executor-business-defaults)。

这组数值是 System 内嵌执行器的部署起点，不表示需要固定创建 32 个操作系统线程，也不预先指定 Go 并发原语。业务、普通 System RPC 及回报共享宿主资源，不能由 32 推导数据库连接池还固定预留多少连接；业务并发 32 和回报 RPC 并发 16 无须相等。128 条等待队列用于吸收短时突发，不增加长期处理吞吐，也不延长原有整轮截止时间；长任务或交接积压仍会延长排队。

回报组件的 256 条已经包含在途结果，不能另加 16 条在途额度；组件外尚待交接的结果由上述有限业务处理者持有，部署说明须区分这些部分，不能将 256 条当作整个进程的结果总量或内存硬上限。沿用自然交接等待传递压力，不另设高低水位接单控制器，也不建立接单到回报结束的统一额度。

结果按下次可发送时间、同时间下的稳定接纳顺序选择：首次为组件接纳时刻，重试为本次调用完成时刻加正退避；优先发送已到期的最早记录，后来接纳的新结果不能插到已到期旧记录前。失败结果保留原位置，不能让发送者阻塞回填已满 channel；更新既有记录或释放位置不等待新结果准入。全部记录都在等待重试时，允许发送者空闲而业务结果交接仍受阻；服务恢复后仍可能等待剩余退避，不承诺立即排空。完整规则见[执行器回报队列](execution.md#executor-result-queue)。

回报时间参数采用内部常量：单次 RPC **2 秒**，应用层最多 **7 次总调用（含首次）**，六次间隔依次为 **1／2／4／8／16／16 秒，各带 ±20% 抖动**。47 秒只是名义退避间隔之和，不含排队和 RPC 时间，既不是结果保留 TTL，也不是交付 SLA。go-zero 原生客户端／调用超时和调度端回报方法超时须与该单次 deadline 协调，并服从共享停机剩余时间。参数范围及边界见[回报初值](execution.md#reporting-defaults)，调度端写库重试不套用本组参数。

派发等待队列满时暂停补充，未接纳工作留在数据库；调度端结果保存组件满时以 `ResourceExhausted` 拒收，不丢弃后仍 ACK。调度端每条先用一次 JOIN 取得 Task 和所属 Instance 的必要信息，排除无合法目标、跨组、关系不符、旧尝试、Task 终态及身份冲突后，再解析仍需使用的冻结重试配置并条件 UPDATE、独立提交；一条结果内部的状态、结果和时间仍原子保存。JOIN 不读取当前 Job、不扫描父整轮 Task，也不把父仍为 RUNNING 或尚未截止增加为结果保存条件。读取后的竞争由 UPDATE 的原尝试、状态和绑定身份条件裁决；已绑定身份必须匹配，空绑定允许结果先到。N 条可写结果的正常路径是 N 次 JOIN 加 N 次 UPDATE 及各自提交，接受这一成本，不宣称等同于批量 SQL。

| 调度端结果保存参数 | 已通过的部署初值 |
| --- | --- |
| 结果保留上限 | 每调度进程 **512 条**，包含首次待处理、延迟重试及正在保存的记录，不额外叠加在途额度 |
| 保存并发 | 每调度进程 **8**；仅一次处理进行期间占用，实际结束即释放，退避不占处理能力 |
| 单条一次处理超时 | **2 秒**，包括取得连接、JOIN 读取、条件更新及提交确认，不含领取前排队和后续退避；停机时受共享剩余宽限限制 |

上述三项已通过 Job 的 `ResultPersistence.Capacity`／`Concurrency`／`SaveTimeout` 接入真实 Queue／Saver，部署可调且必须为正值；它们仍是未经过压测校准的初值。数据库重试间隔使用 **1／2／4／8／16／30 秒、后续名义间隔封顶 30 秒，各带 ±20% 抖动**的内部初值；不设置结果 TTL 或次数耗尽丢弃。第一次可处理时间为接纳时刻，重试为本次处理完成时间加正退避；已到期结果按可处理时间最早优先，同时间采用稳定接纳顺序，不为首次处理和重试切固定份额。结果保持原保留位置，退避期间不占保存并发，同一在途记录不重复领取；全部保留记录退避时，允许保存者空闲而新结果被拒收。

正常完成保存、无数据库错误零行或已确定无效时结束保留；零行不证明此前保存成功，不补查推断原因。后台对已确定无合法目标、跨组、关系不符、旧尝试、Task 终态或身份冲突的记录释放；父 STOPPING 或到期本身不使结果无效。`Data` 缺省合法，业务失败结果不采用其 `Data`，`error`／`panic` 形成的失败结果仍是合法内容。内容无法保存为 JSONB 时，必须定位到该条结果并独立核实，例如需要保存的 JSON 字符串包含 `\u0000`；不能只按 SQLSTATE、错误文案或重复失败次数丢弃。完整依据见[回报错误分类](data-contracts.md#result-error-classification)。

数据库技术错误、原因不明、提交不明及仍需使用的平台坏快照或未知版本，保留该条原结果、退避并告警，不回滚或重放其他已明确提交结果，也不因重做而重新执行业务。结果保存不设置批级总超时或超时后拆批降级，不额外增加锁等待超时及其他细分预算；单条两秒到期或 Context 取消不证明已经回滚，实际操作退出前不能提前归还处理能力。共享 30 秒停机、Task 尝试规则和 Instance 截止时间不变，不套用执行器有限重传或派发 ACK 保存额度。

512 条是局部记录数范围，不是整个进程内存硬上限。结合当前 4 MiB RPC 接收上限，512 份接近上限的报文仅序列化体积就接近 2 GiB，实际还受对象、复制和其他组件影响；部署须结合结果大小验证，不新增队列总字节配额或独立结果长度配置。完整规则见[调度端保存初值](execution.md#scheduler-result-defaults)。

已通过的[派发供给参数](#dispatch-supply-configuration)、创建并发 32、调度派发并发 64、STOPPING 与远端通知的局部参数保留原含义，不因结果保存初值相同或不同而混用计量范围。本轮已确认的调度端保留、并发、单条处理及退避参数继续按本模块实施，不预先冻结 Go 原语或公共组件抽取；仍须验证正常处理、队满、依赖变慢及恢复时的行为，不以队列长度单独推导吞吐。

### Instance 检查提示与处理初值

**2026-10-29 已通过，普通完成及 Leader 复核交接已实现，实际验证见[最新记录](ordinary-readiness-review.md#ordinary-timeout-recovery-progress)。** 结果保存提交后交给本节点的 Instance 检查提示，与已定 Leader 复核交接的候选共用检查组件；保存者不等待父检查完成。检查根据数据库事实进行有限阶段推进或完成判断，不按提示中的旧结果直接写父状态。完整运行规则见[Instance 检查初值](execution.md#instance-check-defaults)。

| Instance 检查参数 | 已通过的部署初值 |
| --- | --- |
| 本地唯一 Instance ID 总量 | 每节点 **512** 个，包含合并等待、排队及处理中；相同 ID 合并为一个条目，处理中条目不在上限之外另计 |
| 检查并发 | 每节点 **8**，同一本地 Instance 不同时执行两个检查；与结果保存的 8 个处理能力分别管理 |
| 单次检查处理预算 | **2 秒**，从实际开始处理计时，覆盖取得连接、必要事实读取、有限状态写入及提交确认，不包含排队和合并等待；停机时继续受共享剩余宽限限制 |

以上三项部署可调，不表示查询、写入或连接能在预算结束时硬退出，实际操作退出前不能提前归还处理能力。**100 毫秒**合并等待为内部初值：从该条目首次提示时刻起算，后续合并提示不延长；到时获得检查资格，不保证立即执行，也不延长 Instance 原截止时间。

检查期间到达的第一条新提示，记录一次后续检查及其最早时间“该提示时刻 + 100 毫秒”，随后提示只合并、不继续推迟。本次结束时，只有已经明确确认父终态才可清掉后续检查；否则沿用原条目和位置额度转到队尾一次，达到已记录的最早时间后可再处理，不重复排队或申请新位置。本次技术错误也不能抹掉已经收到的新提示。

本次没有新提示时，NotReady 或技术错误均结束本地条目，不因错误自行无限重查；后续正常提示或既定 Leader 复核负责补漏。容量满时已有 ID 仍可合并；新的正常提示非阻塞放弃，不影响已经提交的 Task 结果，也不让结果保存者等待检查队列腾空。正常和恢复共用上述资源，Leader 查询及交接遵守[RUNNING 复核初值](execution.md#instance-recheck-defaults)：仅在集合占用低于总量一半时新增恢复 ID，达到水位或满时在扫描剩余预算内等待释放。该水位由集合总量派生，不增加恢复来源计数、独立配置或检查池，也不切分 8 个检查并发；不承诺正常占用持续较高时恢复仍取得位置。

### 派发候选容量与补查 {#dispatch-supply-configuration}

**2026-10-28 已通过，尚未实现。** 以下参数仅约束调度进程派发供给，不套用于执行器、结果回报、RUNNING 或 STOPPING 恢复。完整行为见[派发容量与补充规则](execution.md#dispatch-supply-defaults)，分页见[候选临时分页](data-contracts.md#dispatch-candidate-pagination)。

| 项目 | 初值及计量范围 |
| --- | --- |
| 派发并发 | 每进程 **64**，沿用已定部署配置；覆盖发送前处理和等待接单响应，不等待业务完成 |
| 等待候选总量 | 每进程 **256**，部署可调；包含查出尚未交接的临时页面、待处理提示及其他等待候选，不能另设无界旁路；处理中工作另外受派发并发限制 |
| 候选查询页大小 | 默认最多 **128** 条，实际读取量仍受剩余候选空间限制；不是登记批量或整趟总量 |
| 空闲补查间隔 | 默认 **1 秒**，部署可调，各节点独立上下浮动 **20%**；没有候选或无进展预算用尽时等待，不要求正常本地供给每批等待一秒 |
| Instance 补充份额 | 每次先补充最多 **8** 项，再轮到其他已发现 Instance；没有其他 Instance 时可继续利用空闲能力，不是该 Instance 的并发上限或事务登记批量 |
| 连续无进展读取预算 | 最多 **4 页**；只有本轮补查交接的候选新尝试明确登记提交成功，才恢复到 4 页，不累加，不增加并行扫描趟数 |

正常提交后本地派发和数据库发现共用能力，不按来源切固定比例。候选容量满就暂停补充，剩余工作留在数据库；轮转同时约束候选补充，不能先用一个大 Instance 填满全部候选再声称公平。页大小、轮转份额及读取预算等采用集中默认值；数值是待验证的部署与实现初值，不承诺严格全局公平或实测吞吐。

WAITING 使用本趟固定 ID 上界及 `id` 游标；到期重试固定本趟数据库时间，使用 `(next_dispatch_at, id)` 游标。仅接纳、合并或按既定竞争规则跳过的候选允许前移，队满保留位置；本趟结束后等待下次补查再从头开始，覆盖较小 ID 的迟提交及后来到期工作。扫描位置不表示执行成功，也不是永久消费水位。

候选入队、父 NOWAIT 失败、候选失效、技术失败及提交结果不明不刷新读取预算，无关本地正常派发成功也不刷新。连续 4 页仍无有效登记进展时暂停，等下次约一秒的补查机会；已交接的本轮补查候选后来成功可继续补充，但仍受剩余容量限制，到尾也不立即回到第一页。同 Instance 竞争失败不借分页立即重抢。默认值下纯竞争失败一次连续补查最多返回 512 条候选，不等于每秒最多成功派发 512 条，也不保证数据库只访问 512 行。

发送 RPC、ACK 保存、BUSY 延期与保存重试、非 BUSY 明确拒绝的有限保存及绑定缺失观察已由下方[派发时间预算](#dispatch-time-configuration)独立确认，不从一秒补查间隔推导；分片首次派发查询及登记批量仍随生成协议闭合。执行器[业务并发与等待队列](execution.md#executor-business-defaults)、[回报组件](execution.md#reporting-defaults)均已有独立初值，不从本节派发配置推导。实现后的验证见[派发供给验收](verification.md#dispatch-supply-checks)。

### 单次派发时间预算 {#dispatch-time-configuration}

**2026-10-28 已通过，尚未实现；2026-10-30 已批准将有限响应保存预算扩展到非 BUSY 明确拒绝。** 本节将单次派发、接单响应保存及绑定缺失观察的时间关系一起确定，完整协议见[派发时间预算与确认失败处理](execution.md#dispatch-time-budgets)。各值只作用于下述阶段，不外推为业务执行超时、结果回报预算、恢复扫描周期或取消通知预算。

| 项目 | 初值与起点 |
| --- | --- |
| 一次派发处理总预算 | **10 秒**，从工作协程取出候选、开始处理起，覆盖登记、客户端准备、RPC、响应保存及重试等待 |
| 发送前登记事务预算 | **2 秒**，包括连接等待、事务内查询与更新及提交确认 |
| 接单 RPC 超时 | **3 秒**，从发起调用起，只等待接纳响应，不等待业务完成 |
| ACK 绑定、BUSY 或非 BUSY 明确拒绝保存阶段 | 最多 **4 秒**，从开始处理这份响应起 |
| 响应保存总尝试次数 | 最多 **3 次，包含首次**，只重做原响应的条件写入 |
| 单次响应保存超时 | **1 秒**，包括该次数据库操作的连接及执行等待 |
| 响应保存失败后的间隔 | **200 毫秒**，仍计入保存阶段与总处理预算 |
| 无绑定观察期 | **30 秒**，从数据库 `attempt_registered_at` 起算，包含登记提交期间的耗时 |
| 明确 BUSY 后延期 | **5 秒，上下浮动 20%**，按既定 SQL 的数据库求值时间保存 `next_dispatch_at` |

各阶段同时受剩余总处理预算及停机剩余宽限限制，不在进入阶段或重试时重新获得完整总预算；最多三次也不保证一定尝试满三次。总预算、接单超时、观察期及 BUSY 延期作为主要部署参数，细分保存次数、阶段上限和间隔集中维护，不提前冻结 Go 并发结构或具体配置字段。数值是待校准初值，不是已验证的吞吐、恢复或资源释放时限。

仅登记明确提交才可发送；登记提交不明，或登记已提交但总预算耗尽而尚未发送时，放弃本次发送，按持久化事实进入既有恢复。RPC 超时、断连或没有明确答复不构成 BUSY，也不能证明执行器没有接单，不立即换节点重发或免费返还。预算耗尽不再发起新操作；仍未实际退出的操作不能被视作已释放并发能力。

有效 ACK、明确 BUSY 与[能够确认未接纳的非 BUSY 拒绝](data-contracts.md#dispatch-rejection-settlement)共用上述有限响应保存规则，由收到响应的当前派发处理者直接保存：成功或无错误但更新零行就结束，零行不追加核对；可恢复数据库故障或提交确认不明才在剩余额度内重做原条件写入。耗尽释放原响应，不新增长期保存队列，不重新调用 `DispatchTask`。拒绝未落库且仍完全未绑定时，由既有观察结算兜底，接受拒绝原因未持久化和结算延迟；不能将释放响应视为已回滚或已结算。保存使用独立于已结束接单 RPC 的处理上下文，并继续受总预算约束；父已 STOPPING 时仍遵守原条件更新，不恢复父子状态。接单调用返回或超时不取消已接纳业务的 Context，业务继续受整轮截止与取消控制。

明确非 BUSY 拒绝的条件结算不等待观察期，不返还或额外扣减执行机会，也不改变尝试编号。普通、准备、分片及 Post 都使用本轮冻结预算：仍有机会则按数据库处理时间加本轮重试间隔（默认 10 秒）等待重试，耗尽才最终失败；下一次派发须重新取得父实例授权。执行器本地判定已经过期，不直接决定 Instance 超时。[派发与取消错误映射](data-contracts.md#dispatch-cancel-errors)已通过：认证拒绝使用标准 `Unauthenticated`／`PermissionDenied`，非法输入复用 `bizerror`＋`common.invalid_request`，其他已确认的接单前拒绝统一使用默认 `100001`＋`job.executor.dispatch_rejected`，通过 `ErrorInfo.Reason` 识别，不解析英文 Message。未知 subcode、通用技术错误或无效 ACK 仍按不确定性处理。拒绝耗尽机会时 Task 的 `end_reason=dispatch_rejected`，等待重试仍为 NULL，具体原因保存在摘要中；这不是父 Instance 的超时判定。

观察期跨节点、重复扫描和绑定保存重试均不重置；所有调度节点保持一致，调整派发及保存预算时一并核对时间关系。30 秒为正常处理预算留余量，但到期仅允许条件结算，不证明旧业务已停止，也不保证此刻完成恢复；扫描、数据库故障与积压仍会延迟处理。候选的扫描间隔、分页和处理预算已由下方[无绑定扫描与结算](#unbound-recovery-configuration)独立确定，不套用派发或结果保存预算。

BUSY 延期独立于业务失败默认 10 秒的重试间隔；保存约 4～6 秒后的最早派发时间后，即结束本次处理，由已定的一秒补查在到期后发现并按原协议登记新尝试。不占住派发工作协程等待五秒，不新增 BUSY 次数状态或专用队列，也不延长整轮截止。

go-zero v1.10.3 的客户端及服务端原生默认超时均为 2000 毫秒；落实三秒接单预算时，须协调原生客户端配置／调用超时与执行器 Server 的方法超时，不能只设置外层 Context 而被内部两秒提前截断。现有管理与普通 System RPC 保持各自职责，不将其已有配置当作新增执行器入口已配置完成。该接入核对不增加自定义 RPC 封装；实现验证见[时间预算验收](verification.md#dispatch-time-budget-checks)。

| --- | --- |

每趟扫描固定 `scan_now` 及据此计算的观察截止，使用 `(attempt_registered_at, id)` 临时游标分页；未完成时，下一次执行沿用这些值和游标，但重新取得本次 5 秒预算。候选查询的固定时间上界不替代处理时的复核：每个最多 16 条的小批都重新取得数据库时间及父状态／配置。扫到尾即结束本趟，经过执行后等待，下一趟重新取得时间上界并从头覆盖，不在同次剩余预算内立即重扫。节点退出后临时位置丢失，下次从头发现，不能把临时游标作为永久消费水位。

**每条 Task 单独执行条件 UPDATE，并独立提交。** 不增加父行或 Task 显式锁，也不增加 NOWAIT；UPDATE 仍可能等待其他写入持有的行锁，节点抖动只减少同步冲突。单次操作使用其 1 秒上限与流程剩余预算中的较小值，预算到期停止新操作；Context 取消不保证数据库已回滚或资源已释放，必须等旧操作实际退出才结束本次流程并开始间隔等待，不叠加替代执行。

游标只沿按原候选顺序处理的连续前缀推进：明确提交成功、无错误但更新零行、或复核后已不适用的候选均可越过。某条 Task 的写入发生技术失败或提交不明时，也允许越过该**已尝试项**，但立即结束本次流程；下次从其后继续，之后新一趟再从头补查仍符合条件的记录。这不证明该次已成功或已回滚，也可能延迟失败项的再次处理。取时、候选查询或小批关联读取失败时结束本次流程，不越过尚未核验／处理的候选，不因已取回整页就把游标移到页尾。

复核已观察到父为 STOPPING 时，交给既有停止处理；父已到期时，提示既有完成／超时检查，再继续其他候选，不在本流程直接裁定整轮结果。只有 Task 条件更新实际生效且已明确提交，才提示所属 Instance 检查；不直接派发下一次尝试。普通 Task 结算 SQL 已通过，共用这些扫描参数不表示其他 Task 类型的结算 SQL 已自动通过。

30 秒观察期仅授予条件结算资格，不承诺到期立即恢复。候选竞争、扫描未完成、故障及处理积压均可延迟结算；失败候选仍可由数据库后续重新发现，所以不套用已 ACK 真实结果的内存保留与重试规则。这些初值尚未经过实现和压测，不构成无冲突、硬资源释放期限或恢复 SLA。

### 运行观测

触发入口记录容量拒绝指标和限频错误日志，避免过载期间逐条刷日志。待处理总量、处理并发与积压延迟用于验证触发承载；配置文件初值为 Job 总容量 1024、Instance 创建并发 32、单次处理超时 3 秒，不增加 Job 页面配置。自动工作协程数取创建并发配置，不另设参数；计时起点、手动共享额度及调优原则见[部署初始参数](execution.md#trigger-runtime-defaults)。具体指标名与连接池配合仍须在实现契约中落实。

Task 派发工作协程另按每调度进程默认 **64** 个配置，覆盖发送前数据库处理及等待执行器接单响应，不等待业务完成；与 Instance 创建并发 32、执行器业务并发及结果回报并发分别管理。等待候选总量已定默认 256，分页、轮转及退避采用上方[派发供给初值](#dispatch-supply-configuration)，不将 64 解释为所有组件的统一并发值，见[有界本地派发](execution.md#bounded-dispatch)。实施后须结合数据库等待、派发响应延迟、积压、补查登记成功率及执行器 BUSY 情况压测校准，不据此宣称达到竞品性能。

[派发竞争](execution.md#dispatch-contention)单独批准普通首次启动及已有 Task 新尝试登记的父主键锁改用 `FOR UPDATE NOWAIT`，保留本地正常派发、多节点接续及上述 64 并发，不增加分桶或固定 owner。这不是 STOPPING 锁策略的自动扩大，不将 NOWAIT 推广到其他父事务或普通 CRUD；父状态、截止、执行预算及提交确认等原有授权条件不变。

本地 WAITING 提示按 Instance 合并，已有 Task 提示按 Task ID 与候选携带的原 `attempt_no` 去重；同一 Instance 在本节点最多进行一个登记事务，限制只覆盖登记事务，不跨越后续 RPC 等待。补查节点采用各自独立的小幅随机抖动，已接纳候选按 Instance 从不同起点处理，以减少多节点同步争抢；SQL 查询仍保持索引有序，不在数据库随机排序。父锁竞争失败后跳过本次同一 Instance 候选组，交给后续查询重新发现，不通过立即重排、重放旧提示或重复查询第一页形成忙等，也不把本次跳过变为永久排除。

NOWAIT 仅改变父行锁竞争时的等待行为，不能消除重复读取、事务开销或子 Task UPDATE 与结果保存之间的锁等待，也不构成吞吐或跨节点无冲突保证。[排队、并发与满载处理](execution.md#capacity-model)已确定正常／补查派发共享且不切固定份额、Instance 小批轮转和有处理余量时持续补充；[派发供给初值](#dispatch-supply-configuration)已补齐补查间隔、抖动、等待候选上限、查询页大小、轮转份额及无进展退避，登记批量和具体实现仍待落实，不套用 STOPPING 或远端取消通知参数。以上仅为已批准设计，派发组件尚未实现。

Leader 触发恢复另外使用单批读取上限 **1024** 和查询超时 **5 秒**的部署初值；前者不是待处理队列容量，后者不是整轮扫描／处理预算，也不替代单 Job 的 3 秒处理超时。每次查询只取 `id,next_trigger_at`，下次重新读当前数据库，不维护跨分钟扫描状态。查询短上下文结束不取消已交接工作，失主则按任期规则停止查询和新投递；见[单批触发恢复](execution.md#trigger-recovery-scan)。

RUNNING Instance 复核的 **2 分钟周期、4 分钟开始时间门槛、256 条每页**与上述 Job 参数分开。每趟固定查询时间上界，使用 `(started_at,id)` 临时分页，未扫完下周期继续，扫完后的新一趟重新从头覆盖；不把游标当永久消费水位，不将 256 当检查队列容量或整趟读取总量。候选只取 ID 和分页时间，查询不按 `deadline_at` 二次筛选，不汇总 Task，也不依赖 Job 当前状态，具体见[统一候选查询](data-contracts.md#instance-recheck-query)。交接后使用已定的 512 个唯一 ID、检查并发 8 和单次处理 2 秒，正常和恢复共享资源。

续扫每个周期重新获得该周期 5 秒预算，但沿用原趟 `scan_now` 和游标，不把续扫变成新的时间上界。一次查询使用单次上限与剩余周期预算中的较小值；查询失败结束本周期，下一周期按原位置继续。预算用尽或失主后停止新增查询和交接；已经交给检查组件的工作继续使用自身 2 秒处理预算，不随扫描 Context 取消。扫描停止、切主及停机仍分别遵守既有任期和进程生命周期规则。

新增恢复 ID 时，必须原子核对集合占用低于水位；已存在的 ID 仍可合并，不再占用位置。**达到水位或集合已满时，暂停新增查询及新 ID 交接，在本周期剩余预算内等待本地空间释放后继续，替代此前满时立即退出的 RUNNING 规则。** 等待不持有数据库连接或事务，不忙循环，不为每个候选创建等待协程。最多保留一页 256 条候选和本趟游标，不建立另一个恢复队列；页面大小不是每周期总量限制，不增加总页数上限。

只有候选已接纳或与已有 ID 合并，游标才可前移；首个新 ID 尚不能接纳时停在该处，不能跳过去处理后面的候选。恢复接纳使用水位限制，不将普通提示满时放弃规则套用为恢复游标直接前移。已接纳检查结束但失败、且没有新提示时，仍由后续正常提示或之后新一趟扫描补漏，不因扫描已推进就声称持久化已完成。

默认配置下，本方案只保证恢复不会主动填满检查集合、已接纳条目按既定顺序处理，以及短时拥塞在本周期窗口内消退后可以继续补充。若正常占用持续或覆盖整个扫描窗口不低于水位，恢复可长期没有新增进展；不保证固定恢复份额、绝对来源公平或恢复 SLA，也不将监测描述为防饥饿机制。极小配置总量为 1 时，至少为 1 的恢复门槛退化为共享单位置，不再留下额外正常缓冲余量。循环、索引计划及所列生命周期已有专项验证，正式负载表现仍待阶段 6 测量。

[STOPPING 查询和索引](data-contracts.md#stopping-recovery-query)沿用已定分页协议：每趟固定当前停止记录最大 ID，按临时 ID 游标有界翻页，候选接纳或合并后才推进，队满不越过未接纳项；未扫完下周期继续，完成后新一趟从头覆盖较小 ID 的迟停止、晚提交及处理失败记录，切主重新开始。单周期的 5 秒预算只限制本次扫描／投递，不把临时游标改为永久水位，也不承诺一趟或一个周期扫完。

每个子批次均在独立短事务中，先按父主键取得 `FOR UPDATE NOWAIT` 并确认仍为 STOPPING，再读取该 Instance 的本批未结束 Task；不得先查子 Task 再竞争父锁。父锁取得失败时回滚、结束本次 Instance 处理，不立即重新排队或利用已合并的旧提示立即再抢；失败不改变持久化停止决定，后续周期恢复仍可重新发现。每批提交后释放父锁，下一批必须重新取得，不跨 4 批或 2 秒预算一直持锁。批次为空时，在已取得的父锁内按 `NOT EXISTS` 再确认没有未结束子 Task，才保存父最终状态；不能仅凭读取空页就认定整轮已完成。

父行竞争采用不等待方式，但子 Task 条件 UPDATE 仍可能等待正常结果回报持有的行锁；1 秒单 SQL 超时用于限制该操作，不能宣称整个处理完全不阻塞。2 秒轮转预算到达后不启动下一批，不等于事务或数据库取消必在该时刻结束；实际事务完成、回滚或连接失效的处理结束前，不能提前归还处理额度。技术失败及提交不明继续遵守既定恢复协议，不把不确定结果当作已取消或确定回滚。子处理不使用 Task 游标或 OFFSET，后续从当前未结束集合继续；不增加额外 `lock_timeout`、分桶、固定 owner 或通知机制。

上述容量与竞争处理已批准但尚未编码，两条索引仍未创建。数据库取消容量与下述远端通知参数分别管理，数据库处理不等待 RPC 送达或业务实际退出。

#### 远端取消通知 {#cancel-notification-operations}

**通知按 Instance、组及目标地址去重，不按子 Task 逐条发送。** 例如同一 Instance 的 1000 个 Task 只对应同组 5 个地址，本次枚举产生 5 个目标通知，通信重试另计。目标使用本轮保存的组及 Task 绑定地址，不因 Task 已成功、失败或取消而排除；数据库先完成子状态处理，不应使仍需尽力取消的已知目标从查询范围消失。父最终结束也不取消已经接纳的通知，剩余枚举及发送仍在原通知期限内继续，不因此重置期限。

[地址查询](data-contracts.md#cancel-target-query)使用 `(instance_id, executor_address) WHERE executor_address IS NOT NULL` 部分索引，跨该 Instance 的所有 Task 状态，按地址键集分页，每页最多 32 个不同地址。每页在一个 SQL 内有界跳到下一个不同地址，可采用递归 CTE；不在应用层按地址循环查询形成 N+1，也不读取整轮 Task 再在内存建立全集 Set。不能仅以 `DISTINCT ... LIMIT 32` 的返回条数限制宣称扫描量已经有界，执行计划和高重复地址数据仍须验证。绑定可能在游标经过后才保存；迟到绑定、晚到派发、旧地址或地址缺失造成的遗漏属于尽力通知边界，不为补齐它们重新扫描历史。

通知组件使用独立的 **1 个地址读取协程 → 有界目标队列 → 16 个固定 RPC 工作协程**。每个 Instance 一次交接一页，仍有下一页则回到队尾；目标容量满时暂停读取，只保留地址读取协程当前页尚未交接的有限部分，不为每个 Instance 缓存整页。目标被接纳后才推进地址游标，不越过未接纳项，不通过扩大内存缓冲掩盖背压。

| Instance 通知总量 | 每节点 **256** 个，包含排队、地址读取及仍有目标未完成的 Instance；本地合并重复提示 |
| 目标通知总量 | 每节点 **256** 个，包含排队、发送中及重试等待中的目标，不是仅队列长度 |
| 地址页大小／读取并发 | 每页 **32** 个不同地址，独立 **1** 个读取协程 |
| 目标 RPC 并发 | 固定 **16** 个，不占数据库取消的 2 个协程、派发的 64 个协程或结果消费者 |
| 地址查询超时 | 单 SQL **1 秒**，同时受本次 Instance 剩余通知期限及停机期限约束 |
| 单次 RPC 超时 | **1 秒**，同时受单目标、Instance 和停机剩余期限约束 |
| 单目标尝试次数／间隔 | 最多 **3 次总尝试，包含首次**；可重试通信故障间隔 **1 秒**，永久错误不重试 |
| 单目标处理预算 | **5 秒**，从工作协程开始处理该目标计时，包含创建客户端、建连、发送、重试及等待；预算不足时不保证用满 3 次 |
| 单个 Instance 通知总预算 | **60 秒**，从本地接纳时计时，包含排队、地址查询及全部目标发送；翻页和重复提示合并不重置，受进程停机更短期限约束 |

每个目标通知临时创建直连客户端，同一次通知的有限重试内复用，结束后关闭，不跨通知缓存连接。通知成功只表示执行器处理了本次协作取消请求，不证明业务已经退出；失败不消耗 Task 业务重试次数，也不改变已保存的停止原因和数据库最终状态。

[取消错误映射](data-contracts.md#dispatch-cancel-errors)已通过：无匹配活动同样正常空响应，不返回 NotFound；标准认证错误及 `bizerror`＋`common.invalid_request` 结束同一错误通知，临时不可用、超时、断连和未知错误只在上述原预算内重试同一目标。取消不使用派发拒绝 subcode，不因原执行期限已经过去而拒绝，也不将 RPC 错误码保存为父子记录的结束原因。退出时仍有本机取消能力则正常处理，入口已关闭按通信失败处理，不保证整个停机宽限内始终可访问。

地址查询失败时终止本次剩余枚举，已经入队的目标继续使用原期限；查询到尾也不提前取消尚未完成的目标。Instance 通知期限到达后不再读取地址或启动新目标，取消在途查询和 RPC 的 Context；单目标预算到达也不再尝试该目标。取消 Context 不是硬退出或资源已经释放的保证，实际操作退出前不能提前归还仍被占用的处理额度。通知接纳队满、进程宕机、期限耗尽或有限重试耗尽都可以使部分目标未收到请求，记录相应诊断而不新增可靠补送机制；数据库子状态处理和父最终结束继续按各自恢复协议完成。

上述值是独立的部署初值，不是性能结论或送达时限保证，也不与数据库取消的总量 256、并发 2、子批次 256 混用。地址查询、索引和通知组件均仍处于已批准设计阶段，未编码、未执行迁移或性能测试；完整运行规则见[取消通知容量](execution.md#cancel-notification-capacity)，验收见[通知查询与容量检查](verification.md#cancel-notification-checks)。

#### 执行记录与展示

数据库执行记录用于查看某轮及分片的状态和简短诊断。详细过程、历史尝试详情进入现有服务日志／日志系统，按 Job、Instance、Task、尝试及必要的 traceId 关联，不建设数据库过程日志表或在线滚动日志控制台。

正常完成的 Instance 摘要已有明确来源：普通任务与准备最终失败直接结束时复制相应 Task 的最终摘要，合法空串不由旧尝试文本替补；分片流程记录业务分片总数、成功数、最终失败数及适用 Post 结果，不拼接全部子摘要。正常成功保存 `success`，正常失败统一保存 `execution_failed`，不复制子 `result_unknown`／`dispatch_rejected` 或以最早到达的失败回报解释整轮。人工停止与超时分别为 `manual_stop`、`instance_timeout`，在 STOPPING 时冻结；六个原因值及父子适用范围见[稳定结束原因](data-contracts.md#execution-end-reasons)。正常完成 `finished_at` 是 UPDATE 内 `clock_timestamp()` 求值时的数据库时间，不保证在行锁取得后求值，不作为精确提交或业务退出时间展示。

自动触发的错失忽略和阻塞丢弃只留结构化服务日志，不进入管理端 Instance 历史。日志复用当前判断取得的 Job ID、计划时间、判定时间、新进度及原因，不额外查询业务数据。成功日志在进度提交确认后输出，不能覆盖提交后宕机或采集故障造成的缺失；第一版不提供完整跳过审计或精确计数。完整规则见[跳过留痕](data-contracts.md#trigger-skip-record-proposal)。

平台状态、业务进度和性能指标应分别解释。例如平台已停止不表示所有业务已经退出，分片数量完成比例也不等于业务数据处理比例。第一版展示分片数量统计，不提供业务内部实时进度或 Notify 回调；具体性能指标、告警能力及日志跳转形式仍需后续设计，不能从已有状态表推导为已经具备。

阶段继续根据 Task 类型、已保存结果和分片生成事实推导，不新增权威阶段字段；具体展示名称、组合形式及 API 表达留给管理设计，不在完成协议中确定。

## 7.5 历史记录与维护

第一版纳入基础历史执行记录清理，与 Job 定义删除分开。本轮暂不考虑月分区，当前方案不采用月分区；未来可根据实际数据量和验证结果重新评估，不作为永久禁止。执行记录和服务日志的保留、归档与清理分别设计；保留期限、清理算法、手动或自动机制、维护任务及全量删除入口仍未确定，不因本批事务与索引通过而一并定案。

已确认的 Job 逻辑删除不替代历史清理，也不把软删除字段扩展到 Instance／Task。保留的 Job 定义仅表示删除时的最后配置，不提供配置版本历史或恢复入口；后续历史维护不能靠级联删除 Job 来清除执行记录。

手动请求的成功创建去重依赖 Instance 中的请求身份。清理该记录也会移除原请求号的防重证据，不保证旧号跨清理仍能找回原执行；不为此永久保留请求墓碑或新增请求表。具体保留期、清理与重发的衔接在本模块持久化及历史维护契约中确定。

清理不能破坏活跃执行和恢复依赖，WAITING、RUNNING、STOPPING Instance 及其 Task 不得清理；这一约束与分片封口后集合不增长、Task 终态不可逆共同支撑父锁外完成判定。停止路径只有全部已创建子 Task 终态后才最终结束父，STOPPING 必须保留至数据库处理完成。父最终状态也不等于可以立刻删除历史，具体保留期限、可清理状态、关联数据处理、批次与并发保护仍在数据生命周期设计中确定，再验证维护期间的在线执行不受破坏；不为取消 RPC 的可靠送达额外延长保留。
