# 7 管理与运维

本章确定平台使用者和维护者需要的操作边界。第一版管理、执行查询、基础历史清理、接入交付及内部信任与依赖故障边界已经确认；具体页面、权限点、部署指引和清理机制仍需设计，不表示功能已经实现。

## 7.1 管理能力

| 管理面 | 第一版能力与约束 | 待确定的详细设计 |
| --- | --- | --- |
| 执行器组 | 页面动态维护组名称、标识及对应服务发现标识，数据库保存；无组启停，仅逻辑删除并保护引用与未收敛执行；管理组凭据，实例地址由 etcd 自动发现 | 凭据保护与轮换、操作权限、组变更及删除后的凭据和连接缓存失效，取消恢复依赖 |
| 任务定义 | 新增、编辑、删除、启用和停用；未删除 Job 仅停用时可编辑，仅停用且无待开始／运行中 Instance 时逻辑删除；管理入口校验组引用，不要求在线或远程探测处理器；新建／编辑与删组共用组行锁；配置提交后通过 etcd 通知核对，每分钟兜底，保存成功不等于 Leader 已应用 | 最终 SQL／API／Proto 清单、已定校验与查询契约的实现 |
| 调度策略 | 错失与阻塞提供已定选项；重试次数／间隔、整轮超时在 Job 上配置 | 页面布局、API 字段与校验呈现 |
| 运行控制 | 未删除的启用／停用 Job 均可手动执行，沿用集群阻塞策略、仅允许当次业务参数覆盖，同请求号防重复创建；不改定时进度。手动停止以 Instance 为对象，停用不取消已有执行 | 页面交互、API 请求表达、权限点及并发协议；重新启用重算下一次且不补旧轮次，不要求全部 Instance 结束后才能编辑 |
| 执行查询 | Instance／Task 列表与详情，展示状态、时间、重试和简短诊断；分片总数、成功、失败与未结束数 | 筛选、统计查询与刷新方式、诊断关联；不新增逐条回报更新 Instance 计数 |
| 历史维护 | 提供基础执行记录清理，与删除 Job 定义分开，保护活跃执行及恢复数据 | 手动或自动机制、保留期限、清理方式与操作保护 |

页面不暴露固定的 5 秒迟到容忍值；100ms 完成检查合并窗口只是测试起点，不作为管理配置。已定规则及默认值统一以[第 4 章](behavior.md)为准，避免页面说明与执行协议分别维护不同含义。

Cron 输入遵守[固定六字段规则](behavior.md#cron-contract)，不提供 Job 时区选择。独立预览接口从调度进程当前时间计算未来最多 5 个时间点，不查库、不注册规则，以带偏移的 RFC 3339 返回；不能在浏览器改用 Quartz 解析器或按浏览器本地时区重新解释表达式。接口边界见[管理契约](data-contracts.md#job-management-proposal)，页面布局仍待设计。

第一版固定双端异步回报，不提供同步／异步切换开关。回报队列容量、工作协程数及批量上限属于部署参数；执行器回报重试次数、间隔及单次 RPC 超时使用独立内部常量，不消耗 Task 执行预算。两类参数均不进入 Job 页面，具体数值待确定。

结果缓冲按总待处理条数和固定消费并发控制，报文大小复用 RPC 上限；第一版不提供队列总内存 MB 配额或独立业务结果长度配置。调度端写库故障不设置次数耗尽或保留 TTL 清理，具体边界见[结果保留策略](execution.md#scheduler-result-retention)。

管理操作复用 DogX 菜单与 API 角色权限，不限定为超级管理员专属。第一版不提供重开历史 Instance 或手动选择失败分片重跑；新建一轮手动执行可能再次处理已成功业务，不应包装为等价操作。

Job 配置编辑采用完整可编辑配置提交，与启停入口分开；说明和参数省略／null／空串均清空，其他必需配置缺失拒绝。说明及参数统一去首尾空白，参数内部内容不改；零重试和 false 明确生效，不用创建默认值替代。该入口不做 PATCH，不增加编辑版本号，允许同时编辑停用 Job 时后提交覆盖前者。普通新增 Job 返回 Job ID，不增加请求防重，响应不明时不能盲目自动重建；这与下方手动触发的同请求号重试不同。数据库提交成功不等于 Leader 已应用配置，通知失败仍按分钟核对兜底。

### 手动执行反馈与重发 {#manual-trigger-ui}

手动执行默认沿用 Job 参数，可仅替换本轮业务参数；不临时改写组、处理器、重试、超时或节点地址，也不把当次输入保存回 Job。停用 Job 仍允许手动验证，定时进度不变，集群阻塞判断不能绕过。

一次操作使用同一 `request_id`，网络超时重发沿用原号和原内容；明确再执行一次才换新号。后端提交 Instance 与本轮配置成功后返回 ID，页面提示“已创建执行记录”，后续通过执行记录查看状态，不把提交成功提示成“执行成功”。Job 未删除、原实例已经失败或取消时，同号重发仍返回原 ID，不重开旧记录。

收到明确阻塞拒绝就结束本次操作，不在后台等待补跑。手动与自动入口共用本进程创建并发额度，没有空位时明确返回系统繁忙，不另排手动等待队列。重试沿用原请求号；本次繁忙不能证明此前同号请求没有创建成功。响应不明不等于未创建，不能自动换号再提交；相同请求号改参数返回冲突。拒绝结果不永久留痕，同号迟到重试可能在条件满足后创建；原请求重放仅在 Job 未删除且执行记录仍保留时适用。Job 删除后，旧手动创建请求返回不存在，但原 Instance 仍可按 ID 查询，不能据此认定原请求未执行；完整规则见[手动触发](behavior.md#manual-trigger)。页面布局、请求表达及重试交互在管理契约中细化。

Job 删除沿用 `deleted_at` 标记，不物理清除定义，也不同时清理 Instance／Task。普通管理页面不展示已删除 Job，第一版不提供恢复站；历史按 Instance 快照继续查询，不要求关联有效 Job。必要的只读关联可查看已删除 Job 的最后定义，但这不是每轮执行时的完整配置历史。删除前置条件、并发检查及子 Task 收敛边界见[Job 逻辑删除](behavior.md#job-deletion)。

新增、编辑保存、启用 Job 及手动新建 Instance 时，校验目标组存在且允许引用；已有同请求号成功记录按原查重规则处理，前提仍是 Job 未删除。组内暂无在线执行器不阻止这些管理操作；处理器名称只做必填和本地输入校验，不做远程探测。停用、删除 Job 不依赖组存在或在线，其他删除前置条件不变。该校验不增加到每次 Cron 触发或 Task 派发，完整边界见[组引用与离线配置](data-contracts.md#job-group-reference-proposal)。

基础组管理不要求运维人员逐台录入实例 IP，也不替代业务程序部署。新增组无需修改或重启调度服务来增加映射；业务执行器仍需配置正确的注册范围。组配置动态生效的反馈、缓存及 RPC 客户端更新方式留待详细设计，不承诺提交即全节点同步完成。

第一版组管理不设启停，只做[逻辑删除](data-contracts.md#executor-group-lifecycle)。组引用与删除采用已通过的[共同组行锁协议](data-contracts.md#group-reference-concurrency-proposal)，只串行协调同组的低频新增／编辑与删组，不给执行主路径加锁。未删除 Job（含停用）、原组快照的未结束 Instance 和未收敛 Task 均阻止删组；无恢复依赖的已完成历史不永久阻挡。删除仅标记组定义，不级联删除历史，不自动取消任务或关闭执行器进程。完整组删除仍须补齐凭据、连接缓存失效和取消恢复生命周期，未完成前不开放入口。

## 7.2 业务接入责任

业务团队编写并显式注册具名 Go 处理器，在 Job 配置中引用名称；平台不要求为每种业务任务新增 RPC 方法。业务代码解释参数、访问所属业务域数据，并为准备、分片与收尾可能产生的副作用设计幂等键。

幂等键需匹配业务操作，例如按商户和统计日期约束日报，不能仅依赖 Task ID 或尝试 ID，否则跨 Instance 重跑仍可能重复业务数据。处理器还需配合取消上下文；平台无法保证不响应取消的业务代码立即停止。

合理分片是业务接入规范的一部分，但平台仍负责序列化上限、容量和背压保护。统一 Task 模型不意味着所有阶段必须使用无差别的同一执行队列，也不保证长任务不会影响短任务；阶段公平性与资源配置需在详细设计中落实。

第一版交付普通任务和分片任务接入示例及最小部署说明。平台不提供配置任意 HTTP／RPC 目标的执行方式；处理器可根据业务需要自行调用其他服务，但仍遵守数据所有权与幂等责任。

## 7.3 部署与内部安全

调度服务独立多副本部署，Leader 为其中一个副本额外承担的角色，不另建专用 Leader 部署。执行组件可嵌入所属业务 RPC，也可在同业务域独立 Worker 中运行，两者使用相同协议；轻量任务可嵌入，耗资源或长时间运行的任务宜独立部署，不能将嵌入视为资源隔离。

一个执行器进程归属一个组，可注册多个处理器；同组多个实例使用相同组 Token，并必须兼容被调度的处理器及参数契约。新处理器先完成兼容部署再启用对应 Job；具体发布与存量任务兼容规则在详细设计中补齐。调度服务通过 etcd 发现执行器，不另建调度端注册接口或数据库心跳注册中心。

### 调度时钟与时区 {#scheduler-timezone}

所有调度副本使用相同的服务器／容器进程默认时区；承担规则校验、预览和启用计算的调度后端也遵守同一约定。没有 Job 独立时区字段，不要求执行器或用户浏览器使用同一时区，也不把数据库连接时区当作 Cron 的解释依据。

Job 的到期、错失与下一次时间计算使用调度后端进程时间，与 robfig 同源，不另取数据库当前时间判断到点。相关服务器须通过 NTP 等系统机制校时；时区一致不代表时钟同步，也不承诺各节点毫秒级绝对一致。校时由部署保障，调度框架不自行探测时钟偏差、修正系统时间或自动隔离节点。适用范围见[Job 触发时间来源](behavior.md#trigger-clock)，Instance／Task 的数据库时间规则不变。

#### 时间跳变

下一次实际检查 Job 时，仍按持久化进度和本次判定时间应用既有规则：

- 时间向前跳：已迟到则按固定 5 秒容忍与错失策略处理，不逐轮补跑；跳变本身不触发额外检查。
- 时间向后调：对持续启用的 Job，不倒退已保存的 `next_trigger_at`。本机时间尚未到该时刻时不触发，也不重新生成已消费的旧轮次。

不承诺异常校时期间准点或不漏跑，也不认为系统时间一改变，robfig 已设置的 Timer 就立即重排。明显的时钟故障由运维处理，必要时校正后重启相关调度进程；不新增应用层时钟补偿机制或扫描。显式停用后重新启用仍遵守原启用重算规则，不属于持续启用的进度保护；重算后若再次到达已保留的同一 Job、同一完整计划时间，按[触发持久化协议](data-contracts.md#trigger-transaction-proposal)保留旧 Instance、推进当前 Job，不覆盖参数或重新执行旧轮次。需要再次执行时使用新的手动请求号；历史记录已清理时，不承诺仍能识别旧身份。

#### 部署时区变更

时区由部署环境统一管理，不写死 `Asia/Shanghai`。它是部署固定项，第一版不支持运行中直接切换；变更会改变“每天零点”等表达式含义，须在维护窗口按以下顺序处理：

1. 停用受影响的 Job，安排在途执行结束或按既有停止流程处理。
2. 退出旧时区的调度与管理计算进程，确认在途规则计算和事务已经结束，不让新旧时区同时进行启用或触发计算。
3. 统一修改所有相关进程的部署时区并重启。
4. 重新启用 Job，按新时区计算未来的下一次时间，不补停用期间尚未创建的轮次。

不改写已有 Instance 的历史计划时间或已保存的绝对截止时间，不迁移历史执行记录，也不增加热切换、集群自动校时或数据库进度自动迁移功能。停止与进程重启仍受既有执行、回报及故障边界约束，不保证业务代码的副作用立即停止。相关测试见[时钟与时区运维验收](verification.md#clock-operations-checks)。

### 组凭据管理 {#group-credentials}

组 Token 与管理后台登录凭据分离。创建组时由后端安全随机生成，调度服务维护组配置中的凭据；执行器通过配置文件、环境变量或部署 Secret 注入相同值，同组扩容复用组配置。不提供公开固定默认 Token，也不以空值关闭认证。

凭据不写日志，不随普通组列表返回；生成和查看等管理操作沿用角色与 API 授权。调度服务复用组凭据缓存，不为每次派发或回报额外查询组表；无法取得可用凭据时拒绝调用，不能降级为免认证。凭据格式、存储保护、查看方式、轮换及缓存更新和撤销时效留待详细设计，不承诺配置提交后所有节点立即应用。

etcd 连接凭据与读写范围由部署管理，不复用组 Token。实例注册、任务调用和管理操作的认证责任见[内部信任边界](architecture.md#internal-trust)；内部网络本身不是免认证依据，跨不可信网络需保护传输。

### 依赖故障与恢复边界 {#dependency-boundaries}

| 故障场景 | 服务边界 |
| --- | --- |
| PostgreSQL 不可用 | 不能创建新 Instance、取得新派发授权或推进持久化状态；前置步骤未提交不能凭内存继续派发。认证与基础校验有效且有容量时，回报可入队并确认接收；消费者保留已有结果并退避重试，不按次数或保留 TTL 丢弃，排队、处理中及待重试共同受条数上限约束，满后拒收，不承诺结果已落库 |
| 自动触发队列满或创建事务变慢 | 队满时拒绝新的 Job 提示并记录指标及限频日志，不因此推进触发进度；事务变慢时受数据库操作超时约束，不因变慢就拒绝仍有容量可接纳的提示。后续 Cron 或分钟恢复按事实补查，仍适用 5 秒错失策略，不承诺补跑每轮。手动没有创建额度时返回繁忙；见[触发容量与过载](execution.md#trigger-capacity) |
| Job 恢复查询失败、队满或头部候选持续失败 | 每次只从主库读最早到期的一批，查询失败或投递队满即结束，下一分钟重新查；不分页、不保留跨分钟游标，也不叠加补试。头部大量持续失败、反复队满可能使后续候选长期未获恢复检查，不保证严格公平或一分钟恢复完成；不自动改写异常 Job 的进度或启停状态 |
| Job 配置读取失败或单条 Cron 无效 | 整次读取失败保留原内存规则；首次失败则 Cron 暂不启动，后续核对及独立触发恢复继续。原规则的触发不能绕过数据库检查。单条 Cron 解析无效则移除其残留规则并记录错误，其他规则继续，不自动停用数据库中的 Job；见[配置重载流程](execution.md#job-config-reload) |
| 自动触发时 Cron 解析失败或求不出下一次时间 | 本次不创建 Instance、不推进原进度，记录含 Job ID 与原因的限频错误；不自动停用或新增异常状态。Job 可能仍显示启用但无法自动触发，需管理员修正，必要时修正后重启相关调度进程；不提供专门的内存规则自动修复，见[Cron 异常处理](behavior.md#cron-errors) |
| Job 保存已提交，但 etcd 通知失败 | 请求内通知最多 1 秒且服从上游期限，不另建重试队列；记录日志和指标，不主动将已提交保存改报失败，分钟核对补发现，不保证客户端断线后仍收到成功响应 |
| Job 配置 Watch 中断或历史已压缩 | 可恢复连接故障交给客户端；需要重建时退出旧监听，按 1 秒至最多 30 秒带抖动退避，重新核对。不叠加活跃监听，分钟核对不等待 Watch 恢复；仅在 Leader 资格仍有效时运行 |
| 发现 Leader 租约失效或无法确认有效性 | 关闭任期入口并取消独立上下文，停止自动触发、配置同步和 Job 恢复检查，丢弃未处理提示、等待本地工作退出；接受按最新 Job 合法记账的在途事务仍可能提交。不停止对等 Instance／Task 职责，见[任期生命周期](execution.md#leader-runtime-lifecycle) |
| 本地旧任期清理异常卡住 | 本机不重新参选或叠加新任期，记录错误，必要时运维重启；其他机器可接任，不等待旧机或业务执行完成。进程创建额度不得在实际操作结束前提前归还 |
| etcd 服务发现不可用 | 实例注册、地址更新和新节点发现受影响；已有连接在认证、任务执行权及所需数据库操作有效的前提下可以继续使用，不要求每次 RPC 实时访问 etcd |
| 某组没有可用执行器或派发 RPC 失败 | 影响该组相关 Task，不使其他组整体不可用；按已定的失败、重试与超时规则处理，不增加无限重派额度，具体无节点分类留待派发与恢复协议确定 |
| 执行器明确返回 BUSY | 仅容量满且未接单、未入队、未执行时可条件返还并延期，零重试同样适用；记账失败或提交不明只做有界有限重试，原响应释放或失效后不猜测补返。复用既有检查并退避，不延长整轮截止、不保证换节点；通用通信错误不免费返还 |
| 执行器暂时联系不到调度服务 | 已接收业务可以继续；公共组件有界保留并有限重传结果，积压严重时暂停新任务接收，必要时完成回调接受背压；回报重试耗尽则释放本地结果并记录错误及丢弃指标，不无限等待 ACK；取消请求也可能无法送达 |
| 业务数据库或外部服务故障 | 由处理器按契约返回失败等结果，平台按 Task 规则处理；不把所有业务依赖加入调度服务的全局健康检查 |

控制面故障不保证正在运行的业务立即停止，也不能撤回所有已发出的 RPC。两侧内存结果均不是可靠存储：执行器回报重试耗尽后释放、未报出就退出，或调度端 ACK 已被收到但落库前退出，都可能丢失原结果。ACK 只确认接收，不承诺持久化；不使用本地回报文件或持久卷进行结果补偿，节点替换不依赖原机文件。调度端已确认对可恢复写库故障有界保留、退避和背压，不套用执行器的有限回报耗尽释放；永久无效数据不能无限重试，错误分类、批次隔离和退出处理仍需细化。数量、并发及 RPC 报文上限不等于整个进程内存的硬配额。

业务幂等覆盖后续重跑可能重复的副作用，但不能重建已经丢失的执行结果。已有持久化执行器绑定但无有效结果时，保持当前尝试执行中，等待有效结果、人工停止或整轮截止；失联、重启、回报耗尽及 ACK 后丢失都不能单独授权提前重跑，第一版不新增 Task 活动查询、心跳或独立失联提前重派。明确成功正常推进，明确失败仍按原 Task 预算重试；etcd 注册存活不证明结果能够找回。

整轮超时必须有限、不允许 `0`；新增表单预填 900 秒，用户按业务调整，API 仍必填。接受执行器宕机后等待剩余整轮时间，也接受单个分片丢失结果拖至整轮超时且无法进入正常 Post。到期时 Instance 失败并记录超时原因，未结束 Task 按既有取消规则收敛，不使用剩余预算继续重试，也不把所有 Task 判为业务失败。无绑定的有限观察规则及平台推进恢复不变，权威边界见[已绑定结果等待](execution.md#bound-result-wait)。

依赖恢复后仍遵守停止、整轮超时、重试预算和已提交状态，错失触发沿用既定策略；恢复不等于所有工作重新执行。父 Instance 已终态但子 Task 尚未收敛仍属于恢复范围，包括与停止交错写入的重试候选；新尝试被父行授权检查禁止，已授权在途 RPC 或业务仅能尽力取消。旧 Leader 迟到触发只能按最新 Job 进入短事务记账，停止本地 Cron 不是数据库硬隔离；切主处允许的在途提交见[切主边界](execution.md#leader-config-boundary)。重连与重传契约继续按模块设计。

### 启动与能力就绪 {#startup-readiness}

基础配置缺失或非法时明确报错；短暂依赖故障允许进程保持存活、等待恢复，但相关能力不得假装就绪。进程存活、回报接收容量、数据库推进能力和 Leader 触发资格分别判断；非 Leader 是正常副本状态，不能因此把可接收回报的节点全部摘除。接收 ACK 可用不表示后台落库能力正常，具体探针与背压反馈在详细设计落实。

调度服务就绪不等待所有执行器组上线，某个动态组异常不导致整个调度集群启动失败。嵌入业务 RPC 的执行组件不应仅因调度服务暂不可达就拖垮原业务接口；业务本身对数据库、etcd 等依赖的要求仍然成立。

这些是待实现验证的启动目标，不是框架现成保证。当前依赖的 go-zero v1.10.3 在原生 etcd 注册路径上先注册、再启动 RPC 服务，首次发现读取也依赖 etcd；运行中保留已有地址与无缓存冷启动不是同一种情况。启动编排、重连和探针实现需遵守原生组件的实际约束，不能把“已有连接可继续”外推成“etcd 故障时新进程也能正常启动服务”。

etcd 需要按可用性目标部署和运维，单节点部署不自动具备高可用；注册地址不代表业务健康、剩余容量或 Task 存活。具体验证见[第 8 章](verification.md#trust-dependency-checks)。

选主使用官方 Session＋Election，TTL 部署初值 15 秒且须为正值；此值不是切主 SLA，不保证在 5 秒错失窗口内接任。统一集群前缀必须按环境及逻辑调度集群隔离，选主范围与持久通知标记分开，执行器不得访问这两类范围。短 etcd 请求、配置读取及通知分别采用已定 5／5／1 秒预算，长期竞选、续租与 Watch 使用生命周期上下文，见[etcd 接入约定](execution.md#etcd-integration)。

### 规范衔接

etcd 与仓库当前跨进程协调规范的适用边界已由 [ADR-0009](../../adr/0009-scheduler-domain-and-etcd.md)确认，待用户明确要求开始实现后同步生效规范；其他数据分层、短事务和 Redis 键管理约束继续生效。

## 7.4 日志与可观测性

触发入口记录容量拒绝指标和限频错误日志，避免过载期间逐条刷日志。待处理总量、处理并发与积压延迟用于验证触发承载；配置文件初值为 Job 总容量 1024、Instance 创建并发 32、单次处理超时 3 秒，不增加 Job 页面配置。自动工作协程数取创建并发配置，不另设参数；计时起点、手动共享额度及调优原则见[部署初始参数](execution.md#trigger-runtime-defaults)。具体指标名与连接池配合仍须在实现契约中落实。

Leader 触发恢复另外使用单批读取上限 **1024** 和查询超时 **5 秒**的部署初值；前者不是待处理队列容量，后者不是整轮扫描／处理预算，也不替代单 Job 的 3 秒处理超时。每次查询只取 `id,next_trigger_at`，下次重新读当前数据库，不维护跨分钟扫描状态。查询短上下文结束不取消已交接工作，失主则按任期规则停止查询和新投递；见[单批触发恢复](execution.md#trigger-recovery-scan)。

数据库执行记录用于查看某轮及分片的状态和简短诊断。详细过程、历史尝试详情进入现有服务日志／日志系统，按 Job、Instance、Task、尝试及必要的 traceId 关联，不建设数据库过程日志表或在线滚动日志控制台。

自动触发的错失忽略和阻塞丢弃只留结构化服务日志，不进入管理端 Instance 历史。日志复用当前判断取得的 Job ID、计划时间、判定时间、新进度及原因，不额外查询业务数据。成功日志在进度提交确认后输出，不能覆盖提交后宕机或采集故障造成的缺失；第一版不提供完整跳过审计或精确计数。完整规则见[跳过留痕](data-contracts.md#trigger-skip-record-proposal)。

平台状态、业务进度和性能指标应分别解释。例如平台已停止不表示所有业务已经退出，分片数量完成比例也不等于业务数据处理比例。第一版展示分片数量统计，不提供业务内部实时进度或 Notify 回调；具体性能指标、告警能力及日志跳转形式仍需后续设计，不能从已有状态表推导为已经具备。

## 7.5 历史记录与维护

第一版纳入基础历史执行记录清理，与 Job 定义删除分开。本轮暂不考虑月分区，当前方案不采用月分区；未来可根据实际数据量和验证结果重新评估，不作为永久禁止。执行记录和服务日志的保留、归档与清理分别设计；保留期限、清理算法、手动或自动机制、维护任务及全量删除入口仍未确定，不因本批事务与索引通过而一并定案。

已确认的 Job 逻辑删除不替代历史清理，也不把软删除字段扩展到 Instance／Task。保留的 Job 定义仅表示删除时的最后配置，不提供配置版本历史或恢复入口；后续历史维护不能靠级联删除 Job 来清除执行记录。

手动请求的成功创建去重依赖 Instance 中的请求身份。清理该记录也会移除原请求号的防重证据，不保证旧号跨清理仍能找回原执行；不为此永久保留请求墓碑或新增请求表。具体保留期、清理与重发的衔接在本模块持久化及历史维护契约中确定。

清理不能破坏活跃执行和恢复依赖。父 Instance 已终态并不等于其子 Task 已全部收敛；这类记录仍可能用于取消恢复，不能仅凭父终态就删除。具体可清理状态、关联数据处理、批次与并发保护在数据生命周期设计中确定，再验证维护期间的在线执行不受破坏。

## 7.6 本章完成条件

在已通过功能范围内设计页面、管理 API、授权、部署配置与运维指引。每项操作需要说明作用对象、何时生效和失败后的用户可见结果；配置停用、实例停止和业务实际退出不能混用。

接入示例、最小部署说明、执行查询与基础历史维护均需与实际实现一致。故障排查说明应能通过执行记录定位关联日志，不把未纳入的 Notify、任意调用目标或选择性重跑混入第一版接口和页面。
