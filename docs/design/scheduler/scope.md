# 1 目标与范围

本章定义框架服务的业务场景、第一版能力边界与质量目标，是后续架构和详细设计的输入。第一版功能范围、基准测试规模和质量方向已经通过评审；具体性能门槛在部署资源明确后、正式压测前确认，具体接口和实现不因范围通过而自动定案。

## 1.1 业务场景

本系统定位为 DogX 一体化后台管理项目的内置分布式调度能力，服务本项目及其业务模块，不以供任意外部项目接入的独立调度平台为当前目标。管理界面复用 DogX 后台，后端保持同一 Git 仓库和一个 Go Module；调度服务独立部署，公共执行组件在仓库内复用。一体化指产品和工程组织，不意味着将调度与全部业务任务合并为一个进程。

框架面向后台业务的周期执行需求，例如定期生成经营报表、分批处理商户数据，以及运行无需分片的普通业务任务。数据规模较大时，业务处理器提供主键、范围或数据引用形式的工作项，平台通用拆分后交给多个执行器处理。

框架不理解商户、订单等业务对象，也不拥有这些业务数据。一个 Task 可以处理一批数据，而不是要求每条业务记录都对应一个 Task。工作项和执行粒度见[任务模型](task-model.md)。

## 1.2 设计目标

- **支持多副本部署**：在集群中控制触发与推进，故障恢复不依赖某个调度进程一直存活。
- **形成分片执行闭环**：覆盖准备、生成分片、多节点执行、结果汇总、失败重试与业务收尾，而非只传递分片编号。
- **集中公共执行能力**：通过统一 RPC 入口和公共执行组件承接异步执行、取消协作与结果回报，业务方专注处理器逻辑和幂等。
- **提供必要的运行追踪**：持久化执行实例与执行单元的状态和简短诊断信息，详细过程使用日志系统查询。
- **约束平台资源使用**：采用有界队列、并发和检查批次，避免进程内无限积压或对历史表进行高频全表扫描。

这些目标不等于承诺任意规模、任意故障下都能完成任务。业务重复执行、尽力取消和重试预算的限制属于产品语义，见[行为规则](behavior.md)。

## 1.4 第一版使用与交付闭环

第一版提供从接入业务、管理任务到追踪执行和维护历史的使用闭环。以下为已确认的交付范围，详细页面、接口和维护机制在对应章节继续设计。

| 能力 | 第一版交付 | 保留的边界 |
| --- | --- | --- |
| 任务管理 | Job 新增、编辑、逻辑删除、启用和停用；未删除 Job 仅停用后可编辑 | 停用不取消已有 Instance，也不要求全部执行结束才能编辑；仅停用且无待开始／运行中 Instance 时逻辑删除，保留定义和执行历史，不提供恢复入口，删除与停止、历史清理分开 |
| 执行器组管理 | 页面动态维护组名称、组标识及对应服务发现标识，数据库保存；Job 选择组和处理器；无组启停，仅逻辑删除 | 实例地址由 etcd 自动发现，不手工维护机器清单；删除保护未删除 Job、旧组未结束 Instance 和未收敛 Task；凭据及缓存失效机制仍须设计 |
| 手动执行 | 创建新的 Instance，不改变定时规则 | 不是重开历史 Instance，也不等于只重跑失败分片；已成功业务可能再次执行 |
| 手动停止 | 以 Instance 为对象，按已确认规则尽力取消 | 不等待全部业务实际退出，不保证撤销已发生的副作用 |
| 执行追踪 | Instance／Task 列表和详情，展示状态、时间、重试及简短错误或结果 | 详细过程查日志系统，不建独立尝试历史表或数据库文本日志表 |
| 分片统计 | 展示总数、成功、失败和未结束分片数 | 不是业务工作量完成百分比；具体统计查询和刷新方式待设计，不逐条回报更新 Instance 计数 |
| 历史维护 | 基础历史执行记录清理，保护活跃执行及恢复所需数据 | 手动或自动、保留期限和清理实现留待模块设计，不默认加入分区或归档系统 |
| 管理权限 | 复用 DogX 菜单与 API 角色权限 | 不限定只有超级管理员可操作；具体权限点随管理接口设计 |
| 接入交付 | 普通任务和分片任务示例、最小部署说明 | 通过具名 Go 处理器接入；普通任务不要求空的准备和收尾实现 |

使用者应能按示例接入并注册处理器、在页面维护执行器组、创建 Job、等待定时触发或手动执行、查询本轮与分片结果、按需停止执行，并清理可删除的历史记录。基础执行器组管理在 A2 评审中补充纳入第一版；B1 确认普通单 Task、分片必需 Pre 与可选 Post。具体字段与清理算法分别进入第 6、7 章，处理器接口形式在契约设计中明确。

## 1.5 不作为当前第一版目标的能力

当前不独立发布对外执行器 SDK，不为外部接入拆分 Go Module、维护独立 SDK 版本兼容体系或另建调度管理后台。内部公共执行组件及统一 RPC 协议仍需设计和实现，业务处理器不重复实现接单、取消与回报。服务发现继续复用 go-zero 与 etcd，不另建调度端注册／心跳中心。

已确认不引入 Asynq 作为底座，不增加 MQ 来驱动 Task 派发或完成汇总，不建设通用 DAG／MapReduce 引擎，不为详细执行过程建设数据库文本日志和在线滚动日志控制台。

回报固定采用双端异步模式，不提供同步／异步开关，不引入本地回报文件、持久化消息队列或跨重启结果缓存；执行器更换节点不依赖迁移本地结果文件。进程故障导致未落库结果丢失，是已接受的可靠性边界。第一版不新增 Task 活动查询、心跳或独立失联提前重派；已有持久化绑定但无有效结果时等待有效结果、人工停止或整轮截止。

本次范围评审同时确认以下能力不纳入第一版：

- **业务内部实时进度和 Notify 回调**：保留必要的执行结果回报、平台分片统计及业务 Post；不提供业务处理进度上报和整体进度回调协议。
- **配置任意 HTTP／RPC 目标执行**：第一版只提供统一入口和具名处理器；业务处理器仍可按所属业务的规则调用其他服务。
- **手动选择失败分片重跑或重开历史 Instance**：保留已确认的 Task 自动重试及 Post 行为；手动执行产生新 Instance，不能代替选择性重跑。

跨地域调度、跨语言 SDK、任意上传脚本、广播、动态拆分与再均衡、自适应资源调度和复杂多租户隔离留作后续扩展，不作为第一版交付承诺。执行器分组首先涉及业务程序的发现与定位，不能因高级资源隔离后置，就忽略基础接入关系的设计。

## 1.6 质量目标与容量前提

### 已确认的基准规模

第一版以以下场景作为设计和验收基线。它们是分别验证的测试规模，不是产品硬上限，也不是已经测得的性能；不能将各行数字全部相乘，解释为同一组叠加负载。

| 场景 | 已确认基线 | 主要验证内容 |
| --- | --- | --- |
| 规则管理 | 500 条启用的长期规则 | 加载、同步与长期运行 |
| 集中触发 | 上述规则中 100 条在同一秒到期 | 触发延迟、持久化与积压处理 |
| 单轮分片 | 一个 Instance 生成 1,000 个业务分片 Task | 生成、派发与结果汇总 |
| 多轮并发 | 100 个 Instance，每个生成 10 个业务分片 Task | 多实例竞争与公平推进 |

另外覆盖长短任务混合、集中回报及节点故障。载荷字节数、业务处理耗时、回报速率和部署资源在测试方案中明确，不能只凭 Task 数量推导吞吐。

### 质量保证边界

- 已持久化的工作不能因节点退出或本地通知丢失而静默遗失；恢复仍遵守重试预算、停止及超时规则，不承诺业务一定成功。
- 回报 ACK 仅代表入队接收，未落库结果可能随任一侧进程退出或执行器回报重试耗尽而丢失；回报额度独立于执行预算，耗尽后释放并记录错误及丢弃指标。已有持久化绑定时保持当前尝试执行中，不因上述事件提前重跑；接受宕机后等待剩余整轮时间、单片丢结果拖至超时且无正常 Post。整轮到期 Instance 失败并记录超时原因，未结束 Task 按既有取消规则收敛；详见[已绑定结果等待](execution.md#bound-result-wait)。
- 调度端已 ACK 结果遇到可恢复写库故障时有界保留并退避，队满拒收新结果，不按固定次数或保留 TTL 主动清掉。待处理结果条数包含排队、处理中和待重试，结合固定消费并发及 RPC 报文上限控制容量；不做队列总字节／MB 精确配额，不另加业务结果长度限制或 Job 页面参数。永久无效数据不无限重试堵整批，错误分类与隔离细节留待契约设计；详见[调度端结果保留](execution.md#scheduler-result-retention)。
- 旧回报不能覆盖新结果，终态不能复活，PostTask 不能重复创建；业务副作用仍由处理器保证幂等。
- 内存队列、并发和检查批次有界，过载不能造成进程内无限积压；这不等于数据库积压天然有界，也不代替历史维护。

### 后续量化与验证

| 维度 | 已确认方向 | 后续验收输入 |
| --- | --- | --- |
| 正确性 | 平台保证执行尝试隔离、幂等回报和终态规则；业务负责副作用幂等 | 状态机、持久化协议和对应故障用例 |
| 可用性 | 调度节点可替换，数据库事实支撑恢复；按第 7 章边界处理依赖故障，停止不等待业务实际退出 | 具体恢复与就绪协议、恢复时限及测试部署规模 |
| 性能 | 有界并发、批量处理与本地合并，普通回报不逐条更新 Instance 完成计数或统一锁父；新尝试登记接受每轮每批父行校验、同轮短事务串行的成本 | 部署资源、载荷与耗时分布、单 Task 小 Instance 的协调成本、回报峰值及吞吐和延迟门槛 |
| 可维护性 | 复用 go-zero、PostgreSQL、etcd 与 robfig；不自行实现 Cron 解析或时间轮 | 模块契约、兼容策略和运维交付物 |

延迟分别测量计划时刻到 Instance 有效落库、回报接收 ACK、回报到有效结果落库，以及分片结束到后续平台推进；不能用快速 ACK 代表持久化性能，也不把业务自身耗时混入平台延迟。具体毫秒数、吞吐和故障恢复时限，在部署资源明确后、正式压测前评审确定，不按测试成绩倒定验收标准。指标口径与验证要求见[验证与交付](verification.md)。

固定 5 秒错失容忍不是任务开始执行的 SLA；每分钟配置核对与 Leader 的每分钟触发恢复也都不是执行恢复时限。整轮超时必须为有限正数，不允许 `0` 或无限时长；新增表单预填 900 秒，允许按业务修改，API 仍必填。截止时间约束父行保护下、当前数据库时间的决策，不承诺物理 COMMIT、RPC 到达或业务退出的精确墙钟时限，数据库故障期间也不能保证准时提交终态。
