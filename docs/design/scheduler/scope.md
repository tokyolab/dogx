# 1 目标与范围

本章定义框架服务的业务场景、第一版能力边界与质量目标，是后续架构和详细设计的输入。第一版功能范围、基准测试规模和质量方向已经通过评审；具体性能门槛在部署资源明确后、正式压测前确认，具体接口和实现不因范围通过而自动定案。

2026-11-02 已确认开发验收与正式发布边界：普通执行可以先完成独立开发与隔离环境验收，完整执行能力待分片执行完成后正式发布。不改变既有两种模式的管理契约，不为中间开发版本增加临时模式开关、候选过滤索引或过渡状态；完整管理运维与整体验收范围保持，详见[实施与发布安排](progress.md#ordinary-integration-contract)。

## 1.1 业务场景

本系统定位为 DogX 一体化后台管理项目的内置分布式调度能力，服务本项目及其业务模块，不以供任意外部项目接入的独立调度平台为当前目标。管理界面复用 DogX 后台，后端保持同一 Git 仓库和一个 Go Module；调度服务独立部署，公共执行组件在仓库内复用。一体化指产品和工程组织，不意味着将调度与全部业务任务合并为一个进程。

框架面向后台业务的周期执行需求，例如定期生成经营报表、分批处理商户数据，以及运行无需分片的普通业务任务。数据规模较大时，业务处理器提供主键、范围或数据引用形式的工作项，平台通用拆分后交给多个执行器处理。

框架不理解商户、订单等业务对象，也不拥有这些业务数据。一个 Task 可以处理一批数据，而不是要求每条业务记录都对应一个 Task。工作项和执行粒度见[任务模型](task-model.md)。

## 1.2 设计目标

- **支持多副本部署**：在集群中控制触发与推进，故障恢复不依赖某个调度进程一直存活。
- **形成分片执行闭环**：覆盖准备、生成分片、多节点执行、结果汇总、失败重试与业务收尾，而非只传递分片编号。
- **集中公共执行能力**：通过统一 RPC 入口和公共执行组件承接异步执行、取消协作与结果回报，业务方专注处理器逻辑和幂等。
- **提供必要的运行追踪**：持久化执行实例与执行单元的状态和简短诊断信息，详细过程使用日志系统查询。
- **控制排队与并发**：在主要等待队列、业务执行、RPC／数据库操作及检查批次上设置明确限制，避免无限积压和高频全表扫描；内部短步骤不默认各建处理池、队列或配额。

这些目标不等于承诺任意规模、任意故障下都能完成任务。业务重复执行、尽力取消和重试预算的限制属于产品语义，见[行为规则](behavior.md)。

正常处理效率、过载保护和可维护性共同决定实现，遵循[排队、并发与满载处理](execution.md#capacity-model)的六条原则。各段队列长度、受控并发和有限批量已经能解释积压边界时，不增加跨整个生命周期的统一计数；额外协调须说明现有简单方案无法满足的实际需要。

## 1.4 第一版使用与交付闭环

第一版提供从接入业务、管理任务到追踪执行和维护历史的使用闭环。以下为已确认的交付范围，详细页面、接口和维护机制在对应章节继续设计。

| 能力 | 第一版交付 | 保留的边界 |
| --- | --- | --- |
| 任务管理 | Job 新增、编辑、逻辑删除、启用和停用；未删除 Job 仅停用后可编辑 | 停用不取消已有 Instance，也不要求全部执行结束才能编辑；仅停用且无待开始／运行中／停止中 Instance 时逻辑删除，保留定义和执行历史，不提供恢复入口，删除与停止、历史清理分开 |
| 执行器组管理 | 数据库保存组配置；组 `name` 是执行器配置的接入身份，etcd 发现 Key 单独手工维护，二者创建后不可修改；Job／Instance 引用稳定组 ID，Job 另选处理器；无组启停，仅逻辑删除；Token 创建时生成，详情按既有权限返回、页面遮挡并可显示复制，列表不返回，不提供修改或重置 | 实例地址由 etcd 自动发现；删除保护未删除 Job、旧组未结束 Instance 和未收敛 Task。[组缓存](operations.md#group-cache)每节点每 60 秒完整替换，未命中合并同组回源，取得有效组后继续认证；不做增删差异同步或新增组变更通知。成功替换后检查已建客户端，组存在则复用，不存在则先移出缓存再关闭；查询失败不替换、不清理。清理不另查库、不等待排空或远端业务，少量在途 RPC 中断按通信结果不明处理；本地并发协调防止迟到旧结果挂回已清理客户端。定向取消仍不跨通知缓存；设计规则尚未实现 |
| 手动执行 | 创建新的 Instance，不改变定时规则 | 不是重开历史 Instance，也不等于只重跑失败分片；已成功业务可能再次执行 |
| 手动停止 | 以 Instance 为对象，提交 STOPPING 停止决定后按 Instance 分批取消未结束 Task，全部子记录终态后父才进入 CANCELED | 管理成功仅确认停止决定已提交；远端取消独立、尽力发送，不等待业务实际退出，不保证撤销已发生的副作用。STOPPING 仍计入未结束；配置阻塞丢弃的 Job 继续丢弃新轮次，并行策略不因此阻塞；删除与历史保留继续受保护 |
| 执行追踪 | Instance／Task 列表和详情，展示状态、时间、重试及简短错误或结果 | 详细过程查日志系统，不建独立尝试历史表或数据库文本日志表 |
| 分片统计 | 展示总数、成功、失败和未结束分片数 | 不是业务工作量完成百分比；具体统计查询和刷新方式待设计，不逐条回报更新 Instance 计数 |
| 历史维护 | 基础历史执行记录清理，保护活跃执行及恢复所需数据 | 手动或自动、保留期限和清理实现留待模块设计，不默认加入分区或归档系统 |
| 管理权限 | 复用 DogX 菜单与 API 角色权限 | 不限定只有超级管理员可操作；具体权限点随管理接口设计 |
| 接入交付 | 普通任务和分片任务示例、最小部署说明 | 通过具名 Go 处理器接入；普通任务不要求空的准备和收尾实现 |
| 启动与退出 | 所需依赖、处理器及队列初始化后才接收，就绪不等待 Leader 或所有组在线；整个进程默认总计 30 秒可配置退出宽限，两套 Server 与所有清理共享 | 调度端停止生产工作和新回报接纳、结束任期并有限善后落库；执行端拒新单且不使用 BUSY，已接纳任务和回报可在剩余宽限内继续。到期停止启动排队任务、取消运行 Context、结束等待，由宿主结束进程，组件不调用 `os.Exit` 或强杀 goroutine；退出可丢失内存结果，不授权业务取消、失败或重派，亦不延长原整轮期限 |

使用者应能按示例接入并注册处理器、在页面维护执行器组、创建 Job、等待定时触发或手动执行、查询本轮与分片结果、按需停止执行，并清理可删除的历史记录。基础执行器组管理在 A2 评审中补充纳入第一版；B1 确认普通单 Task、分片必需 Pre 与可选 Post。具体字段与清理算法分别进入第 6、7 章，处理器接口形式在契约设计中明确。

## 1.5 不作为当前第一版目标的能力

当前不独立发布对外执行器 SDK，不为外部接入拆分 Go Module、维护独立 SDK 版本兼容体系或另建调度管理后台。内部公共执行组件的通信协议与装配已按[执行 RPC 协议与装配](data-contracts.md#execution-rpc-contract)通过，生成与运行实现尚未完成，业务处理器不重复实现接单、取消与回报。服务发现继续复用 go-zero 与 etcd，不另建调度端注册／心跳中心。

已确认不引入 Asynq 作为底座，不增加 MQ 来驱动 Task 派发或完成汇总，不建设通用 DAG／MapReduce 引擎，不为详细执行过程建设数据库文本日志和在线滚动日志控制台。

第一版不提供执行器组 Token 重置、更换或自动轮换。创建组后管理接口不再修改 Token；组无编辑入口，不提供替代修改途径，也不将轮换作为第一版开工前置条件。生成、存储、读取保护及缓存仍按[组凭据管理](operations.md#group-credentials)落实。

回报固定采用双端异步模式，不提供同步／异步开关，不引入本地回报文件、持久化消息队列或跨重启结果缓存；执行器更换节点不依赖迁移本地结果文件。进程故障导致未落库结果丢失，是已接受的可靠性边界。第一版不新增 Task 活动查询、心跳或独立失联提前重派；已有持久化绑定但无有效结果时等待有效结果、人工停止或整轮截止。

本次范围评审同时确认以下能力不纳入第一版：

- **业务内部实时进度和 Notify 回调**：保留必要的执行结果回报、平台分片统计及业务 Post；不提供业务处理进度上报和整体进度回调协议。
- **配置任意 HTTP／RPC 目标执行**：第一版只提供统一入口和具名处理器；业务处理器仍可按所属业务的规则调用其他服务。
- **手动选择失败分片重跑或重开历史 Instance**：保留已确认的 Task 自动重试及 Post 行为；手动执行产生新 Instance，不能代替选择性重跑。

跨地域调度、跨语言 SDK、任意上传脚本、广播、动态拆分与再均衡、自适应资源调度和复杂多租户隔离留作后续扩展，不作为第一版交付承诺。执行器分组首先涉及业务程序的发现与定位，不能因高级资源隔离后置，就忽略基础接入关系的设计。

## 1.6 质量目标与验证基线 {#quality-baseline}

### 已确认的基准规模

第一版以以下场景作为设计和验收基线。它们是分别验证的测试规模，不是产品硬上限，也不是已经测得的性能；不能将各行数字全部相乘，解释为同一组叠加负载。

| 场景 | 已确认基线 | 主要验证内容 |
| --- | --- | --- |
| 规则管理 | 500 条启用的长期规则 | 加载、同步与长期运行 |
| 集中触发 | 上述规则中 100 条在同一秒到期 | 触发延迟、持久化与积压处理 |
| 单轮分片 | 一个 Instance 生成 1,000 个业务分片 Task | 生成、派发与结果汇总 |
| 多轮并发 | 100 个 Instance，每个生成 10 个业务分片 Task | 多实例竞争与公平推进 |

另外覆盖长短任务混合、集中回报及节点故障。载荷字节数、业务处理耗时、回报速率和部署资源在测试方案中明确，不能只凭 Task 数量推导吞吐。

### 质量保证边界

- 已持久化的工作不能因节点退出或本地通知丢失而静默遗失；恢复仍遵守重试预算、停止及超时规则，不承诺业务一定成功。
- 回报 ACK 仅代表入队接收，未落库结果可能随任一侧进程退出或执行器回报重试耗尽而丢失；回报额度独立于执行预算，耗尽后释放并记录错误及丢弃指标。已有持久化绑定时保持当前尝试执行中，不因上述事件提前重跑；接受宕机后等待剩余整轮时间、单片丢结果拖至超时且无正常 Post。整轮到期后，经检查确认尚不具备完整最终结果，才条件保存 Instance STOPPING 及超时原因；分批处理未结束 Task 并确认子记录全部终态后，父才进入 FAILED。低频复核及数据库处理都可使平台终态晚于截止保存。详见[已绑定结果等待](execution.md#bound-result-wait)与[统一 Instance 复核](execution.md#instance-recheck-direction)。
- 调度端已 ACK 结果逐条以 JOIN 取得 Task／Instance 归属、认证组及本轮冻结重试上限、间隔，再条件 UPDATE、独立提交；最终仍核验原尝试、执行中状态及绑定身份，不设整批总超时或超时拆批。[调度端结果保存安排与初值](execution.md#scheduler-result-defaults)已定为每节点组件保留 512 条（待首次处理、待重试和在途合计）、保存并发 8、单条处理超时 2 秒，三项可部署调整；2 秒含连接等待、读取、更新提交，不含排队退避。一次处理结束释放处理能力，退避保留原位置，按到期最早及稳定同时间顺序处理，不切首次／重试固定份额；内部退避基准 1／2／4／8／16／30 秒、以后封顶 30 秒，各次上下浮动 20%。可恢复数据库故障、性质不明的技术错误及提交不明保留原条目，不按次数或 TTL 丢弃；零行正常结束但不证明此前成功。满载拒收新结果，即使全部在退避；不重放其他已明确成功的条目，不另建无界缓冲或全生命周期共用额度。不做队列总字节／MB 精确配额，不另加业务结果长度限制或 Job 页面参数；永久无效条目按[已定证据边界](data-contracts.md#result-error-classification)单独处理，技术故障及平台配置异常仍保留，SQL／驱动适配及实现验证待完成，停机与内存易失边界保持。
- 执行器每进程默认业务处理并发 32、业务等待队列 128，均为部署配置。32 包含业务运行及业务已完成但结果交接尚未结束的处理，128 仅包含尚未领取的等待任务、不含处理中；所有处理器类型共享，不按 Job／Instance 叠加。回报满载时当前处理者继续占用处理位置等待交接，不建立全生命周期共用额度，也不冻结 Go 线程结构，详见[业务处理初值](execution.md#executor-business-defaults)。
- 执行器回报组件默认保留 256 条结果，覆盖待首发、待重试和在途；发送并发默认 16，单次 RPC 结束即释放发送能力，等待退避保留原结果位置。按已到期的最早可发送时间及稳定同时间顺序选择，不切首发／重试固定份额；满载由有限业务处理者等待交接，不引入全生命周期共用额度。单次 2 秒、最多 7 次应用层调用含首次，六次退避为 1／2／4／8／16／16 秒且各上下浮动 20%；基准合计 47 秒不是保留 TTL。256／16 为部署配置，其余为内部常量，详见[回报初值](execution.md#reporting-defaults)。
- 旧回报不能覆盖新结果，终态不能复活，PostTask 不能重复创建；业务副作用仍由处理器保证幂等。
- 主要队列限定长度，执行与外部操作限制并发，查询和写入限制每批条数；等待交接、在途和重试中的对象都要纳入资源分析，不能把积压转移到无界协程或旁路队列。允许下游变慢时向上游传递等待或拒收，不要求每次交接永不阻塞；这不等于数据库积压天然有界，也不代替历史维护。

延迟分别测量计划时刻到 Instance 有效落库、回报接收 ACK、回报到有效结果落库，以及分片结束到后续平台推进；不能用快速 ACK 代表持久化性能，也不把业务自身耗时混入平台延迟。具体毫秒数、吞吐和故障恢复时限，在部署资源明确后、正式压测前评审确定，不按测试成绩倒定验收标准。指标口径与验证要求见[验证与交付](verification.md)。

固定 5 秒错失容忍不是任务开始执行的 SLA；每分钟配置核对与 Leader 的每分钟触发恢复也都不是执行恢复时限。整轮超时必须为有限正数，不允许 `0` 或无限时长；新增表单预填 900 秒，允许按业务修改，API 仍必填。截止时间约束新工作授权及执行器业务 Context，不因重试或恢复延长；父仍 RUNNING 且已具备完整最终结果时允许迟到的平台收尾，不保证严格按截止时刻裁决成功失败。自动超时先检查完成事实、人工停止保留操作原因，已有终态不覆盖，详见[终态规则](behavior.md#terminal-order)。不承诺物理 COMMIT、RPC 到达或业务退出的精确墙钟时限，数据库故障期间也不能保证准时提交终态。

RUNNING Instance 统一复核已定为 Leader 每 2 分钟执行或续扫，候选开始时间必须早于本趟数据库时间减 4 分钟，每页 256 条。无积压时首次周期复核通常在开始后约 4～6 分钟，短超时也适用，不保证扫描一次完成或固定恢复 SLA；无有效 Leader 时该周期复核暂停，正常结果驱动仍由各节点本地推进。不增加独立超时扫描、恢复时间轮、延迟恢复队列、恢复分桶或下次检查字段，具体范围见[统一复核协议](execution.md#instance-recheck-direction)。

STOPPING 停止恢复与上述 RUNNING 复核分开：同一 Leader 每 2 分钟独立按 `status = 6` 有界发现候选，新 Leader 就绪后也进行一次有界检查，不使用 4 分钟开始时间门槛；处理复用既有后台恢复容量，与 RUNNING 分页和预算分别管理。停止决定提交后先立即交本地处理，周期检查补节点退出或提示丢失。数据库依赖恢复且持续获得公平处理容量时继续完成，不因固定次数耗尽而遗忘停止决定；不增加全局 Task 扫描、停止标记、可靠通知表或新延迟队列。详见[停止协议](data-contracts.md#instance-termination-sql)。
