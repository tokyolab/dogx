## 数据库延迟专项诊断 {#history-database-diagnosis}

用户要求先定位数据库变慢的原因，再讨论实现调整。本节沿用原始 A/B/C 结果，另外记录诊断复现；不改变产品代码、连接池、验收门槛或恢复策略。证据在忽略目录 `bin/test-tools/history-db-diagnosis-20261123/`，时间均为北京时间。

### 环境与复现边界

- D/E 位于同一块 WDC WD20EARZ SATA 机械硬盘，C/F 位于 KIOXIA NVMe；原测试的 PostgreSQL 数据、WAL、CSV 日志全部在 D 盘，未通过链接分散到其他物理盘。
- 诊断保持 PostgreSQL 18.6、`shared_buffers=64MB`、`work_mem=4MB`、`max_connections=60`、持久化设置和原负载；补充 `auto_explain` 100ms 实际计划、目标每 100ms 的数据库等待、主机磁盘与进程采样。两个 Job 进程继续跟踪全部 SQL。
- `HDD-C1` 仅因准备错过激活余量退出，没有进入正式窗口。随后 HDD/SSD 都使用忽略目录中的 Go overlay，将预定激活时刻的准备余量从 5 分钟延到 8 分钟；原测试源码、30 分钟窗口和所有成功门槛保持不变。
- `HDD-C2` 于 **12:01** 开始，在 **12:08:36.133** 因 Job 115 / 计划时刻 12:08:06 的 Instance `101421` 仍为 RUNNING 而失败，退出码 1。保留了失败前观察到的 1,519 个成功父记录；这不是完整窗口通过。
- NVMe 对照将数据库、WAL、CSV 日志一起放在 F 盘的独立测试目录，正式窗口为 **12:19–12:49**。17 项已采集数据库设置一致；报告 `Passed=true`、退出码 0，完整窗口与最终数据核验通过。
- 清理按进程启动时间计时，各组准备耗时不同，实际清理相对窗口的位置也不同。HDD-C2 复用此前准备失败的隔离集群，SSD 使用新集群；不能把对照称为严格单变量实验或据此给出磁盘提速倍数。按实际清理时段对齐，不假定清理都发生在窗口第 10、20 分钟。

| 时间 | 实际操作 | 索引／处理量 | PostgreSQL 共享块读取耗时 | Execute 耗时 |
| --- | --- | --- | --- | --- |
| 12:08:02.811 | 插入单个 Task | 1 行，读 1 块 | 666.589ms | 765.503ms |
| 12:08:02.811 | 登记执行尝试 | `idx_job_task_dispatch_due`，索引返回 1 行，读 1 块 | 665.938ms | 667.657ms |

上述三条操作分别有 7、7、4 个同 PID／query ID 的 `IO/DataFileRead` 等待样本，另有同时段的 `LWLock/BufferContent` 与 WAL 写入等待。这是数据库内部等待的直接证据，不是仅根据应用慢日志推测。PostgreSQL 文件读取计时包含操作系统文件 I/O 与缓存行为，不能把一个共享块读取等同为一次物理硬盘 I/O。

### 磁盘、内存与连接

- **12:08:01.600–12:08:09.611**，机械盘连续约 8 秒平均队列至少为 1；最重的 **12:08:03.614–05.605** 区间平均队列 **9.879**，984 次写入，平均写耗时 **19.995ms**。这是约 2 秒计数区间的平均值，不是单次 I/O 的 P95。
- 在 12:07:20–12:08:40 分析窗口内（采样截至进程停止），CPU 平均约 **10.2%**、采样峰值 **37%**，可用内存最低 **15.34 GiB**，page-out 采样均为 0。没有 CPU 或全机内存耗尽的证据。
- 12:07:35.997578–12:07:57.999607 的累计统计记录约 **265.4 MB WAL**、客户端关系写入 **180.1 MB** 和 **35,706 次缓冲淘汰**。随后 12:08:00.999768–12:08:11.001225，客户端仅读取 **1.61 MB** 却累计 **6,554ms**，后台写入器写 **1.22 MB** 却累计 **6,178ms**。这些是有上报延迟、跨后台的统计增量，不是逐秒物理盘精确归属；它们与实际计划、等待和磁盘队列方向一致。
- 客户端后端采样峰值为 **26**，另有 2 个诊断连接；未见 `53300` 或连接数耗尽消息。原始 C1 已配对的三条慢调用中，应用耗时与 PostgreSQL Bind＋Execute 仅差约 **0.6–1.4ms**，不支持把这些秒级延迟归为应用连接池排队。
- 连接开销不能全部排除：HDD-C2 故障窗口确有频繁建拆连接，一次主机采样记录到 PostgreSQL 进程树的 82 个不同 PID，其中 61 个在此前 5 秒内新建。进程树包括主进程和后台进程，额外短命子进程是否属于启动、认证或取消请求尚未确认，不能称为 82 个数据库连接；未采集客户端池等待指标，也没有确定每个短命进程的角色。5 次 `57014` 均为客户端请求取消，随后伴随 5 次 `08006`，不作为数据库崩溃证据。

### 为什么短暂变慢导致超过 30 秒不推进

本次已经把目标父与具体 SQL 对上，补齐原 C1 缺失的状态证据：

1. Instance `101421` 的 PRE Task `100009719` 于 **12:08:06.393** 保存成功，**06.407** 提交完成，业务准备与结果回报已经完成。
2. 父检查的几个查询各消耗约 100ms Bind；读取准备结果时，Bind 又耗时 **1,473.451ms**，而随后的 Execute 仅 **0.038ms**。
3. 进入分片生成事务后，父行锁已取得；再次确认 PRE／分片存在性时，共享 **2 秒检查预算**耗尽。应用在 **08.508** 报告检查失败，后端随后取消，尚未插入分片 Task。
4. 失败检查在没有新的并发提示时不立即重试；现有低频恢复要求父开始超过 4 分钟、每 2 分钟扫描。因而这次短暂数据库延迟被放大为超过 30 秒的流程停滞。测试在失败后停止，没有推断它之后是否由恢复推进。

目标 1.47 秒 Bind 有一个明确观测限制：前 3 个样本未报告等待，随后出现 **1.300 秒采样空档，覆盖约 86% 的 Bind 时段**；采样查询本身只耗约 0.5–1.55ms。不能将这整段 Bind 都指定为某个 I/O 等待，也不能把空档或 NULL 等待改称 CPU 耗时。主机计数采集实际多为约 2 秒间隔，全部统计按真实端点计算。

当前证据最明确地指向**本机这套存储布局下的 I/O 压力**，伴随连接抖动，其额外开销尚未独立量化；未发现能解释本次故障的全表扫描、缺索引或连接上限不足。清理产生的写入与后续写回可以在清理事务结束后继续影响在线操作，不能把清理完成时刻当成 I/O 影响结束时刻。数据、WAL、日志共享磁盘，各自贡献尚未独立拆分；不据此归因杀毒软件、硬盘损坏或 Windows 平台本身。

## 结论边界

先依据专项诊断确定环境影响与现有恢复行为，再单独评审改法。此前关于清理节奏的建议不作为已批准方案；没有通过加固定等待、增加连接池、提高正常路径 2 秒预算或放宽 30 秒门槛来消除失败。本轮未修改产品行为。

本轮验收夹具及诊断代码的 `integration,e2e,load` 标签 lint 通过（0 issues）。C 失败后只增强测试诊断：保留已观察的成功明细，并在失败时输出当次已读取的父 ID／状态，不新增数据库探测、不改变负载或门槛；专项诊断重跑使用了这些增强。此前 A1/A2/B1/C1 原始结果保持不变。

原始 A/B/C、专项 HDD 与 NVMe 对照使用的隔离 PostgreSQL／Redis 均已正常停止，相关测试宿主和 Schema 已清理，原始证据保留；未操作用户开发环境。本次提交仅保存测试及文档，前端与产品逻辑未改；远端验证以本次提交的检查结果为准。没有把本机结果登记为新的 GitHub CI，也不把此前 CI 覆盖率沿用为本次测试代码的覆盖率。

父成功时间由每 500ms 的独立查询观察；`Task.finished_at - business.finished_at` 只表示结果记录时间差，不是 COMMIT 延迟。数据库累计指标有统计延迟，30 秒采样可能遗漏短时等待；清理窗口的稀疏数据库统计需要列出实际采样端点，不能插值伪造精确成本。本轮未收集子进程覆盖率，不推算 unit、integration、全项目或 patch 覆盖率。
