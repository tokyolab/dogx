# 3 任务模型

本章建立全系统共享的术语，区分长期任务、一轮执行、可派发工作和执行尝试，并界定业务分片与平台状态汇总的职责。**核心概念、统一 Task、状态与生命周期、发送前条件登记尝试及提交记账、BUSY 条件返还与延期已确认；处理器分工、输入输出语义与共同执行约束已通过，Post 仅接收公共输入和分片汇总统计。普通 Task 所需公共字段、类型／状态编码及单例唯一索引已通过，[执行 RPC 协议与装配](data-contracts.md#execution-rpc-contract)与[非 BUSY 明确拒绝结算](data-contracts.md#dispatch-rejection-settlement)均已通过，工作项生成及其余持久化协议仍待闭合。** 数据字段以[Task 契约](data-contracts.md#task-field-contract)为准，不从语义命名推导尚未批准的 RPC 或分片字段。

## 3.1 核心概念与关系

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| Job，任务定义 | 长期保存的配置，描述做什么、何时执行以及执行模式 | 每天生成商户经营日报 |
| Instance，执行实例 | 一次触发形成的一轮执行，保存本轮必要执行配置，承载整体状态与整轮时间预算 | 某日的这一轮日报生成 |
| Task，执行单元 | 本轮中可以独立派发、追踪和重试的业务执行单元 | 准备工作项、处理一批商户、生成本轮结果报告 |
| Attempt，执行尝试 | 同一 Task 的一次授权执行身份，用于区分原始执行和重试，隔离迟到结果 | 某分片的第一次执行和一次重试 |
| Executor，执行器 | 接收 Task、运行处理器并回报状态的运行组件 | 某业务服务中的执行组件及其多个副本 |
| Executor Group，执行器组 | Job 引用的业务寻址配置，关联对应服务发现范围；不是一台机器 | 商户任务组，通过其发现标识查找执行器实例 |
| Processor，处理器 | 业务方实现并按名称注册的具体处理逻辑 | 商户日报处理器 |

一个 Job 可以产生多个 Instance；一个 Instance 包含本轮需要执行的 Task。Task 自动重试仍使用原 Instance、原 Task 身份，只产生新的执行尝试，不创建另一轮任务。任务定义、某次运行、一个业务分片以及一次尝试不能混为一条概念。

一个执行器进程归属一个组，可以注册多个 Processor；一个组可以有多个兼容的执行器进程实例，同组共享组 Token。组用于业务程序寻址，不是每个 Job 的分类标签；组凭据也不是 Task 执行尝试身份。注册发现和调用认证见[总体架构](architecture.md#internal-trust)。

这里将 Attempt 作为逻辑概念，不代表单独建立 Attempt 表。第一版不保留独立的尝试历史表，但仍需持久化当前尝试标识、重试计数和必要状态，以校验回报及关联日志。

第一版支持手动触发，启用或停用 Job 均可按集群阻塞规则创建新的 Instance，不改变定时进度；允许仅当次业务参数覆盖，同请求号重发返回原执行，不重开历史 Instance，也不提供手动选择失败分片重跑。行为边界见[手动触发规则](behavior.md#manual-trigger)，具体接口与交互在管理设计中明确。

## 3.2 统一 Task 建模

需要交给业务执行器运行的准备、业务分片和业务收尾使用统一 Task 逻辑模型，第一版共用 Task 表，以类型区分，不另建准备表和收尾表。普通业务执行同样复用 Task 执行机制。

| 业务工作 | 职责 | 与其他阶段的区别 |
| --- | --- | --- |
| 普通执行 Task | 完成简单业务任务 | 不因统一建模被迫增加空的准备或收尾处理器 |
| PreTask，准备 Task | 执行业务准备，返回可序列化工作项数组 | 有效结果为后续生成分片提供输入 |
| 分片 Task | 执行一份业务工作项 | 多个分片可在不同执行器并行处理；一个 Task 可以处理多条业务记录 |
| PostTask，收尾 Task | 在分片结束后执行业务收尾，例如查询业务记录生成报告 | 属于业务收尾，不接收分片执行明细，不是平台内部的状态汇总或 Reduce |

统一的是持久化、派发、当前执行尝试、结果校验、完成检查、取消和恢复机制，不是各阶段的业务语义。准备产出工作项、分片执行业务、收尾处理业务产物；各阶段的失败后果和推进条件不同，见[行为规则](./behavior.md)。普通与分片不各建一套父终态并发协议，普通只有一个业务 Task，分片也允许只有一个分片。

第一版明确两条执行路径：普通任务只创建一个普通 Task，不组合准备或收尾阶段；分片任务必须通过 PreTask 提供工作项，PostTask 可选。正常推进至收尾且配置了 Post 的分片 Instance，若产生 N 个分片，对应 N＋2 条 Task；未配置 Post 则为 N＋1 条。准备失败或整轮提前终止时不强行补齐后续 Task。普通、分片及可选 Post 的接口分工和输入输出语义已通过，见[处理器契约](data-contracts.md#processor-contract)；Post 不提供分片结果集合或查询能力。第一版不提供业务进度回调。

### 统一模型的收益与限制

统一模型主要用于复用可靠执行协议，减少扩展时阶段之间的实现差异。它不意味着只修改模型就能提高吞吐，也不自动并行化单轮准备和收尾：一次准备、一次业务收尾仍分别由一个执行器处理。

统一表会增加相应的记录、状态写入和索引维护，但不统一建模也需要可靠保存准备和收尾的执行事实，不能与完全不持久化的直接 RPC 作不等价比较。[排队、并发与满载处理](execution.md#capacity-model)与[派发供给参数](execution.md#dispatch-supply-defaults)已分别明确共享边界和调度端候选初值，登记批量、其余并发数和队列长度继续单独设计；统一 Task 不要求所有类型无差别地进入同一无界队列。

## 3.3 业务收尾与平台汇总 {#business-post}

平台内部检查分片是否结束、计算整体状态、判断是否生成 PostTask，属于调度服务推进逻辑，不额外创建业务 Task，也不派发给业务处理器更新调度表。

**Post 是分片全部结束后的可选业务收尾钩子，不是 Instance 终态之后的回调。** 第一版普通任务只运行 Execute，不支持 Post。需要收尾的分片任务在业务 Post 结束后，由平台确定 Instance 终态；一个逻辑 PostTask 可以有多次执行尝试，业务仍需幂等。准备失败、停止或整轮超时可能不运行 Post，连接关闭等必要资源释放不能只依赖它。

以下是业务使用示例，不代表平台预置这些处理器：

| 场景 | 分片处理 | Post 的业务用途 |
| --- | --- | --- |
| 批量导入用户 | 各片创建或更新数据，将必要的处理明细及不合格原因写入业务记录 | 查询本轮业务导入记录，生成错误文件并更新业务批次；不是查询或更新调度 Instance |
| 批量导出文件 | 各片生成文件，保存到对象存储，并将文件引用写入业务记录 | 查询业务侧文件记录生成统一下载清单；分片汇总统计有最终失败时标明不完整，不将其发布成完整成功结果 |
| 分批清理历史数据 | 各片删除所属范围的过期数据 | 通常不需要 Post；平台本身提供 Task 统计和 Instance 终态 |

业务数据行数与 Task 数不是同一统计口径。某个分片正常完成校验并识别出不合格记录，不等于有同样数量的 Task 失败；分片中途失败也不表示它没有写入任何业务数据。Post 仅接收本轮公共输入与分片汇总统计，需要的业务明细或产物由业务自行保存、按业务批次或 InstanceID 关联查询。框架不传递各分片执行明细、不提供结果查询入口，也不替业务读取业务表，见[Post 参数语义](data-contracts.md#post-input)。

| 动作 | 执行方 | 是否属于业务 Task |
| --- | --- | --- |
| 解释业务参数并执行分片 | 业务处理器 | 是 |
| 校验回报并保存 Task 结果 | 调度服务 | 否 |
| 检查分片生成完整且无未结束分片 | 调度服务 | 否 |
| 唯一创建本轮 PostTask | 调度服务 | 创建业务 Task 的平台动作，本身不另建 Task |
| 根据分片汇总统计及自有业务记录完成收尾 | 执行器运行 Post 处理器 | 是 |
| 按分片及收尾最终结果确定 Instance 终态 | 调度服务 | 否 |

例如十个分片全部成功：结果先由调度服务保存，再在父状态及原截止允许时唯一创建已配置的 PostTask；Post 执行业务收尾并回报。部分或全部分片最终失败，也仍在父运行且未到期时创建已配置 Post，不按失败比例跳过业务收尾；PreTask 最终失败则直接结束，不生成分片或执行 Post。调度服务根据有效结果确定本轮终态，业务 Post 不直接修改 Instance。未配置 Post 时，分片完整生成且全部成功或最终失败后，由平台直接汇总并结束本轮，不创建空 Post 或平台汇总 Task。

收尾判断的对象是**业务分片集合**，不能笼统查询“所有 Task 是否结束”，把准备或收尾本身混进未结束分片。进入收尾需要分片已完整生成且全部成功或最终失败；仍待重试的失败分片尚未结束，取消不能冒充业务成功或失败。分片生成完成后集合固定，不能在收尾判断过程中随意追加；活跃 Instance 的 Task 不得被历史清理移除，这与最终状态不可逆共同支撑稳定完成事实。

平台的最终结束判断与创建后续业务阶段分开：最终结束仅依据本轮快照、Task 类型及已经保存的完整结果，不生成分片、Post 或重试。正常完成在父锁外读取最少稳定事实，再条件更新仍运行中的父 Instance；按适用阶段确认分片生成封口、Task 终态不可逆及已配置 Post 结果完整，合法零分片也须有明确生成完成事实。准备最终失败不要求生成分片或执行 Post。父仍 RUNNING 时，即使已过截止仍可按完整结果结束；STOPPING 只按冻结停止决定完成数据库处理；创建后续阶段及新尝试仍须遵守原截止与父状态授权。自动超时仅在明确未具备最终结果后进入父短事务，不把更新零行或技术错误当作结果未齐，也不在父锁内重新查整轮 Task，见[终态竞争](behavior.md#terminal-order)。

正常结束的 Instance 摘要取自最终事实：普通 Task 和准备最终失败直接结束时复制相应 Task 的最终摘要，保留合法空串；分片流程记录总数、成功数、最终失败数及适用 Post 结果的汇总，不拼接所有子摘要。正常执行失败原因统一，不按哪个失败先回报决定；具体原因码仍待字典明确，Task 和日志保留详细诊断。结果保存与父推进分开，不要求每条结果查询当前 Job 或汇总本轮。

第一版展示分片总数、成功、失败和未结束数，只计算业务分片 Task，不表示业务工作量完成百分比。统计查询和展示刷新方式仍待设计，不新增逐条结果回报更新 Instance 计数的路径。部分分片最终失败后的收尾、停止和超时规则见[行为规则](./behavior.md)，结果落库与并发推进协议见[执行流程与可靠性](./execution.md)。

## 3.4 工作项数组与分片职责

分片业务通过准备阶段产出可序列化工作项数组。业务方定义元素的含义，平台按通用规则切分数组、保存分片参数并派发；执行器中的业务处理器解释收到的子数组。

数组元素可以是单个主键、一组主键、ID 范围或待处理数据的引用。平台不解释商户、订单等业务结构，不直接替业务查询跨域数据。范围和引用的有效性、覆盖范围及处理语义由业务方负责。

因此，平台的“单片数量”表示数组元素数量，不一定等于商户数量，也不等于实际计算量。一个元素如果代表一个范围，可能覆盖很多商户；按元素个数均分不保证计算负载均匀。具体分片数算法和配置形式尚待确定，不预设一种业务分片规则。

有效准备结果已持久化后，平台据此保存分片 Task 及参数；生成完整后才开放分片派发，生成完成事实也要触发完成检查。准备成功结果已保存但平台生成中断时，只恢复生成过程，不重新运行业务准备；仅收到入队 ACK 不能作为生成分片的依据。生成执行权、分批保存和完整性标记在[执行流程与可靠性](./execution.md)及[数据与接口](./data-contracts.md)中继续设计。

## 3.5 分片粒度与容量边界

Task 是调度执行单元，不与单条业务数据一一对应。合理粒度需要在两类成本之间权衡：分片过细会放大 RPC、状态写入及结果回报开销；分片过粗会增加长尾耗时和失败重做成本。

以 100 万商户的日报为例，可以产生约 1,000 个分片，每份处理约 1,000 个商户，而不是为每个商户生成一条 Task。这只是粒度示例，不是默认参数或性能承诺。业务也可以返回范围工作项，在执行器内分页读取所属业务的数据。

减少 Task 条数不必然减少参数总字节数。即使分成 1,000 片，如果仍传递全部商户资料，准备返回值、序列化、网络传输和持久化仍可能成为瓶颈。工作项宜表达必要的业务输入，具体参数大小、数组数量与批次限制需要结合契约和容量验证确定。

平台必须说明队列长度、处理并发及满载时如何等待或拒收，不能将过载保护完全交给业务方；业务方仍应根据计算量选择粒度。[排队、并发与满载处理](execution.md#capacity-model)确认进程共享业务队列和处理并发，不按每个 Job／Instance 独立扩池。[执行器流程](execution.md#executor-processing-flow)在业务完成后交给有界回报组件，保留位置已满时当前有限业务处理者持有结果等待，独立回报继续。回报组件默认保留 256 条待首发、待重试及在途结果，默认 16 次发送并发；一次 RPC 结束即释放发送能力，退避期间保留原位置，按已到期的最早可发送时间及稳定同时间顺序安排，不切首发／重试固定份额。ACK、永久错误或调用次数耗尽后释放结果，参数见[回报初值](execution.md#reporting-defaults)。该局部限制不与接单、业务等待或执行共用额度，也不把统一 Task 模型推导为具体 Go 编码结构。[业务处理初值](execution.md#executor-business-defaults)已定为每执行器进程并发 32、等待队列 128，均可部署调整；32 包含业务运行和已完成但结果尚未交接完的处理，128 只计尚未领取的等待任务、不含处理中。普通、准备、分片和收尾共用，不按 Job／Instance 叠加。[派发供给](execution.md#dispatch-supply-defaults)的每 Instance 先补最多 8 项是候选轮转份额，不是业务分片粒度、登记事务批量或该 Instance 的并发上限。

调度端每条结果以一次 JOIN 取得 Task／Instance 归属、认证组及本轮冻结重试配置，最终条件 UPDATE 核验原尝试、执行中状态及绑定身份，每条独立提交，不设整批总超时或超时拆批。[调度端结果保存安排与初值](execution.md#scheduler-result-defaults)已定为每节点组件保留 512 条待首次处理、待重试及在途结果，保存并发 8，单条一次处理超时 2 秒，三项可部署调整；2 秒包含连接等待、读取、更新及提交，不含排队和退避。处理结束即释放处理能力，退避保留原条目原位置，按已到期最早可处理时间及稳定同时间顺序选择；内部退避基准 1／2／4／8／16／30 秒、以后封顶 30 秒，各次上下浮动 20%。512 只约束结果组件内部，不与接单或业务执行共用额度；全部条目在退避但已满时仍拒收新结果。结合 RPC 报文上限验证实际内存，不做总字节／MB 精确配额，不另加业务结果长度限制或 Job 页面参数。ACK 后可恢复数据库故障仍保留对应原条目，不按固定次数或 TTL 主动丢弃。[回报错误分类与无效结果处理](data-contracts.md#result-error-classification)已通过；[执行 RPC 协议与装配](data-contracts.md#execution-rpc-contract)已通过；Proto 生成、SQL／驱动适配及实现验证，以及准备工作项数组、分片参数和生成过程的数量、大小、存储契约仍须继续完成。

Task 重试可能重做部分业务数据，处理器需要按业务键保证幂等。平台级业务检查点不属于当前第一版交付承诺，若要纳入需另行评审范围。准备数组如何暂存、是否保留完整原数组及历史数据如何清理，尚未由数组模型确定，不应从示例推导为既有能力。

## 3.6 执行尝试与记录边界

每个 Task 独立区分原始尝试与重试；各 Task 读取 Instance 创建时保存的同一份重试配置，但不共享一轮总次数池，也不随 Job 后续编辑变化。普通执行、准备、分片和收尾均沿用这一机制，配置范围见[本轮执行配置](behavior.md#instance-execution-config)，具体默认值及预算见[行为规则](./behavior.md)。

当前尝试身份使用 `(TaskID, attempt_no)`，用于拒绝旧回报覆盖新尝试，幂等回报与更新前状态条件校验用于保护平台推进。`attempt_no` 为每次新派发递增的 BIGINT 编号，不需要全局唯一；它只能保护调度状态，不能撤销旧尝试已经造成的业务副作用，也不意味着框架保证业务恰好执行一次。

尝试身份与执行预算不是同一个概念。`used_attempts` 记录已占用的次数，包含首次，普通首次派发时它与 `attempt_no` 均为 1。执行器明确容量满且未接单、未入队、未执行的 BUSY，不消耗 Task 执行重试次数；调度端只对当前有效尝试原子完成关闭、一次减少 `used_attempts` 及设置最早可派发时间，零重试同样可延期。BUSY 不回退 `attempt_no`，后续登记必须使用新编号；无需新增 Attempt 历史表或独立关闭字段，旧状态条件仍须校验。通用通信错误及 BUSY 答复丢失不免费返还，详见[BUSY 背压](execution.md#busy-backpressure)。

第一版在 Instance、Task 中保存查询与恢复所需状态、时间、重试计数和简短结果或错误摘要，不建立独立 Attempt 表，不将详细文本执行日志写入数据库。详细过程进入现有服务日志／日志系统，通过 `job_id`、`instance_id`、`task_id`、尝试标识关联，必要时携带 traceId。数据库不保存每次尝试的完整结构化历史；字段含义及保留规则见后续[数据与接口](./data-contracts.md)和[管理与运维](./operations.md)。

## 3.7 参考概念与未纳入能力

字节 Scheduler 文章区分 `PreProcess`、`ShardingProcess`、`Notify`、`PostProcess`。本设计借鉴准备、分片和收尾的职责，但不据此推导相同表结构或完全相同接口。DogX 统一 Task 共表是本项目已确认的选择，不是对参考项目存储实现的断言。

文章中的 `Notify` 是调度侧向业务处理器传递整体进度的回调，不是执行器向调度服务提交完成结果的 RPC，也不必然意味着短信或消息通知。DogX 第一版不提供业务内部实时进度或 Notify，不建立 NotifyTask；必要的执行结果回报、平台统计和业务收尾不受影响。

参考文章对四个入口的说明、原文表述歧义及证据边界集中在[参考资料](./references.md)，不作为当前未决接口的替代定义。

## 3.8 状态与生命周期 {#lifecycle}

状态表达执行进度，Task 类型表达工作职责，结束原因解释为什么结束，三者不能混为一套枚举。六个稳定原因及 Task／Instance 各自适用范围见[结束原因字典](data-contracts.md#execution-end-reasons)，等待重试的 Task 原因仍为 NULL。Task 类型编码已定为 1 普通、2 准备、3 分片、4 收尾；六态编码依次为 1 待执行、2 执行中、3 等待重试、4 成功、5 失败、6 取消。持久化字段见[Task 契约](data-contracts.md#task-field-contract)，阶段输入按[执行 RPC 协议与装配](data-contracts.md#execution-rpc-contract)由 oneof 表达，数据库类型在适配层显式映射，不以 Proto 字段编号推导；源文件及生成代码尚未实现。

### 状态集合

| 对象 | 未结束状态 | 终态或配置状态 |
| --- | --- | --- |
| Job | 不适用 | 启用、停用是计划配置，不是某一轮的执行状态 |
| Instance | 待开始、运行中、停止中 | 成功、失败、取消 |
| Task | 待执行、执行中、等待重试 | 成功、失败、取消 |

Instance 待开始表示已经创建，但尚未首次有效开始推进；运行中覆盖准备、分片生成、派发、执行、重试等待、平台汇总和业务收尾。同一 Instance 可以同时存在执行中和等待重试的分片，因此不再为 Instance 增加“等待重试”状态。

Instance 保留原编码 1 待开始、2 运行中、3 成功、4 失败、5 取消，新增 **6 停止中（STOPPING）**。停止中表示停止决定已经持久化，尚需完成子 Task 的数据库取消及父终态保存，不表示等待取消 RPC 成功或业务代码退出。进入停止中时冻结 `end_reason`，人工停止最终转取消，整轮超时最终转失败；`finished_at` 在进入终态时才保存。停止中仍属于未结束，继续阻挡同 Job 的阻塞丢弃触发、Job／组删除及历史清理，但不再允许新增 Task、Post 或执行尝试。页面独立显示“停止中”，不与阶段拼接成另一套状态。

Task 在[当前尝试登记提交](execution.md#attempt-registration)时进入执行中并占用一次执行机会，此时可能尚未发出 RPC，随后也可能处于派发在途、执行器排队、执行业务或等待结果；业务已完成、回报已 ACK 但未有效落库时也可能仍显示执行中。该状态不证明业务代码正在运行。已有持久化绑定但无有效结果时保持当前尝试执行中，等待有效结果、人工停止或整轮截止，不新增等待结果状态或内存等待对象；失联、重启、回报耗尽及 ACK 后丢失不能单独授权重跑。无绑定仍适用有限观察及条件结算，详见[已绑定结果等待](execution.md#bound-result-wait)与[绑定缺失处理](execution.md#missing-binding)。

调度端对已 ACK 结果的可恢复写库故障、性质不明的技术错误及提交不明保留并退避，不按固定次数或 TTL 主动丢弃，也不套用执行器有限回报清理。每条条件写入独立提交，失败只保留该原条目，不重放其他已明确成功的结果；保留不改变 Task 状态的持久化条件，不新增结果等待状态或执行尝试，重新写库仍须校验当前尝试及终态条件。零行正常结束但不证明此前保存成功。一次处理结束释放保存并发，退避保留组件内原位置，安排按[调度端结果保存安排与初值](execution.md#scheduler-result-defaults)执行。永久无效条目按[回报错误分类](data-contracts.md#result-error-classification)所需证据单独处理；配置损坏、未知版本或数据库技术故障不直接判为结果无效，SQL／驱动适配及实现验证仍待完成；进程退出仍可能丢失未落库结果。

Task 失败只表示最终失败。有重试机会时，本次尝试失败可条件进入等待重试，而不是先把 Task 写成失败再恢复。明确 BUSY 的条件返还与延期也复用等待重试状态，不占执行预算，零重试同样适用。等待重试只是候选，不代表业务一定执行失败，也不证明父 Instance 仍可执行；下一次登记必须经过[父行授权检查](execution.md#authorization-terminal)。成功、失败和取消均为不可逆终态；手动重新执行创建新的 Instance，不重开历史记录。

### Instance 语义转换

| 转换 | 触发条件 | 推进方 |
| --- | --- | --- |
| 待开始 → 运行中 | 平台首次有效开始推进，确定整轮开始与适用的截止时间 | 取得必要推进权的调度节点 |
| 运行中 → 成功 | 普通 Task 成功，或分片流程及已配置 Post 满足完整成功条件；本轮未终止，允许在截止后按结果结束 | 调度服务内部完成推进 |
| 运行中 → 失败 | 具备本轮正常最终失败条件 | 调度服务内部完成推进 |
| 待开始／运行中 → 停止中 | 有效手动停止，冻结人工停止原因，即使已过截止也不改判超时 | 调度服务停止处理 |
| 运行中 → 停止中 | 自动超时先检查仍不具备最终结束条件，父锁内复核仍运行且已到整轮截止，冻结超时原因 | 调度服务超时处理 |
| 停止中 → 取消／失败 | 本轮所有已存在 Task 均已终态；按冻结的人工停止／超时原因保存对应父终态，不等待 RPC 或业务退出 | 调度服务停止处理及恢复 |
| 停止中 → 停止中 | 重复停止、超时检查或迟到结果不改变停止决定；继续未完成的数据库处理 | 所有推进入口共同保证 |
| 任一终态 → 原终态 | 重复请求、迟到回报或重复恢复不改变终态 | 所有状态写入入口共同保证 |

业务 Post 仅回报自身结果，不直接更新 Instance。分片最终失败仍等待其他分片及已配置 Post 结束，不能提前套用“运行中 → 失败”结束整轮。终态判定顺序见[停止、超时与正常结束竞争](behavior.md#terminal-order)。

### Task 语义转换

| 转换 | 条件 |
| --- | --- |
| 首次创建即为执行中，仅普通 Task | 本地派发工作协程已取出普通 Instance 候选，在单父行短事务中启动 Instance、插入唯一 Task 并保存首次执行信息；提交即占一次机会，明确确认提交后才派发 |
| 待执行 → 执行中 | 取得本地容量，短事务锁单条父 Instance 并按当前数据库时间检查状态和截止；满足生成完整性、时机和预算等条件，登记原始尝试及机会并提交 |
| 执行中 → 成功 | 当前有效尝试的成功结果被接受并持久化 |
| 执行中 → 等待重试 | 当前尝试按协议结算为失败或结果不确定且仍有额度；或明确 BUSY 原子关闭当前有效尝试、一次返还并延期。只形成候选，可与父 STOPPING 交错；零重试也可因 BUSY 进入 |
| 等待重试 → 执行中 | 到达最早派发时间且有本地容量，经同一父行授权关口检查当前时间与整轮状态，再条件登记下一尝试及预算并提交 |
| 执行中 → 失败 | 当前尝试按协议结算为最终失败，不再有可用重试机会 |
| 任一未结束状态 → 取消 | 整轮终止，当前 Task 的取消条件更新生效 |
| 任一终态 → 原终态 | 重复或旧回报不得回退、复活或覆盖已有终态 |

此表定义主生命周期，不替代通信事件处理协议。明确成功正常推进，明确失败仍按原 Task 预算形成重试候选；已有持久化绑定但无有效结果不会仅因失联而转入等待重试或失败。BUSY 延期复用 `next_dispatch_at` 与既有检查，采用退避且不延长整轮截止，重复或旧 BUSY 不得返还多次或复活已结束尝试。[时间预算](execution.md#dispatch-time-budgets)已定 BUSY 默认 5 秒上下浮动 20%，保存后释放派发处理，不占住协程等待，也不沿用业务失败的 10 秒重试间隔。父进入停止中后不再授予新尝试，未结束 Task 按取消规则收敛，不把所有 Task 判为业务失败。父停止决定、各批子取消及父最终结束不使用一个大事务；恢复以持久化 STOPPING 为入口，全部子 Task 终态后才结束父，详见[子任务收敛](behavior.md#task-convergence)。无节点分类及完整条件写入继续在对应模块细化，不能自行添加隐含重派机会。

### 阶段与空工作项

不另维护一套 Instance 阶段权威字段。普通、准备、分片和收尾由 Task 类型区分，展示阶段依据 Task、有效结果及分片生成事实推导；这不省略持久化生成完成事实，也不授权用进程内缓存代替恢复依据。具体展示形式、名称及 API 表达留给管理设计，本节不新增阶段命名或拼接展示规则；展示查询的批量读取方式在管理与数据模块设计，不新增逐条回报写 Instance 阶段的路径。

合法空工作项数组表示准备成功、本轮无分片数据。平台持久化“零分片且生成完成”后触发推进：配置了 Post 则在父仍运行且原截止允许时创建唯一 PostTask，提供零计数并按统一重试规则执行；未配置 Post 且父仍运行时可按结果成功结束，不因仅平台收尾发生在截止后而改判超时。不能等待不存在的分片回报，也不能用缺少 Task 推导零分片生成完成。结果缺失或格式非法不是合法空数组，不能默认按零分片成功处理；消息存在性与 JSON 字节表达已按[执行 RPC 协议与装配](data-contracts.md#execution-rpc-contract)确定，序列化与校验仍须实现验证。
