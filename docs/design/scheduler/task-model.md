# 3 任务模型

本章建立全系统共享的术语，区分长期任务、一轮执行、可派发工作和执行尝试，并界定业务分片与平台状态汇总的职责。**核心概念、统一 Task、状态与生命周期、发送前条件登记尝试及提交记账、BUSY 条件返还与延期已确认；完整通信故障与终止竞争协议、工作项契约及处理器接口仍待详细设计。** 本章不以语义命名提前确定数据库字段、枚举数值或 RPC 接口。

## 3.1 核心概念与关系

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| Job，任务定义 | 长期保存的配置，描述做什么、何时执行以及执行模式 | 每天生成商户经营日报 |
| Instance，执行实例 | 一次触发形成的一轮执行，保存本轮必要执行配置，承载整体状态与整轮时间预算 | 某日的这一轮日报生成 |
| Task，执行单元 | 本轮中可以独立派发、追踪和重试的业务执行单元 | 准备工作项、处理一批商户、生成本轮结果报告 |
| Attempt，执行尝试 | 同一 Task 的一次授权执行身份，用于区分原始执行和重试，隔离迟到结果 | 某分片的第一次执行和一次重试 |
| Executor，执行器 | 接收 Task、运行处理器并回报状态的运行组件 | 某业务服务中的执行组件及其多个副本 |
| Executor Group，执行器组 | Job 引用的业务寻址配置，关联对应服务发现范围；不是一台机器 | 商户任务组，通过其发现标识查找执行器实例 |
| Processor，处理器 | 业务方实现并按名称注册的具体处理逻辑 | 商户日报处理器 |

一个 Job 可以产生多个 Instance；一个 Instance 包含本轮需要执行的 Task。Task 自动重试仍使用原 Instance、原 Task 身份，只产生新的执行尝试，不创建另一轮任务。任务定义、某次运行、一个业务分片以及一次尝试不能混为一条概念。

一个执行器进程归属一个组，可以注册多个 Processor；一个组可以有多个兼容的执行器进程实例，同组共享组 Token。组用于业务程序寻址，不是每个 Job 的分类标签；组凭据也不是 Task 执行尝试身份。注册发现和调用认证见[总体架构](architecture.md#internal-trust)。

这里将 Attempt 作为逻辑概念，不代表单独建立 Attempt 表。第一版不保留独立的尝试历史表，但仍需持久化当前尝试标识、重试计数和必要状态，以校验回报及关联日志。

第一版支持手动触发，启用或停用 Job 均可按集群阻塞规则创建新的 Instance，不改变定时进度；允许仅当次业务参数覆盖，同请求号重发返回原执行，不重开历史 Instance，也不提供手动选择失败分片重跑。行为边界见[手动触发规则](behavior.md#manual-trigger)，具体接口与交互在管理设计中明确。

## 3.2 统一 Task 建模

需要交给业务执行器运行的准备、业务分片和业务收尾使用统一 Task 逻辑模型，第一版共用 Task 表，以类型区分，不另建准备表和收尾表。普通业务执行同样复用 Task 执行机制。

| 业务工作 | 职责 | 与其他阶段的区别 |
| --- | --- | --- |
| 普通执行 Task | 完成简单业务任务 | 不因统一建模被迫增加空的准备或收尾处理器 |
| PreTask，准备 Task | 执行业务准备，返回可序列化工作项数组 | 有效结果为后续生成分片提供输入 |
| 分片 Task | 执行一份业务工作项 | 多个分片可在不同执行器并行处理；一个 Task 可以处理多条业务记录 |
| PostTask，收尾 Task | 处理本轮分片结果，例如汇总错误或生成报告 | 属于业务收尾，不是平台内部的状态汇总，也不是仅针对成功结果计算的 Reduce |

统一的是持久化、派发、当前执行尝试、结果校验、取消和恢复机制，不是各阶段的业务语义。准备产出工作项、分片执行业务、收尾承接结果；各阶段的失败后果和推进条件不同，见[行为规则](./behavior.md)。

第一版明确两条执行路径：普通任务只创建一个普通 Task，不组合准备或收尾阶段；分片任务必须通过 PreTask 提供工作项，PostTask 可选。正常推进至收尾且配置了 Post 的分片 Instance，若产生 N 个分片，对应 N＋2 条 Task；未配置 Post 则为 N＋1 条。准备失败或整轮提前终止时不强行补齐后续 Task。具体处理器接口形式继续设计，第一版不提供业务进度回调。

### 统一模型的收益与限制

统一模型主要用于复用可靠执行协议，减少扩展时阶段之间的实现差异。它不意味着只修改模型就能提高吞吐，也不自动并行化单轮准备和收尾：一次准备、一次业务收尾仍分别由一个执行器处理。

统一表会增加相应的记录、状态写入和索引维护，但不统一建模也需要可靠保存准备和收尾的执行事实，不能与完全不持久化的直接 RPC 作不等价比较。队列容量、公平性与批量操作仍需单独设计；统一 Task 不要求所有类型无差别地进入同一无界队列。

## 3.3 业务收尾与平台汇总

平台内部检查分片是否结束、计算整体状态、判断是否生成 PostTask，属于调度服务推进逻辑，不额外创建业务 Task，也不派发给业务处理器更新调度表。

| 动作 | 执行方 | 是否属于业务 Task |
| --- | --- | --- |
| 解释业务参数并执行分片 | 业务处理器 | 是 |
| 校验回报并保存 Task 结果 | 调度服务 | 否 |
| 检查分片生成完整且无未结束分片 | 调度服务 | 否 |
| 唯一创建本轮 PostTask | 调度服务 | 创建业务 Task 的平台动作，本身不另建 Task |
| 根据分片结果完成业务收尾 | 执行器运行 Post 处理器 | 是 |
| 按分片及收尾最终结果确定 Instance 终态 | 调度服务 | 否 |

例如十个分片全部成功：结果先由调度服务保存，再通过完成检查唯一创建已配置的 PostTask；Post 执行业务收尾并回报。调度服务根据有效结果确定本轮终态，业务 Post 不直接修改 Instance。未配置 Post 时，分片完整生成且全部最终结束后，由平台直接汇总并结束本轮，不创建空 Post 或平台汇总 Task。

收尾判断的对象是**业务分片集合**，不能笼统查询“所有 Task 是否结束”，把准备或收尾本身混进未结束分片。进入收尾需要分片已完整生成且全部达到最终状态；仍待重试的失败分片尚未结束。分片生成完成后集合固定，不能在收尾判断过程中随意追加。

第一版展示分片总数、成功、失败和未结束数，只计算业务分片 Task，不表示业务工作量完成百分比。统计查询和展示刷新方式仍待设计，不新增逐条结果回报更新 Instance 计数的路径。部分分片最终失败后的收尾、停止和超时规则见[行为规则](./behavior.md)，结果落库与并发推进协议见[执行流程与可靠性](./execution.md)。

## 3.4 工作项数组与分片职责

分片业务通过准备阶段产出可序列化工作项数组。业务方定义元素的含义，平台按通用规则切分数组、保存分片参数并派发；执行器中的业务处理器解释收到的子数组。

数组元素可以是单个主键、一组主键、ID 范围或待处理数据的引用。平台不解释商户、订单等业务结构，不直接替业务查询跨域数据。范围和引用的有效性、覆盖范围及处理语义由业务方负责。

因此，平台的“单片数量”表示数组元素数量，不一定等于商户数量，也不等于实际计算量。一个元素如果代表一个范围，可能覆盖很多商户；按元素个数均分不保证计算负载均匀。具体分片数算法和配置形式尚待确定，不预设一种业务分片规则。

有效准备结果已持久化后，平台据此保存分片 Task 及参数；生成完整后才开放分片派发，生成完成事实也要触发完成检查。准备成功结果已保存但平台生成中断时，只恢复生成过程，不重新运行业务准备；仅收到入队 ACK 不能作为生成分片的依据。生成执行权、分批保存和完整性标记在[执行流程与可靠性](./execution.md)及[数据与接口](./data-contracts.md)中继续设计。

## 3.5 分片粒度与容量边界

Task 是调度执行单元，不与单条业务数据一一对应。合理粒度需要在两类成本之间权衡：分片过细会放大 RPC、状态写入及结果回报开销；分片过粗会增加长尾耗时和失败重做成本。

以 100 万商户的日报为例，可以产生约 1,000 个分片，每份处理约 1,000 个商户，而不是为每个商户生成一条 Task。这只是粒度示例，不是默认参数或性能承诺。业务也可以返回范围工作项，在执行器内分页读取所属业务的数据。

减少 Task 条数不必然减少参数总字节数。即使分成 1,000 片，如果仍传递全部商户资料，准备返回值、序列化、网络传输和持久化仍可能成为瓶颈。工作项宜表达必要的业务输入，具体参数大小、数组数量与批次限制需要结合契约和容量验证确定。

平台必须提供有界队列、容量边界与背压保护，不能将系统不被过量工作拖垮的责任完全交给业务方；业务方仍应根据计算量选择粒度。这一要求适用于任何架构，不是本地持久化后直接派发的特有限制。

调度端结果缓冲的容量已确定按排队、处理中和待重试的结果条数合计，结合固定消费并发与 RPC 报文上限控制，不做队列总字节／MB 精确配额，不另加业务结果长度限制或 Job 页面参数。这个边界不改变准备工作项数组、分片参数及生成过程仍需设计的容量与存储契约，详见[调度端结果保留](execution.md#scheduler-result-retention)。

Task 重试可能重做部分业务数据，处理器需要按业务键保证幂等。平台级业务检查点不属于当前第一版交付承诺，若要纳入需另行评审范围。准备数组如何暂存、是否保留完整原数组及历史数据如何清理，尚未由数组模型确定，不应从示例推导为既有能力。

## 3.6 执行尝试与记录边界

每个 Task 独立区分原始尝试与重试；各 Task 读取 Instance 创建时保存的同一份重试配置，但不共享一轮总次数池，也不随 Job 后续编辑变化。普通执行、准备、分片和收尾均沿用这一机制，配置范围见[本轮执行配置](behavior.md#instance-execution-config)，具体默认值及预算见[行为规则](./behavior.md)。

当前尝试标识用于拒绝旧回报覆盖新尝试，幂等回报与更新前状态条件校验用于保护平台推进。它们只能保护调度状态，不能撤销旧尝试已经造成的业务副作用，也不意味着框架保证业务恰好执行一次。

尝试身份与执行预算不是同一个概念。执行器明确容量满且未接单、未入队、未执行的 BUSY，不消耗 Task 执行重试次数；调度端只对当前有效尝试原子完成关闭、返还登记占用的一次机会及设置最早可派发时间，零重试同样可延期。后续登记必须使用新尝试身份，不能随预算返还而复用旧标识；无需新增 Attempt 历史表。通用通信错误及 BUSY 答复丢失不免费返还，详见[BUSY 背压](execution.md#busy-backpressure)。

第一版在 Instance、Task 中保存查询与恢复所需状态、时间、重试计数和简短结果或错误摘要，不建立独立 Attempt 表，不将详细文本执行日志写入数据库。详细过程进入现有服务日志／日志系统，通过 `job_id`、`instance_id`、`task_id`、尝试标识关联，必要时携带 traceId。数据库不保存每次尝试的完整结构化历史；字段含义及保留规则见后续[数据与接口](./data-contracts.md)和[管理与运维](./operations.md)。

## 3.7 参考概念与未纳入能力

字节 Scheduler 文章区分 `PreProcess`、`ShardingProcess`、`Notify`、`PostProcess`。本设计借鉴准备、分片和收尾的职责，但不据此推导相同表结构或完全相同接口。DogX 统一 Task 共表是本项目已确认的选择，不是对参考项目存储实现的断言。

文章中的 `Notify` 是调度侧向业务处理器传递整体进度的回调，不是执行器向调度服务提交完成结果的 RPC，也不必然意味着短信或消息通知。DogX 第一版不提供业务内部实时进度或 Notify，不建立 NotifyTask；必要的执行结果回报、平台统计和业务收尾不受影响。

参考文章对四个入口的说明、原文表述歧义及证据边界集中在[参考资料](./references.md)，不作为当前未决接口的替代定义。

## 3.8 状态与生命周期 {#lifecycle}

状态表达执行进度，Task 类型表达工作职责，结束原因解释为什么结束，三者不能混为一套枚举。以下是已确认的语义，不指定数据库编码或协议字段名。

### 状态集合

| 对象 | 未结束状态 | 终态或配置状态 |
| --- | --- | --- |
| Job | 不适用 | 启用、停用是计划配置，不是某一轮的执行状态 |
| Instance | 待开始、运行中 | 成功、失败、取消 |
| Task | 待执行、执行中、等待重试 | 成功、失败、取消 |

Instance 待开始表示已经创建，但尚未首次有效开始推进；运行中覆盖准备、分片生成、派发、执行、重试等待、平台汇总和业务收尾。同一 Instance 可以同时存在执行中和等待重试的分片，因此不再为 Instance 增加“等待重试”状态。

Task 在[当前尝试登记提交](execution.md#attempt-registration)时进入执行中并占用一次执行机会，此时可能尚未发出 RPC，随后也可能处于派发在途、执行器排队、执行业务或等待结果；业务已完成、回报已 ACK 但未有效落库时也可能仍显示执行中。该状态不证明业务代码正在运行。已有持久化绑定但无有效结果时保持当前尝试执行中，等待有效结果、人工停止或整轮截止，不新增等待结果状态或内存等待对象；失联、重启、回报耗尽及 ACK 后丢失不能单独授权重跑。无绑定仍适用有限观察及条件结算，详见[已绑定结果等待](execution.md#bound-result-wait)与[绑定缺失处理](execution.md#missing-binding)。

调度端对已 ACK 结果的可恢复写库故障保留并退避，不按固定次数或 TTL 主动丢弃，也不套用执行器有限回报清理。保留结果不改变 Task 状态的持久化条件，不新增结果等待状态或执行尝试；重新写库仍须校验当前尝试及终态条件。永久无效数据不无限重试堵住整批，进程退出仍可能丢失未落库结果，具体错误分类与隔离契约继续设计。

Task 失败只表示最终失败。有重试机会时，本次尝试失败可条件进入等待重试，而不是先把 Task 写成失败再恢复。明确 BUSY 的条件返还与延期也复用等待重试状态，不占执行预算，零重试同样适用。等待重试只是候选，不代表业务一定执行失败，也不证明父 Instance 仍可执行；下一次登记必须经过[父行授权检查](execution.md#authorization-terminal)。成功、失败和取消均为不可逆终态；手动重新执行创建新的 Instance，不重开历史记录。

### Instance 语义转换

| 转换 | 触发条件 | 推进方 |
| --- | --- | --- |
| 待开始 → 运行中 | 平台首次有效开始推进，确定整轮开始与适用的截止时间 | 取得必要推进权的调度节点 |
| 运行中 → 成功 | 普通 Task 成功，或分片流程及已配置 Post 满足成功条件；本轮未终止且未到期 | 调度服务内部完成推进 |
| 运行中 → 失败 | 适用阶段最终失败，或尚未结束但已到整轮截止时间 | 调度服务内部完成或超时推进 |
| 待开始／运行中 → 取消 | 有效手动停止；已有终态不覆盖，已到期则按超时优先规则处理 | 调度服务停止处理 |
| 任一终态 → 原终态 | 重复请求、迟到回报或重复恢复不改变终态 | 所有状态写入入口共同保证 |

业务 Post 仅回报自身结果，不直接更新 Instance。分片最终失败仍等待其他分片及已配置 Post 结束，不能提前套用“运行中 → 失败”结束整轮。终态判定顺序见[停止、超时与正常结束竞争](behavior.md#terminal-order)。

### Task 语义转换

| 转换 | 条件 |
| --- | --- |
| 待执行 → 执行中 | 取得本地容量，短事务锁单条父 Instance 并按当前数据库时间检查状态和截止；满足生成完整性、时机和预算等条件，登记原始尝试及机会并提交 |
| 执行中 → 成功 | 当前有效尝试的成功结果被接受并持久化 |
| 执行中 → 等待重试 | 当前尝试按协议结算为失败或结果不确定且仍有额度；或明确 BUSY 原子关闭当前有效尝试、一次返还并延期。只形成候选，可与父终态交错；零重试也可因 BUSY 进入 |
| 等待重试 → 执行中 | 到达最早派发时间且有本地容量，经同一父行授权关口检查当前时间与整轮状态，再条件登记下一尝试及预算并提交 |
| 执行中 → 失败 | 当前尝试按协议结算为最终失败，不再有可用重试机会 |
| 任一未结束状态 → 取消 | 整轮终止，当前 Task 的取消条件更新生效 |
| 任一终态 → 原终态 | 重复或旧回报不得回退、复活或覆盖已有终态 |

此表定义主生命周期，不替代通信事件处理协议。明确成功正常推进，明确失败仍按原 Task 预算形成重试候选；已有持久化绑定但无有效结果不会仅因失联而转入等待重试或失败。BUSY 延期复用 `next_dispatch_at` 与既有检查，采用退避且不延长整轮截止，重复或旧 BUSY 不得返还多次或复活已结束尝试。整轮终止后不再授予新尝试，未结束 Task 按取消规则收敛，不把所有 Task 判为业务失败。父终态与子状态不承诺一次事务同时完成，恢复必须覆盖父已终态而子仍未终态的情况，详见[子任务收敛](behavior.md#task-convergence)。无节点分类、BUSY 退避数值及完整条件写入在对应模块细化，不能自行添加隐含重派机会。

### 阶段与空工作项

不另维护一套 Instance 阶段权威字段。普通、准备、分片和收尾由 Task 类型区分，展示阶段依据 Task、有效结果及分片生成事实推导；这不省略持久化生成完成事实，也不授权用进程内缓存代替恢复依据。展示查询的批量读取方式在管理与数据模块设计，不新增逐条回报写 Instance 阶段的路径。

合法空工作项数组表示准备成功、本轮无分片数据。平台持久化“零分片且生成完成”后触发推进：配置了 Post 则创建唯一 PostTask，提供空结果集合并按统一重试规则执行；未配置 Post 则成功结束，仍受整轮终止与截止时间规则约束。不能等待不存在的分片回报。结果缺失或格式非法不是合法空数组，不能默认按零分片成功处理；序列化及校验细节在契约设计中确定。

## 3.9 待补齐与完成条件
