# 5 执行流程与可靠性

本章将[总体架构](./architecture.md)、[任务模型](./task-model.md)和[行为规则](./behavior.md)串成一次执行的主路径，并说明节点故障、结果重复和并发推进下的可靠性边界。各机制围绕同一个目标：持久化事实决定下一步，本地状态加速处理，业务执行不承诺恰好一次。

**设计成熟度：无整轮固定归属、本地直接派发、尝试登记与父状态协调、提交记账、原生路由及绑定、异步回报、重试与结果保留、提交结果不明恢复及完成推进的规则已确认。** 2026-10-23 已通过停止协议修订：先持久化 `STOPPING` 和停止原因，再有界处理子 Task，全部子记录终态后才结束 Instance；替代此前父先终态的顺序。正常完成的事实分支、父条件 UPDATE、结束时间与摘要语义，以及自动超时仅在明确未就绪后进入父短事务的衔接保持。正常完成允许平台收尾迟于截止；新工作授权仍在必要短事务内按当前数据库时间校验父状态及截止。人工停止保留已提交原因，已有停止决定或终态不覆盖。B2 [闭环总审](progress.md#b2-review)按本轮修订后的规则继续有效；[普通完成读取](data-contracts.md#ordinary-completion-query)及[稳定结束原因](data-contracts.md#execution-end-reasons)已于 2026-11-02 通过；分片生成封口字段、完整分片事实查询 SQL／索引及其余未定参数仍在对应模块细化，本章不是已经实现验证的完整协议。

## 5.1 一轮执行的主路径 {#main-flow}

当前普通阶段 1～5 核心已完成，阶段 6 进行中。最新执行器骤停、etcd 恢复与本机收尾结果见[本机收尾记录](ordinary-readiness-review.md#ordinary-local-checkpoint)。GitHub Linux 实际运行、race、覆盖率和代表性负载尚待验证；以下分片生成、阶段推进及 Post 仍是待实施契约。

### 普通任务 {#ordinary-flow}

普通任务主路径与职责已通过评审。Job 配置普通执行模式，Instance 沿用创建时保存的模式和其他执行配置；每轮只创建一条普通执行 Task，不增加 Pre／Post，也不建立整轮固定归属。

1. 触发入口按既定规则保存 WAITING Instance 和本轮配置，确认提交后向本节点推进组件发送有界提示。提示丢失、队列满或节点退出，由所有调度节点参与的有界恢复接续；读取候选不等于取得执行权。
2. 本地派发工作协程取出普通 Instance 候选后，在短事务中按主键锁住这一条 Instance，复核仍为 WAITING、本轮为普通模式且满足首次派发条件。锁后读取当前数据库时间，保存 `started_at`，按本轮超时时长计算 `deadline_at`，将 Instance 改为 RUNNING；同时创建该轮唯一的普通 Task，直接保存为执行中，保存首次执行尝试的标识、登记时间并占用一次执行机会。以上变化合并在同一个事务中，不先提交待执行 Task 再另开事务登记首次尝试。
3. 只有该事务获得明确提交成功确认后，当前工作协程才向执行器发送本次尝试的 RPC，不经过第二次派发排队或重复登记。数据库连接获取、父行 NOWAIT 尝试、事务及后续 RPC 都在这份派发并发内完成，事务内不调用 RPC；父锁冲突按[派发竞争规则](#dispatch-contention)退出，其他失败和提交结果不明沿用[尝试登记协议](#attempt-registration)及[不补发同次尝试](#commit-unknown)的规则。
4. 执行器接单后异步运行具名处理器；派发槽位不等待业务结束。业务完成结果交给执行器的有界回报缓冲，按可发送时间以有限并发单条提交；一次 RPC 结束即释放发送并发，结果等待重试不占发送者。
5. 任意调度接收节点完成基础校验、成功入队后返回接收 ACK；后台校验并保存有效 Task 结果，提交后由调度服务内部推进 Instance 终态。仍可重试的失败保持本轮运行中；已有完整最终结果时按[终态规则](behavior.md#terminal-order)条件结束，不因平台收尾迟于截止自动改判超时，也不覆盖已有父终态，不由业务处理器直接更新 Instance。

首次开始、首个 Task 创建与首次执行信息的原子性，保证正常协议不会提交“本轮已经开始，但首个 Task 或首次执行信息未保存”的状态。重复推进看到本轮已开始时，退出首次启动处理；已有 Task 的后续处理沿用其持久化状态和恢复规则，不再创建第二条、不重设开始或截止时间，也不能直接重发已经登记的尝试。普通首次 Task 保存 `attempt_no=1`、`used_attempts=1`；字段与单例唯一索引见[已确认契约](data-contracts.md#task-field-contract)，[首次创建与重复推进 SQL](data-contracts.md#ordinary-start-sql)已通过：锁后校验并取时，先条件更新父行一条，再插入 Task；单例冲突整笔回滚。只有本事务实际新建 Task 且明确提交成功才派发，无操作成功或内存中已有 ID 均不构成发送许可。

这里的“登记首次尝试”就是保存这次准备派发的执行信息，不是另建一条历史记录或独立记账模块。首次提交占用一次执行机会；默认额外重试 3 次，正常首次执行加重试最多有 4 次机会。执行尝试标识用于区分前后请求及迟到结果，不等于业务实际执行次数；明确 BUSY 的条件返还继续沿用既定规则，不混同标识与剩余额度。

没有可用派发工作协程时，普通 Instance 保持 WAITING，不提前创建 Task 或启动整轮倒计时；仅在有界队列中等待也不算开始。首次有效开始后，派发等待、业务执行和重试共用同一预算；截止后不再授权新工作，已经具备最终结果的纯平台收尾仍可按结果结束。锁后取时使用数据库当前时间，不使用事务开始时的旧时间。事务明确回滚时不留下部分开始状态或占用机会；提交结果不明时不凭内存猜测发送 RPC，实际已提交的首次尝试仍遵守[不补发同次尝试](#commit-unknown)的规则。

Task 的有效结果已保存但 Instance 更新中断时，只恢复平台结束步骤，不重新执行业务。主路径通过不表示 Task 表、执行器、RPC 或故障测试已经实现。

需要重新执行时遵守[统一重试规则](./behavior.md#retry)，不叠加另一份通信重派额度；整轮超时按终止规则处理，不作为自动重试整轮的理由。普通任务只创建一个普通 Task，不组合准备或收尾阶段，接口形式在契约设计中确定。业务进度回调不纳入第一版。

### 分片任务

| 步骤 | 已确认处理方式 | 可靠性要求 |
| --- | --- | --- |
| 1. 触发 | 通过同 Job 短事务创建本轮 Instance，自动触发同时推进进度 | 遵守[统一触发记账](#trigger-accounting)、[自动触发身份](behavior.md#trigger-identity)及[切主与配置变更边界](#leader-config-boundary) |
| 2. 准备 | 取得必要推进权，唯一创建 PreTask，提交后派发 `PreProcess` | 不在等待业务结果期间持续持有整轮归属 |
| 3. 生成 | 有效准备结果持久化后，按通用规则拆分工作项数组，保存分片 Task 与参数 | 确认生成完整后才开放派发；生成完成事实提交后也通知完成检查 |
| 4. 派发 | 生成节点按本地派发容量，对已知 Task 小批量条件登记当前尝试，提交后直接经 RPC 派发 | 不等待下一轮数据库扫描；正常派发与恢复复用[尝试登记协议](#attempt-registration)，不提前授权全部积压 |
| 5. 回报 | 任意接收节点成功入队即 ACK，后台幂等保存有效结果，提交后按 Instance 合并检查 | ACK 不表示落库；待重试分片仍未结束；跨节点允许重复检查，不允许重复推进 |
| 6. 可选收尾 | 分片生成封口、所有分片均已成功或最终失败且配置了 Post 时，在父仍运行且未到期的单 Instance 短事务中唯一创建 PostTask，提交后派发 `PostProcess`；未配置则直接进入平台结束步骤 | 部分或全部分片最终失败仍执行已配置 Post；准备最终失败不进入 Post，收尾重试不新建第二条 PostTask |
| 7. 结束 | 已配置 Post 则等待其最终结果持久化，未配置则直接按分片最终结果更新 Instance | 不抹除分片最终失败，不覆盖停止或超时，不因平台推进失败重新执行业务 |

生成完整后，本轮分片集合固定。分片路径必须有准备阶段；PreTask 最终失败时直接结束本轮，不生成分片、不进入正常 Post；有效准备成功结果后的生成故障只恢复平台生成。合法空数组按零分片生成完成主动推进，有 Post 则在父运行且未到期时创建／授权，无 Post 则由平台按结果成功结束，不等待分片回报。完整阶段结局见[第 4 章](./behavior.md#stage-outcomes)，工作项含义、粒度及容量边界见[任务模型](./task-model.md)与[数据契约](./data-contracts.md)。

普通和分片路径均使用 [Instance 创建时保存的执行配置](behavior.md#instance-execution-config)。包括稍后生成的 Pre／分片／Post、重试及跨节点恢复，不再从当前 Job 获取本轮执行策略。首次有效开始时，以本轮保存的超时时长形成截止时间，Job 编辑不能改变或延长本轮预算。

提交后未推进、本地队列满、到期工作、节点失联或结果不明，均需要由有界检查重新发现并调用同一套推进／恢复逻辑。正常路径不依赖最初派发节点持续存活，恢复路径也不能绕过已成功结果、执行预算或终止规则。

首批触发模块止于[持久化交接](data-contracts.md#trigger-durable-handoff)：保存 WAITING Instance 和本轮配置，开始、截止及结束时间仍为空。提交确认后的本地 ID 提示仅加速后续推进，不是可靠消息或执行授权；候选与配置按有界批次读取，恢复不得用永久 ID 水位跳过晚提交记录。首次开始与创建首个 Task 在执行模块按数据库条件协调，本批不实现假消费者或另加扫描循环。

### 同 Job 的触发记账 {#trigger-accounting}

**Cron 正常回调、Leader 的低频恢复检查及规则注册后的到期检查共用同一触发入口。** 三者只提示检查某个 Job，不凭本地计时或扫描快照直接创建 Instance；处理哪轮以 `Job.next_trigger_at` 的最新持久化值为准。恢复时机见[低频触发恢复](behavior.md#trigger-recovery)，注册后的检查见[配置加载与重载](#job-config-reload)。

1. 开启短事务，以 Job 主键等值条件锁定单表单行；读取最新配置、删除状态、启用状态与触发进度。Job 不存在或 `deleted_at` 非空时结束，不创建 Instance 或推进进度。
2. 取得锁后，读取一次调度进程的 `time.Now()`，判断是否到期及是否超过 5 秒迟到容忍，不沿用回调、入队、扫描或事务开始时刻，也不另取数据库当前时间。未到期或自动触发条件不满足时结束本次处理。
3. 按既定错失和阻塞策略决定是否创建 Instance。需要阻塞判断时，用适配索引的 `EXISTS` 查询同 Job 是否还有未结束 Instance，不加载或锁住全部实例。
4. 已到期时，按当前 Cron 规则计算严格晚于本次判定时间的第一个时刻。应当执行时，在同一事务中创建 Instance 并推进 `Job.next_trigger_at` 到该时刻，`Instance.scheduled_at` 保存锁内读取的旧进度；应当忽略或丢弃时，也推进到该时刻。每次最多创建一轮，5 秒内积压也不逐轮补建；完整区间规则见[到期处理](behavior.md#trigger-advancement)。
5. 提交后再推进准备或业务执行。事务中不包含执行器 RPC、通知或其他外部 I/O，也不等待业务完成。

创建 Instance 时，复用锁内已读取的最新 Job，将本轮必要执行配置随 Instance 一起保存；自动、恢复及手动创建均适用。手动指定当次业务参数时，保存覆盖后的实际参数，不更新 Job。已经创建的 Instance 后续沿用自身配置，不再以 Job 编辑改写本轮策略。

到期计算复用[六字段 Cron 与调度时区规则](behavior.md#cron-contract)。到期判断、错失判断和下一次时间计算共用锁后读取的同一个进程时间，注册、预览、启用和推进统一按调度进程默认时区计算；完整适用范围见[Job 触发时间来源](behavior.md#trigger-clock)。解析失败或求不出下一次时间时，按[Cron 异常处理](behavior.md#cron-errors)结束该 Job 本次事务，不创建 Instance、不推进进度、不自动停用；记录限频错误，其他 Job 继续。

同一 Job 的短暂触发记账串行，不同 Job 可以并行。事务使用默认 `READ COMMITTED`，不增加全局调度锁、每 Job 的 Redis／etcd 锁或整轮固定负责人。候选批次和处理并发有界；每个实际处理的 Job 仍有单行协调、必要的阻塞查询及写入成本，不称为一次批量查询即可完成，也不按每个 Task 重复查询 Job。

自动 Instance 以 `(job_id, scheduled_at)` 的部分唯一索引兜底，正常与错失不能分成两个唯一身份。插入仅处理指定自动身份的冲突，`DO NOTHING RETURNING id` 未返回行时保留旧记录并推进当前 Job，不重新派发旧 Instance；其他写入错误不能被吞掉。新进度只保证严格晚于锁后本次判定时间，不保证晚于物理提交时间；事务耗时期间新时间点已到，下一次入口按新进度处理，不在锁内不断追赶。Job 行锁与后续 Instance 查询分成不同语句，使用锁取得后的新快照；具体协议及五个索引见[触发事务与必要索引](data-contracts.md#trigger-transaction-proposal)。

例如每 5 分钟一次的 Job，Cron 和恢复都发现 `Job.next_trigger_at = 2026-10-15 10:00:00+08:00`。先取得锁的一方在到点后创建该轮 Instance，并推进到 `2026-10-15 10:05:00+08:00`；另一方取得锁后重读，若新时间尚未到期则退出。若新值已经到期，只能按最新进度判断下一轮，不能用原扫描值再建该日期该时刻的 Instance。入口来源不决定错失分类：恢复在 5 秒内发现仍按正常触发，Cron 回调超过 5 秒同样应用错失策略。

事务明确回滚时，Instance 创建和进度推进均不生效。提交响应丢失不能当作回滚；后续正常回调或恢复重入统一入口，依据最新持久化进度和触发身份判断，不盲目重放旧 INSERT。已创建的 Instance 由原推进／恢复路径接续，不因本地未收到确认另建一轮。这里是触发记账恢复，不是 B2 的 Task 尝试登记，也不改变后者“登记不明不补发”的限制。

所有 Instance 创建入口均须共用同 Job 的阻塞协调，包括手动触发。手动入口不要求 Cron 到期，也不推进 Cron 进度；启用和停用均可手动执行，同请求号防重复创建，见[手动触发记账](#manual-trigger-accounting)。Instance 结束不反向取得 Job 锁，阻塞的检查点语义见[阻塞策略](behavior.md#blocking)。

切主及配置变更按下节处理；Job 行锁不证明事务来自当前 Leader。Job 仅停用后可编辑，重新启用时重算下一次，见[编辑与重新启用](behavior.md#job-edit-enable)。触发身份、区间折叠、Cron 输入及[时钟与时区运维边界](operations.md#scheduler-timezone)已确认；本批事务、五索引及[跳过留痕](data-contracts.md#trigger-skip-record-proposal)也已定，统一计算与持久化实现仍须完成。忽略或丢弃仅在确认提交后输出服务日志，不在事务内写日志或另建跳过记录。

### 触发容量与过载 {#trigger-capacity}

**自动触发采用按 Job 合并的有界待处理队列，由固定工作协程执行触发短事务；容量不足时拒绝本次内存提示，不因此推进数据库触发进度，后续沿用既有恢复。** 本节只约束 Job 到点至创建 Instance 的处理，不包含 Task 派发、执行器业务或结果回报。

#### 自动入口与容量统计

Cron 回调、规则注册后的到期检查和 Leader 每分钟恢复检查，共用本任期的一套 Job ID 待处理队列。提交提示后立即返回，不等待数据库，不为等待入队额外创建协程；工作协程调用[同 Job 短事务](#trigger-accounting)，不在该池内调用执行器 RPC 或等待业务完成。

容量按排队与处理中占用的 Job 总数计算，同一 Job 在本任期内只占一个槽位。队列只表达“需要检查这个 Job”，不保存每个 Cron 周期的独立事件；本次处理哪轮仍以数据库中的 `Job.next_trigger_at` 为准。

| 提示到达时的本地状态 | 处理方式 |
| --- | --- |
| 尚未接纳该 Job，且有空位 | 占用一个槽位，排到队尾 |
| 该 Job 已经排队 | 合并提示，不重复入队，也不推迟它已有的位置 |
| 该 Job 正在处理 | 只保留一个“结束后再检查”标记；本次结束后复用原槽位排到队尾，不同时启动第二个处理 |
| 尚未接纳该 Job，且总容量已满 | 拒绝本次提示，记录拒绝指标及限频错误日志；不阻塞提交方或建立额外等待队列 |

取出、接收新提示、结束与释放的交界必须避免清掉新提示；没有后续提示且本次处理结束时释放该 Job 槽位。再次排队复用原槽位，不能在满载时偷偷增加溢出集合。队尾轮转避免一个已接纳 Job 连续独占工作协程，但不承诺持续超载时所有被拒 Job 都能在固定时间内获得处理。

#### 队满、写库失败与恢复

拒收提示本身不写 `Job.next_trigger_at`，也不创建失败或取消的 Instance。后续 Cron 回调或既有[每分钟触发恢复](behavior.md#trigger-recovery)重新检查持久化进度，不新增补偿队列、专用扫描或本地 Job 退避重试对象。

恢复检查每次从主库读取最早到期的一批候选，队满或查询失败即结束，下一分钟重新查询，不立即空转重扫。不分页、不保存跨分钟游标，也不保证头部持续失败或反复满载时后面的候选必能轮到；已接纳 Job 的队内去重与队尾轮转保持不变。具体规则见[单批触发恢复](#trigger-recovery-scan)，不将低频恢复变成高频正常调度。

数据库连接获取、锁等待和事务执行均须有超时，自动处理同时受原任期上下文约束。失败不会自行产生下一次检查提示；处理中确实收到的新提示仍按上述合并规则处理。事务明确回滚和提交结果不明沿用触发记账协议，不能仅凭超时认定没有创建成功。

并发许可覆盖实际进行的创建事务操作，不能在操作尚未结束时先释放额度、再用额外协程放任旧操作继续。客户端操作结束也不证明数据库未提交；结果不明仍按后续读取的持久化事实恢复。

#### 手动创建与任期边界

手动执行不进入自动队列，自动和手动入口共用本进程的 Instance 创建并发额度。手动请求没有空位时明确返回系统繁忙，不另建等待队列；取得额度后，仍按[手动触发记账](#manual-trigger-accounting)在提交成功后返回 Instance ID。繁忙仅表示本次请求未获处理，不证明同请求号的此前请求没有成功，重试仍遵守原请求身份规则。

自动队列、合并状态及工作协程属于原 Leader 任期，失主后停止接纳和启动新自动工作，不将旧队列带入新任期。创建并发额度属于进程，不能因同进程重新当选或同时接收手动请求而另起不受约束的创建并发。非 Leader 上的手动入口也受自身进程额度保护；这不是跨节点全局限流，也不是整个数据库所有操作的并发上限。

#### 迟到代价与部署参数

排队时间不冻结错失判定。10:00 收到提示、10:00:06 才取得 Job 行锁，仍按锁后调度进程时间应用固定 5 秒规则，不能因为回调准时就保证创建正常 Instance。每天 10:00 的 Job 若因过载到 10:01 才被恢复发现，默认忽略策略跳过该轮，立即执行一次策略最多补一轮，且仍受阻塞规则约束。

#### 部署初始参数 {#trigger-runtime-defaults}

以下三个配置文件参数采用已确认的实现初始默认值，不增加 Job 页面配置。自动工作协程数直接采用 Instance 创建并发配置，不再提供独立旋钮。

| 参数 | 初始默认值 | 作用范围 |
| --- | --- | --- |
| 待处理 Job 总容量 | 1024 | 排队中与处理中的不同 Job 合计；同一 Job 的后续检查复用槽位，不是启用规则数量上限 |
| Instance 创建并发 | 32 | 自动与手动共用的进程级额度，跨本进程 Leader 任期保留；不是 Task 派发或业务执行并发 |
| 单次触发处理超时 | 3 秒 | 开始处理后的总预算，包含并发额度、数据库连接、Job 行锁等待及事务执行与提交 |

自动工作协程取出 Job 开始处理时计时，不包含此前的自动队列等待；手动请求立即尝试取得额度，没有空位即返回繁忙，不预留手动专用额度。调用方剩余期限更短时采用更短期限，自动处理同时受原任期上下文约束。超时不会冻结固定 5 秒错失判断，也不能证明事务未提交；不得提前释放额度后另起协程继续旧数据库操作。

这三个值是实现起点，不是已验证的性能上限。实现后比较 8、16、32、64 等创建并发档位，同时观察触发延迟、数据库等待、吞吐和资源占用，再校准默认值；不以实现前得出最终最优值作为开工前提。数据库连接池还承接 Task 登记、绑定、结果及其他查询，须一并核算，不能将创建并发直接当作连接池或全集群并发上限。

队列用于吸收短时波动，不以加长队列代替处理能力。Job 恢复采用下节独立的单批读取上限和查询超时，不将其混同为队列容量或触发处理预算。本节不确定 Task 派发或执行器容量，也不承诺 3 万规则同秒及时处理，相关验证见[触发容量验收](verification.md#trigger-capacity-checks)。

### Leader 单批触发恢复 {#trigger-recovery-scan}

仅当前 Leader 在接任时立即检查一次，之后由独立循环每 1 分钟检查一次；不与配置同步合并。循环串行运行，不重叠执行，不累计并补跑错过的周期 tick。

1. 每次读取前取当前调度进程时间，只查询主库中 `deleted_at IS NULL`、已启用、`next_trigger_at` 非空且已到期的 Job，按 `next_trigger_at, id` 升序读取一批，仅返回 `id` 和 `next_trigger_at`。
2. 单次 `LIMIT` 的部署初值为 **1024**，该次查询超时的部署初值为 **5 秒**；不执行后续分页，不跨周期保存游标或本次时间上界。候选查询不加行锁，具体 SQL 见[单批恢复查询](data-contracts.md#trigger-recovery-scan-proposal)。
3. 查询成功后，依次非阻塞 `Offer` 到本任期已有的 Job ID 队列；已接纳的 Job 按原规则合并，拒收新 Job 时立即结束本次，不等待容量、不新增缓冲，也不等待触发事务完成。未投递的候选不跨周期保留。
4. 查询失败或超时则结束本次，不在失败分支重试。下一周期重新读取当时最早到期的候选，不续接旧列表；进度已推进、停用或删除的 Job 按最新事实处理。
5. 查询和提交提示都受 Leader 任期约束，失主即取消查询并停止新投递。查询的短超时上下文只约束这次读取，不能作为已交接工作的父上下文；已入队工作使用原任期上下文和独立的单次 **3 秒**触发处理预算。

**5 秒仅是恢复查询超时，不是本次恢复的总处理预算，也不是固定的错失容忍值。** 每次读取上限与队列容量虽然初值同为 1024，仍是不同作用范围的部署参数。

成功推进后，Job 退出原来最老的积压位置；高频 Job 下次仍可能到期，但按新进度排序。大量头部 Job 持续失败或队列反复满载时，后面的候选可能长期得不到恢复检查。第一版接受这一边界，不承诺严格公平或一分钟恢复完成；不通过恢复扫描自动停用 Job 或改写其进度。此规则只适用于 Job 触发查漏，不替换 Instance／Task 的共同恢复，也不取消已接纳 Job 的队内轮转。

### 手动触发记账 {#manual-trigger-accounting}

手动触发沿用管理 API 的用户鉴权与输入校验，管理 RPC 按既有用例校验后直接调用进程内触发组件，按[手动触发规则](behavior.md#manual-trigger)使用同 Job 的短事务协调，不复用自动触发的计划时间身份：

1. 以 Job 主键等值条件锁定单表单行，读取当前配置与删除状态；Job 不存在或 `deleted_at` 非空时返回不存在，不继续查重。确认未删除后，再用下一条 SELECT 核对同 Job、同 `request_id` 是否已经创建 Instance。
2. 已创建且请求内容一致时，返回原 Instance ID；请求内容冲突则拒绝。不再对原 Instance 重新做创建阻塞检查，也不因原实例已终态或 Job 参数已修改而创建第二轮。
3. 尚未创建时，校验当前创建条件，允许 Job 停用；按当前阻塞策略检查集群中同 Job 的未结束 Instance。被阻塞则明确拒绝，不保存一个等待自动解除的请求。
4. 创建新的待开始 Instance，同事务保存手动请求身份、请求内容比较所需事实和本轮执行配置；当次参数覆盖只作用于本轮，不更新 Job 或 `next_trigger_at`。
5. 收到提交成功确认后返回 Instance ID；后续推进按持久化 Instance 接续，不在创建事务内派发 RPC，也不等待业务执行。

部分唯一索引按 `(job_id, request_id)` 保护手动成功创建，与自动触发约束分开。UUID、覆盖标记及快照参数比较按[字段契约](data-contracts.md#execution-config-field-draft)执行：入口先校验覆盖组合，合法覆盖字符串去首尾空白后用于保存及比较。取得 Job 锁后另发 SELECT 查重；指定手动身份的 INSERT 冲突未返回行时，再用下一条 SELECT 读取原记录并比较，不以无变化 UPDATE 换取旧 ID。冲突后仍查不到原记录时返回可重试的不确定结果，不在事务内无限循环；完整规则见[已确认的触发持久化协议](data-contracts.md#trigger-transaction-proposal)。输入及错误语义按[已定管理契约](data-contracts.md#job-input-query-proposal)落实，不建立独立请求表，也不因请求去重增加 Redis 锁或请求队列。

提交结果不明时保留“不确定”的反馈，调用方用原请求号重入核对，不盲目新建。尚无成功记录时，重试可能按此时的配置及阻塞条件创建；明确拒绝不永久留痕，响应丢失后再次到达也不保证重放第一次拒绝。Job 已逻辑删除时，即使原 Instance 仍保留，创建入口也返回 Job 不存在，原 Instance 仍可按 ID 查询；该响应不证明原请求未执行。历史记录被清理后不保证原号仍能查重，清理与请求重试的实现边界在持久化及管理契约中衔接。

该入口只同步确认创建事实，不改变 Task 回报的异步接收协议，不启动整轮执行倒计时，也不因客户端未收到响应取消已经提交的 Instance。

### Job 逻辑删除事务 {#job-deletion-transaction}

删除沿用管理 API 的用户鉴权，管理 RPC 完成既有输入与用例校验后，在一个短事务中执行：

1. 通过 Job 主键等值条件单独锁定一行，读取 `deleted_at` 与启停状态；不存在或已删除的记录不进入后续删除流程，已启用则拒绝删除。
2. 确认未删除且停用后，另发一条 `EXISTS` 查询，检查同 Job 是否存在 `WAITING`、`RUNNING` 或 `STOPPING` Instance。活跃 Instance 部分索引及查询须同步包含 `status = 6`，不拉取历史列表、不锁住全部 Instance，也不按 Task 逐条查询。存在未结束轮次时拒绝。
3. 满足条件时通过 GORM `Delete` 保存 `deleted_at` 删除时间，沿用 System 行为不额外补写 `updated_at`；保留原停用状态及 `next_trigger_at`，不物理移除 Job 行，不改写 Instance／Task。
4. 提交后才按已有机制发送 etcd 配置提示；通知失败仍由分钟核对补齐，不在事务中进行外部 I/O。

删除与手动／自动创建、启用和编辑在同一 Job 行上协调。必须先取得 Job 锁，再发活跃 Instance 查询，以使用 `READ COMMITTED` 下锁后的新语句快照：并发创建先提交时，删除能看到其待开始／运行中 Instance 而拒绝；删除先提交时，后续创建、编辑或启用看到删除标记而拒绝。检查时仍活跃、随后恰好结束的轮次允许使本次删除被保守拒绝，不要求每次 Instance 结束反向锁 Job。

删除只改变定义的可用性，不是停止执行或清理历史。所有 Instance／Task 继续保留；`STOPPING` 尚有数据库处理工作，必须继续阻止删除。恢复不依赖普通 Job 查询可见，历史查询基于 Instance 快照，显式只读关联已删除 Job 时只能取得删除时的最后定义，不能把它作为本轮执行配置。规则及用户可见边界见[Job 逻辑删除](behavior.md#job-deletion)，验收见[删除专项](verification.md#job-deletion-checks)。

### 切主与配置变更边界 {#leader-config-boundary}

**第一版不增加数据库全局任期锁。发现失主后取消该任期的本地工作；残留触发必须按数据库中的最新 Job 重新判断，接受切主交界处旧任期的合法事务提交。** etcd 选主控制正常触发来源，Job 短事务保护持久化记账；两者不构成“新 Leader 当选后，旧节点一笔事务也不能提交”的保证。

#### 每次选主使用独立的本地上下文

每次当选创建新的 `leaderCtx`，用于该任期的 Cron 触发处理、配置同步、触发恢复和触发记账数据库操作。发现失去 Leader 资格或无法确认资格有效时，取消该上下文并停止安排新工作；待处理工作也不得脱离原任期继续启动。相同进程再次当选时使用新上下文，不能只检查一个重新变为 `true` 的 `isLeader`，让上个任期的工作复活。

停止 robfig 不能终止已经启动的回调；取消 Context 也不能证明在途数据库事务一定回滚。取消信号继续传递至数据库操作，但提交结果仍按持久化事实处理，不因取消而重放旧 INSERT。不承诺从 etcd 租约失效起固定几秒内所有旧动作消失，也不承诺只残留一笔事务。

已有 Instance／Task 的正常推进、派发与回报属于对等节点职责，不使用 `leaderCtx` 控制其生命周期。失主不取消这些合法工作，仍须满足各自执行权与终态规则。[RUNNING Instance 统一复核](#instance-recheck-direction)和 [STOPPING 恢复](#stopping-recovery)仅将周期候选发现归于 Leader 任期：失主取消查询并停止新投递；已交给进程级检查或后台处理组件的提示不随任期清空，不把查询上下文作为其处理上下文。

#### 旧回调只提示检查 Job

触发回调携带 Job ID 作为检查提示，不以旧 Cron、旧启停状态、旧参数或扫描时的 `next_trigger_at` 直接创建 Instance。进入[同 Job 短事务](#trigger-accounting)后，重读最新配置、状态及进度，用锁后读取的调度进程时间应用到期与错失规则，并按当前持久化事实判断阻塞。

例如 A 失主后仍有一笔在途触发事务，B 已当选并检查同一个 Job。A 若按当前数据库事实合法创建本轮 Instance 并推进进度，B 随后取得锁就按新进度处理，不再用旧值重复创建。若 A 的事务最终回滚，B 取得锁后可按原进度判断。接受哪个节点完成这次合法记账，不等于允许旧节点凭过期快照授权触发。

#### 管理变更与触发协调

编辑、启停和删除 Job 与触发记账在同一 Job 行上协调，以成功提交的顺序决定后续处理。编辑只允许未删除且停用，状态检查与保存须和启用协调，不能凭过期快照更新已启用或已删除 Job；启用时依据未删除的当前配置原子保存新触发时间。删除按[单行锁后校验并标记](#job-deletion-transaction)执行；普通更新利用同一行的写入互斥，涉及并发读改写时才按仓库规范使用主键单行显式锁，不把普通 CRUD 全部改成 `FOR UPDATE`。

| 已提交的先后顺序 | 后续行为 |
| --- | --- |
| 停用或删除先提交，触发随后检查 | 看到已停用或已删除，不创建自动触发的 Instance；内存规则尚未移除也不能绕过检查 |
| 触发先提交，随后停用 | 已创建 Instance 保留，停用不追溯取消该轮；如需停止，走 Instance 停止入口 |
| 停用状态完成编辑，尚未重新启用，旧回调随后检查 | 看到停用就不创建 Instance，不能因规则已修改而恢复自动触发 |
| 编辑后重新启用已提交，旧回调随后检查 | 按最新启用状态、当前配置和启用时重算的进度判断，不沿用旧回调携带的规则、参数或时间 |

不在触发事务中查询 etcd 或执行其他外部 I/O，也不增加跨所有 Job 的数据库任期锁。只读一次任期值再比较并不能排除检查后切主；第一版不引入这一额外协调链路，接受上述在途提交边界。

配置通知采用 etcd Watch 加每 1 分钟数据库核对；串行加载、差异应用、监听衔接与任期隔离按下节执行，不要求每次触发携带配置版本作为授权依据。编辑与启用的进度规则已确认，Job 逻辑删除不清理已有 Instance／Task；本轮执行及恢复继续使用创建时保存的配置，不依赖当前 Job 可见。

### Leader 任期生命周期 {#leader-runtime-lifecycle}

**任期资源独立创建、完整退出后再参选；进程资源跨任期复用。** 这条规则防止反复切主累积 Cron、队列和工作协程，不要求其他机器等待旧节点清理完才接任。

| 生命周期 | 管理的资源 | 退出边界 |
| --- | --- | --- |
| 调度进程 | 数据库连接、Instance 创建并发额度、对等 Instance／Task 推进、派发及回报组件 | 不随失主销毁，也不等待业务执行完成才清理本地任期 |
| 一次 Leader 任期 | 独立 `leaderCtx`、Cron、Job 合并队列与自动工作协程、配置工作协程、Watch、触发恢复循环及 Instance 周期发现驱动，后者分别发现 RUNNING 与 STOPPING 候选 | 失主后停止入口、取消并等待本任期工作退出，不复用到下一任期；各分支临时游标丢弃，已接纳的进程级检查与后台处理不随任期销毁 |

#### 启动与首次装载

先准备好本任期的有界队列与消费能力，再启动配置核对、监听及独立触发恢复。Cron 初始保持未启动；完整读取启用规则后，在未运行的 Cron 中批量注册有效规则，再启动并确认实际初始化完成，最后提交注册后的到期检查。这样避免首次装载大量规则时，边运行边逐条添加导致反复排序。

`Start()` 返回不代表 Cron 已完成全部条目的下一次时间计算。首次启动和后续热更新都须在整批应用完成后确认一次，再提交新增／替换规则的到期检查；具体顺序见[配置加载流程](#job-config-reload)。合法空配置可以启动空 Cron；单条非法规则继续隔离，不阻止其余规则生效。

首次查库失败时 Cron 不启动，但配置入口、分钟核对和独立触发恢复继续运行。后续成功时按同一首次装载路径启动，不把恢复检查串在加载成功之后。整个过程不写入或重置 `Job.next_trigger_at`，也不承诺切主后的所有规则都能在 5 秒内恢复触发。

#### 失主与资源释放

1. 关闭本任期入口，取消 `leaderCtx`，停止接纳和启动新的自动工作。
2. 停止 Cron、Watch、配置核对、Job 触发恢复及 RUNNING／STOPPING 候选发现等任期工作来源；丢弃旧任期的 Job 提示，不在失主后排空执行旧触发队列。已接纳到进程级检查或后台处理组件的提示按原数据库协议处理，不因来源是旧 Leader 就清空。
3. 等待本任期已启动的短操作、回调和工作协程退出，再释放引用。并发额度仍覆盖实际在途操作，不能先归还额度、再将旧操作留给脱离管理的协程。
4. 本地旧任期清理完成后，才能重新参选；再次当选使用新任期对象，但复用进程级创建额度。

启动、配置应用和停止必须协调，防止加载迟到返回后重新启动已停止的 Cron。robfig 的 `Stop()` 不会取消已经启动的回调，其返回的等待 Context 也不覆盖 DogX 自己的数据库工作协程，不能代替整套任期退出管理。

Go 不能强制终止任意协程。清理异常卡住时，本机保持不重新参选并记录错误，不能通过不断创建新任期掩盖；其他机器仍可接任，必要时由运维重启旧进程。本规则不另设固定清理秒数或自动强杀机制。

取消不证明在途事务回滚，继续接受[旧任期合法提交](#leader-config-boundary)。丢弃提示不推进数据库进度，后续由新 Leader 按持久化事实恢复；对等推进和手动请求不被任期上下文一并取消。对应场景见[任期生命周期验收](verification.md#leader-runtime-checks)。

### etcd 选主与配置通知接入 {#etcd-integration}

**选主采用官方 `concurrency.Session + Election`；配置通知使用一个持久标记，失败由既有分钟核对兜底。** 两者共用 etcd 基础设施，但键空间和生命周期分开，不增加可靠消息队列或每 Job 分布式锁。

#### 选主会话与租约

使用项目当前依赖的 etcd client/v3 v3.5.21。租约 TTL 的部署初值为 **15 秒**，必须校验为正值；这是 DogX 的选择，官方 Session 默认值为 60 秒。续租交给官方组件，等待当选使用候选生命周期上下文，不套触发事务或普通短请求的超时。

会话结束或主动退出后，关闭任期入口并按[生命周期规则](#leader-runtime-lifecycle)清理。旧工作完整退出后才能重新参选；会话建立或竞选失败采用退避，不不断叠加会话或后台协程。普通可恢复网络故障优先由客户端处理，不能将一次请求失败直接等同于租约失效。

`Session.Done()` 表示租约已不再续约、已过期或会话已被孤立；当选返回后仍须检查会话及当前生命周期没有结束，才安装 Leader 运行资源。选主不提供数据库提交硬隔离，旧在途合法事务仍按同 Job 短事务协调。

15 秒不是接任时限，更不保证赶上 5 秒错失容忍。接任还受故障检测、etcd 可用性、选举及规则装载影响；期间遗漏沿用既定忽略或执行一次策略，不因采用租约而承诺每轮都能补跑。

#### 键空间与访问权限

同一逻辑调度集群的副本配置统一前缀，组件集中维护固定后缀。例如：

| 用途 | 键或范围 | 生命周期 |
| --- | --- | --- |
| Leader 选主 | `/dogx/<cluster>/scheduler/election/` | 官方 Election 管理候选键，绑定选主租约 |
| Job 配置变更标记 | `/dogx/<cluster>/scheduler/job-config-changed` | 普通持久键，不挂 Leader 租约，不设置 TTL |

不同环境、不同调度集群隔离前缀，不能让连接不同业务数据库的集群误用同一范围。通知值固定为 `reload`；每次 Put 都会推进 etcd revision 并产生事件，不额外读取、自增或生成随机版本，监听方也不能因为值相同就忽略事件。

选主范围仅允许调度服务访问和维护；通知由负责管理保存的后端写入，Leader 读取和监听。执行器无权操作这些范围，etcd 认证独立于组 Token。部署按实际进程职责授权；etcd 原生写权限也允许删除，不能将其描述成仅允许 Put。

#### 提交后的通知预算

管理事务提交成功后，在当前请求中调用一次标记 Put，最多使用 **1 秒**总预算，并服从更短的上游剩余期限；上游已经取消时可以跳过。应用不另加业务重试，不为每次保存派生后台协程或建立通知队列；客户端自身可能重试，不能把“一次调用”解释成恰好一个网络请求。

通知失败记录日志和指标，不回滚数据库，也不把已提交保存主动改报为保存失败；仍由每分钟配置核对补发现。上游超时或连接断开时，不能保证客户端收到成功响应。通知成功仅说明标记已写入，不证明 Leader 已加载，更不证明首轮已执行。

#### 监听恢复与 I/O 边界

首次或重建时，精确读取标记键，以响应头的 revision 为 `R`，从 `R + 1` Watch，再发出一次配置核对信号；键不存在时也使用响应头 revision，不依赖键自身的版本。Put、Delete 均只表示需要核对，删除标记不等于删除 Job。

可恢复的 Watch 连接故障优先交给官方客户端重连。监听关闭、历史压缩等需要应用重建时，退出旧监听后重建并重新核对；失败采用从 **1 秒增长至最多 30 秒、带随机抖动**的内部退避，不在已有 Watch 仍恢复时再叠加另一套监听。任期结束须取消相关上下文；监听故障不阻断仍有资格的 Leader 的分钟配置核对。

| 操作 | 初始预算 | 约束 |
| --- | --- | --- |
| 主动发起的普通短 etcd 请求 | 5 秒 | 如建租约、读通知位置及主动退选；更短上游期限优先 |
| 配置数据库完整读取 | 5 秒 | 仅该次读取的预算；失败不应用半批结果，不套触发处理的 3 秒预算 |
| 管理提交后的通知写入 | 1 秒 | 上述单次应用调用的总预算，不额外业务重试 |
| 等待当选、持续续租、Watch | 生命周期上下文 | 不套 3 秒或 5 秒短超时；退出由相应生命周期取消 |

这些是实现初值，不增加 Job 页面字段，也不是整个组件的固定退出时限。短建租约请求与长会话续租的上下文必须分开，不能把 5 秒上下文直接作为整个 Session 的生命周期；官方 Campaign 内部取消清理同样不能被宣称保证在短请求预算内结束。具体库行为见[接入依据](references.md#etcd-integration-evidence)，故障要求见[etcd 接入验收](verification.md#etcd-integration-checks)。

### 配置加载与重载 {#job-config-reload}

**每个 Leader 任期使用一个串行配置工作协程，完整读取启用 Job 的轻量配置后只应用差异；已有 Cron 正常触发不随加载暂停。** 配置同步不推进 `Job.next_trigger_at`，也不替代独立的每分钟触发恢复。

#### 通知与首次加载

一个调度集群维护一个 etcd 配置变更标记，管理事务提交后更新标记，提示 Leader 重新核对 PostgreSQL。不保存完整 Job 配置，不为每个 Job 创建监听，也不增加配置版本表；键、权限、发布失败反馈与预算按[etcd 接入约定](#etcd-integration)执行。

新任期按[任期生命周期](#leader-runtime-lifecycle)创建独立资源，Cron 初始不运行；配置工作协程及一个待核对信号先就绪。接任、etcd 通知、每分钟核对和 Watch 重建完成都使用同一配置入口。分钟核对从任期开始运行，不能以首次加载成功为启动前提。

首次建立或重建监听时，先读取 etcd 当前 revision `R`，从 `R + 1` 衔接 Watch，再安排一次数据库核对。读取与监听之间发生的标记变更可在历史仍保留时被接收；历史压缩导致无法续接时，重新取得当前位置、建立监听并重新核对，不要求逐条回放全部旧配置。revision 只表示 etcd 监听位置，不是 PostgreSQL 的 Job 版本，也不改变数据库与通知之间的双写窗口。

Watch 故障不能单独阻塞配置工作协程及分钟核对；是否还允许运行，由已有 Leader 资格控制决定。确认失主或无法确认资格有效时，按任期边界停止新工作，不因配置兜底而绕过选主。

#### 串行核对与差异应用

待核对信号容量为 1，只表示“还需核对”，不是变更事件历史。工作协程先取走信号，再读库和应用；处理期间的新提示可以留下下一轮信号，结束时不能将它清掉。连续提示可以合并，但不通过不断延长等待来推迟已经安排的核对，也不为每条通知新建协程或排队项。

每次从 PostgreSQL 主库用一次查询读取全部未删除且启用 Job 的 ID、Cron 等定时注册字段，明确包含 `deleted_at IS NULL`，不逐 Job 补查，不读取业务参数、Instance 或 Task。只在查询完整成功后应用结果，不能把读取失败或半批结果当成“剩余 Job 已删除”。合法空结果则表示当前没有有效启用规则。

| 数据库与当前内存的差异 | 应用动作 |
| --- | --- |
| 新出现且规则有效 | 注册新规则 |
| 同一 Job 的 Cron 等定时字段变化 | 解析新规则后替换旧规则 |
| 已停用或删除，不再出现在完整结果中 | 移除该 Job 的内存规则 |
| 定时注册字段未变化 | 保持原规则，不删除再注册 |
| 单个 Job 的 Cron 解析无效 | 移除该 Job 残留的旧规则并记录错误，继续处理其他有效 Job；不自动修改数据库启停状态 |

`next_trigger_at` 是运行进度，不参与规则差异比较，不能因每轮进度推进而重建 Cron。只修改名称等非定时字段也不要求重建；触发时仍在同 Job 事务中读取当前配置。核对成本随启用规则数量增长，当前按几百条规则采用全量轻量读取与内存比较，容量由既定基准验证。

同一任期不并发执行多次配置加载，因此不会出现新加载先应用、旧加载后返回覆盖它的顺序倒置。读库期间又有配置提交仍可能产生短暂延迟，后续提示或分钟核对继续收敛；内存快照不是数据库触发授权。

#### 注册后检查到期

首次装载时，完整读取启用规则，在未启动的 Cron 中注册全部有效规则，再启动 Cron；热加载时则向已运行的 Cron 应用本次差异。两条路径都在整批应用后确认 Cron 已完成初始化或接收新增／替换条目，再将这些 Job ID 提交给[统一触发入口](#trigger-accounting)检查一次。未变化的规则不额外检查。

robfig v3.0.1 的 `Start()` 只启动运行协程；热加载的添加调用返回，也可能早于接收方完成该条目的下一次时间计算。因此，仅等待调用返回不能充当初始化确认。例如检查时还是 09:59:59.9，而 Cron 在 10:00:00.1 才计算未来时间，首轮可能要等分钟恢复才发现。

适配层可在协调好生命周期的前提下，使用运行中 `Entries()` 的一次快照往返确认本批已处理；每批一次，不逐条复制全量条目。这是利用运行循环的同步行为，不是库提供了独立就绪接口。确认过程与停止须协调，不能把停止后直接读取内存条目当成运行就绪；不修改第三方库，不增加零值 `Next` 巡检或自动重建。

例如首轮是 10:00，读取配置时为 09:59:59，注册完成时已到 10:00:01。robfig 新规则从注册时刻向后计算，不能依靠它补回过去的 10:00；注册后的检查读取原 `next_trigger_at`，此时迟到 1 秒，按正常规则处理。若已超过 5 秒，则应用错失策略。尚未到期就退出，不表示启用后强制立即执行，也不重新初始化首轮时间。

检查与正常 Cron 回调、恢复检查并发时，共用同 Job 短事务与自动触发身份。配置工作协程不逐个等待触发事务，提交检查受统一触发入口的容量限制；无法及时接纳或处理时仍由独立的恢复检查兜底，不增加专用无界队列。首次加载可能产生一批新增规则，不能承诺所有注册后检查都在 5 秒内完成；接纳、合并及队满处理遵守[触发容量与过载](#trigger-capacity)，采用[1024／32／3 秒部署初值](#trigger-runtime-defaults)。

#### 失败与任期退出

| 情况 | 处理规则 |
| --- | --- |
| 整次查询失败 | 保留已有规则，记录错误，等待下一次通知或分钟核对；不因失败立即自行唤醒形成重试空转 |
| 首次加载失败 | Cron 保持未启动，保留后续核对入口与分钟周期；独立的触发恢复继续，不停止整个加载流程 |
| Watch 中断或历史不可续接 | 可恢复连接故障由客户端处理；需要应用重建时退避重建并核对数据库，不叠加活跃监听，不将通知缺口解释为没有配置变化 |
| 加载尚未返回时失主 | 取消原任期工作，丢弃迟到加载结果，不再安装新规则或发起注册后检查 |
| 同一进程再次当选 | 本地旧任期清理完成后才重新参选；当选后使用新任期运行对象，旧工作不复用新任期的 Cron 或规则映射 |

停止旧任期 Cron 仍不证明已发起回调或数据库事务全部撤销，继续遵守[合法在途提交边界](#leader-config-boundary)。对等 Instance／Task 推进不随配置工作协程退出而取消。

本节确认的是 Job 规则同步流程，不将它扩展为执行器组、Token 缓存的同步协议。Cron 异常按[已定简化规则](behavior.md#cron-errors)处理，不增加检查内存零值 `Next` 并自动重建的分支。通知键、权限、I/O 预算及重连遵守[etcd 接入约定](#etcd-integration)；触发处理采用[已定部署初值](#trigger-runtime-defaults)，其 3 秒预算不直接套用于配置加载。异常时钟遵守[运维边界](operations.md#scheduler-timezone)。对应验证见[配置同步验收](verification.md#job-config-sync-checks)。

## 5.2 对等节点与推进执行权 {#advancement}

Leader 负责长期规则触发、接任时和每 1 分钟的 Job 触发进度恢复，以及每 2 分钟分别发现 [RUNNING 复核](#instance-recheck-direction)与 [STOPPING 恢复](#stopping-recovery)候选，不负责全局所有 Task 的逐个派发。已经创建的 Instance／Task 由包括 Leader 在内的所有调度节点按自身空闲容量取得必要执行权并正常推进，不向 Leader 请求分配。准备推进、结果接收和收尾创建可以发生在不同节点；正常结果提交后立即提示本节点检查，停止决定提交后立即进行本地有界处理，不等待 Leader 或周期扫描。

例如 A 为 Leader 并创建 I1，B 取得准备推进权、派发准备 Task，并在结果持久化后生成分片；分片结果可以由 C 接收，满足条件时由候选节点唯一创建 PostTask。后续步骤不要求返回 B。A 故障后新 Leader 接替触发和 RUNNING／STOPPING 候选发现，执行协调仍按持久化工作和执行尝试恢复，不接管一个持续到终态的 Instance 负责人，也不接收其他节点转发的正常检查请求。

“对等、无状态”表示持久化状态与恢复不绑定某个固定节点，不是没有连接、缓存、在途 RPC 或临时回报队列，也不是承诺内存结果不会丢失。结果尚未落库时，进程退出可能丢失其唯一副本；恢复结算不能依赖原节点的本地文件。各节点仍须识别：

- 当前获准进行的推进或派发动作。
- 仍然有效的远端执行尝试。
- 已失效的协调动作与迟到结果。
- 可以恢复的平台步骤，以及成功结果已持久化、不能因平台推进失败再次调用的业务步骤。

取得推进权不代表可以重跑本轮全部 Task。etcd 选主限定触发及上述统一复核发现的 Leader 范围，不能替代生成、派发和收尾创建的防重。Task 发送前通过 PostgreSQL 条件写入登记当前尝试，不增加每 Task 的 Redis 或 etcd 锁。新尝试登记与父 Instance 终态通过下述单行短事务协调，结果回报不统一锁父；生成及其他推进权的持久化和恢复协议仍待设计。

## 5.3 有界本地派发与持续补充 {#bounded-dispatch}

普通 Task 按[主路径](#ordinary-flow)合并首次启动和执行信息；分片 Task 则先保存，确认完整生成后，由生成节点直接启动本地有界派发。节点已经知道刚生成的 Task，不需要再次扫描发现它们，也不等待其他节点领取。较大 Instance 按小批量补充，必要时按 Instance 分页读取剩余工作，不把全部 Task 无限制装入内存。准备结果不要求返回原派发节点；完成生成的节点负责当前本地派发，不因此取得整轮固定归属。

节点只在有容量时取得工作，空闲且无工作时退避，避免大量预领后长期排队。本地派发队列、并发派发数、同时准备的 Instance 数量都必须有界；队列满时暂停补充，已提交工作仍留在共享持久化状态中。

**本地派发采用有界队列和固定数量工作协程，不在这套机制之外另建“槽位对象管理”。** 队列限制待处理工作的积压量，固定工作协程限制同时进行的派发处理；文中的“派发槽位”仅指可用的本地派发并发名额，不是数据库字段、分布式锁或执行器业务线程。

**每个调度进程的派发工作协程默认 64 个，通过部署配置调整，不进入 Job 页面。** 工作协程随派发组件启动，空闲时等待队列，处理完一项后继续消费，退出服从[进程停机规则](operations.md#process-shutdown)，不是每派发一次就重新创建。这 64 个并发覆盖发送前数据库处理及等待接单响应，不是执行器业务并发、结果上报并发或整个集群的上限；也不改变触发阶段已定的 Instance 创建并发 32。该值是压测起点，不代表已验证吞吐。

工作协程取出候选后，才按下节协议校验并登记执行尝试，再在明确提交成功后发 RPC、等待接单响应；入队不占用执行机会，也不能仅为排队提前登记。不得取出后为每条工作无限启动 goroutine，或让无界生产协程阻塞着等待入队。本次派发处理结束后继续消费，不等待远端业务执行完成；队满则暂停补充，未接纳工作保留在数据库，由后续推进或既有恢复接续。

普通路径采用[首次开始与首次执行信息同事务保存](#ordinary-flow)。这不取消分片路径按 Instance 有界小批量登记，不要求每条分片 Task 单独开事务；批内发送同样不能绕过派发并发上限。[排队、并发与满载处理](#capacity-model)已确定共享派发、小批轮转和有处理余量时持续补充，不按正常／恢复来源硬切份额；[派发供给参数](#dispatch-supply-defaults)已确定等待候选总量、查询页、补查周期及轮转初值，登记批量仍须随完整分片协议落实。

恢复发现的实际派发复用上述工作协程，不另设恢复专用派发池；候选扫描、Instance 完成检查及后台状态收敛不占用这 64 个派发协程。这里不排除已定的发送前授权、ACK 绑定和 BUSY 返还写库，它们仍属于单次派发处理。完整职责划分见[恢复资源分工](#recovery-resources)。

公平性需要覆盖两个维度：

- 多个 Instance 之间，避免一个大实例长期占满派发能力。
- 同一 Task 模型的不同阶段之间，避免海量分片长期挤占准备和收尾。

派发候选按 Instance 小批轮转，涵盖准备、分片和收尾等合法工作；只有一个 Instance 有可派发工作时，可充分使用空闲派发能力，不设置每个 Instance 的固定派发份额。轮转须覆盖候选补充，不能先让大 Instance 填满全部缓冲，再声称已解决公平性。每次先补充最多 8 项后让其他已发现 Instance 获得补充机会，只有一个 Instance 时可继续补充；这不是登记批量，也不承诺跨节点严格公平或数据库深处的候选立即得到处理。具体编码组织仍须结合完整流程落实。单个大 Instance 的初始派发仍受当前派发节点能力限制；其他节点可安全取得待处理工作继续补充，但这不等于单轮派发可以无限横向扩展。

派发 RPC 等待的是**接收确认**，不是业务执行结束；接收确认返回后可以释放本地派发槽位并补充下一批，不必等业务完成。执行器必须维护自身执行并发和队列上限，接收失败、超时及重试不能形成无界堆积。调度器有界派发不能替代执行器容量保护。

### 排队、并发与满载处理 {#capacity-model}

**2026-10-28 已通过并修订，尚未实现。** 本节用队列长度、处理并发、每批条数及队满行为说明运行规则，不将“容量控制”当作需要额外开发的组件。执行器采用下述已确认流程；具体 Go 并发原语、组件内部结构及尚未确认的参数初值仍结合完整需求确定，解释代码和数字示例不构成实现约束。

#### 设计原则

1. **兼顾正常处理效率、过载保护和可维护性。** 在满足正确性与已定故障语义的前提下，优先选择简单、常见、容易验证的方案。新增跨阶段协调、动态配额或专门控制组件，须说明实际收益以及简单方案不能满足的场景。
2. **在主要入口、慢操作和积压处设置保护。** 分别明确业务、RPC 和数据库处理并发，以及主要队列可等待的条数；内部短步骤不默认各建队列、处理池、计数器或配置项。不能每增加一个 Job 或 Instance，就叠加一套不受进程约束的业务处理能力。
3. **用实际持有位置解释资源规模。** 排队、处理中、在途、重试和交接等待都要纳入分析；允许通过队列长度、有限并发和有界批次推导整体积压，不要求跨接单、业务和回报维护统一总量或共用额度。不能把积压藏在无界等待协程、旁路队列或不断复制的对象中。
4. **允许拥塞向上游传递。** 下游变慢时，可以依职责暂停补充、等待交接或拒绝新接纳，不要求每个阶段永不等待。过载处理须遵守各类工作已定的确认和故障协议，不能把队满解释为任意丢弃已接收结果。
5. **按职责协作，不机械拆分执行设施。** 长业务不能让回报和取消完全得不到处理机会；职责独立不要求每个内部步骤单独建池或各阶段吞吐互不影响。异步回报不承诺本地交接永不等待，数据库事务不得包含 RPC、交接等待或重试退避。
6. **结合 Go 的完整流程选择实现，以端到端效果验证。** channel、受控启动的 goroutine、固定消费者等按实际需要选择，不把一种组织形式推广为全项目模板。验收关注有效执行吞吐、结果落库速度、排队延迟、故障恢复及资源占用，不能仅凭 ACK 更快或提前执行了更多业务判断方案更好。

#### 调度端共享与持续补充

- 正常产生与补查发现的可派发工作共用既有派发能力，不按来源预留固定比例，不另建恢复专用派发池。按 Instance 小批补充与轮转，只有一个 Instance 有工作时允许充分利用空闲能力。
- 有积压且仍有处理能力时持续补充，不在每批之后强制等待一个扫描周期；没有候选、等待队列满或发生故障时，分别等待后续发现、暂停补充或按原规则退避。父 NOWAIT 冲突及技术失败仍按[派发竞争规则](#dispatch-contention)退出，不能借持续消费立即重抢。
- 入队不登记执行尝试，不能预先登记全部积压再等待发送；登记与发送继续遵守已有并发、批量和提交确认协议。未接纳的持久化工作保留数据库依据。
- 上述持续供给不取消 Job、RUNNING 和 STOPPING 已定的低频扫描周期、门槛及独立预算，也不把候选页大小当作一趟吞吐上限。各类候选的剩余周期与参数继续按原范围细化。

#### 执行器接单、执行与结果交接 {#executor-processing-flow}

实现状态：2026-11-04 公共 `pkg/jobexecutor.Runtime` 与 reporter 已落实本节流程，真实普通处理器结果已通过 RPC／PostgreSQL 组件联测；System 内嵌接线和调度端完整派发、父完成仍待实现，详见[执行器运行记录](ordinary-readiness-review.md#ordinary-executor-runtime-progress)。四阶段调用能力不代表分片生成、持久化及阶段推进已实现。

执行器采用以下流程：

```text
接单
  ↓
有界业务等待队列
  ↓
有限并发的业务处理
  ↓
有界结果缓冲（保留待发、等待重试和在途结果）
  ↓
独立、有限并发的单次回报 RPC
```

普通、准备、分片和收尾共用进程内的业务等待队列和业务处理并发，不为每个 Job 或 Instance 独立增加一套处理者，也不默认为每轮预留固定份额。2026-10-28 已通过[业务部署初值](#executor-business-defaults)：每个执行器进程默认业务处理并发 32、等待队列 128，均可通过部署配置调整。[回报机制与初值](#reporting-defaults)另已通过：结果缓冲默认保留 256 条，包含待首次发送、等待重试和在途记录；同时进行的回报 RPC 默认 16 个。各值分别约束所属阶段，不是接单到回报结束的统一额度。

| 环节 | 处理规则 |
| --- | --- |
| 新请求接单 | 通过认证、报文和能力校验，并处理活动期防重后，成功交给有界业务队列才返回 ACK；队列不能接纳时，对确实未接单、未入队、未执行的请求返回 BUSY，不新增无限等待者。重复活动尝试返回既有接单结果；停机等其他拒绝沿用原契约 |
| 领取与执行业务 | 处理并发受进程配置约束，按既定截止和取消规则启动处理器；排队不重置整轮期限，不能仅因已经 ACK 就忽略启动前的取消或到期检查 |
| 业务结束与交接 | 业务实际退出即清理活动防重记录。处理者把当前结果交给回报缓冲；缓冲满时持有这一份结果等待交接，期间不领取下一项，也不另外启动业务绕过并发限制。此时业务已经结束，等待的是本地交接 |
| 结果回报 | 回报组件保留原记录，按可发送时间安排有限并发的单次 RPC。调用结束即释放发送并发；可重试失败只更新该记录的下次发送时间，不让发送者等待退避，也不重新争抢缓冲位置。ACK、永久错误或尝试耗尽才释放结果 |
| 下游变慢与恢复 | 回报缓冲逐渐积满，使业务处理者等待交接，随后业务等待队列也可能积满并拒绝新接单。已有结果的完成处理和重试安排继续运行；结果结束并释放位置后，等待者完成交接。全部记录等待重试时允许发送者空闲而新结果仍等待，服务恢复也不跳过剩余退避；不另设跨阶段总量计数或高低水位控制器 |

回报组件中的每条结果从交接成功到本条回报结束始终保留原位置，发送不会提前释放位置；在途及等待重试不是缓冲以外的另一份结果积压。业务处理者等待交接的结果尚未进入该缓冲，每个处理者至多持有当前一份，由有限业务处理并发约束。整体滞留规模由这两处实际保留共同说明，不新增接单到回报结束的统一配额，也不以额外 goroutine 或旁路队列隐藏积压。

ACK 只确认接纳，不承诺业务已开始。活动防重不延长到结果交接完成或回报 ACK，已完成尝试不因此变成长期去重缓存。正在运行的长业务不能被抢占；结果交接等待也可能延长已接纳任务的排队时间，本流程不提供 Instance／阶段的严格公平或立即开始保证。

排队取消仍按[取消契约](data-contracts.md#cancel-response-contract)标记并阻止启动，不因本流程新增每个排队取消都必须回报的义务；取消路径若产生结果，也必须沿用有界交接。运行任务只有实际退出才视为业务结束。停机期间在既有剩余宽限内继续交接与回报，宽限耗尽可结束等待；不能因等待交接延长停机，也不能为晚返回结果创建无界后台处理，见[共享宽限和晚返回保护](operations.md#process-shutdown)。

#### 执行器业务部署初值 {#executor-business-defaults}

**2026-10-28 已通过，2026-11-04 已落实公共 Runtime 配置与处理流程，尚未接入 System 生产配置或压测。** 实际验证见[执行器运行记录](ordinary-readiness-review.md#ordinary-executor-runtime-progress)。以下两个参数按执行器进程配置，普通、准备、分片和收尾共同使用，不按每个 Job／Instance 增加一套，也不进入 Job 管理页面。

| 参数 | 默认值 | 计量范围 |
| --- | --- | --- |
| 业务处理并发 | **32** | 从开始处理一个 Task 到完成该结果交接，占用一个处理位置；包括业务仍运行及业务已结束但等待结果交接的任务 |
| 业务等待队列长度 | **128** | 尚未领取处理的 Task 数量，不包含上述处理中任务；不能接纳新任务时按原契约返回 BUSY，重复活动请求及停机拒绝仍分别处理 |

两者均可通过部署配置调整。例如 20 个任务仍在执行业务、12 个任务已经完成但等待结果交接时，32 个处理位置已经占满，暂不领取下一项。后 12 个任务的业务已经结束，活动防重已清理，不能把交接等待记为业务仍运行；也不能派生替补业务绕过并发限制。仅发出取消信号不能证明业务退出，仍按既定取消和停机规则处理。

32 是 System 首版内嵌部署的适中起点，限制的是业务处理并发，不是固定 32 个操作系统线程。128 用于吸收短时派发突发，不提高长期处理吞吐；在任务耗时相同、下游正常的简化模型中，32 个处理中任务加 128 个等待，队尾约需等待四轮处理时间，这不是实际等待上限。长任务和回报拥堵仍会延长等待，排队不延长 Instance 原截止，启动前继续检查取消和到期。

业务并发 32 与回报 RPC 并发 16 不要求相等，应比较业务结果产生速率与回报接收速率；回报缓冲只吸收暂时差额，持续拥堵按已定交接等待传递压力。现有 System 数据库连接池上限 50 只是验证背景，不能据此推导每个任务恰占一个连接或保证普通 RPC 预留 18 个连接，也不因本项调整现有数据库配置。实现后观察业务等待、实际运行与交接等待、普通 RPC 延迟、数据库连接等待、CPU 和回报积压，验证并校准部署初值，见[排队、并发与满载验收](verification.md#capacity-model-checks)。具体 Go 内部组织仍按完整流程选择，初值不构成性能保证。

#### 职责隔离与拥塞传导

创建 Instance 不等待执行器 RPC，派发不等待远端业务结束；结果保存、Instance 合并检查、后台数据库取消和远端取消沿用各自职责。回报和取消可以独立取得处理机会，业务结束后等待本地结果交接不违反这一分工。独立处理能力不等于数据库、CPU 或网络硬隔离，也不承诺上下游互不影响。

派发等待队列满时暂停补充；执行器业务等待队列满时明确 BUSY，沿用已定机会返还与延期。执行器通过上述结果交接传递压力；调度端结果队列满时拒收，不对未接收结果返回成功。已确认结果的保留、有限回报重试、进程退出损失及取消尽力边界均不改变。

调度端按[结果保存初值](#scheduler-result-defaults)有界保留已接收结果，以有限并发逐条关联读取、条件更新和独立提交。每次保存尝试结束即释放保存能力，失败结果保留原位置等待退避，不占用保存者空等，不重新保留或重放已经明确提交成功的其他结果，也不能无限积攒待重试记录。处理不等待凑批，详见[写库故障处理](#scheduler-result-retention)。

#### 配置边界与待落实事项

主要处理并发、业务队列长度和执行器结果缓冲条数采用部署配置；调度端结果保存已改为逐条独立提交，不再设置结果写库批量上限。其余轮转、补充和退避使用少量集中默认值，不为每个内部步骤增加独立配额。配置须直接说明约束的是排队记录、回报组件全部保留记录、同时进行的调用还是其他职责的每批条数，不能把队列长度命名为全链路待处理总量。[派发供给参数](#dispatch-supply-defaults)的等待候选范围和分页规则、触发创建并发 32、派发并发 64、停止及通知的局部参数保持原口径，不因结果保存粒度调整自动改变。

本节不增加快慢两套派发能力、实时节点负载心跳、自定义负载路由或本地持久消息系统。有限通信预算和退避不能保证故障执行器组完全不影响其他组；原生负载均衡仍可能选中业务队列已满的节点。业务及等待队列按[32／128 初值](#executor-business-defaults)、回报按[已通过参数](#reporting-defaults)、调度端保存按[结果保存初值](#scheduler-result-defaults)验证；其余恢复参数继续落实，并按[排队、并发与满载验收](verification.md#capacity-model-checks)验证吞吐、延迟和资源占用，不据此承诺性能优于其他实现。

### 派发缓冲、候选补充与扫描退避 {#dispatch-supply-defaults}

**2026-10-28 已通过，2026-11-05 已接入普通首次派发与重试供给，实际验证见[实施记录](ordinary-readiness-review.md#ordinary-retry-progress)。** 本节落实调度端的容量初值、候选补充、临时分页与无进展退避，只规定行为及参数，不提前确定新的 Go 并发原语或内部编码结构。正常产生与数据库发现的工作继续共享派发能力，不新增恢复专用派发池或来源固定份额；分片阶段登记及恢复扫描尚未实现。

#### 容量与配置初值

| 项目 | 初值及范围 |
| --- | --- |
| 派发并发 | 每进程 **64**，沿用已批准值，覆盖发送前数据库处理及等待接单响应 |
| 等待候选总量 | 每进程 **256**，包括已查出尚未交给派发处理的临时页、待处理提示等等待候选；不只计算某个队列长度 |
| 单次候选查询 | 最多 **128 条**，实际读取量还受剩余等待候选容量限制 |
| 无工作时补查间隔 | **1 秒**，各节点独立上下浮动 **20%**；无有效进展而暂停的补查也等待该机会 |
| Instance 轮转份额 | 每次先补充最多 **8 项候选**，有其他已发现 Instance 时让出补充机会，只有一个时可继续补充 |
| 无有效进展的连续读取预算 | 最多 **4 页**；仅本轮补查候选产生明确提交成功的新尝试登记，才恢复至 4 页，不累加 |

等待候选与正在处理的工作分开计量，后者另外受 64 个派发并发限制；临时查询页和提示列表不能构成 256 之外的无界积压。重复候选继续按既定身份合并，交接不能让同一工作同时消失在两侧计量之外，也不因保留一个 Instance 提示就允许把该轮全部 Task 搬入内存。候选入队仍不登记尝试或消耗执行机会。

并发、等待容量及补查间隔作为主要部署配置，不进入 Job 页面；分页、轮转和退避使用集中默认值，不为每个内部步骤增设配置。上述初值用于后续验证和调整，不代表已测得吞吐或响应时限。8 项只是补充时让出机会的位置，不是单事务登记批量或每个 Instance 的并发上限；登记批量仍待完整分片协议闭合。

#### 及时派发与持续补充

Instance 创建或分片生成确认提交后，仍及时提示本节点补充派发，不等待一秒周期。数据库补查用于发现 WAITING Instance、到期重试及接续持久化工作；到期重试属于正常到期工作，不能仅因采用查库发现就视为少量异常恢复。

有候选且有容量时继续处理与补充；满载暂停，剩余工作留在数据库。有多个已发现 Instance 时按上述小批份额轮转，轮转覆盖补充机会，不能只轮转一个已被大 Instance 填满的队列。正常来源与补查来源共用同一能力，不预留比例；只有一个 Instance 有工作时允许使用空闲能力。轮转不保证数据库深处候选或各节点之间的严格公平，也不抢占已经运行的业务。

#### 临时分页与暂停接续

WAITING 候选每趟固定 ID 上界并按 `id` 续扫；到期重试每趟固定数据库时间上界并按 `(next_dispatch_at, id)` 续扫。两类候选分别保留本趟位置，不用永久消费水位；具体查询见[候选分页契约](data-contracts.md#dispatch-candidate-pagination)。

只有已经接纳、合并或按既定竞争规则明确跳过的候选才能被临时游标越过。容量不足时停在未接纳处，恢复容量后继续；本地按 Instance 调整处理次序不能使游标跨过尚未交接的候选。竞争失败不使游标回退到第一页，也不能借下一页对同一 Instance 立即重抢。

每趟结束后等待下一次补查，再从头覆盖；低 ID 迟提交、后来到期或此前跳过的持久化工作由后续遍历再次发现。游标只代表本趟候选遍历进度，不证明登记或派发成功。分页不建立跨查询数据库快照，也不替代派发事务重新核验父状态、期限及原尝试。

#### 无有效进展时退避

连续读取最多 4 页仍没有本轮补查候选产生明确提交成功的新尝试登记时，暂停新增补查，等待下一次约一秒的补查机会，保留未完成的本趟位置。预算控制的是查询继续执行的条件，不取消已经接纳的工作，也不阻塞正常提交后的及时派发。

- 候选入队、父 NOWAIT 失败、候选失效、技术失败及提交结果不明都不算有效进展，不刷新读取预算。
- 本轮补查交接的候选明确完成新尝试登记后，可将读取预算恢复到 4 页并继续补充；只恢复，不按成功数量累加，不增加并行扫描趟数。无关的本地正常派发成功不能刷新一条始终竞争失败的补查。
- 暂停后，已交接的补查候选后来明确登记成功，可以提前续扫，但仍须有候选容量；满载时不能因预算恢复而继续读取。
- 扫到末尾仍等待下一次补查，不因最后一页有登记成功就立即从头重查。NOWAIT 同组跳过、不立即重排及技术故障退避规则继续独立生效，不能用成功反馈绕过。

默认值下，全部竞争失败的一次连续补查最多返回 512 条候选，随后退避；512 不是数据库实际访问行数、每秒成功派发上限或整个扫描趟次上限。持续产生有效登记进展时可以继续供给，混合竞争下仍有额外读取和失败事务成本；须验证实际查询计划、候选重复率和登记吞吐。

本节不改变 RUNNING 的两分钟复核、STOPPING 恢复或 Job 触发恢复，不将其并入一秒补查。发送及 ACK 绑定预算已由[派发时间预算](#dispatch-time-budgets)另行确认，[执行器业务初值](#executor-business-defaults)与[回报机制和初值](#reporting-defaults)也已独立通过；登记批量和分片首次可派发查询仍分别待定。对应[供给验收](verification.md#dispatch-supply-checks)是已批准的完整验收要求，普通首次与重试共享供给的实际覆盖见[阶段 4 记录](ordinary-readiness-review.md#ordinary-retry-progress)；分片、恢复及正式负载验证仍待完成，不将局部测试等同于全表验收。

### 单次派发时间预算与确认失败处理 {#dispatch-time-budgets}

**2026-10-28 已通过；2026-10-30 已批准将有限响应保存预算扩展到非 BUSY 明确拒绝。普通首次与重试派发的登记、接单、响应保存及 BUSY 延期已实现，实际覆盖见[普通重试记录](ordinary-readiness-review.md#ordinary-retry-progress)；未知结算与自动观察扫描已接入生产，见[最新记录](ordinary-readiness-review.md#ordinary-unbound-scan-progress)。** 本节共同确定登记、接单等待、响应保存、绑定缺失观察及明确 BUSY 延期的初值；沿用现有状态协议、派发并发和条件写入，不增加同次业务重发、长期响应队列或新的 Go 编码结构。

#### 时间初值与计时起点

| 项目 | 初值 | 起点及适用范围 |
| --- | --- | --- |
| 单次派发处理总预算 | **10 秒** | 工作协程取出候选、开始处理时起算，覆盖登记、必要客户端准备、RPC、响应保存及重试等待；不从候选入队起算 |
| 发送前登记事务预算 | **2 秒** | 包括取得数据库连接、事务内查询与更新及提交确认；不把预算分别重新赋给每条 SQL |
| 接单 RPC 超时 | **3 秒** | 从发起调用开始，只等待接纳响应，不等待业务完成 |
| ACK 绑定、BUSY 或非 BUSY 明确拒绝保存阶段 | **最多 4 秒** | 从开始处理这份响应起算，覆盖保存及失败间隔 |
| 响应保存次数 | **最多 3 次，包含首次** | 仅重做同一原响应的条件写入，不重发 `DispatchTask` |
| 单次响应保存超时 | **1 秒** | 包括该次数据库操作的连接等待和执行等待 |
| 保存失败后的间隔 | **200 毫秒** | 计入保存阶段及总处理预算，不在数据库事务中等待 |
| 无绑定观察期 | **30 秒** | 从数据库 `attempt_registered_at` 起算，不因换节点、重复扫描或保存绑定重试重置 |
| 明确 BUSY 延期 | **5 秒，上下浮动 20%** | 沿用原 SQL，以数据库求值时间计算并保存 `next_dispatch_at`；默认约 4～6 秒 |

各阶段同时受剩余总处理预算和共享停机宽限约束，不在进入下一阶段时重新取得完整总预算。最多三次不保证一定尝试满三次；总预算也不承诺依赖操作或资源必然在第 10 秒全部退出。超时后停止发起新的操作，已经发起的操作须实际退出后才释放仍被占用的并发能力，不能通过另外开启无界后台处理绕过预算。

总预算、接单超时、观察期及 BUSY 延期作为主要部署参数，不进入 Job 页面；细分事务、保存阶段、次数及间隔集中维护，不为每一步增加配置。数值是后续数据库等待和 RPC 延迟验证的起点，不是已测得的恢复时限。所有调度节点的观察期保持一致；调整派发或保存预算时联动检查观察期余量，不由某个节点临时延长数据库中的观察起点。

#### 发送许可与预算耗尽

登记仍须通过既定父行 NOWAIT、数据库时间、父状态、原尝试和执行预算校验；收到明确提交确认后才可发送。登记超时、断连或提交不明时放弃本次发送，不能凭事后读回状态补发。登记虽已确认提交，但发送前总预算耗尽时也放弃发送，按持久化事实进入既有无绑定观察及结算路径，不免费重发或返还机会。

RPC 超时、断连或没有明确答复，不等于执行器未接单；不能推断 BUSY、立即换节点重发同次尝试或直接结束业务。允许已占用机会而业务实际未运行的原有取舍不变。登记和新派发仍须服从整轮授权及截止规则，单次处理预算不延长 Instance 期限。

执行器接纳后的业务 Context 独立于派发 RPC 生命周期，仍受整轮截止和取消控制。3 秒限制接单等待，不是业务执行超时；派发调用返回或超时本身不取消已经接纳的业务。

#### 接单响应的有限保存

有效接纳 ACK 进入[绑定条件更新](data-contracts.md#executor-binding-sql)；明确未接单 BUSY 进入[机会返还与延期条件更新](data-contracts.md#ordinary-busy-settlement)；能够确认未接纳的非 BUSY 拒绝进入[当前尝试结算](data-contracts.md#dispatch-rejection-settlement)。三类响应共用上述有限保存预算，由收到响应的当前派发工作协程直接保存，使用原 Task、原尝试和原响应数据，不增加绑定、待返还或拒绝响应的长期队列。

- 明确保存成功，或无错误但更新零行，立即结束；零行不补查、不宣称本次新增绑定、返还或拒绝结算成功。
- 可恢复数据库故障或提交确认不明，才在上述有限次数和时间内重做同一条件写入；不重发业务，不把保存重试当作新执行机会。
- 耗尽后释放原响应，后续按数据库实际状态继续。不能撤销可能已经提交的绑定、返还或拒绝结算，也不能凭已丢失的 BUSY 响应补返机会。拒绝未落库且仍完全未绑定时，由既有观察结算兜底；接受明确拒绝原因可能未持久化及结算延迟，不凭已经释放的响应重建结论。
- 保存使用独立于已结束接单 RPC 的响应处理上下文，但仍服从原总预算和停机宽限。父 Instance 已进入 STOPPING 时继续按原条件写入规则处理，不恢复父子状态，不因业务 Context 已结束就误用它取消全部元数据保存。

这些是派发响应的有限保存预算，不套用于调度端已经 ACK 的业务结果；后者在可恢复写库故障下仍按[结果保留协议](#scheduler-result-retention)有界保留和退避，不增加按次数或 TTL 丢弃。

#### 观察期与 BUSY 等待

观察从事务内保存的数据库登记时间开始，包含提交确认期间的耗时，不能只按 RPC 与绑定保存阶段相加计算。30 秒给默认正常处理预算留出余量，但极端停顿或写库故障下仍可能出现旧业务正在执行、平台却按结果不确定结算的情况，不证明旧业务已经停止。

到观察期只取得条件结算资格，不使尝试自动失效。绑定或有效结果先保存时不按无绑定处理；仍满足条件时才依原协议关闭尝试，随后是否重试另经预算和父授权检查。扫描等待、数据库状态和处理积压仍影响实际结算时间，不承诺 30 秒恢复；扫描与处理参数已另按[观察到期扫描与结算安排](#unbound-recovery-defaults)确认，不从观察期直接推导。

明确 BUSY 保存约 4～6 秒后的最早派发时间后，结束本次处理并释放已退出工作占用的派发能力，不占住工作协程等待五秒。到期由既有约一秒的候选补查发现，重新取得授权并登记新的尝试。该延期独立于业务失败默认 10 秒重试间隔，不增加 BUSY 次数状态，也不保证下次换节点；重复保存不得刷新已经生效的延期，整轮截止不延长。

#### go-zero 超时衔接及剩余范围

项目采用的 go-zero v1.10.3 中，原生客户端和 Server 的默认超时均为 2000 毫秒。实现 3 秒接单预算时，须协调原生客户端配置／调用超时与执行器 Server 方法超时，不能只给外层 Context 设置三秒而被内部默认两秒提前截断。现有 System 普通 RPC 与 Job 管理入口保持各自职责；不新增重复的 RPC 配置类型或自定义通信包装来替代原生能力。

执行器业务并发与等待队列已由[业务初值](#executor-business-defaults)、回报缓冲、发送并发及重传参数已由[回报提案](#reporting-defaults)另行确认；无绑定扫描与处理按[已定安排](#unbound-recovery-defaults)实施，分片生成和登记批量仍分别闭合，不由本节推定。配置边界见[时间配置](operations.md#dispatch-time-configuration)，对应[时间预算验收](verification.md#dispatch-time-budget-checks)继续保留完整要求；普通派发预算与保存处理的实际覆盖见[普通重试记录](ordinary-readiness-review.md#ordinary-retry-progress)，未知结算核心的预算与部分进展验证见[最新记录](ordinary-readiness-review.md#ordinary-unknown-progress)。自动观察扫描及生产接线的当前范围见[扫描记录](ordinary-readiness-review.md#ordinary-unbound-scan-progress)，完整进程故障和负载验收仍按阶段 6 推进。

### 派发候选合并与跨节点竞争 {#dispatch-contention}

**2026-10-26 已通过，普通首次启动及重试登记已实现，实际验证见[实施记录](ordinary-readiness-review.md#ordinary-retry-progress)。** 普通首次启动及已有 Task 的新尝试登记，将原等待式父行 `FOR UPDATE` 修订为 `FOR UPDATE NOWAIT`。普通、准备、分片和收尾共用派发竞争原则，不重开各类型的生成条件或状态机；分片阶段登记仍待实施。本节不把 NOWAIT 扩展到分片生成、Post 创建、人工停止决定、正常完成或普通 CRUD。STOPPING 子取消已单独批准，不是本次修订的默认授权来源。

#### 父行竞争与退出

取得本地派发容量后，每个有界登记批次仍开启默认 `READ COMMITTED` 短事务，按 Instance 主键尝试锁定单表单行。父锁冲突时回滚，不继续该事务中的子 Task 查询或写入，不登记尝试、不消耗执行机会、不发送 RPC；工作协程处理其他 Instance。取得父锁后，仍须读取数据库当前时间、复核父状态和截止，并按原候选尝试及预算条件登记，不能把 NOWAIT 成功当成执行许可。

候选按 Instance 组织。一组争锁失败，本次处理中该 Instance 的其余尚未登记候选也暂时跳过，不逐 Task 连续争同一父锁，不立即重排，也不利用已合并的旧提示立即重抢。持久化待处理状态保留，后续查询重新发现；不设置永久跳过记录。事务结束释放父锁，RPC 及业务执行不占父锁；已登记且确认提交的其他发送计划不因这次竞争失败而被重置。

#### 本地合并与登记并发

- WAITING 提示按 Instance ID 合并；已有 Task 候选按 Task ID 与读取时的原尝试编号去重，不把旧候选替换成数据库最新编号。
- 同一节点、同一 Instance 同时只进行一个登记事务，其余候选在既有有界派发组织中合并或留待后续处理，不另建无界等待协程。
- 本地登记限制在登记事务结束后释放，不持有到 RPC 返回或业务执行完成；不同已授权 Task 的发送仍可在原派发并发范围内进行。事务及处理实际尚未退出时，不能提前归还仍占用的资源额度。
- 本地合并不是跨节点互斥、数据库领取标记或整轮负责人；节点退出不影响其他节点按持久化事实接续。提交不明仍按原协议放弃本次发送，不凭读回状态补发同次尝试。

#### 有限补查与处理顺序

正常路径仍在持久化后提示本节点直接派发，周期补查不是每条新任务的必经路径。各节点的补查采用独立、小幅随机抖动；已经接纳的有界候选按 Instance 分组后，从不同起点处理，减少总是同时争抢同一头部候选的概率。SQL 仍按既有索引有序查询，不使用 `ORDER BY random()`；本地处理顺序与数据库分页位置分开，不能因打散次序跳过未接纳项。

竞争失败不立即重查第一页，也不使当前遍历反复退回头部；后续重新遍历须能再次发现较小 ID 的迟提交或先前未处理记录，不把临时游标当永久消费水位。[派发供给参数](#dispatch-supply-defaults)已确定 256 等待候选、每页最多 128、空闲补查 1 秒及上下 20% 抖动、每 Instance 先补最多 8 项，以及连续 4 页无有效登记进展时退避；既定每进程 64 个派发工作协程不变。登记批量和具体编码组织继续落实，不套用 STOPPING 参数，也不以预算恢复绕过同组竞争失败退出规则。

#### 成本与保证边界

NOWAIT 改变的是父行锁冲突时是否等待，不是证明 SELECT 加锁比条件 UPDATE 更快。单行状态变更能由条件 UPDATE 完成时不应额外先读锁；派发需要保护父状态、截止与子 Task 登记之间的决策，因此保留原本就需要的父锁，不用 `UPDATE status = status` 制造父写入来取锁。

跨节点重复候选读取、失败事务及迟到取得锁后发现已处理的成本仍存在；父锁成功后的子条件 UPDATE 也可能等待其他写入。NOWAIT 不消除连接等待、SQL 执行时间或全部锁等待，不保证性能优于其他实现。失败后处理其他 Instance、避免立即重复争抢，是控制竞争成本的组成部分；具体吞吐与公平性须验证。验收见[派发竞争检查](verification.md#dispatch-contention-checks)。

### 发送前的尝试登记 {#attempt-registration}

正常派发和恢复接续共用以下规则，适用于普通、准备、分片及收尾 Task：

普通 Task 的首次派发直接在[首次启动事务](#ordinary-flow)中插入执行中 Task 并保存本次执行信息，不再重复执行下面针对已有 Task 的条件更新；容量前置、父行检查、执行预算和提交确认规则相同。后续重试按[已通过的条件更新](data-contracts.md#ordinary-retry-registration)处理原 Task，不重建 Task 或重置 Instance 计时。

1. 先取得本地派发容量，再处理容量范围内的一小批候选 Task；没有槽位时不提前登记执行尝试。
2. 候选按 Instance 组织。每个短事务仅以主键等值条件对一条 Instance 记录尝试 `FOR UPDATE NOWAIT`，冲突按[竞争规则](#dispatch-contention)回滚退出本次该组处理。取得锁后按当前数据库时间校验本轮仍允许执行、未到截止时间，再对该轮的有界一批 Task 做条件更新：Task 仍可派发、已到最早可派发时间、当前尝试未被其他节点推进且预算允许。当前尝试标识、机会记账及进入执行中状态必须原子保存，不逐条先查再改。
3. 数据库返回本次成功登记的 Task；本次收到明确提交成功确认后，只对这些 Task 发送对应尝试的 RPC。提交结果不明则按[恢复规则](#commit-unknown)放弃本次本地发送；条件未满足的条目也不发送，事务中不包含 RPC。
4. 派发槽位释放后继续补充；积压仍保存在数据库，不把整轮分片提前标为执行中后长期排在内存里。

正常节点与恢复节点同时处理同一 Task 时，共享条件写入约束同一次尝试的登记；失败的一方不得凭旧信息发送。该机制保护平台授权和记账，不保证业务恰好执行一次，也不增加整轮负责人。

普通重试候选保留读取时的 `attempt_no`，与 Task／Instance ID 一起参与条件更新；即使其他节点已执行新尝试并再次回到等待重试，也不能把旧候选替换成最新编号继续派发。登记原子递增 `attempt_no` 和 `used_attempts`、更新当前登记时间，清空最早派发时间及旧执行器绑定；首次开始与整轮截止不变。预算只看已用次数，明确 BUSY 返还后仍可再次占用该机会，不把编号当作预算。

重试登记保留 `result_summary` 作为最近保存的说明，清空业务 Data 和终态字段；摘要不一定属于当前尝试，不能据其非空判断已有本次结果。后续有效结果覆盖摘要，包括成功返回空摘要。新尝试的返回记录加明确提交成功才允许发送，零行不发送也不换用最新编号重试；[专项验收](verification.md#ordinary-retry-registration-checks)覆盖旧候选、预算、终止及提交交界。

有界检查补充遗漏、积压和到期重试，不是每条新 Task 的正常必经步骤。已经登记为执行中的 Task 不能直接被恢复节点重新发送；没有绑定及结果时遵守[有限观察与条件结算](#missing-binding)，已有绑定但结果不明或执行器失联时遵守[等待整轮超时](#bound-result-wait)，不据此提前重派。

### 记账时点与写入成本 {#dispatch-accounting}

**尝试登记提交成功就占用一次执行机会。** 仅在本地排队、尚无派发槽位或登记事务确定未提交，不占用机会。明确未接单的 [BUSY](#busy-backpressure) 可条件返还本次已占机会，但不能扩展到通信结果不明。登记已提交、节点却在实际 RPC 前宕机时，恢复节点不能据此免费重发；平台无法可靠区分“没有发送”与“已发送但确认丢失”。重试次数为 `0` 时，可能业务实际尚未执行，Task 最终却失败。通信故障处理继续遵守[统一预算](behavior.md#retry)，不额外叠加通信重派额度。

记账以数据库实际提交为准，不以调度进程是否收到确认决定是否占机会；只有发送资格要求本次获得明确提交成功确认。确认不明时的保守处理见[提交结果不明恢复](#commit-unknown)。

已保存为待派发的 Task 通常需要一次条件更新。批量操作减少数据库往返，不消除每条记录的行更新、WAL、相关索引维护及行锁竞争。例如 1,000 条 Task 每批 20 条，登记环节约为 50 次批量更新，但仍修改 1,000 条记录；这只是成本示例，不是批次默认值，也不包含后续确认和结果保存的写入。

每个 Instance 的登记批次还增加一次父行加锁和状态／截止校验。同一轮的这些短事务串行，不同轮可并行，提交后的 RPC 与业务执行不占父锁。跨 Instance 不用 `IN` 一次锁多条父记录；这一按轮协调成本已单独接受，处理数量和批次必须有界。大量单 Task 的小 Instance 难以摊薄这部分成本，不能把批量称为消除所有逐轮往返；容量验证必须覆盖该场景。

普通 Task 已确认在本地派发容量与全部派发前提具备后，将 Instance 首次启动、Task 插入和首次执行信息合并提交，省去随后单独登记首次尝试的事务和更新；不消除父行检查、Task 插入、WAL 或索引维护。其他 Task 类型的创建衔接仍在对应路径设计，不能为了省一次写入提前授权全部分片。正常路径仍是持久化后本地直接派发，不改为全节点高频扫描抢任务。

### 新尝试登记与整轮终止协调 {#authorization-terminal}

**新尝试的执行许可及新增 Task 必须与父 Instance 的停止决定、超时决定和正常结束互斥；保存结果不统一取得这把父行锁。** 首次启动、每个实际插入 Task 的生成批次、Post 创建及新尝试登记，都在短事务中按主键等值锁定同一条 Instance；在该事务内复核允许的父状态并完成相应插入或授权，不能仅在生成开始前查一次。正常完成在父锁外读取稳定完成事实，再以 `status = 2` 条件 UPDATE 父行，不先持父锁查询 Task 或汇总结果。UPDATE 本身仍取得数据库行锁，并与授权事务协调，不是无锁操作。人工停止与自动超时在父短事务中保存 `STOPPING` 和原因，按[终止契约](data-contracts.md#instance-termination-sql)执行，不在该事务中批量取消子 Task。显式锁只针对单表单行，不使用范围、多行、跨表或 advisory lock；事务采用默认 `READ COMMITTED`，不包含 RPC、Redis 等外部 I/O。

| 竞争顺序 | 持久化结果与执行边界 |
| --- | --- |
| STOPPING 或终态先提交 | 后续授权取得锁后拒绝新增 Task、Post 或新尝试；不能仅以“尚未终态”作为执行资格 |
| 登记先提交，随后停止 | 已登记尝试可能正在发送或运行，只能尽力取消；后续新尝试仍被禁止 |
| 派发授权父锁被占用，或取得锁后已到截止 | 锁冲突按 NOWAIT 回滚退出；取得锁后仍用当前数据库时间复核，不用排队、连接获取或事务开始时的旧时间继续授权。生成和 Post 创建等其他父事务不因本项自动改为 NOWAIT |
| 正常结束与人工停止竞争 | 正常完成只从 RUNNING 条件结束，人工停止保存 STOPPING 及人工停止原因；先有效提交者决定后续路径，不能将 STOPPING 再按正常完成结束，也不按超时优先改写已保存原因 |

新工作授权的时间判断边界是**取得父锁后的受保护决策点**，不是事务开始时间、执行器自报时间或本地缓存时间。决策在截止前有效，随后事务成功提交，并不保证物理 COMMIT 或 RPC 到达也发生在同一截止毫秒之前；不能把该协议解释成精确的墙钟截断。锁内判断已到期时拒绝登记新尝试，交由统一完成／超时处理检查，不能凭旧候选直接强制超时或在授权父锁内扩大为整轮结果汇总。普通首次开始按[已定 SQL](data-contracts.md#ordinary-start-sql)在锁后取得数据库当前时间，并由快照时长形成首次截止；[普通重试登记 SQL](data-contracts.md#ordinary-retry-registration)同样锁后取时但不重置截止。正常完成不以当前时间是否越过截止否定完整结果，自动超时与人工停止按[已定终态规则](behavior.md#terminal-order)执行。正常完成条件 UPDATE、超时衔接及普通完成读取已定，完整分片事实查询 SQL／索引和其他类型授权继续细化，不改变 Job 触发使用进程时间的规则。

**等待重试只是候选状态，不是再次执行的许可。** 失败结果、明确 BUSY 或未知结算按当前 Task 的尝试、旧状态及预算条件写入，不要求每条处理都锁父。它们与父进入 STOPPING 交错时，子 Task 可以短暂进入或留在等待重试，BUSY 的条件记账修正也可以交错完成；这不恢复父状态，不授予新尝试，也不能覆盖子 Task 已有终态。真正再派发必须经过上述父行登记关口。若已观察到父停止决定，则走取消收敛，不能把“可以短暂交错”用作继续推进的理由。

`STOPPING` 提交确认后，子 Task 按[已定条件更新](data-contracts.md#instance-termination-sql)统一有界分批取消，普通、准备、分片和收尾不分支处理；已有成功、最终失败或取消不覆盖，不为取消而补建尚未生成的分片或 Post。子更新与尽力取消 RPC 是独立的提交后工作，均不占用决定停止的父事务。有效结果与子取消仍按允许旧状态的条件写入竞争，先形成有效子终态者保留；未结束候选由后续批次继续处理。

仅当父仍为 `STOPPING` 且按该 Instance 查询 `NOT EXISTS` 未结束 Task 时，才条件保存最终父状态和 `finished_at`：人工停止为 `CANCELED`，整轮超时为 `FAILED`。停止原因在进入 `STOPPING` 时已冻结，不由重试或后续入口改写；全部子终态、停止后不能新增 Task、子终态不可逆共同支撑结束判定。无子 Task 时也执行同一最终确认。`STOPPING` 恢复按[独立候选分支](#stopping-recovery)继续处理，不再以父已经终态但子未收敛作为正常停止协议的恢复状态。平台终态仍不证明业务已经退出。

该协议不恢复整轮固定负责人，不把所有结果写入串到父行上。接收 ACK、结果落库和新执行授权仍是不同事实；登记、BUSY 返还及结果写入的[提交结果不明](#commit-unknown)按已确认规则恢复，不按普通回滚处理。

## 5.4 延迟派发能力复用 {#deferred-dispatch}

失败重试需要持久化“最早可派发时间”，BUSY 延后复用这一能力：Task 在派发前已经入库，收到 BUSY 后需要延后时，更新原 Task 的最早派发时间，由既有待处理检查在到期后继续处理。不新建 BUSY 专属表、队列、扫描器或另一套延迟调度系统。

本地直接派发和恢复检查都遵守这一时间，避免其他节点提前重派。本地计时器可以加速，但不能成为到期工作的唯一依据。保存时间是为了共享派发时机，并不是因为没有时间字段就会丢失 Task；它也不解决执行器负载不均的问题。

### 明确未接单的 BUSY 处理 {#busy-backpressure}

**BUSY 专指执行器明确回复容量已满，本次未接单、未入队且未开始业务执行。** 这是可确认的容量拒绝，不是普通业务失败或不确定的通信失败。执行器已经接受任务后，不得再用 BUSY 表示内部执行失败。

| 情况 | 已确认处理 |
| --- | --- |
| 收到当前尝试明确未接单的 BUSY | 条件返还本次已占执行机会，关闭本次尝试并延期；不消耗 Task 执行重试预算 |
| Job 执行重试次数为 `0` | 仍允许 BUSY 延期再派发，不把未运行的容量拒绝当作一次业务失败 |
| RPC 超时、断连或通用不可用响应 | 不能推断为 BUSY，不能返还；遵守原有通信不确定性和绑定规则 |
| BUSY 响应丢失，或返还事务失败／提交结果不明 | 不凭推测免费重派；持有原响应时仅做有界有限的条件记账重试，不建立长期待返还队列 |
| 持续 BUSY 直至整轮到期或手动停止 | 按整轮终止规则结束，不延长期限，不再正常派发 |

返还、关闭当前尝试及设置最早可派发时间必须原子提交，并校验当前尝试身份及允许的旧状态；重复或迟到 BUSY 不能重复返还、覆盖已有有效结果或恢复子 Task 终态。返还只减少 `used_attempts`，不回退 `attempt_no`，延期写入 `next_dispatch_at`。该记账修正不统一锁父，可以与父进入 STOPPING 交错；延期仅产生候选，下一次新尝试仍须经过[父行授权检查](#authorization-terminal)，父已有停止决定时子 Task 由停止处理取消收敛。数据库事务不包含 RPC；[普通 BUSY 条件更新 SQL](data-contracts.md#ordinary-busy-settlement)已通过，由收到响应的固定派发工作协程直接保存，校验原编号、执行中状态、正已用次数及双绑定为空，不新增响应队列。

后续派发登记新的尝试身份，不因返还预算而复用旧 ID；已关闭尝试的迟到消息不得重新生效。不增加 Attempt 历史表，尝试身份也不能仅由可增可减的预算计数推导。实际派发次数可以超过原始执行加配置重试次数，但已占且未返还的执行机会仍受统一预算约束。

BUSY 延期复用原 Task 的最早可派发时间、既有有界检查和派发容量控制；必须退避，不能立即循环发送。不新建专用表、队列、扫描器或独立 BUSY 次数池。BUSY 等待包含在本轮时间预算内，[已定初值](#dispatch-time-budgets)为 5 秒上下浮动 20%，独立于业务失败重试间隔；保存后释放派发处理，不占住协程等待到期，执行器容量仍另行确定。

BUSY 保存失败或提交结果不明时，只由当前派发工作协程对原 Task、原尝试和尚未结算的旧状态做**有界有限重试**，不套用执行结果的长期保留规则。原响应释放、进程退出，或未知结算／取消先提交后，不能凭“业务其实没有执行”补返机会；实际未执行也可能消耗一次预算。已落库的返还仍有效，不因本地处理报错撤销。更新零行即结束，不补查猜原因，不重新派发业务；重复保存不再次返还或刷新已生效的延期。保存采用[已定时间预算](#dispatch-time-budgets)：阶段最多 4 秒、最多 3 次含首次、单次 1 秒及失败间隔 200 毫秒，并受原 10 秒总预算及停机宽限约束；见[提交结果不明恢复](#commit-unknown)。

再次派发继续使用原生 go-zero 负载均衡，不自行排除上次节点，也不保证下一次换节点或一定能执行成功。容量持续不足仍可能导致整轮超时；本规则避免把明确未运行的容量拒绝直接耗成业务失败，不承诺消除集群负载不均。

## 5.5 派发路由与执行入口 {#dispatch-routing}

首次派发和重试均复用 go-zero 原生服务发现与负载均衡。etcd 提供服务地址发现及更新，RPC 客户端选择可用连接；请求不经过 etcd 转发。调度器不自行挑选执行器，不按 Task 排除上次节点，也不保证重试更换实例。

go-zero 当前默认 `p2c_ewma` 依据 RPC 时延和在途调用等信息选择连接，不掌握异步业务 Task 的剩余执行容量。接收确认很快返回后，业务仍可能运行很久，因此派发 RPC 并发不等于业务执行并发，也不能保证各执行器的业务负载均匀。容量保护与两端背压仍是独立设计内容。

执行器通过统一 RPC 入口接收工作，一次调用派发一个 Task 的当前尝试，按处理器名称定位本地注册业务代码，由 Task 类型区分普通执行、准备、分片和收尾。成功纳入有界执行管理后才返回接单 ACK，不等待业务完成；不增加批量接单协议，调度端仍可有界并发派发和批量登记。公共执行组件负责容量保护、异步执行、执行上下文、取消协作和结果回报；业务处理器返回结果，不手写回报 RPC，不直接维护调度表。消息及活动期防重见[派发接单契约](data-contracts.md#dispatch-acceptance)，明确非 BUSY 拒绝的结算见[拒绝结算协议](data-contracts.md#dispatch-rejection-settlement)。

服务发现解决“发给哪个执行器实例”，处理器名称解决“执行哪段代码”。统一入口是多个执行器共同实现的协议，不是单点转发服务。具体分组、部署和信任边界归入[总体架构](./architecture.md)，消息字段与处理器签名归入[数据与接口](./data-contracts.md)，不通过本节默认决定。

普通、准备、分片和 Post 的明确非 BUSY 拒绝共用已通过的[结算规则](data-contracts.md#dispatch-rejection-settlement)：只对按契约能够确认未接纳的响应立即尝试条件结算，不等待 30 秒观察；通用不可用、超时、断连和无效 ACK 仍不能推断为拒绝。结算使用本次派发已有的本轮冻结重试配置，原 Task／Instance／尝试、执行中状态及双绑定为空共同限制写入，不新增父行锁或查询当前 Job 配置。已有机会不返还、不重复扣减，执行编号不变；有余量则按数据库处理时间加本轮重试间隔（默认 10 秒）形成等待重试候选，耗尽才最终失败。后续派发仍须重新检查父状态、截止和预算，保存及有限重试不直接发送业务。

拒绝结算保存接单被拒绝的诊断并清空业务结果，不描述为处理器已经运行后失败。零行停止、不补查；确认提交后可提示 Instance 检查。执行器的截止拒绝不代替调度端以数据库时间作出的完成／超时判定。耗尽时 Task 的 `end_reason` 统一为 `dispatch_rejected`，等待重试时仍为 NULL，具体原因保存在摘要中。该规则不改变阶段生成及正常推进协议；[派发与取消错误映射](data-contracts.md#dispatch-cancel-errors)已通过，实现仍待验证。

派发接纳前的认证拒绝沿用 `Unauthenticated`／`PermissionDenied`，非法输入使用 `bizerror`＋`common.invalid_request`；处理器缺失、能力不满足、接单前已过执行期限及明确未就绪／退出拒收统一使用 `100001`＋`job.executor.dispatch_rejected`。这些可识别拒绝才进入已定结算；未知 subcode、通用技术错误、超时、断连和无效 ACK 仍不证明未接纳，不解析英文 Message。已接纳或接纳结果不确定时不得伪装为拒绝；活动中的重复尝试按原约定返回 ACCEPTED，不因队满或退出改报拒绝。业务运行失败走结果回报。

### 接单后的执行器身份绑定 {#executor-binding}

第一版保留 go-zero 原生服务发现和组内负载均衡，不改为调度业务代码先选执行器。执行器每次进程启动生成一次新的 UUIDv4 作为 `executorInstanceId`，用于区分同一地址上的不同启动进程，不替代组 Token 认证。当前尝试绑定持久化为 `job_task.executor_instance_id UUID` 与 `executor_address VARCHAR(255)`；未知时允许为空，见[字段契约](data-contracts.md#task-field-contract)。

正常派发沿用以下顺序：

1. 取得本地容量，条件登记当前尝试及执行机会，事务提交后发送 RPC。
2. 原生负载均衡选择接收执行器；执行器在接单响应中提供本次进程实例标识，不等待业务完成。
3. 调度端取得本次调用的实际对端地址，按[已确认的绑定 SQL](data-contracts.md#executor-binding-sql)同时保存进程实例标识与地址；仅原请求对应的当前执行中尝试、且两项绑定均为空时写入。零行结束，不追加查询或据此取消；已有结果或后续尝试不能被迟到的绑定更新覆盖。
4. 后续取消通过已保存的地址定向调用，按 Instance 匹配本机活动，不携带或强制校验预期进程实例标识，不再随机负载均衡到同组其他节点。接单、绑定及结果核验仍保留进程身份。第一版不为已接单 Task 新增活动查询或心跳核对。

执行器直连部署下，可以通过 gRPC 的 `Peer` 取得实际连接地址；它在调用完成后提供，不等于派发前已知目标，也不能从地址推导启动身份。引入代理后，对端地址可能不是执行器，不得直接沿用该假设；可定向寻址是接入契约的要求。

注册描述可选节点，接单响应关联本次实际受理者，两者不是重复注册。Task 仍在发送前登记时进入执行中，不为绑定另加生命周期状态；接单确认不代表业务结果。正常派发继续复用组级客户端；取消的定向客户端按[通知级生命周期](#cancel-routing)创建和关闭，不跨通知缓存。

正常接单后通常增加一次绑定行更新，当前设计基线由固定派发工作协程直接保存，失败时只有限重试元数据，不新建绑定缓冲或凑批等待；采用[已定时间预算](#dispatch-time-budgets)：保存阶段最多 4 秒、最多 3 次含首次、单次 1 秒及失败间隔 200 毫秒，并服从原总预算及停机宽限。该写入及其失败重试占用派发处理时间，行更新、WAL 和持久化延迟均须纳入容量验证，不宣称本路线比先选址更快。保留此路线是为了复用已有发现、连接可用性筛选和负载均衡，减少第一版自研目录与路由的维护范围。

绑定不授予新执行许可，不额外读锁父 Instance；父为 `STOPPING` 而子 Task 仍执行中且满足条件时，允许补存目标信息，不恢复任何状态。子已收敛则不写入。接受迟到绑定错过既有取消通知的窗口，不增加可靠补取消机制；更新零行也不证明应该取消该目标上的本轮工作。

接单 ACK 丢失，或调度节点收到 ACK 后、绑定提交前退出，可能留下已在执行但没有持久化目标的尝试；不能假定总能定向查询或取消。该窗口按下面已确认的规则处理，不增加 Task 级心跳、执行租约、广播寻找或免费重派机会。

### 取消通知粒度与定向客户端 {#cancel-routing}

**取消通知按批次（Instance）发送，同一轮按本轮执行器组和已保存的不同 RPC 地址分别通知，不逐 Task 发送。第一版不跨取消通知复用定向客户端。** 例如一轮 1,000 个 Task 分布在 5 个已知地址，只产生 5 个目标通知，通信重试另计；Task 表用于定位地址，不意味着每条 Task 发送一次 RPC。 管理操作仍是停止整轮，不增加单独停止某个 Task 的管理功能。

确认 Instance 的 `STOPPING` 和停止原因已经提交后，调度端有界读取本轮已保存的非空执行器地址，按本轮执行器组和目标 RPC 地址去重；不按 Task 状态过滤，也不只使用本次成功取消行的地址。请求携带 InstanceID、组认证信息及取消原因，不携带预期进程实例 ID。每个目标完成组认证后，对本机当前属于该 Instance 的排队或运行任务请求取消；只查现有有界活动记录，不新增长期取消缓存。请求不通过组内负载均衡，不向整个执行器组广播。数据库中的子 Task 仍按既定规则分别收敛，通信应答不证明业务实际退出。

取消依据是已经确认持久化的停止决定，不是父已终态或本次子 Task UPDATE 成功。不等待全部子状态更新完成；子更新零行、失败或提交不明时，仍可对已取得地址尽力通知。停止决定未确认时不能凭本地意图发送取消。数据库状态处理不等待通知成功，通知失败、耗尽或丢失都不能阻止父子状态最终结束。两条路径的交接见[停止超时与子 Task 收敛](data-contracts.md#instance-termination-sql)，不在每个子批次重新查询并通知整轮全部地址。

一次目标通知的客户端生命周期如下：

1. 在有界发送并发内，使用 go-zero 原生单地址直连客户端连接已知目标。
2. 发送本 Instance 的取消请求；同一次目标通知中的有限重试共用这个客户端，不逐次重试重建。
3. 通知成功、明确结束、预算耗尽或调度进程停止时，结束本次调用并关闭客户端；不保存供下一次通知使用。

不增加地址到客户端的长期缓存、引用计数或闲置淘汰机制，不修改默认负载均衡。正常派发和结果回报的组级发现客户端仍长期复用。取消使用独立的有界控制调用上下文，不能复用已因整轮超时而取消的业务 Context；本轮已确定[独立通知容量及通信初值](#cancel-notification-capacity)，不套用数据库取消批量或派发容量。

取舍是每次独立通知可能重新建连，成功且无重试时可能只发送一次 RPC 就关闭。集中超时或停止时，握手开销和通知延迟会增加；有界并发只限制峰值，不消除开销。绑定缺失、旧执行所在目标未知和已授权派发晚于取消到达的窗口不因此解决，平台终态也不证明业务副作用已经停止。

**取消请求不校验预期进程实例 ID，已确认。** InstanceID 不复用，终态不恢复，重新运行创建新 Instance。同一地址重启后，没有该 Instance 的活动就不操作；若仍有该轮的迟到执行，也应请求取消；其他 Instance 不受影响。此项只简化取消协议，接单 ACK、执行绑定和结果核验仍保留进程身份。

[取消处理与响应语义](data-contracts.md#cancel-response-contract)已确认：本机排队活动标记取消、运行活动取消业务 Context 后回复，无匹配活动也正常回复，不等待业务退出。调度端对永久错误不重试，对通信故障只有限重试同一目标；响应及通知耗尽均不改变已保存的停止决定或最终状态，不替代子 Task 条件收敛，也不作为父结束前置条件。重试不消耗业务执行预算，通信初值按下节执行；消息表达见已通过的[执行 RPC 协议与装配](data-contracts.md#execution-rpc-contract)，[派发与取消错误映射](data-contracts.md#dispatch-cancel-errors)也已通过，Proto 生成与实现验证仍须完成。

取消正常空响应包括没有匹配活动，不返回 NotFound；认证错误 `Unauthenticated`／`PermissionDenied` 或 `bizerror`＋`common.invalid_request` 结束本目标通知，临时故障和未知错误在原预算内重试同一地址，不使用派发专用拒绝 subcode。取消不因原业务期限已经过去而被拒绝，也不继承已取消的业务 Context；退出中仍有能力处理本机取消时正常处理，入口已停止服务则按通信失败处理，不保证停机期间始终可访问。取消 RPC 错误不写入父子记录的结束原因。

### 远端取消通知来源、容量与预算 {#cancel-notification-capacity}

**2026-10-26 已通过。单目标 `execution.Canceller`、递归地址枚举、独立有界 `execution.Notifier` 及宿主接线已实现，当前范围及验证见[停止运行链路记录](ordinary-readiness-review.md#ordinary-stop-runtime-progress)。** 本节细化按 Instance 的远端通知，不改变 [STOPPING 数据库取消](#stopping-processing)的每批父主键 NOWAIT、子批量与恢复职责；地址分页、数据库子批次和 RPC 停止粒度是三件不同的事。

#### 提示来源及重复边界

- 新的 STOPPING 决定及原因明确提交后，分别向本地数据库取消组件和远端通知组件交接。两者不互相等待，不以父行是否已最终结束或某批子更新是否成功作为通知前提；未确认持久化停止决定时不能发送。
- 不在每个子取消批次、每次两分钟 STOPPING 恢复扫描时重新通知整轮。重复停止请求若只是读到已有停止决定，也不自动开启新一趟通知；周期恢复负责数据库收敛，不承担取消 RPC 的周期重发。
- 提交结果不明后的确认、通信重试等边界仍可能造成重复通知，不承诺全局恰好一次。本地按 Instance 合并排队或处理中提示，不创建全局通知锁、持久化发送记录或永久已通知集合；合并不重置本次期限，也不积累完成后必须再通知一遍的义务。
- 本地 Instance 通知容量已满时，本次尽力通知可未被接纳，记录拒收及未确认情况，不无限等待或新增旁路协程；数据库取消继续。提交后进程退出、提示丢失或未接纳都可能导致没有发出远端通知，周期恢复不保证补送。

#### 地址读取与发送分工

使用一个地址读取协程，向有界目标队列投递，由固定目标 RPC 工作协程发送。不同目标可并发，一个坏地址只占自己的处理额度，不要求同一 Instance 的其余地址等它重试完；这条链路不占数据库取消的 2 个并发或派发的 64 个工作协程。

地址通过[已定地址索引及有界定位查询](data-contracts.md#cancel-target-query)取得，不按 Task 状态过滤，也不取本次子 UPDATE 的返回地址代替全轮已知目标。每个 Instance 每次最多读取一页不同地址，交接完本页后轮到待枚举集合队尾；已无后续地址时停止枚举。目标接纳后才前移地址游标，队满暂停读取和后续翻页，不继续查库再丢弃未接纳目标。读取端至多暂存当前一页未交接地址，不为每个 Instance 各藏一页，也不加载全轮 Task 或完整地址集合。

Instance 容量包含排队、正在读取地址以及地址读取已结束但仍有目标待处理的轮次；目标容量包含排队、发送及有限重试等待，不因取出队列就释放。全部地址已处理或停止枚举、且已接纳目标也已结束后，释放该 Instance 的本地记录。正常业务、数据库状态更新与远端通知仍共享数据库、CPU 和网络，独立工作协程不是资源硬隔离。

#### 部署初值及通信预算

| 参数 | 初值 | 适用边界 |
| --- | --- | --- |
| 本地待通知 Instance 总容量 | 256 | 包含排队、枚举及目标尚未处理完的轮次，按 Instance 合并 |
| 地址读取并发 | 1 | 不按 Instance 或地址新建无界读取协程 |
| 地址每页 | 最多 32 个不同地址 | 每页交接后轮转；不是每页 32 条 Task，也不是 32 次 RPC 合批 |
| 目标通知总容量 | 256 | 包含排队、发送和等待重试；不含读取端至多一页的有界交接缓冲 |
| 目标 RPC 发送并发 | 16 | 一个工作项是向一个地址发送本 Instance 的取消，不是停止单条 Task |
| 单条地址查询超时 | 1 秒 | 仍受本次 Instance 通知剩余预算约束 |
| 单次 RPC 超时 | 1 秒 | 与单目标和 Instance 剩余预算取更短者 |
| 单目标总尝试次数 | 最多 3 次，包含首次 | 只对超时、断连、临时不可用等通信故障重试同一地址 |
| 通信重试间隔 | 1 秒 | 在同一目标预算内等待，不新增无限重试或可靠补送队列 |
| 单目标处理总预算 | 5 秒 | 从开始处理该目标起，覆盖建连、调用及重试等待，不保证一定执行满三次 |
| 一次 Instance 通知总预算 | 60 秒 | 从本地接纳起覆盖排队、地址查询、目标等待及发送；翻页、合并及重试均不重新计时 |

单目标等待发送也消耗 Instance 的 60 秒预算，但单目标 5 秒从实际开始处理时才计算。继续使用独立的有界控制 Context，不继承已因整轮到期而取消的业务 Context；进程停机仍服从既定共享有限宽限，不为通知另外延长宿主退出时间。

正常响应（包括没有本轮活动）即结束目标通知；Token、组或参数明确错误不重试。通信失败在剩余额度内重试原地址，不换节点、不广播；同一次目标通知只创建一个临时直连客户端，重试内共用，结束后关闭，不跨通知缓存。

#### 查询失败、父终态及期限耗尽

- 地址查询失败时，结束本次剩余地址枚举并记录失败；已接纳的目标继续使用原预算，不因一个读库错误撤销已持久化的停止决定或已取得的目标。
- Instance 已转 CANCELED／FAILED，不停止已接纳通知的剩余枚举与发送。数据库终态不证明执行器业务已退出，通知仍可在原 60 秒预算内继续；不重新计时，也不因此扫描历史终态补送。
- 总预算耗尽或进程退出时，不再读取地址或启动新目标／重试，排队目标结束等待，在途调用取消 Context 并正常释放资源；Context 结束、超时或客户端返回不证明事务、网络调用、连接和处理额度在同一时刻已全部释放，仍在运行的工作不能提前归还并发额度。
- 迟到绑定落在地址游标之前、旧尝试地址已被清空、地址未知及派发晚于取消到达的窗口继续接受。不存在匹配活动的成功回复也不能保证未来不会有已授权的迟到执行。
- RPC 成功、失败、耗尽或丢失均不参与父子数据库终态判定，不以发送结束延长 STOPPING；执行器仍须按组认证和 Instance 匹配本机活动，不校验预期进程 UUID。

这些数值是部署初值，不是吞吐或送达时限保证。地址索引的正常写入／历史空间成本、临时建连、集中超时和大批离线目标均须按[通知专项验收](verification.md#cancel-notification-checks)验证；本项通过不等于索引、运行组件或测试已经实现。

### 绑定缺失的观察与条件结算 {#missing-binding}

本规则适用于当前尝试已经登记提交，但没有持久化执行器绑定，也没有已提交执行结果或结算的情况。它同时覆盖登记后未发送、执行器接单但 ACK 丢失，以及 ACK 已收到但绑定未提交；没有绑定不能证明业务尚未开始。已有绑定但最终结果未落库属于另一条恢复路径，不能直接套用本规则。

#### 有限观察与正常补齐

观察期从当前尝试登记时保存的数据库时间开始计算；换调度节点、重复扫描或重试保存绑定都不重置起点。它是平台内部的派发确认观察期，不是业务执行超时，不随整轮超时时长延长；整轮先到期时服从终止规则。[派发时间预算](#dispatch-time-budgets)已确定默认 30 秒，包含登记提交期间的耗时；调度节点配置保持一致，调整派发或保存预算时联动检查观察期余量，不承诺绝不会与迟到写入竞争。

观察期间，有效接单 ACK 可触发条件保存绑定；保存失败按[绑定协议](data-contracts.md#executor-binding-sql)只有限重试元数据持久化，不重新派发业务。有效执行结果可以先于绑定提交，不能仅因绑定缺失而拒绝当前有效尝试的结果。内存中收到 ACK 或结果成功进入异步队列，都不是持久化证据，不能替代数据库条件。

#### 到期后的持久化裁决

观察期到期只取得条件结算资格，不立即使尝试作废。恢复节点必须再次确认仍是当前有效尝试、处于允许结算的旧状态、未绑定且未有本次有效结果或结算。重试保留的 `result_summary` 可能来自旧尝试，不能用其非空阻止未知结算，也不能用其为空证明当前尝试无结果。结算本身不授权新执行，父终态与下一次登记按[统一协调规则](#authorization-terminal)处理。绑定保存、有效结果和未知结算通过持久化协议竞争：

| 先成功生效的数据库操作 | 后续处理 |
| --- | --- |
| 保存执行器绑定 | 不再按绑定缺失结算，转入已知执行器处理路径 |
| 保存有效执行结果 | 按结果处理，未知结算条件不再成立 |
| 将当前尝试结算为结果不确定 | 关闭本次尝试，迟到绑定及结果不得恢复它 |

以数据库条件写入成功提交为准，不以某节点内存中的消息到达顺序裁决。尝试标识与允许的更新前状态必须共同校验：即使下一次尝试还未创建，已经结算并进入等待重试的旧尝试也不能再接受迟到结果。迟到绑定不能覆盖有效结果、新尝试或终态，也不能静默替换一个冲突的已有执行器身份。

“关闭本次尝试”由 `job_task.status` 与 `attempt_no` 表达，不增加独立关闭字段。以第一次执行为例：

| 阶段 | `attempt_no` | `status` | 其他字段 |
| --- | --- | --- | --- |
| 首次登记完成 | 1 | 2：执行中 | 本次机会已占用 |
| 无绑定、无结果的未知结算提交，且仍有预算 | 1 | 3：等待重试 | 设置 `next_dispatch_at`；`finished_at`、`end_reason` 仍为空，不再次扣减 `used_attempts` |
| 到期且获父行授权，登记第二次执行 | 2 | 2：执行中 | 占用下一次机会，更新当前登记时间，清空最早派发时间 |
| 若未知结算时已无预算 | 1 | 5：失败 | 设置 `finished_at` 和结果不确定的终态原因，最早派发时间为空 |

状态从执行中改为等待重试并提交后，第一次结果即使业务成功也不再采纳；第二次开始后，还会因执行编号不匹配而拒绝。关闭的是数据库中本次执行的结果接纳资格，不证明执行器业务停止，也不撤销已产生的副作用。拒绝已关闭尝试的迟到成功是本系统明确选择的结果规则，不是仅有执行编号就必然要求这样处理。

上述竞争语义、[绑定 SQL](data-contracts.md#executor-binding-sql)、[普通结果条件更新](data-contracts.md#task-result-persistence)及[普通未知结算 SQL](data-contracts.md#ordinary-unknown-settlement)已通过；观察条件使用本批数据库时间减观察期，默认 30 秒已确认。普通未知结算核心、`result_unknown` 原因及固定英文诊断已实现并完成专项验证，见[实施记录](ordinary-readiness-review.md#ordinary-unknown-progress)；自动观察扫描与生产调用已接入，范围及验证见[自动扫描记录](ordinary-readiness-review.md#ordinary-unbound-scan-progress)。Task 条件更新保护当前尝试，新执行许可另外经过父行授权关口，不能把未知结算成功当作再次发送许可。

普通未知结算复用已有有界恢复批次，批量取得父关系和本轮配置。前置观察到父运行、时间有效且尚未到期后，才按原执行编号、执行中状态、双绑定为空及观察期条件更新 Task；父已终态或到期走既有终止路径，运行时间异常跳过并诊断。UPDATE 使用当前行已用次数决定等待重试或最终失败，清空 Data 并更新最近的结果不确定诊断，不变更编号、计数或登记时间。当前摘要可以来自旧尝试，不参与无结果条件。

只有该条 Task 本次更新且独立提交明确成功后才提示 Instance 检查，不在结算流程重发；零行结束、不补查。写库失败或提交不明时释放临时候选，已尝试项可按下节临时游标规则越过，但立即结束本次运行，后续新一趟从头覆盖仍合格的失败项；这里没有未落库业务结果需要保留，不能与结果回报的有界保留混同，也不能因释放候选或前移游标就断言提交成功或已经回滚。对应[专项验收](verification.md#ordinary-unknown-settlement-checks)的有界结算核心已完成所列测试，自动扫描接续已接入，当前范围与验证见[实施记录](ordinary-readiness-review.md#ordinary-unbound-scan-progress)，完整进程故障及负载验收仍归阶段 6。

#### 观察到期扫描与结算安排 {#unbound-recovery-defaults}

**2026-10-29 已通过。普通有界结算、自动观察扫描与 ServiceContext 启停已接入，当前范围及验证见[实施记录](ordinary-readiness-review.md#ordinary-unbound-scan-progress)。** 各调度节点独立参与无绑定观察到期恢复，每节点同一时刻只运行一个扫描／结算流程，并在本地串行结算；不依赖 Leader 任期，不把 RUNNING／STOPPING 的 Leader 发现规则扩展到本分支。流程在既有后台恢复职责内读取并处理有界候选，不另建待结算队列、长期结果保留缓存或专用处理池，也不占派发、结果保存或 Instance 检查的处理并发。具体 Go 并发原语和内部组织不由本节冻结。生产配置为 `UnboundRecovery`：`ScanInterval` 默认 10 秒并在每次实际结束后增加 ±20% 抖动，`PageSize` 默认 128，`RunTimeout` 默认 5 秒，`OperationTimeout` 默认 1 秒，`ObservationPeriod` 默认 30 秒；复核子批最多 16 条。宿主把相同观察期和操作预算传给扫描器及 Settler，各节点保持相同观察期配置。停止时取消扫描、等待实际返回后才关闭共享连接；该流程不承担 STOPPING 收敛、超时或 Leader Instance 复核。

| 参数 | 初值 | 范围与配置归属 |
| --- | --- | --- |
| 两次运行之间的等待 | 10 秒，各节点独立上下浮动 20% | 本次运行实际结束后再等，默认约 8～12 秒；部署可调，不是固定每 10 秒启动 |
| 候选查询每页 | 最多 128 条 | 部署可调，只保留当前有界页，不是本次运行或整趟的总量上限 |
| 父状态与本轮配置复核短批 | 最多 16 条 | 内部初值；每短批重新取得数据库处理时间并批量复核，不逐 Task 补查父 |
| 单次数据库操作预算 | 1 秒 | 部署可调，包含连接等待、执行及适用的提交；仍服从本次运行剩余预算 |
| 一次运行总预算 | 5 秒 | 部署可调，从运行开始计时，包含取时、候选查询、批量复核及逐条保存，不含运行后的等待 |

处理顺序为：读取一页候选，按最多 16 条重新取时并关联／批量读取父状态和本轮冻结配置，再按原候选顺序逐条条件更新、独立提交。只读取结算所需字段，不加载整份业务参数或结果，不读取当前 Job 配置。小批复核不是多条 UPDATE 的共同事务；每条没有与其他 Task 共同提交的业务要求，独立提交及时释放已取得的行锁，失败不回滚此前已明确提交的其他条目。

前置已看到父 STOPPING 时交已有停止处理，父已终态则退出该候选，父仍运行但已到期时交完成／超时检查，随后继续其他候选；不凭未知尝试直接写父超时。运行时间异常或其他明确不适用的候选按原协议跳过并诊断。符合条件的候选仍使用原尝试编号、执行中状态、双绑定为空及观察到期的条件 UPDATE；结算不扣次或返还次数，也不直接授权新尝试。普通 Task 的两预算分支已定，其他类型的具体写入继续按所属阶段契约落实，不因公共扫描通过就视为全部类型 SQL 已完成。

每趟固定数据库扫描时间 `scan_now` 和观察门槛，按 `(attempt_registered_at, id)` 使用临时键集分页；[候选查询](data-contracts.md#unbound-recovery-query)返回登记时间供分页使用，不为游标额外查询。预算内完成当前页后可以继续下一页，不另设 128 条运行总量。到尾后结束本趟，经过运行后等待，再以新数据库时间从头开启下一趟；不在同次运行剩余预算内立即重扫。未完遍历在下一次运行取得新的 5 秒预算，沿用原扫描上界和游标；节点退出后临时状态丢失，下次从头发现，不保存永久消费水位或持久领取标记。

扫描时间只限制本趟候选范围。每个处理短批重新取得 `processed_at`、计算观察阈值及重试时间，并重新复核父状态和冻结配置；候选跨运行接续时不复用上次处理时间或已读取的父状态缓存。扫描不锁行，批量读取不锁父，Task 条件 UPDATE 也不新增父或 Task 显式锁，不套用派发／停止处理的 NOWAIT。跨节点、ACK、结果及取消仍可能竞争同一 Task 行锁；独立抖动和本地串行只减少碰撞，不保证立即跳过或没有重复查询与零行更新。

临时游标按原查询顺序处理过的连续前缀推进：

| 当前候选情况 | 本趟位置与后续动作 |
| --- | --- |
| 该条更新并明确提交成功 | 可以越过，并按原协议提示 Instance 检查；不是直接重派 |
| 条件 UPDATE 无错误零行，或前置核验明确不适用 | 可以越过，继续其他候选；零行不证明此前已结算成功 |
| 单条写入技术失败或提交结果不明 | 可以越过该已尝试项，但立即结束本次运行，不继续下一条、不立即重做该写入；下次运行续接后方，后续新一趟从头覆盖仍满足条件的失败项 |
| 处理预算到期，候选尚未开始处理 | 不能越过该未处理项，保留最后已处理位置；下次重新读取及复核 |
| 候选查询、取时或小批关联读取失败 | 结束本次运行，尚未完成核验／开始处理的条目不前移；不把查询失败当成空页或已经处理 |

写入失败项前移只表示本趟已经尝试，不表示提交成功或确定回滚，也不永久排除该 Task。这样避免一个持续写入失败的候选固定堵住后方；代价是该失败项可能等整趟遍历结束后才再次处理。原事务实际已提交时，其新状态由既有重试或完成推进接续；未提交且仍合格时由后续新一趟再次发现。未处理项不能因为整页已读入内存或其他条目提交成功而被跳过。候选页和小批缓存可在运行结束时释放，仅保留本趟上界及已处理游标，不保存真实业务结果的副本。

一次数据库操作使用 1 秒与运行剩余时间中的较小预算。预算到期停止新操作并取消在途调用；操作及必要清理实际结束后，才结束本次运行并开始约 10 秒的等待。超时不保证行锁、连接或事务恰在一秒内释放，也不证明没有提交；不重叠启动下一次运行、不追赶积累的周期 tick。单个父到期不是结束整次扫描的条件，5 秒运行预算用尽或数据库技术错误才按上述规则结束本次。

30 秒仍仅表示观察到期、取得条件结算资格，不证明旧业务没有执行或已经停止；观察等待、运行间隔、分页积压及依赖故障共同影响实际恢复时间，不承诺 30 秒完成恢复。后续实际重试复用普通派发资源，不让后台结算等待派发 RPC。对应[候选恢复验收](verification.md#unbound-recovery-query-checks)与[结算验收](verification.md#ordinary-unknown-settlement-checks)继续验证真实扫描成本、碰撞等待、失败项复查时间及正常派发／结果保存延迟。

#### 预算与父终态约束

当前尝试登记提交时已占用一次执行机会，未知结算不再重复扣减。有剩余预算时，Task 可条件进入等待重试，沿用既定重试间隔，默认 `10 秒`；这只是候选，真正重试须在父仍允许执行时登记新尝试并占用下一次机会。预算耗尽则 Task 条件转为失败，原因注明执行结果不确定；不免费重发，也不广播寻找旧执行。

Instance 已 STOPPING、已终态或到期，不再授权新尝试或允许迟到消息恢复执行；前置批量读取不锁父，读取后父若进入 STOPPING，子仍可能交错结算为等待重试或最终失败；不改变父停止决定，未终态候选继续取消收敛。未知目标可能无法定向取消。数据库不可用时，不能仅凭本地计时器宣布结算成功；数据库恢复后再做条件处理，因此观察期不是保证完成恢复的 SLA。

**明确接受的代价：原业务可能仍在运行，甚至已经成功；若绑定和结果均未落库，平台仍可能重试，或将 Task 标记为结果不确定的失败。** 有限观察不能证明旧业务已停止；平台失败不等于业务一定失败，拒绝旧回报也不能撤销副作用，重复执行仍由业务幂等性兜底。

## 5.6 派发不确定性与业务幂等 {#idempotency}

第一版允许有界重试或恢复造成重复业务执行。派发超时、确认丢失或绑定缺失条件结算时，旧执行可能已经产生副作用，甚至仍在运行；平台不承诺业务恰好执行一次，也不承诺任何故障下必达或必定成功。已有绑定的失联执行不因此提前重派，按[等待整轮超时](#bound-result-wait)处理。

| 责任边界 | 已确认要求 |
| --- | --- |
| 是否先核实旧执行 | 不强制每次超时先查询原执行器，不以证明旧任务绝未执行为重派条件 |
| 执行器有限防重 | 复用本机排队／执行活动记录，按 Task 与当前尝试身份避免重复接纳；业务实际退出后释放，不等待回报 ACK。不引入本地磁盘记录、跨重启去重或已完成尝试的长期缓存 |
| 平台状态正确性 | 保留执行尝试与更新前状态条件校验；旧尝试不得覆盖新尝试，重复回报不得重复推进，终止 Instance 不得复活 |
| Task 创建 | 各阶段仍需创建防重；PostTask 每轮唯一，不因接受业务重复就放松持久化防重 |
| 业务副作用 | 准备、分片、收尾只要会产生副作用，业务方都要保证幂等；平台拒绝旧回报不能撤销旧业务副作用 |
| 重派范围 | 必须服从[统一预算](./behavior.md#retry)和整轮终止规则，不以通信恢复名义无限重跑 |

业务幂等依据应匹配实际操作，例如商户日报按“商户 ID＋统计日期”保证唯一或允许覆盖重算。仅用 Task ID 或执行尝试标识可能无法保护跨 Instance 重跑。

允许重复业务执行不取消结果持久化时的尝试与状态校验、本地合并检查、Post 唯一创建及有界恢复。接收 ACK 不承诺结果持久化，框架仍对已保存数据和后续推进的一致性负责。

## 5.7 结果上报与确认边界 {#result-report}

执行器通过 go-zero RPC 回报结果，使用 etcd 发现的调度端执行器通信 Server 地址，不使用管理 Server 的发现目标，由 RPC 客户端负载均衡选择可用接收节点。回报无须经 Leader 中转，也不要求返回原派发节点；Leader 作为对等副本仍可接收回报。执行器不直接写调度表，数据所有权及状态推进集中在调度服务。

**第一版固定采用双端异步、有界内存缓冲，不提供同步／异步切换开关，不使用本地回报文件、持久化消息队列或跨重启结果缓存。回报 ACK 只表示调度端成功接收进内存队列，不表示已落库，也不表示该结果已被状态机采纳。** Task 状态和后续推进仍以有效结果的持久化提交为准。

### 执行器的有界回报缓冲与单次发送 {#executor-result-queue}

**2026-10-28 修订通过，2026-11-04 已实现公共 reporter，实际验证见[执行器运行记录](ordinary-readiness-review.md#ordinary-executor-runtime-progress)。结果由回报组件保留，发送者每次只负责一次 RPC，等待重试不占发送并发。** 本节替代此前“发送者持有结果完成全部退避重传后再取下一条”的安排，也将仅统计等待项的结果队列改为包含待首次发送、等待重试和在途记录的局部结果缓冲；不增加接单、业务和回报共用的总量额度。

业务处理器返回结果后，公共组件按[执行器处理流程](#executor-processing-flow)交接一份结果。交接成功后由回报组件保留原结果、原 Task／尝试身份、应用层已发起调用次数及下次可发送的本地时间，直至 ACK、永久交付失败或有限尝试耗尽。发送只是使用原记录，不提前释放保存位置；失败后更新原记录，不阻塞着将结果回填到可能已被新结果占满的队列。

业务处理器不负责网络上报，也不等待远端接收 ACK；组件内部的本地交接可以等待。缓冲满时，当前业务处理者持有这一份已完成结果，交接完成前不领取下一项，活动防重则已在业务实际退出时清理。已有结果的 RPC 完成处理、重试安排和位置释放不等待新结果准入，避免发送者等待回填、队列又等待发送者消费的循环阻塞；不得另起无界等待协程保存交接结果。

首次发送和到期重试共享有限发送并发，不拆固定来源份额。安排规则如下：

1. 新结果以交接成功的本地接纳时刻作为首次可发送时间，即可参与发送；可重试失败以本次调用结束时间加正退避，形成下一次可发送时间。
2. 有空闲发送能力时，选择已到时间的最早一条，同时间保持稳定的本地接纳顺序。后来的新结果不能持续插到已到期结果前面，持续失败的记录每次退到未来，不能一直占住发送者。
3. 每次 RPC 只发送一个 Task 当前尝试的结果，不为凑批等待。调用结束即释放发送并发；同一记录在途期间不得再次选中。本地串行发送不证明超时的远端请求未被接收，重复回报仍由调度端条件写入处理。
4. 没有已到期结果时等待最早时间或新的可处理事件，等待记录仍占原保留位置，不以无界等待协程或旁路记录保存积压，也不通过数据库扫描安排本地重传。相对等待和排序使用进程内单调计时语义；具体 Go 容器及并发原语结合完整流程选择，不提前冻结实现。

公平性只针对已经进入回报组件的记录，不保证按所有业务完成时刻全局排序，也不保证固定交付时间。RPC 自身的等待仍会占发送并发；缓冲全部用于等待重试时，允许发送者空闲而新的结果仍等待交接。服务恢复不跳过剩余退避；本方案消除发送者占着结果等待退避的连带阻塞，不承诺故障期间无限接纳或恢复瞬间排空。

结果积压通过交接等待传向业务等待队列，后者满时才对无法接纳的新请求返回 BUSY。回报组件保留条数和发送并发见[已通过初值](#reporting-defaults)，业务处理并发及等待队列采用[32／128 部署初值](#executor-business-defaults)。结果报文复用 RPC 层大小限制，不额外设置业务结果长度或缓冲总字节配额；条数有限不等于进程内存硬上限，业务结果构造、序列化、RPC 缓冲和 GC 也须验证。缓冲满不直接丢弃已有结果；永久错误或尝试耗尽按下节释放。停机遵守[共享宽限和晚返回保护](operations.md#process-shutdown)，交接等待不能无限延长退出。

### 回报重试预算与清理 {#report-retry}

**结果回报重试与 Task 执行重试独立。** 回报只是重发同一 Task、同一次执行尝试的已有结果，不重新调用业务处理器、不登记新执行尝试，也不消耗 Job 配置的 Task 执行重试次数。Job 执行重试次数为 `0` 时，仍允许按回报规则重传。

第一版用框架内部独立常量控制回报尝试次数、间隔和单次 RPC 超时，不进入 Job 配置页面。2026-10-28 已通过[7 次总调用、2 秒单次超时及带抖动退避](#reporting-defaults)，不沿用 Task 默认的 3 次额外执行重试和 10 秒间隔；普通、准备、分片及收尾结果共用这套回报规则。

一次 RPC 响应确认本条结果。2026-10-30 已通过的[回报错误分类与无效结果处理](data-contracts.md#result-error-classification)确定下列动作，只作用于结果回报，不外推到派发或取消接口，不新增一套错误框架，也不按错误文案解析分支。

| 本次回报结果 | 执行器动作 |
| --- | --- |
| 正常接收 ACK | 结束上报并释放原结果；ACK 仍不证明已落库或状态机已采纳 |
| 队列满返回 `ResourceExhausted`，或未就绪、退出、认证依赖失败返回 `Unavailable` | 按已有独立预算有限重传，原记录更新下次可发送时间，单次调用结束即释放发送并发 |
| 明确认证失败 `Unauthenticated`／`PermissionDenied` | 不再重传该条，记录错误及丢弃指标后释放；不能把组缓存未命中或认证依赖查询失败当作明确认证失败 |
| 既有 `bizerror` 携带 `common.invalid_request` | 作为永久报文错误结束该条，不匹配可变 Message 文案 |
| 网络超时、断连、响应丢失、未知错误码或异常响应 | 不能确定永久无效时保守地有限重传，不据此认定业务执行失败或消息未曾被接收 |

通用 `ResourceExhausted` 不能证明报文超大。只有本地能够证明当前报文超出实际发送上限，或已确定格式不符合契约时，才可按永久报文错误释放；无法确认来源时沿用有限重传，不凭服务端错误字符串推断。`Data` 缺省合法；业务失败结果不采用其 `Data`，处理器返回 `error` 或发生 `panic` 后形成的失败结果都是合法上报内容，不能当成回报失败。

仅实际发起应用层调用消耗一次尝试，等待、安排或重新参与选取不重置也不额外消耗次数。永久拒绝或尝试耗尽后记录错误及丢弃指标并释放，不静默截断、无限重传或重新调用业务；即使原业务实际成功，也不为保住结果无限占用内存。各条结果独立处理，不维护批内部分接收或重组逻辑；完整应答及校验分工见[结果上报契约](data-contracts.md#result-report-contract)。

本地释放结果不直接把数据库 Task 改成失败，不自行触发业务重跑，也不能撤销调度端可能已经接收或保存的同一结果。若后续恢复协议允许重新执行业务，仍按原 Task 执行预算及整轮终止规则记账。整轮超时用于未结束任务的兜底，不因回报重试延长期限。

这一取舍优先保证执行器长期运行，接受结果因有限重试耗尽而丢失，不仅限于进程退出导致的丢失。调度端采用不同的[写库故障保留规则](#scheduler-result-retention)，不套用执行器回报耗尽后的释放策略。

### 回报部署初值与重传常量 {#reporting-defaults}

**2026-10-28 已通过，2026-11-04 已实现并通过组件测试，尚未完成生产接线或压测。** 具体范围见[执行器运行记录](ordinary-readiness-review.md#ordinary-executor-runtime-progress)。以下只作用于执行器结果回报，不外推为业务并发、调度端写库参数或 Task 执行重试规则。

| 参数 | 初值 | 范围与口径 |
| --- | --- | --- |
| 回报缓冲保留条数 | **256 条** | 部署参数，包含待首次发送、等待重试和在途记录；发送期间不释放原位置，业务处理者尚未交接的结果不计入此缓冲 |
| 同时进行的回报 RPC | **16 个** | 部署参数，只约束正在调用的发送并发，不包含退避等待；每次调用结束后可处理其他到期结果 |
| 单次 RPC 超时 | **2 秒** | 内部常量，服从更短的进程停机剩余时间；框架客户端、调用 Context 和服务端方法超时须协调 |
| 应用层总调用次数 | **7 次，包含首次** | 内部常量，收到 ACK 或永久拒绝提前结束；不等于底层网络恰好发送 7 次，不重置业务执行预算 |
| 六次失败后的重试间隔 | **1、2、4、8、16、16 秒，各上下浮动 20%** | 内部常量，从上次调用结束计算；等待不占发送者，不增加独立重试并发或来源份额 |

名义退避时间合计 **47 秒**，不包含排队和 RPC 耗时，也不是保留 TTL、交付时限或故障恢复承诺。这组初值增加对几十秒短暂不可用的补报机会，同时接受结果保留更久、更容易填满缓冲的代价；停机剩余宽限不足时不保证用满 7 次。正常停机仍允许已接纳业务在剩余宽限内产生和交接结果，宽限耗尽后结束交接等待、停止新发送并取消在途调用，不重置原重传次数。

正退避、随机抖动和有限次数抑制连续重投，但有限并发不等于严格 QPS 限流。实际内存还受报文大小及编码等开销影响；默认 256 条不代表进程内存硬上限。以单条持续失败、连续新结果、缓冲满载、整体断网及恢复、ACK 丢失和停机验证吞吐、回报延迟、重试机会及内存，见[结果上报验收](verification.md#result-report-checks)；初值不是已验证的性能结论。

### 调度端入队与后台落库 {#scheduler-result-queue}

**2026-10-29 已确认：Task 结果逐条关联读取、条件更新和独立提交，替代此前批量预读及多条结果小批量提交的正常路径。不设置整批保存超时，也不增加整批超时后改为单条保存的降级机制。** 同日通过[结果保留、保存并发及重试初值](#scheduler-result-defaults)，2026-10-30 通过[回报错误分类](data-contracts.md#result-error-classification)；单次保存预算、Instance 执行期限和进程共享停机宽限分别适用，不混用。Protobuf 已生成，普通单条 Saver／仓储、结果 Queue／消费者及 RPC 接纳适配已实现；Job 生产配置、宿主接线、独立回报 Server 及普通父完成推进已落实，实际验证见[父完成记录](ordinary-readiness-review.md#ordinary-completion-progress)，普通重试接续见[阶段 4 记录](ordinary-readiness-review.md#ordinary-retry-progress)。遗漏恢复与分片阶段推进仍待实施，不能把本地完成提示当作持久化恢复保障。

1. 按[内部信任边界](architecture.md#internal-trust)完成组 Token 认证及报文格式等基础校验，报文大小复用 RPC 接收上限，保留已认证的组上下文。组缓存未命中先走既定回源；认证依赖查询失败返回 `Unavailable`，不当作 Token 错误。
2. 不查 Task 表，对本次请求的单条结果进行基础校验并尝试交给有界结果队列；成功入队才返回接收 ACK，队列满返回 `ResourceExhausted`，未就绪或退出返回 `Unavailable`。明确认证失败与永久报文错误按[已定分类](data-contracts.md#result-error-classification)拒绝，不能丢弃结果却回复已接收。
3. 后台从已到期结果中选取一条进行本次保存，用一次关联查询取得该 Task 与所属 Instance 的必要字段。先按[结果保存协议](data-contracts.md#task-result-persistence)排除无合法目标、跨组、关系不符、旧尝试、Task 已终态或执行器身份冲突等已确定失效的结果，再解析仍需使用的本轮冻结配置；不让无效结果因无须使用的坏快照而长期占位。最终写入仍以原尝试号、执行中状态和空或匹配的执行器绑定身份为条件；每条 Task 的结果、目标状态和相关时间使用同一条条件 UPDATE 原子保存、独立提交。不先查 Task 再补查 Instance，不读取当前 Job 配置替换本轮快照，也不扫描整轮 Task 或在此统计完成情况。
4. 该条结果的提交确认后，通知本节点进行对应阶段的推进检查，不等待其他结果全部保存；不因入队或 ACK 提前生成分片、创建 PostTask 或结束 Instance。

结果保存与 Instance 推进是两个分支：前者按 Task 类型核验和持久化本次业务输出，准备结果供后续生成读取，普通／分片／收尾结果供相应完成判定读取；后者消费已提交事实，根据本轮快照和 Task 类型决定结束、等待或进入仍获授权的后续阶段。不能把每条结果回报直接展开为查询当前 Job、扫描整轮 Task 和更新父 Instance；结果提交后的提示只交接检查职责，不承诺父推进已经完成。

认证和接收不能代替持久化授权校验。关联查询取得可信的 Task／Instance 所属关系、执行器组及本轮冻结的重试上限和间隔；组身份沿用入口认证结果，不再次查询或校验 Token。查询后的内存判断不能替代 UPDATE 的原尝试、旧状态及绑定条件，重复入队、旧尝试或跨组引用不能覆盖有效状态。已有绑定必须匹配回报进程；绑定尚未保存时仍允许当前有效尝试的结果先保存。结果不补写绑定；失败仍有预算则直接进入等待重试，不先保存最终失败再恢复，也不在此扣次数或增加执行编号。每条结果按该次保存取得的数据库处理时间设置结束时间及最早重试时间，不使用前次读取或执行器自报的旧时间，不冒充业务真实结束时间；当前普通结果 UPDATE 内共用一次数据库取时，不另发取时查询。

单条关联读取放弃批量预读摊薄查询往返的收益：N 条正常结果约有 N 次关联查询及 N 次条件 UPDATE，另有实际取时方式和事务提交的成本。每次只查询该条必要字段，不为一次结果拆成多次关联补查，也不增加批量预读组件、凑批等待或预读批量参数；后续仅在实测查询往返成为瓶颈时再评估有界预读优化。逐条保存仍有行写、WAL、索引和提交成本，不能宣称具有批量事务的吞吐。

某条查询或保存发生技术失败、原因不明或提交不明，或仍需使用的平台快照损坏、配置版本未知时，只保留该条原结果、退避并告警，按[已定分类](data-contracts.md#result-error-classification)处理；不回滚或重放已经明确提交的其他结果，也不将尚未保存的结果当作成功。不得仅凭 SQLSTATE、数据库异常名称或重复失败次数推定结果永久无效。只有已经定位到该条结果内容，并独立核实需要保存的内容确实无法用 JSONB 表示，例如 JSON 字符串包含 `\u0000`，才可按确定无效内容释放；平台配置或 SQL 缺陷不属于此类。结果保存不新增父必须 RUNNING 且尚未截止的前提，父 STOPPING 或到期本身不使结果无效，仍遵守既定[父子终止竞争](data-contracts.md#task-result-persistence)；保存结果不等于授予新执行机会。积压向入口传导，不因已经 ACK 就把写库错误仅记录日志后丢弃。

影响一行且确认该条保存已提交，才表示本次结果生效；无错误但零行只表示本次未应用，不补查猜测原因，也不证明此前已经保存成功。单条保存正常完成后释放该条已处理结果，可对已核实归属的 Instance 发本地检查提示，包括重复结果重做后零行的情况；检查只按数据库当前事实推进，不恢复父终态或直接重派，不再向执行器反向确认落库。单次数据库操作仍须限制等待，并使用后台组件生命周期及剩余停机宽限控制，不沿用已经返回的入站 RPC Context；超时不能被当作确定回滚或结果已保存的证据。

执行器结果缓冲条数和发送并发，以及调度端结果保留条数、保存并发和单条保存预算属于部署参数，不进入 Job 页面；执行器不设置网络合批窗口或批次数量参数，调度端不设置结果合批提交参数。执行器按[回报初值](#reporting-defaults)、调度端按[保存初值](#scheduler-result-defaults)分别执行，不因数值相同就共享配置含义。[进程停机](operations.md#process-shutdown)采用已确认的共享有限宽限。逐条结果保存不取消下面的分片完成检查合并；回报错误分类及[执行 RPC 协议与装配](data-contracts.md#execution-rpc-contract)已定，当前协议、普通单条保存与结果队列实现见[结果队列进度](ordinary-readiness-review.md#ordinary-result-queue-progress)，完整生产装配与进程验收仍待完成。

### 调度端写库故障与结果积压 {#scheduler-result-retention}

**调度端已经接收的结果逐条独立保存；遇到可恢复的数据库故障或提交不明时，有界保留受影响的原结果并退避重试，结果队列满后拒收新结果，不按固定重试次数或保留 TTL 主动丢弃。** 不以整批结果为重试单元，不重放已经明确提交成功的其他结果。写库重试不占 Task 执行预算，也不重新调用业务处理器。上述保留、退避与并发行为已落实到 `taskresult.Queue`，Job 生产接线已落实，当前验证范围见[生产接线进度](ordinary-readiness-review.md#ordinary-result-wiring-progress)。

| 情况 | 已确认处理 |
| --- | --- |
| 可恢复的数据库故障持续存在 | 保留受影响的原结果并按条退避重试，不无限积攒新结果，不因失败次数或等待时间达到阈值就丢弃，不高频空转；一次尝试结束即释放保存能力，退避不占保存者，其他已明确提交的结果独立释放 |
| 单条保存提交结果不明 | 保留该条原结果，退避重做原条件更新；不假定已经回滚，不覆盖已生效或已失效的状态，不重放其他已明确提交的结果 |
| 结果队列已满 | 以 `ResourceExhausted` 拒收新回报，不对未接收结果返回成功 ACK，不另建无界等待队列或为每条结果新增等待协程 |
| 数据库恢复 | 重新按 Task 归属、当前尝试、状态及整轮终止规则处理；有效结果提交后才推进，不因曾经 ACK 就无条件写入 |
| 正常完成保存或无数据库错误的 UPDATE 零行 | 结束该条处理并释放原位置；零行不证明此前已保存，不补查猜测原因，也不据此宣称业务成功 |
| 已有 JOIN 确定无合法目标、跨组、关系不符、旧尝试、Task 终态或身份冲突 | 结束该条保留；先排除失效，再解析仍需使用的冻结配置，不为已无效结果保留坏快照重试 |
| 确定的格式错误或结果内容无法用 JSONB 表示 | 按[已定永久无效边界](data-contracts.md#result-error-classification)记录并释放；必须定位结果内容并独立核实，不能仅凭 SQLSTATE 或失败次数推断 |
| 仍需使用的平台快照损坏、未知配置版本或平台 SQL 缺陷 | 保留原结果、退避并告警，不当作业务方的永久无效结果；占满既定 512 条时继续背压，不通过次数或 TTL 腾空 |
| 已接收结果全部在等待退避，保留空间已满 | 允许保存者暂时空闲且新回报仍被拒收，不增加旁路接纳；依赖恢复后仍可能等待剩余退避，不保证立即排空 |
| 接收节点落库前退出 | 接受内存结果丢失，不依赖本地文件、持久化队列或执行器必然重报来补回 |

2026-10-29 的逐条保存及保留安排替代此前“消费者保留整批、整批重试结束后再领取”的口径。结果保存组件从接纳至结束处理始终保留该条原结果，等待首次保存、等待重试和在途都计入同一个局部保留上限，不另外增加在途额度。一次保存尝试只处理一条结果，调用结束并完成必要收尾后释放本次保存能力；失败仅更新原记录的下次处理时间，不阻塞回填满队列，也不反复复制或新增无界等待协程。这是保存组件内部的记录边界，不是接单、业务执行、回报及落库跨生命周期共用的额度；具体 Go 并发原语和内部实现按完整流程确定。

新结果的可处理时间为组件接纳时刻；可重试结果的下次处理时间为本次保存结束时刻加正退避。选取已经到期且当前不在处理中的最早记录，时间相同时保持稳定接纳顺序；每次处理期间同一条记录不得再次选中，不为首次保存与重试切分固定份额。查询、更新或提交阶段失败都属于这条结果本次保存尝试，不另起多套重试计数；退避按连续失败次数推进，参数见[保存初值](#scheduler-result-defaults)。本地相对等待使用进程计时，不查询数据库安排本地重试，也不持有事务等待退避。

这些约束不等于整个 Go 进程的内存硬上限：业务结果构造、序列化、RPC、对象和 GC 仍有额外开销。结合实际 RPC 报文上限与结果体积验证占用，大结果场景应调整保留条数；第一版不做队列总字节配额或按 MB 准入，也不增加独立业务结果长度限制或 Job 页面参数。准备工作项数组的生成和暂存仍按其独立契约设计。逐条结果保存不撤销已定的任务生成、尝试登记或 STOPPING 子取消批次规则。

数据库是调度端推进的必要依赖，故障期间由保存组件有界保留已有结果，满后拒收新结果；让出保存能力只消除退避空等，不消除数据库故障或保留空间被占满的影响。执行器有限重报与调度端保留采用不同规则。内存保留不延长整轮截止时间，也不使已停止或超时的 Instance 复活；进程停机在[统一宽限](operations.md#process-shutdown)内尽力保存已接收结果，预算到期可以结束等待，不把该期限当作正常运行期结果 TTL。[回报错误分类](data-contracts.md#result-error-classification)已定，[执行 RPC 协议与装配](data-contracts.md#execution-rpc-contract)已通过，协议与普通结果队列已实现；驱动和队列生命周期验证范围见[结果队列进度](ordinary-readiness-review.md#ordinary-result-queue-progress)，Job 结果停机装配已落实，实际验证见[生产接线记录](ordinary-readiness-review.md#ordinary-result-wiring-progress)，System 执行器停机接线仍待完成。

### 调度端结果保存初值 {#scheduler-result-defaults}

**2026-10-29 已通过；2026-11-04 已落实 Saver／Queue 及 Job 生产配置和宿主接线，压测尚未完成。** 部署配置为 `ResultPersistence.Capacity`、`Concurrency` 和 `SaveTimeout`，分别传给 Queue 和 Saver；实际验证见[Job 生产接线进度](ordinary-readiness-review.md#ordinary-result-wiring-progress)。以下只作用于调度端已接收结果的保存，不替代执行器回报参数、Task 执行预算或其他调度职责的批次规则。

| 项目 | 初值 | 计量与配置边界 |
| --- | --- | --- |
| 每节点结果保留上限 | 512 条 | 部署可调，包含待首次保存、等待退避和在途结果；已接纳记录至释放始终占原位置，不能另外再加 8 条在途额度 |
| 每节点保存并发 | 8 | 部署可调，同时处理的单条结果数；覆盖必要读取、更新及提交，一次尝试结束后让出，不在退避期间占用 |
| 单条一次保存预算 | 2 秒 | 部署可调，从该条进入本次保存处理起算，含连接等待、必要关联查询、更新及提交确认，不含排队和退避；服从剩余停机宽限 |
| 可重试失败退避 | 1／2／4／8／16／30 秒，之后保持 30 秒，各上下浮动 20% | 内部初值；从本次保存结束计算下次可处理时间，不设重试次数耗尽或结果保留 TTL |

8 个保存并发是当前 Job 默认共享数据库连接池上限 50 背景下的部署起点，不是独占或预留 8 个连接，也不保证其他职责没有连接等待；创建、派发、管理、恢复和完成检查仍共用数据库资源。它与执行器 16 个回报 RPC 并发无须相等，应结合有效落库吞吐、积压、连接等待和其他路径延迟进行验证与调整，不能凭并发数承诺性能。512 条只限制局部记录数，不能据此推导整个进程的内存硬上限。

2 秒只约束该条结果本次保存，不给一组结果设置共同处理期限，不增加整批超时或超时拆批规则。后台使用组件生命周期派生的 Context，不沿用已经返回的入站 RPC Context；停机时同时服从整个进程剩余的 30 秒共享宽限。到期取消不证明数据库已经回滚、锁已释放或提交未发生；本次调用完成必要收尾后才归还保存能力，提交不明仍仅保留该条并重做原条件写入。具体驱动行为、错误分类、条件 SQL 和停机交界按[结果保存验收](verification.md#task-result-persistence-checks)验证，不提前固定 Go 编码结构。

### 易失结果与恢复边界 {#volatile-results}

| 故障位置 | 已确认的处理边界 |
| --- | --- |
| 调度端未接收，或执行器未收到 ACK，且未确定永久拒绝 | 按已定错误分类在独立回报额度内重传同一尝试；不占执行重试预算，重复回报不得重复推进 |
| 回报重试耗尽 | 释放执行器本地结果，记录错误及丢弃指标；不直接修改 Task 状态或重新运行业务，原结果可能已在调度端接收或落库 |
| 执行器在结果有效落库前退出 | 内存结果可能丢失，不依赖原机文件或持久卷重放 |
| 调度端 ACK 已收到、执行器已释放结果，接收节点落库前退出 | 唯一结果副本可能丢失，执行器重传不能保证补回；执行器甚至仍然在线 |
| 有效结果已提交，后续检查提示丢失 | 按持久化事实恢复平台推进，不重新执行已确认成功的业务步骤 |

平台不保证每条业务执行结果跨进程故障无损保存，也不能从“节点仍在线”推断当前尝试仍在运行。没有绑定及结果时按[绑定缺失规则](#missing-binding)有限观察并条件结算；已有绑定但无有效结果时按下述规则等待整轮终止，不再因失联或结果丢失提前重派。任何路径都不能承诺重建原来的真实成功结果。

### 已绑定但无结果时等待整轮超时 {#bound-result-wait}

**当前尝试已有持久化执行器绑定，但没有有效落库结果时，第一版不因执行器失联、重启或回报丢失而提前结算重派，统一由有限整轮超时兜底。** 执行器仍在线但回报重试耗尽、调度端已 ACK 却在落库前退出，也遵守同一规则。

| 事件 | 已确认处理 |
| --- | --- |
| 有效成功结果落库 | 按正常规则推进，不因为曾经失联而拒绝仍有效的结果 |
| 有效失败结果落库 | 有剩余预算时可形成重试候选，下一次执行仍须经过父行授权检查；不因处理结果而统一锁父 |
| 无有效结果，包括已知执行器退出 | 当前尝试保持执行中，不创建新尝试、不返还已占机会，不凭节点离线提前重派 |
| 有效手动停止 | 按既定取消规则终止，不必等到超时 |
| 整轮到期 | 自动检查先尝试按完整最终结果结束；仍不具备条件时，保存 STOPPING 及超时原因，未结束 Task 按取消规则收敛，全部子终态后 Instance 最终失败；即使有剩余执行次数，也不再授权新工作 |

“等待结果”只是对执行中状态的描述，不新增状态、独立 Task TTL、活动探测或心跳，也不在某个调度节点持续保留一个等待对象。首次开始及截止时间持久化，由 [RUNNING Instance 统一复核](#instance-recheck-direction)补上遗漏的完成或超时处理；重试、换节点或丢失回报均不延长期限。整轮超时不允许 `0` 或无限时长；新增表单预填 900 秒，实际执行使用本轮已保存的配置，不在恢复时补默认值。

接受的代价是故障恢复不够及时：例如整轮预算 15 分钟、第 1 分钟执行器宕机，在没有有效结果或人工停止时仍须等待剩余 14 分钟才到整轮截止，平台保存超时终态还可能叠加周期复核及排队延迟，而不使用剩余次数换节点重跑。一个分片永久丢失结果也可能拖到整轮超时，阻止正常 Post，并按既定阻塞策略影响后续触发。已成功 Task 不改为失败，不将缺少回报当作业务明确失败。

这一规则保证未结束尝试有整轮终止边界，不保证每轮自动恢复成功；平台超时不证明业务代码已经退出，数据库不可用时也不能保证准时提交终态。已持久化的有效结果仍可恢复平台推进；没有绑定的尝试仍按独立观察与条件结算处理。[普通结果条件更新](data-contracts.md#task-result-persistence)及迟到结果处理已通过；[停止超时与统一子取消条件写入](data-contracts.md#instance-termination-sql)也已通过，具体实现、索引与参数继续落实，不改变上述选择。

普通回报只条件更新自己的 Task，不逐条锁定 Instance，也不为每条回报更新 Instance 完成计数。回报用于保存执行结果，不另存一份重复业务日志。详细日志位置见[管理与运维](./operations.md)。

Instance 停止决定、各 Task 的取消／结果落库、父最终结束不承诺一次原子变更。父先进入 STOPPING，各 Task 按自身终态条件收敛，全部子终态后才最终结束父；任何有效子结果都不得撤销停止决定、恢复父终态、授予新尝试或启动正常收尾。短暂重试候选不等于获准执行，已取消 Task 不能被迟到成功覆盖。[普通结果条件写入](data-contracts.md#task-result-persistence)与接收应答语义保持；[停止超时及子取消协议](data-contracts.md#instance-termination-sql)采用本轮修订的顺序，所有 Task 类型共用有界批处理，恢复接续数据库处理，不保证补送取消通知；具体实现仍待完成。

结果回报与 `Notify` 不是同一个方向：前者由执行器向调度服务提交，后者是平台向业务处理器发送的整体进度回调。第一版保留结果回报，不提供业务内部实时进度和 Notify，见[目标与范围](./scope.md)。

## 5.8 Instance 完成检查与本地合并 {#completion-check}

正常路径为：**结果提交 → 本节点按 Instance 合并检查 → 读取阶段所需完成事实 → 按结果结束或进入仍获授权的后续阶段**。普通与分片共用完成检查及终态竞争机制，不为普通任务另设一套完成并发协议；阶段职责与完成条件仍有区别。不增加 Redis 完成计数器、MQ 或整轮固定负责人。

这里合并的是“本轮是否具备推进或结束条件”的检查提示，不是执行器上报 RPC，也不合并或省略 Task 结果。例如同一 Instance 的 10 条结果在本节点检查开始前陆续提交，可以只保留一个待检查提示；10 条结果仍分别保存。它主要减少密集分片回报的重复查询，普通或仅一个分片的任务沿用同一机制，不承诺它们也有同等合并收益。

### 事件来源与合并边界

- 普通、准备、分片或收尾 Task 进入最终状态的有效结果先提交，再发出本地待检查提示；不能在提交前判断整轮完成。
- 失败后还有重试的分片保持未终态，不能把重试等待当作分片已完成；准备与收尾结果按各自阶段推进，不一律执行分片汇总查询。
- 分片生成完整的持久化事实提交后也通知检查，不能仅依赖结果回报；合法空数组同样走该路径。生成完成后集合固定，最终分片状态不得被普通迟到回报逆转；生成封口字段及原子协议仍待设计。
- 每个节点维护按 Instance ID 去重、有容量上限的待检查集合，以有限并发处理。同一节点、同一 Instance 同时最多运行一个检查，不提前固定 Go 并发原语或内部结构。
- 合并窗口默认 `100ms`，从首次提示到达开始计算，后续提示不延长；它是内部初值，不做 Job 页面配置。具体初值及提示生命周期按下节执行。
- 检查期间若又有结果提交，必须保留一次后续检查。标记清理、重新排队和新事件登记须协调，不能因“已有检查在运行”直接丢弃后续事件，也不能由旧检查结束时清理掉新提示。

合并只在接收节点内部生效。同一 Instance 回报分散到多个节点时仍可能分别检查，大量不同 Instance 的稀疏回报也不容易合并。不能宣称全局只查一次；验证需要同时观察完成延迟、查询次数和数据库负载。

| 参数 | 默认值 | 计量范围与配置归属 |

| 保留的唯一 Instance ID | 512 个 | 每调度进程共用，包含等待合并、排队及正在检查；部署可调 |
| 同时进行的检查 | 8 个 | 每调度进程共用，不按 Job／Instance 叠加；部署可调 |
| 单次检查处理预算 | 2 秒 | 从实际开始处理算，包含连接等待、必要事实读取、本次有限状态写入及提交；不含排队或合并等待；部署可调 |
| 合并窗口 | 100ms | 从首次提示算，后续提示不延长；集中维护的内部初值，不做 Job 页面参数 |

这里只保留 Instance ID 和本地安排检查所需的信息，不在集合中复制 Task 结果或维护完成计数。三个部署初值独立于结果保存组件，即使数值相同，也不共用结果保留位置、处理预算或并发额度。普通、准备、分片、收尾阶段共用检查安排，实际完成条件仍按下节区分。

提示按以下规则处理：

1. 尚无该 ID 时，尝试接纳一个条目，最早检查时间为首次提示到达时间加 100ms。到点只表示可处理，不保证立即开始；合并等待及排队不占检查并发。
2. ID 已在等待时，只合并提示，不重复排队、不增加条目，也不延长原最早检查时间。集合满时，已有 ID 的提示仍可合并；新的正常提示不等待空位，放弃本次加速提示，不影响已提交的 Task 结果，也不让结果保存处理者等待检查结束。
3. ID 正在检查时，检查期间的第一条新提示确定下一轮最早时间为该提示到达时间加 100ms，后续提示继续合并，不延长这个时间。当前检查不与下一轮并发执行。
4. 本次检查结束后，若期间有新提示且未明确确认父 Instance 已终态，保留原条目并重新排到队尾一次，沿用已记录的下一轮最早时间；不在结束时重新加 100ms，也不重新申请集合位置。重新排队给其他 Instance 留出处理机会，不在当前处理者内连续循环检查同一 ID。
5. 检查开始、期间提示登记、结束清理及重新排队必须协调。一个新提示要么归入尚未结束的条目并安排后续检查，要么在旧条目释放后按新提示接纳规则处理，不能被旧检查的清理覆盖。

例如检查读到最后一个分片尚未完成，随后该分片结果提交并通知，本轮检查仍可能返回尚不具备条件；期间登记的新提示必须在本轮之后再安排检查。只有明确确认父终态，才可以直接清理期间合并的后续提示；UPDATE 零行、技术错误和提交不明都不能当作这一确认。

| 本次检查情况 | 条目结束规则 |
| --- | --- |
| 明确尚未具备推进条件，期间没有新提示 | 释放条目，等待后续通知；不持续轮询该 Instance |
| 期间有新提示，父未确认终态 | 保留条目，按已记录时间重新排到队尾一次 |
| 数据库技术错误或提交不明，期间没有新提示 | 结束本次本地处理并记录错误，由后续通知或既定 Leader 复核重新读取事实；错误本身不产生无限重查 |
| 数据库技术错误或提交不明，但期间有新提示 | 新提示仍按上述规则安排后续检查，不能因本次失败一并清掉 |
| 明确确认父已终态 | 释放条目及其合并提示，不再推进 |

无新提示时的成功有限推进或本次条件写入未应用，同样结束本次本地处理，不由旧提示自行循环；有新提示且父未确认终态时仍重新安排。零行只表示本次未应用，不证明此前已经成功，也不是 `NotReady`；检查失败不转成正常完成或超时停止。持续新提示仍可能触发后续检查，100ms 合并窗口不是数据库故障退避机制。

2 秒只约束一次必要事实读取及有限状态推进，不包含等待业务完成、派发 RPC、循环生成整轮分片或 STOPPING 的整轮子状态处理。具备阶段条件时进入对应授权／交接流程，停止处理交给已有停止组件，不能占着检查处理者等待这些工作全部结束。具体分片生成交接仍随生成协议闭合，不借本节冻结 Go 组织方式。

检查使用进程组件生命周期及独立处理 Context，不复用已返回的入站 RPC Context。预算到期发起取消，不证明数据库已回滚、锁已释放或写入未提交；在途调用及必要清理实际结束后才释放检查并发，之后再按提示规则结束或重排。共享 30 秒停机宽限及内存提示易失边界保持。

检查失败且没有后续提示时，已提交 Task 结果仍在数据库中，但父推进可能延迟至既定 Leader 复核，甚至因剩余期限不足而无法启动后续阶段；不承诺本地错误会很快补上。集合满、通知丢失及进程退出也沿用同一补漏边界。参数是部署初值，需验证密集／稀疏回报的查询量、完成延迟及数据库负载；不根据合并次数或更快 ACK 宣称性能提升。

### 查询最小必要事实

完成检查先解释父状态，已有终态即退出，WAITING 由首次启动路径处理，STOPPING 转停止处理；只有父仍 RUNNING 时，根据 Instance 本轮快照与 Task 类型判断相应的最少事实，不因当前时间越过截止就跳过结果检查，也不改读当前 Job 决定本轮模式或 Post 选项。普通模式使用已通过的[一次 LEFT JOIN 查询](data-contracts.md#ordinary-completion-query)，父与普通 Task 来自同一语句快照；父优先是解释顺序，不要求两次 SELECT。读取不加显式锁、不加载业务 Data，复用现有单例索引。已通过的判定分支如下：

| 本轮事实 | 正常推进结论 |
| --- | --- |
| 普通模式，普通 Task 已成功或最终失败 | 按该 Task 结果结束 Instance；待执行、执行中、等待重试均不具备结束条件 |
| 分片模式，PreTask 最终失败 | Instance 失败；不生成分片、不等待或创建 Post |
| PreTask 成功，但分片尚未完整生成封口 | 尚不具备最终结果；生成属于另一个受父状态和截止限制的推进动作 |
| 已生成封口，但仍有未成功也未最终失败的分片 | 尚不具备正常结束或创建 Post 的条件；等待重试不算最终失败 |
| 已生成封口，分片均成功或最终失败，未配置 Post | 无最终失败则成功，否则失败；明确的合法零分片按零计数成功结束 |
| 已生成封口，分片均成功或最终失败，配置了 Post | Post 未最终结束则尚不具备整轮结果；父仍运行且未到期时可进入唯一 Post 创建／授权，即使全部分片最终失败也适用 |
| 已满足分片条件，配置的 Post 已成功或最终失败 | 分片与 Post 都无最终失败才成功，否则失败；Post 成功不能抹除分片失败 |

对已封口的分片集合，先用适配索引的存在性检查判断是否仍有未完成工作，仅在需要推进或结束时读取必要统计和摘要；不在每条回报中加载整轮 Task 列表。正常分片汇总以成功／最终失败为输入，不将取消冒充业务成功或失败。合法零分片必须有明确生成完成事实，不能只因查不到 Task 就结束。

这些父锁外读取依赖三项稳定性前提：分片封口后集合不再增长；Task 成功、最终失败及取消不回退；活跃 Instance 的 Task 不被历史清理移除。Instance 父行锁本身不能冻结所有子 Task。普通与分片共用机制不等于忽略准备／收尾阶段；状态编码见[Task 字段契约](data-contracts.md#task-field-contract)。普通完成查询已收口；具体生成封口字段、完整分片查询 SQL 和索引仍待细化，执行计划待实施验证，`EXISTS` 不保证必然避免大量扫描。

具备本轮最终结束条件时走[正常完成条件更新](#instance-finalization)；仍需生成分片、创建 Post 或执行重试时，只能进入对应的新工作授权协议，截止后不得启动。只有成功读取并明确判定最终结果尚未齐备，才属于 `NotReady`；条件 UPDATE 零行、查询／写入技术错误及提交不明都不是 `NotReady`，不能据此改判超时。本地集合只保存加速提示，不是完成数量或状态的权威来源。

普通模式另按[异常分类](data-contracts.md#ordinary-completion-query)区分：同一查询成功返回 RUNNING 父而普通 Task 缺失或已取消，记录诊断、不补建 Task、不正常完成，但可按明确未完成进入原截止后的既有超时流程；不能把已知异常事实等同于查询失败。仍需使用的冻结配置不可解读、未知状态和数据库技术错误必须报错，不能转换为 NotReady；父已终态或 STOPPING 时先走对应分支，不把普通 Task 异常规则套给分片模式。

### 通知丢失与容量耗尽

集合满、数据库暂时异常、节点退出或提交后未通知，都不能丢失已提交结果。“结果已齐但未推进”按[RUNNING Instance 统一复核](#instance-recheck-direction)，由 Leader 每 2 分钟从 Instance 侧有界选择开始已超过 4 分钟的候选，再定向读取所选轮次的 Task 事实；不从 Task 表跨轮次查找完成结果或待推进标记。“Post 已保存但未派发”仍由派发恢复接续。不新增独立的全表汇总轮询，也不永远只检查最老一批。统一复核分页、[本地检查安排与初值](#instance-check-defaults)及[扫描预算与恢复补充](#instance-recheck-defaults)均已通过；恢复按共享集合占用量补充，拥塞时预算内等待，不保证持续或覆盖整个扫描窗口的拥塞下仍能接纳恢复候选。

## 5.9 原子创建收尾与并发终止 {#post-creation}

多个节点可以重复判断“可能已完成”，但只有通过持久化协议才能创建已配置的业务收尾。该机制已经确认，不使用额外 Redis 分布式锁或专门的数据库锁表；未配置 Post 时直接进行平台终态推进，不为套用本流程创建空 Post。

候选推进者按以下顺序处理：

1. 开启 PostgreSQL 默认 `READ COMMITTED` 事务，以 Instance **主键等值条件**执行 `SELECT … FOR UPDATE`，只锁单表的一条记录。
2. 锁内重新检查本轮仍允许推进，并按当前数据库时间确认尚未到截止；已存在 PostTask 则结束创建尝试，不能把事务外完成检查当作写入许可。Post 创建属于新工作授权，不适用允许迟到的平台终态收尾。
3. 复核分片生成完整，且全部分片成功或最终失败；待重试分片尚未结束，取消不能冒充业务成功或失败。部分或全部分片最终失败都不阻止已配置 Post；PreTask 最终失败则不走本创建路径。该判断依赖已固定的分片集合和不回退的最终状态，Instance 行锁不会自动锁住所有 Task。
4. 按 Instance 保存的收尾选项及本轮执行配置创建 PostTask，提交事务并释放行锁；不改读编辑后的 Job。PostTask 记录本身表示收尾工作已创建，不为这把锁额外增加一个独立阶段字段。
5. 本次成功创建者提交后执行正常路径的本地有界派发；已有但未派发的 PostTask 由共同恢复协议接续，不绑定创建节点。

数据库同时保证**同一 Instance 最多一条 PostTask**，兜底防止其他入口或遗漏检查造成重复创建。已定[单例部分唯一索引](data-contracts.md#task-field-contract)覆盖普通、准备、收尾类型，不覆盖分片类型，不能改成无条件“每类 Task 每轮只有一条”。Post 重试仍复用原记录，实际迁移及创建 SQL 尚待对应模块实现。

同一 Instance 的两个候选者依次取得锁，后取得者看到已有 PostTask 后退出；不同 Instance 锁不同记录，可并行推进。锁只保护少量数据库校验与插入，不读取和组装整批业务结果，不包含 RPC、Redis 等外部 I/O，也不持有到执行器完成。这是短事务并发保护，不是整轮归属。

派发 Post 时仅提供[公共输入与分片汇总统计](data-contracts.md#post-input)，不组装或传输分片执行明细，不增加供 Post 使用的结果查询 RPC。Post 所需业务记录由处理器查询自己的业务存储，调度服务不读取业务表。这不取消平台判断分片是否结束、计算统计和确定 Instance 终态所需的内部查询。

停止、超时和收尾创建通过同一 Instance 状态协议协调：

| 竞争顺序 | 必须保持的结果 |
| --- | --- |
| 停止或超时先提交 | 收尾事务复核后不再创建 PostTask |
| PostTask 先提交，随后停止或超时 | 阻止后续正常派发和重试，对在途及运行中执行尽力取消 |
| 终止后收到成功回报 | 不得把 Instance 改回成功，也不得恢复后续派发 |

提交与实际 RPC 之间仍有竞争窗口，行锁不保证停止后绝无 RPC 或业务副作用；沿用[尽力取消、不等待实际退出](./behavior.md#stop-semantics)的规则。PostTask 记录唯一也不等于 Post 业务恰好执行一次。

## 5.10 Instance 汇总归属 {#instance-finalization}

平台完成检查、结果统计和 Instance 状态更新由**调度服务内部推进逻辑**负责，不放进业务 Post 处理器，也不另建“平台汇总 Task”。PostTask 只承载业务收尾，其执行结果与分片结果一起成为平台终态判断的输入。

普通 Task、分片及已配置 Post 的结果均由共同完成机制处理，但须满足各自阶段的最终结束条件。仍可重试的失败不算最终结果；准备最终失败、合法零分片、Post 缺失等按[阶段结局](behavior.md#stage-outcomes)及[完成前置条件](#completion-check)判断，不机械地用“当前查到的 Task 都已终态”代替完整流程。Post 成功不能抹除分片最终失败。

**正常完成条件更新、结束时间和摘要语义已通过。** 先在父锁外读取稳定完成事实及必要摘要，再以 `WHERE id = :instance_id AND status = 2` 条件更新父记录，目标仅为成功 `3` 或失败 `4`，不附加 `deadline_at` 条件；不先显式锁父再查询整轮 Task，也不把已过截止的完整结果改判超时。UPDATE 自身取得行锁，与新授权及其他终态写入协调。对应 SQL 由[数据契约](data-contracts.md#instance-completion-contract)统一维护，普通完成读取已通过，完整分片事实查询与索引仍待设计，不因更新语句通过就宣称执行模块已经实现。

正常完成的 `finished_at` 在 UPDATE 中使用 `clock_timestamp()`，表示该表达式在 UPDATE 中求值时的数据库时间，不保证在实际行锁取得后求值，也不是事务提交或业务退出时刻；不能沿用授权事务“锁后单独读取时间”的解释。审计字段沿用现有更新规范，不承担业务时间语义，不倒填截止时间。

正常结束的结果摘要与原因按以下来源保存，不依赖回报到达先后：

- 普通 Instance 复制普通 Task 的最终摘要；PreTask 最终失败直接结束时复制该 PreTask 最终摘要，合法空字符串也原样保存，不能回退拼接旧尝试说明。
- 分片 Instance 生成包含业务分片总数、成功数、最终失败数，以及适用 Post 结果的汇总摘要，不拼接全体子 Task 的摘要或详细输出。
- 正常成功保存 `success`，正常失败统一保存 `execution_failed`；即使子原因为 `result_unknown` 或 `dispatch_rejected`，也不直接复制为父原因。人工停止和超时分别保存 `manual_stop`、`instance_timeout`，STOPPING 时冻结、最终结束沿用。六个稳定值及 Task 的 NULL／终态语义见[原因字典](data-contracts.md#execution-end-reasons)，任务级诊断仍保留在 Task。

只有影响一行且明确确认提交，才表示本次结束成功。零行只表示本次未应用，不能据此宣称已成功或转入超时；查询／写入失败、提交不明同样不能当作 `NotReady`。按已有有界处理与恢复重读数据库事实，不覆盖已有终态，不重复本次终态后的动作，也不重新执行业务。

Task／Post 最终结果已持久化、Instance 更新中断时，只恢复平台结束，不重新执行业务；即使恢复时已超过截止，只要父仍为 RUNNING 且具备本轮完整最终结果，仍可按结果结束。允许有效结果在截止后才保存并赶上正常结束，不以执行器自报结束时间还原精确截止裁决。已有 STOPPING、超时、取消或其他终态均不覆盖；与并发超时或人工停止竞争时，不保证结果完整就必定由正常完成获胜。

### 自动超时与人工停止的分工 {#terminal-check-routing}

自动超时入口复用上述**仅终态判定与保存**：已有父终态则退出；父为 STOPPING 则接续已保存的停止决定，不重判原因；父为 RUNNING 且具备完整最终结果时尝试按结果结束。只有成功读取并明确返回 `NotReady`，才进入父单行短事务。该事务按主键锁住 Instance，锁后另取当前数据库时间，重读父状态与有效截止；已有停止决定或终态则保持，仍为 RUNNING 且已到期才尝试保存 `status = 6` 和超时原因，`finished_at` 仍为空；尚未到期不修改。正常完成 UPDATE 零行、技术失败和提交不明均不得当作 `NotReady` 转入超时。

父锁内不重新查询或汇总全部 Task。接受明确 `NotReady` 之后、父超时事务提交之前最后一个结果刚好到达，而超时停止决定先提交的竞争窗口；不能因这个窗口再持父锁扩大整轮查询。先检查完成只是本次检查顺序，不承诺全局完成绝对优先，已有停止决定和父终态均不可被正常完成覆盖。

这里的“仅终态判定”不创建分片、Post 或重试，不延长原截止。人工停止不经过超时原因改写：父为 WAITING 或 RUNNING 时保存 STOPPING 及人工停止原因；已有 STOPPING 时保留原原因，已有终态时保留原值。停止决定确认后，在停止决定事务之外另开每批父主键 NOWAIT 短事务，统一有界取消未结束子 Task，并独立尽力通知执行器；子状态全部终态后再条件结束父记录。复用 Instance `end_reason` 保存停止决定，不新增停止标记或命令表；该字段在 STOPPING 中表示已确定的结束原因，不代表本轮已经结束，Task 的原因字段语义不因此改变。

管理停止成功表示已确认停止决定落库，不表示全部子状态已经处理完或执行器已经停止。STOPPING 是非终态，页面单独显示“停止中”；阻塞丢弃、Job／组删除保护及历史保留均按未结束处理。数据库处理缓慢会延后解除阻塞，并使 `finished_at` 包含这段平台处理时间；不新增停止请求时间字段。重复请求可按已有停止决定继续处理，但提交结果不明时不能显示为确定已接受，见[提交不明处理](#commit-unknown)。

## 5.11 待处理检查与恢复边界 {#recovery}

有界检查不仅在节点宕机后运行，也承接正常积压、队列满和到期工作。覆盖待派发、到期重试、绑定缺失观察、整轮超时、结果齐备但漏推进，以及 STOPPING 的子状态处理与父最终结束。执行恢复独立于下一次 Job Cron 及 Job 启停，不因低频或停用而遗漏旧轮次。RUNNING Instance 的遗漏推进、正常完成及到期处理统一按下节发现，处理复用[完成／超时判定](#terminal-check-routing)；STOPPING 通过[独立候选分支](#stopping-recovery)发现。已绑定无结果的失联执行不增加独立失联重派扫描。各类查询均须有索引与数量、时间预算，不扫描全部历史；RUNNING 复核的 2 分钟周期、4 分钟开始时间门槛及每页 256 条保持，STOPPING 共用 2 分钟驱动但不套 4 分钟门槛，其他类别参数不因此一并批准，也不混用每分钟 Job 触发恢复周期。

派发与推进队列、回调及计时用于加速处理，已持久化的待处理事实不能随它们丢失。执行器业务 Context 沿用本轮 `deadline_at` 并协作取消；服务端独立按数据库事实结束平台状态，不依赖执行器一定回报超时，也不以发出取消信号代替业务实际退出或释放执行槽位。第一版不新增时间轮、固定 500ms 宽限或独立 Task 超时。结果回报队列允许持有未落库的唯一易失副本，丢失后按既定尝试结算或整轮超时处理，不能宣称从数据库恢复原结果。不为派发或回报增加 MQ、本地文件，也不依赖跨节点额外唤醒保证恢复；这不影响管理配置变更后的主动通知。

### Leader 统一复核 RUNNING Instance {#instance-recheck-direction}

**2026-10-22 完整提案已通过，2026-11-05 普通模式复核与自动超时已接通，实际验证见[实施记录](ordinary-readiness-review.md#ordinary-timeout-recovery-progress)。Leader 每 2 分钟执行或续接一趟有界复核，候选为开始已超过 4 分钟、仍处于 RUNNING 的 Instance，每页 256 条。** 当前普通模式补正常完成遗漏及到期处理；分片阶段推进仍待后续实施。正常事件驱动路径仍由各调度节点立即推进，不等待扫描。

#### 职责与候选范围

- 复用现有 Leader 资格，只由 Leader 发现这类候选并有限投递到**本节点已有 Instance 检查组件**，不新建恢复处理队列或向其他节点转发 ID。检查逻辑与正常结果驱动路径共用，不建立整轮负责人。
- 每趟开始读取一次数据库当前时间 `scan_now`，固定 `eligible_before = scan_now - 4 分钟`；查询 `status = 2 AND started_at < eligible_before`，按 `(started_at, id)` 排序。`started_at` 是首次有效开始时间，阶段变化及执行重试不刷新，也不使用审计时间判断业务进度。
- 候选查询不加 `deadline_at` 过滤，不因当前 Job 停用、删除或下一次 Cron 很远而排除旧轮次；只返回 ID 及分页所需的开始时间，不锁行、不修改状态、不在候选 SQL 聚合或全局扫描 Task。具体 SQL 与部分索引见[数据契约](data-contracts.md#instance-recheck-query)。
- 确定 Instance 后才定向读取该轮必要 Task 事实，不增加逐 Task 待推进标记，也不让每条结果更新共享父进度字段。首次启动、待派发及到期重试、无绑定观察到期结算、STOPPING 恢复、人工停止及 Job 触发恢复不并入本 RUNNING 查询；它们保留各自协议。

#### 一趟扫描与有界投递

1. 新 Leader 在依赖及本地检查组件就绪后立即开始一次有界扫描，仍应用 4 分钟门槛；不要求所有执行器组在线，也不重建全量内存恢复队列。
2. 后续每 2 分钟执行或续接扫描。同一任期只有一趟在途遍历，前一趟未结束则继续，不并行开新一趟或补跑积累的 tick。固定本趟时间上界，分页时不不断追赶新到期或新开始的记录。
3. 采用 `(started_at, id)` 临时键集分页，每页最多 256 条，只保留有界页数据。候选成功接纳或与已有提示合并后才推进投递游标，不等待实际检查完成；检查期间的新事件仍遵守既有标记重查规则。
4. 恢复新增 ID 受下节补充门槛约束；达到门槛或检查集合满时停在首个未接纳项之前，暂停新增查询，在本周期剩余预算内等待集合释放空间再继续，不能越过该项。预算结束后下周期从已接纳位置继续；不无限等待入队，不用新建协程绕过容量。
5. 查询失败结束本次执行，保留本趟上界及已接纳位置，下周期重试；已接纳但实际检查失败时，处理中真实的新提示仍按[本地合并规则](#instance-check-defaults)安排后续检查，否则交后续通知或新一趟扫描再发现。不回退已接纳游标，也不在当前页头无限阻塞其他候选。
6. 读到本趟末尾后结束遍历，不利用本周期剩余时间立刻从头重扫；后续周期开启新一趟时重新取数据库时间、从头开始。临时游标不是永久消费水位，迟提交到游标之前的记录、仍健康运行或此前处理失败的记录均须再次覆盖；不持有跨页长事务或长期数据库快照。

每页 256 是部署初值，不是每趟或每周期最多 256 条，也不是吞吐承诺。[本地检查安排与初值](#instance-check-defaults)保持：每节点保留 512 个唯一 ID、检查并发 8、单次处理 2 秒及内部合并窗口 100ms。扫描时间预算、补充门槛与拥塞处理按下节执行，不混用检查处理、派发或 Job 恢复的参数。

生产配置使用 `InstanceRecovery.Interval` 共用默认 2 分钟驱动；RUNNING 的 PageSize／RunTimeout／SQLTimeout 与 STOPPING 自身预算独立。两条分支各自即时首轮、逐次串行，忙分支跳过 tick，不影响另一分支、不积累补跑。失主取消两条发现流程，并等待实际返回后释放任期资源；已经交给进程级队列的处理不随任期取消。

恢复交接遵守以下规则：

1. 候选 ID 已在集合中时按既定规则合并，不增加位置，即使达到门槛或集合已满也可成功合并；成功后才推进游标。检查期间的合并仍保留后续检查，不能因来源为恢复就忽略提示。
2. 新 ID 只有在共享集合当前占用量低于补充门槛时才接纳。检查占用量与接纳须协调，不能依据查询前的旧空位数量一次塞入整页。门槛取整数且至少为 1，避免极小容量配置无法接纳任何恢复 ID；不改变集合自身的总量限制。
3. 默认已有 240 个 ID 时，恢复可先补至 256，之后暂停；正常提示仍可使用全部 512 个位置。门槛限制的是恢复新增条目时的全局占用量，不是恢复条目数、每周期总量或正常提示的上限；不按条目来源维护独立额度，也不切分 8 个检查并发。
4. 达到门槛或集合已满时，恢复暂停新增查询及需要新位置的交接，在本周期剩余时间内等待集合释放空间后再尝试。已有页仍按顺序处理，不跳过首个未接纳项去挑后面的可合并 ID；没有补充空间时不继续查询后续页。
5. 等待不持有数据库连接或事务，不忙循环，不为未接纳候选派生额外等待协程；扫描只保留当前有界页（默认最多 256 条）和分页位置。未交接页内容可在周期结束时释放，下周期从最后成功接纳的位置重新查询，不能因为查到或读入内存就提前推进游标。

补充门槛与 100ms 合并等待共同作用时，不能一达到门槛就结束本周期，否则快扫描可能在检查开始前填入首批后退出，变相将门槛当作每两分钟的总处理量上限。预算内等待允许检查释放位置后继续补充，不另设本周期总页数或 256 条总量上限；它仍受实际检查速度及 5 秒交接窗口限制，不承诺固定吞吐。

预算到期停止新查询与交接并取消在途扫描查询；查询失败直接结束本周期，保留本趟上界及已接纳位置，下周期继续，不在本周期反复重查。失主同样停止发现和交接，但丢弃任期内的临时位置。查询超时或预算取消不证明数据库、连接或必要清理已经完成，不能据此重叠启动另一条扫描；已接纳检查可以按原协议继续。

公平性限定为：默认配置下，恢复新增 ID 不主动把整个集合填满；已到期、已接纳提示按排队顺序获得处理机会，检查期间新提示产生的重查仍转队尾，不让后来的提示不断插队；短暂拥塞在预算内消退后，恢复可继续补充。正常提示与恢复共用集合和检查能力，本规则不是严格来源公平或故障资源隔离。容量至少为 2 时，半量门槛给正常提示留下缓冲余量；极小容量为 1 时，门槛至少为 1 的边界使其退化为共享单位置，不能再保证留下额外空位。

当正常负载持续让占用量达到门槛，或拥塞恰好覆盖每个完整扫描窗口时，恢复仍可能长期无法接纳新候选；即使平均负载不高，也不保证每周期都有进展。可调整预算与观测无进展不能消除这一边界。不预留恢复位置或固定处理份额，不承诺恢复 SLA；验收同时观察整趟遍历速度、正常完成延迟和拥塞时游标进展，不能只证明队列没有溢出。详见[统一复核验收](verification.md#instance-recheck-query-checks)。

#### 检查时的处理顺序

1. 父已终态则退出，父已 STOPPING 则交已定停止处理，不能用扫描时的 RUNNING 快照恢复正常推进或覆盖停止原因。
2. 在父锁外读取本轮最少必要事实。普通、Pre、已封口分片、配置的 Post 及合法零分片按共同完成契约判断；完整最终结果具备时尝试正常结束，即使此时已过截止也不强制超时。
3. 只有成功读取并明确不具备最终完成条件，且当前已到截止，才进入原超时父单行短事务，锁后重新读取数据库时间及父状态。技术错误、正常完成 UPDATE 零行、提交不明不能当作 `NotReady`。
4. 未到期且具备后续阶段条件时，进入已有生成／Post 等授权协议；仍在等待 Task 时退出。截止后不得创建分片、Post 或授权新尝试；绑定执行器失联、结果丢失也不构成提前重派许可。

实际处理使用新读取的数据库时间，不使用可能跨周期保留的 `scan_now` 作授权或超时裁决。超时决定保存为 STOPPING 后，子状态处理与尽力取消走停止协议；只有数据库中的子 Task 全部终态后才结束父，但不等待 RPC 成功或业务退出。健康运行实例一般只读事实后退出，不要求每次复核都锁父或写父，但仍有读开销及少量并发竞争。

#### 切主、恢复延迟及取舍

- 失主停止新候选发现和投递，取消在途发现查询，丢弃本地扫描位置；已交给进程级检查组件的工作可按原数据库并发协议完成。新 Leader 从数据库重新开始，不转移旧游标或内存队列，接受交界处重复检查。
- 没有有效 Leader 时，本周期复核及由它承担的超时发现暂停；正常结果接收、持久化、本地检查与合法派发不因此停止。这是 Leader 新增的候选发现职责，不是 Instance owner 或所有执行恢复集中化。
- 无积压且扫描正常运行时，首次周期检查约发生在开始后 **4～6 分钟**。短于 4 分钟的整轮超时也服从该过滤，不能承诺截止后 2 分钟内保存超时；排队、数据库故障、切主及扫描积压都可进一步延迟，不构成恢复 SLA。
- 4 分钟门槛只排除刚开始的实例，不表示已经精确识别异常。健康长任务超过门槛后仍可能在后续趟次重复检查；不保证正常路径严格先执行，也不通过新增阶段活跃时间、`next_check_at` 或每结果父写入来缩小候选。
- 延迟保存超时不延长 `deadline_at` 或执行器协作取消期限。尚未终态的旧轮次可能使后续触发按阻塞策略丢弃；并行策略可能积累更多非终态记录。遗漏阶段推进在恢复时可能已无剩余预算，不能因此延长期限。

不新增内存延迟恢复队列、时间轮、恢复分桶、永久 owner 或独立高频超时扫描。Cron 仍为单 Leader 加 robfig、不按 Job 分桶。生成执行权、分批保存与封口、其他类别候选及剩余容量参数仍需独立闭合；本次仅记录已批准设计，不新增模型字段、迁移或运行代码。

### Leader 恢复 STOPPING Instance {#stopping-recovery}

**停止决定提交后立即在本节点进行有界处理是正常路径；Leader 每 2 分钟按独立 STOPPING 候选分支补漏。** 此职责于 2026-10-23 通过，2026-10-26 另已通过[单批父 NOWAIT 协调与容量](#stopping-processing)；单批处理、工作队列、新 Leader 就绪检查及每 2 分钟 STOPPING 发现已接通，见[停止运行链路记录](ordinary-readiness-review.md#ordinary-stop-runtime-progress)。它与 RUNNING 复核共用既有周期驱动，不增加停止专用延迟队列、时间轮、固定 owner 或可靠通知系统；确实增加了一类数据库候选查询和后台处理工作，不能表述为“没有新增扫描”。

- 候选按[已通过的查询](data-contracts.md#stopping-recovery-query)只从 `job_instance` 的 `idx_job_instance_stopping (id) WHERE status = 6` 有界读取，再按 Instance 定向处理 Task；不全局扫描 Task。不套 RUNNING 的 4 分钟开始时间门槛，也不要求 `started_at` 或 `deadline_at` 非空，因为 WAITING 也可被人工停止。
- 新 Leader 在依赖及本地后台处理能力就绪后立即做一次有界检查；后续每 2 分钟续接未完遍历或开启新一趟。STOPPING 候选与 RUNNING 候选分别分页、分别限定工作预算，不让一个分支耗尽另一个分支的处理机会；其独立初值已在[取消竞争与容量](#stopping-processing)确认：每页 256、每周期扫描／投递 5 秒；数值相同不表示与 RUNNING 共用额度。
- 一趟开始读取当前 STOPPING 最大 ID 固定为 `upper_id`，以 `id > after_id AND id <= upper_id ORDER BY id` 有界翻页；空集结束。分页仅是本趟临时位置，不是永久消费水位。候选接纳或合并后才推进，不等待实际处理成功；队满不越过拒收项，查询失败不推进，预算耗尽后下周期从原位置续扫。固定上界防止持续新增大 ID 延长本趟；后续新一趟从头覆盖游标经过后才停止的较小 ID、晚提交、先前处理失败及全部子状态已结束但父尚未结束的记录。
- 后台复用同一停止处理：每批先按父主键尝试 `FOR UPDATE NOWAIT`，取得后确认 STOPPING，再按 `instance_id` 及 `status IN (1, 2, 3)`，通过 `idx_job_task_unfinished_instance (instance_id, id)` 部分索引按 ID 取当前一批，条件取消并提交释放锁。不使用 Task 游标或 OFFSET，不把全部 ID 加载后再切分；同一索引用于无未结束子记录时的父最终 `NOT EXISTS`。争锁失败或技术失败结束本次处理，不立即重排；成功但份额耗尽时队尾轮转，不能无限重做首批。保留 STOPPING 由后续提示或恢复接续，不设置永久数据库重试耗尽，不与远端取消的有限重试混同。
- 失主停止本任期候选发现并丢弃临时位置；已经接纳的进程级后台处理可按数据库协议完成。没有 Leader 时，周期补漏暂停，但各节点提交停止决定后的正常处理仍可继续。新 Leader 不接收旧游标或内存队列，允许换主时重复处理。

数据库和服务恢复、处理获得公平容量且无永久数据损坏或不可恢复缺陷，是最终完成的前提，不承诺固定完成时间。STOPPING 积压期间继续按非终态保护删除和历史保留；配置了阻塞丢弃策略的 Job 继续丢弃后续触发，并行策略不因此阻塞；取消 RPC 失败不构成维持 STOPPING 的理由。最终父更新成功后不为可靠通知再保留该候选。

上述查询和两条部分索引已通过，索引已在此前迁移中创建；子定位与最终 NOT EXISTS、STOPPING 父候选发现均已接通，具体范围见[停止运行链路记录](ordinary-readiness-review.md#ordinary-stop-runtime-progress)；Task 未结束索引也由正常活跃任务维护，需验证写入和清理成本，不只计算取消读取收益。取消竞争与部署初值见下节；这两条索引不覆盖取消目标地址查询；[通知地址索引与有界查询](data-contracts.md#cancel-target-query)已实现，递归定位 SQL、首屏和续屏索引计划已有真实 PostgreSQL 验证，见[停止运行链路记录](ordinary-readiness-review.md#ordinary-stop-runtime-progress)。

### STOPPING 取消竞争与容量 {#stopping-processing}

**2026-10-26 已通过。`ProcessBatch` 已实现一次父 NOWAIT 短事务下的有界取消或最终父更新；工作队列、处理份额轮转与 STOPPING Leader 发现已接通，见[停止运行链路记录](ordinary-readiness-review.md#ordinary-stop-runtime-progress)。** 本节只细化 STOPPING 的数据库取消处理，不改变单 Leader 触发、对等结果接收及本地推进架构，不增加分桶、整轮负责人或跨节点转发。Leader 的 STOPPING 周期发现与停止决定提交节点的即时处理共用以下协议；[派发候选竞争](#dispatch-contention)同日另行批准，不由本节自动推导，也不共用本节容量参数。

#### 每批处理与竞争退出

1. 每个批次开短事务，按 Instance 主键执行 `FOR UPDATE NOWAIT`。父行锁不能立即取得时，回滚并结束本次 Instance 处理，不读子 Task、不等待竞争者完成；工作协程继续处理其他候选。
2. 取得父锁后复核仍为 STOPPING，再按已有索引读取当前一批未结束子 Task，执行原条件取消；不能使用锁外预读的旧子列表，不增加 Task 显式多行锁。每批明确提交后释放锁，下一批重新取得父锁并查询。
3. 已无未结束子 Task 时，在当前父事务内执行原 `NOT EXISTS` 条件终态更新；已有终态直接退出，不重复修改结束时间。所有子批次仍分别提交，不把整轮停止放进一个长事务。
4. 父锁只覆盖单批数据库工作，不包含 RPC、整轮结果统计或等待业务退出。锁顺序为父→子；正常结果写库不锁父，结果事务提交后才提示父检查，不能持子锁反向等待父锁。

NOWAIT 只解决取得父行处理资格时的等待，不能解释为所有数据库操作完全无等待。子 UPDATE 仍可与结果、迟到 ACK 或 BUSY 写入竞争；单条 SQL 超时限制这类占用。父 NOWAIT 冲突是正常竞争结果，子查询／更新超时是技术失败，不能混为“另一节点正在取消”。技术失败结束本次处理，提交不明不宣称确定回滚或成功，后续按持久化状态继续。

#### 本地合并、轮转与后续恢复

- 本地以 Instance ID 合并提示，排队与处理中只占一份容量；同一节点同一 Instance 不同时交给两个取消协程。
- 父锁冲突不立即重排，处理中积累的旧重复提示也不能触发马上再抢。后续新的提示或 Leader 后续新一趟扫描可以再次发现 STOPPING；若原持锁者随后故障，不承诺当前失败节点立即接替。
- 成功处理但仍有未完成工作，达到本次批次／时间份额后放回队尾；转移排队位置不另占一份容量，也不能占住工作协程等待队列空位。失败或竞争退出不套用成功后的立即队尾轮转，不在同一个 Instance 上紧循环。
- 扫描游标仍只代表候选已被接纳或合并，不等待实际取消完成；争锁失败不能使游标退回或重新从第一页开始。未接纳项仍保留在游标之后，未完成遍历下周期续扫，后续新一趟覆盖失败或晚进入 STOPPING 的记录。
- 不保存子 Task 游标，不增加领取字段、延迟重试队列或节点租约。每次从该 Instance 当前最前面的未结束子记录继续，数据库停止义务不设永久重试耗尽。

#### 部署初值

以下数值只适用于 STOPPING 的数据库处理，不用于 Job 触发、RUNNING 复核、正常派发、结果写库或远端取消通知：

| 参数 | 初值 | 边界 |
| --- | --- | --- |
| 候选每页 | 256 个 Instance | 固定上界、临时 ID 游标规则不变 |
| 每周期扫描／投递预算 | 5 秒 | 队满也立即停止；不额外设每周期 1024 个候选上限 |
| 本地待处理容量 | 256 个 Instance | 包含排队与处理中，按 ID 合并；候选读取另只保留有界单页 |
| 每节点取消处理并发 | 2 | 使用后台额度，不占用 64 个派发协程或结果消费者 |
| 每批取消量 | 最多 256 条 Task | 仅当前 Instance 的未结束记录 |
| 单 Instance 每次处理份额 | 最多 4 批，或达到 2 秒处理预算后不再启动下一批 | 成功未结束则队尾轮转；不持父锁跨批次 |
| 单条 SQL 超时 | 1 秒 | 覆盖本节数据库操作，不等于整个事务的硬上限 |

2 秒是本次处理的让出预算，不能解释为两秒内一定完成、回滚或释放数据库连接；达到预算后不再启动下一批。SQL 超时、Context 结束和客户端返回都不能代替实际事务结果确认，未知提交仍按原协议处理。本节不修改全局数据库超时或事务隔离级别。部署可调初值必须通过普通任务、单轮大量分片、停止洪峰及正常派发／回报背景负载压测校准，不据此承诺吞吐。

所有节点仍共享数据库和其他进程资源；独立并发额度不是硬隔离。竞争失败次数、子查询／更新次数、批次延迟、积压及正常派发／回报延迟须纳入[停止竞争与容量验收](verification.md#stopping-recovery-checks)。数据库最终结束不等待远端取消；目标地址的[有界查询](data-contracts.md#cancel-target-query)及[通知容量、超时和重试参数](#cancel-notification-capacity)已另行通过，不能混用本节数据库处理额度，执行模块仍未授权编码。

恢复负责发现和接续持久化工作，不把所有检查、聚合与清理交给派发工作协程。以下职责分工已通过；RUNNING 与 STOPPING 的候选方向及周期按上节规则执行，未定查询细节与参数仍须分别闭合。

| 工作 | 处理归属 | 边界 |
| --- | --- | --- |
| 待开始的 Instance、到期且符合派发条件的待执行或等待重试 Task | 复用已有有界派发组件及每进程默认 64 个工作协程 | 恢复只有限投递候选；工作协程按已有协议重新校验、登记并在明确提交后派发。普通首次 Task 仍与首次开始同事务创建为执行中，不增加待执行中间步骤 |
| 遗漏的阶段推进、正常完成及到期处理 | Leader 统一发现，复用本节点已有按 Instance 合并的检查组件及固定检查协程 | 正常结果仍由提交节点提示本地检查；遵守阶段授权和完成／超时规则，不在派发或结果落库协程内执行整轮检查，不将其他正常推进转发给 Leader |
| 未绑定尝试的未知结果结算 | 各节点后台恢复，每节点一个不重叠扫描／结算流程，本地串行 | 按[已定运行安排](#unbound-recovery-defaults)批量复核、逐条独立提交，不占派发／结果保存／Instance 检查并发，不另建长期候选队列；不新增父或 Task 显式锁 |
| STOPPING 的子状态处理及父最终结束 | 后台恢复组件按有界处理量执行 | 不占派发或结果保存协程；即时处理与恢复共用单批父 NOWAIT 协议及每节点 2 个并发额度，不与未知结算合并容量或锁协议 |
| 上述候选查询 | 后台有界扫描；RUNNING 与 STOPPING 的独立候选分支归 Leader，其余不并入本次职责变更 | 不由派发工作协程或结果落库消费者承担；两个 Leader 分支各有预算和公平遍历，查询和处理均有界，不扫描全部历史 |
| 接收到的执行结果保存 | 保持已有独立结果队列及受控并发的后台保存 | 不兼任恢复扫描或清理；明确提交后只提示 Instance 检查，恢复不能重建已丢失的未落库结果 |

普通和分片共用上述职责分工，不按五类候选机械增加五个线程池、五套队列或独立进程。分片候选仍须满足生成完整性等前提，具体字段和查询随生成协议补齐；不得把尚未确认的分片查询当作已定执行协议。

恢复发现的真实派发与新任务派发共享等待队列和处理并发，必须有限补充，队满暂停该投递，未接纳工作仍以数据库事实为依据；不能由一次积压恢复无限塞入候选。[排队、并发与满载处理](#capacity-model)已确定不按正常／恢复来源划固定份额，按 Instance 小批补充与轮转，只有一个 Instance 有工作时可充分使用空闲派发能力；[供给参数](#dispatch-supply-defaults)进一步确定候选总量 256、每页最多 128、每 Instance 先补最多 8 项及补查退避。登记事务批量和具体编码组织仍待落实，不承诺正常任务优先或严格全局公平。同样，恢复引起的完成检查复用已有检查资源，不另造一套父推进逻辑。

分开工作协程只划分处理职责与并发额度，不提供数据库、CPU 或 I/O 的硬隔离。同一调度进程继续共用数据库连接池；扫描、聚合、未知结算和子取消均需限制批次及并发，并验证积压时对派发和结果保存的影响。统一复核周期及页大小已定，STOPPING 的容量、并发及处理份额按[已定初值](#stopping-processing)执行；其余队列容量、类别周期、处理预算和具体公平机制仍在后续设计中闭合。

子 Task 状态收敛与向执行器发送取消 RPC 仍是两件事；通知使用另行批准的[独立读取与发送容量](#cancel-notification-capacity)，不借用数据库取消或派发工作协程。客户端生命周期沿用[单次通知内复用、结束关闭](#cancel-routing)，不增加可靠补送或长期缓存。

### 数据库提交结果不明的恢复 {#commit-unknown}

数据库可能已经提交成功，但调度端因确认丢失而收到超时或断连。**提交报错不等于事务回滚，普通查询没有看到改动也不证明原事务已经结束。** 本规则复用当前尝试、允许的旧状态、STOPPING、既有缓冲和恢复检查，不为提交不明另加状态、历史表、发送凭证或补偿队列。

| 不确定的写入 | 已确认恢复规则 | 接受的代价 |
| --- | --- | --- |
| 人工停止的 STOPPING 决定 | 不宣称已接受或凭内存发取消；在当前请求有限预算内可重新进入同一父行协议核实，仍不明则由调用方查询或重试 | 实际已提交时，Leader 可据 STOPPING 继续处理且保留人工原因；若意图实际未落库，后台无法凭空恢复，原实例可能继续至正常结束或原截止 |
| 正常完成的父终态 | 不把提交不明转换为 `NotReady` 或超时；既有恢复重读本轮事实和父状态，仍具备结果且父运行时重新条件结束 | 不重新执行业务，不覆盖已经保存的父终态，不将 UPDATE 影响一行等同于提交确认 |
| 自动超时的 STOPPING 决定 | 释放候选；仍 RUNNING 时由运行复核按原完成／超时规则处理，已 STOPPING 时由停止恢复继续，不覆盖已有原因或终态 | 不承诺数据库故障时准时终止，不把提交不明视为确定回滚 |
| STOPPING 后的子取消或父最终结束 | 依据已持久化停止决定重读状态，继续有界条件取消或在无未结束子记录时结束父；已终态不反向恢复 | 数据库处理不保证补发取消通知；父最终状态已提交后不新增可靠通知恢复机制 |
| 新尝试登记 | 不发 RPC，撤掉本次本地发送计划并释放派发槽位；即使事后看到该尝试已登记也不补发。已提交的按既有观察、结算与预算恢复；实际未提交且仍可执行的 Task 由普通流程重新竞争登记 | 业务可能没运行，却占用一次执行机会；零重试可能最终失败 |
| 接单 ACK 绑定 | 当前固定派发工作协程内有限重做原请求身份及原目标的条件更新；零行停止且不追加核对，不重发业务或返还机会；采用[已定保存预算](#dispatch-time-budgets) | 耗尽或退出释放 ACK，不能恢复未保存的目标；已有绑定仍有效，无绑定则沿用观察结算，不保证可定向取消 |
| BUSY 关闭与返还 | 持有原响应时，在有界有限处理重试内，重做原 Task、原尝试且尚未结算状态下的原子关闭、一次返还及延期；已经生效或失效则不再修改 | 原响应释放或随进程丢失后不能猜测补返；未知结算或取消先提交时，迟到 BUSY 也不能返还，可能消耗实际未执行的机会 |
| 非 BUSY 明确拒绝结算 | 当前派发处理者按原身份、执行中及双绑定为空条件有限重做；不增减次数、不重发业务，零行停止；采用[已定保存预算](#dispatch-time-budgets) | 耗尽后释放原响应，未落库且仍符合条件的由无绑定观察兜底；接受拒绝原因可能未持久化及结算延迟，不新建可靠响应队列 |
| 普通未知结果结算 | 释放本批临时候选，由已有有界恢复及退避按当前数据库事实重新发现；实际未提交且仍合格的再竞争，实际已提交的由重试或完成推进接续，不直接派发 | 不宣称回滚或已结算成功；恢复可能延后，不保证观察期到点就完成。没有未落库业务结果，不新增长期等待缓存 |
| 执行结果保存 | 保留该条原结果，按已有有界结果保留规则退避重做同一次条件写入；未生效且仍有效则保存，已生效则不重复修改，已失效则不覆盖当前状态 | 各条独立提交和释放，失败或提交不明不重放其他已明确提交的结果；积压有界、队满拒收，进程退出仍可能丢失未落库结果 |

登记进入不明分支后，不因迟到确认或读回状态恢复原发送计划，也不另外退款。没有登记的候选仍须重新经过本地容量、父状态与截止、Task 状态和预算条件；不能凭一次查询“没看到”就直接发送。释放本地槽位不等于原数据库事务或锁已释放，未决事务仍可能使后续条件写入等待或超时，沿用数据库操作超时与退避处理。

BUSY 只检查尝试 ID 不够，还必须检查**尚未结算的旧状态**；否则在下一次尝试尚未创建时，同一消息仍可能重复返还。关闭、返还与延期在同一事务中原子完成，不能单独重试减计数。BUSY 的有限记账重试不是重新派发业务，不占执行重试额度，也不建立常驻等待对象；普通 Task 见[已定条件更新](data-contracts.md#ordinary-busy-settlement)，具体内部参数在容量设计中明确。

结果保存继续采用[已确认的有界保留](#scheduler-result-retention)，可恢复错误不按次数或 TTL 丢弃，不能混用 BUSY、ACK 绑定或非 BUSY 明确拒绝的有限处理策略。结果重做后即使没有再次修改记录，也可以重新发出本地 Instance 检查提示；提示只促使按数据库当前事实检查，不拿原消息直接再生成分片、Post 或结束本轮。重复提示通过既有合并、条件推进与恢复处理，不重复产生业务工作。

正常成功路径不额外增加一次写后查询。异常路径需要核对时，以 PostgreSQL 主库为准，不用缓存或延迟副本作恢复裁决；读回只是判断依据，不能替代后续条件写入。结果保存仍按单条关联读取、判断提交结果并重做原条件写入，不重放其他已明确提交的结果；重做仍校验原尝试与旧状态，不能把提交报错当作未生效的证明。其他操作的批量核对或批量事务按各自契约处理，不套用结果保存的独立提交边界。具体 SQL、错误分类及各自的批次规则在对应模块落实。

RUNNING Instance 统一复核的 2 分钟周期、4 分钟门槛、每页 256 条及开始时间部分索引已通过；其他类别尚未确认的检查间隔、批量、索引，以及共享容量和公平性仍依赖各自设计与压测，不凭空设定吞吐承诺，也不直接套用每分钟 Job 触发恢复参数。重点验证提交交界故障、单轮大任务、密集回报、跨节点分散回报、稀疏小 Instance 及重试洪峰，见[验证与交付](./verification.md)。

依赖故障时哪些能力暂停、继续或拒绝请求，见[管理与运维](operations.md#dependency-boundaries)。数据库前置步骤未提交不能凭内存越过授权派发；失去 Leader 资格不自动停止其他满足执行权条件的推进。回报成功入队可确认接收，数据库故障时有界保留并背压；两侧内存结果均不保证跨进程退出保存。依赖恢复后的处理仍服从预算与终止规则，普通未知结算核心及条件写入已实现并完成专项验证，自动观察扫描及生产调用也已接入，当前范围及验证见[实施记录](ordinary-readiness-review.md#ordinary-unbound-scan-progress)；完整进程故障及负载验证仍待阶段 6。
