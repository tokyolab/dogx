# 5 执行流程与可靠性

本章将[总体架构](./architecture.md)、[任务模型](./task-model.md)和[行为规则](./behavior.md)串成一次执行的主路径，并说明节点故障、结果重复和并发推进下的可靠性边界。各机制围绕同一个目标：持久化事实决定下一步，本地状态加速处理，业务执行不承诺恰好一次。

**设计成熟度：无整轮固定归属、本地直接派发、尝试登记与父终态协调、提交记账、原生路由及绑定、异步回报、重试与结果保留、提交结果不明恢复及完成推进的规则已确认。** 等待重试只是候选状态，结果回报不统一锁父；截止在锁内按当前数据库时间判断。B2 [闭环总审](progress.md#b2-review)已通过；具体 SQL、批次契约和待定数值仍在对应模块细化，本章不是已经实现验证的完整协议。

## 5.1 一轮执行的主路径 {#main-flow}

### 普通任务

1. 触发入口按既定触发和阻塞规则创建 Instance，同时保存本轮必要执行配置。
2. 调度节点取得必要推进权，保存业务执行 Task，事务提交后通过本地有界派发交给执行器；不建立整轮固定归属。
3. 执行器异步运行具名业务处理器，将完成结果交给公共组件的有界回报队列，由固定工作协程小批量提交。
4. 接收节点完成基础校验、成功入队后返回接收 ACK；后台消费者校验并持久化有效结果，提交后才尝试结束本轮，保存状态及简短诊断。

需要重新执行时遵守[统一重试规则](./behavior.md#retry)，不叠加另一份通信重派额度；整轮超时按终止规则处理，不作为自动重试整轮的理由。普通任务只创建一个普通 Task，不组合准备或收尾阶段，接口形式在契约设计中确定。业务进度回调不纳入第一版。

### 分片任务

| 步骤 | 已确认处理方式 | 可靠性要求 |
| --- | --- | --- |
| 1. 触发 | 通过同 Job 短事务创建本轮 Instance，自动触发同时推进进度 | 遵守[统一触发记账](#trigger-accounting)、[自动触发身份](behavior.md#trigger-identity)及[切主与配置变更边界](#leader-config-boundary) |
| 2. 准备 | 取得必要推进权，唯一创建 PreTask，提交后派发 `PreProcess` | 不在等待业务结果期间持续持有整轮归属 |
| 3. 生成 | 有效准备结果持久化后，按通用规则拆分工作项数组，保存分片 Task 与参数 | 确认生成完整后才开放派发；生成完成事实提交后也通知完成检查 |
| 4. 派发 | 生成节点按本地派发容量，对已知 Task 小批量条件登记当前尝试，提交后直接经 RPC 派发 | 不等待下一轮数据库扫描；正常派发与恢复复用[尝试登记协议](#attempt-registration)，不提前授权全部积压 |
| 5. 回报 | 任意接收节点成功入队即 ACK，后台幂等保存有效结果，提交后按 Instance 合并检查 | ACK 不表示落库；待重试分片仍未结束；跨节点允许重复检查，不允许重复推进 |
| 6. 可选收尾 | 所有分片最终结束且配置了 Post 时，通过单 Instance 短事务唯一创建 PostTask，提交后派发 `PostProcess`；未配置则直接进入平台结束步骤 | 部分分片最终失败仍执行已配置 Post；收尾重试不新建第二条 PostTask |
| 7. 结束 | 已配置 Post 则等待其最终结果持久化，未配置则直接按分片最终结果更新 Instance | 不抹除分片最终失败，不覆盖停止或超时，不因平台推进失败重新执行业务 |

生成完整后，本轮分片集合固定。分片路径必须有准备阶段；准备最终失败且没有有效结果时，不生成分片、不进入正常 Post；有效准备结果后的生成故障只恢复平台生成。合法空数组按零分片生成完成主动推进，有 Post 则执行，无 Post 则由平台成功结束，不等待分片回报。完整阶段结局见[第 4 章](./behavior.md#stage-outcomes)，工作项含义、粒度及容量边界见[任务模型](./task-model.md)与[数据契约](./data-contracts.md)。

普通和分片路径均使用 [Instance 创建时保存的执行配置](behavior.md#instance-execution-config)。包括稍后生成的 Pre／分片／Post、重试及跨节点恢复，不再从当前 Job 获取本轮执行策略。首次有效开始时，以本轮保存的超时时长形成截止时间，Job 编辑不能改变或延长本轮预算。

提交后未推进、本地队列满、到期工作、节点失联或结果不明，均需要由有界检查重新发现并调用同一套推进／恢复逻辑。正常路径不依赖最初派发节点持续存活，恢复路径也不能绕过已成功结果、执行预算或终止规则。

首批触发模块止于[持久化交接](data-contracts.md#trigger-durable-handoff)：保存 WAITING Instance 和本轮配置，开始、截止及结束时间仍为空。提交确认后的本地 ID 提示仅加速后续推进，不是可靠消息或执行授权；候选与配置按有界批次读取，恢复不得用永久 ID 水位跳过晚提交记录。首次开始与创建首个 Task 在执行模块按数据库条件协调，本批不实现假消费者或另加扫描循环。

### 同 Job 的触发记账 {#trigger-accounting}

**Cron 正常回调、Leader 的低频恢复检查及规则注册后的到期检查共用同一触发入口。** 三者只提示检查某个 Job，不凭本地计时或扫描快照直接创建 Instance；处理哪轮以 `Job.next_trigger_at` 的最新持久化值为准。恢复时机见[低频触发恢复](behavior.md#trigger-recovery)，注册后的检查见[配置加载与重载](#job-config-reload)。

1. 开启短事务，以 Job 主键等值条件锁定单表单行；读取最新配置、删除状态、启用状态与触发进度。Job 不存在或 `deleted_at` 非空时结束，不创建 Instance 或推进进度。
2. 取得锁后，读取一次调度进程的 `time.Now()`，判断是否到期及是否超过 5 秒迟到容忍，不沿用回调、入队、扫描或事务开始时刻，也不另取数据库当前时间。未到期或自动触发条件不满足时结束本次处理。
3. 按既定错失和阻塞策略决定是否创建 Instance。需要阻塞判断时，用适配索引的 `EXISTS` 查询同 Job 是否还有未结束 Instance，不加载或锁住全部实例。
4. 已到期时，按当前 Cron 规则计算严格晚于本次判定时间的第一个时刻。应当执行时，在同一事务中创建 Instance 并推进 `Job.next_trigger_at` 到该时刻，`Instance.scheduled_at` 保存锁内读取的旧进度；应当忽略或丢弃时，也推进到该时刻。每次最多创建一轮，5 秒内积压也不逐轮补建；完整区间规则见[到期处理](behavior.md#trigger-advancement)。
5. 提交后再推进准备或业务执行。事务中不包含执行器 RPC、通知或其他外部 I/O，也不等待业务完成。

创建 Instance 时，复用锁内已读取的最新 Job，将本轮必要执行配置随 Instance 一起保存；自动、恢复及手动创建均适用。手动指定当次业务参数时，保存覆盖后的实际参数，不更新 Job。已经创建的 Instance 后续沿用自身配置，不再以 Job 编辑改写本轮策略。

到期计算复用[六字段 Cron 与调度时区规则](behavior.md#cron-contract)。到期判断、错失判断和下一次时间计算共用锁后读取的同一个进程时间，注册、预览、启用和推进统一按调度进程默认时区计算；完整适用范围见[Job 触发时间来源](behavior.md#trigger-clock)。解析失败或求不出下一次时间时，按[Cron 异常处理](behavior.md#cron-errors)结束该 Job 本次事务，不创建 Instance、不推进进度、不自动停用；记录限频错误，其他 Job 继续。

同一 Job 的短暂触发记账串行，不同 Job 可以并行。事务使用默认 `READ COMMITTED`，不增加全局调度锁、每 Job 的 Redis／etcd 锁或整轮固定负责人。候选批次和处理并发有界；每个实际处理的 Job 仍有单行协调、必要的阻塞查询及写入成本，不称为一次批量查询即可完成，也不按每个 Task 重复查询 Job。

自动 Instance 以 `(job_id, scheduled_at)` 的部分唯一索引兜底，正常与错失不能分成两个唯一身份。插入仅处理指定自动身份的冲突，`DO NOTHING RETURNING id` 未返回行时保留旧记录并推进当前 Job，不重新派发旧 Instance；其他写入错误不能被吞掉。新进度只保证严格晚于锁后本次判定时间，不保证晚于物理提交时间；事务耗时期间新时间点已到，下一次入口按新进度处理，不在锁内不断追赶。Job 行锁与后续 Instance 查询分成不同语句，使用锁取得后的新快照；具体协议及五个索引见[触发事务与必要索引](data-contracts.md#trigger-transaction-proposal)。

例如每 5 分钟一次的 Job，Cron 和恢复都发现 `Job.next_trigger_at = 2026-10-15 10:00:00+08:00`。先取得锁的一方在到点后创建该轮 Instance，并推进到 `2026-10-15 10:05:00+08:00`；另一方取得锁后重读，若新时间尚未到期则退出。若新值已经到期，只能按最新进度判断下一轮，不能用原扫描值再建该日期该时刻的 Instance。入口来源不决定错失分类：恢复在 5 秒内发现仍按正常触发，Cron 回调超过 5 秒同样应用错失策略。

事务明确回滚时，Instance 创建和进度推进均不生效。提交响应丢失不能当作回滚；后续正常回调或恢复重入统一入口，依据最新持久化进度和触发身份判断，不盲目重放旧 INSERT。已创建的 Instance 由原推进／恢复路径接续，不因本地未收到确认另建一轮。这里是触发记账恢复，不是 B2 的 Task 尝试登记，也不改变后者“登记不明不补发”的限制。

所有 Instance 创建入口均须共用同 Job 的阻塞协调，包括手动触发。手动入口不要求 Cron 到期，也不推进 Cron 进度；启用和停用均可手动执行，同请求号防重复创建，见[手动触发记账](#manual-trigger-accounting)。Instance 结束不反向取得 Job 锁，阻塞的检查点语义见[阻塞策略](behavior.md#blocking)。

切主及配置变更按下节处理；Job 行锁不证明事务来自当前 Leader。Job 仅停用后可编辑，重新启用时重算下一次，见[编辑与重新启用](behavior.md#job-edit-enable)。触发身份、区间折叠、Cron 输入及[时钟与时区运维边界](operations.md#scheduler-timezone)已确认；本批事务、五索引及[跳过留痕](data-contracts.md#trigger-skip-record-proposal)也已定，统一计算与持久化实现仍须完成。忽略或丢弃仅在确认提交后输出服务日志，不在事务内写日志或另建跳过记录。

### 触发容量与过载 {#trigger-capacity}

**自动触发采用按 Job 合并的有界待处理队列，由固定工作协程执行触发短事务；容量不足时拒绝本次内存提示，不因此推进数据库触发进度，后续沿用既有恢复。** 本节只约束 Job 到点至创建 Instance 的处理，不包含 Task 派发、执行器业务或结果回报。

#### 自动入口与容量统计

Cron 回调、规则注册后的到期检查和 Leader 每分钟恢复检查，共用本任期的一套 Job ID 待处理队列。提交提示后立即返回，不等待数据库，不为等待入队额外创建协程；工作协程调用[同 Job 短事务](#trigger-accounting)，不在该池内调用执行器 RPC 或等待业务完成。

容量按排队与处理中占用的 Job 总数计算，同一 Job 在本任期内只占一个槽位。队列只表达“需要检查这个 Job”，不保存每个 Cron 周期的独立事件；本次处理哪轮仍以数据库中的 `Job.next_trigger_at` 为准。

| 提示到达时的本地状态 | 处理方式 |
| --- | --- |
| 尚未接纳该 Job，且有空位 | 占用一个槽位，排到队尾 |
| 该 Job 已经排队 | 合并提示，不重复入队，也不推迟它已有的位置 |
| 该 Job 正在处理 | 只保留一个“结束后再检查”标记；本次结束后复用原槽位排到队尾，不同时启动第二个处理 |
| 尚未接纳该 Job，且总容量已满 | 拒绝本次提示，记录拒绝指标及限频错误日志；不阻塞提交方或建立额外等待队列 |

取出、接收新提示、结束与释放的交界必须避免清掉新提示；没有后续提示且本次处理结束时释放该 Job 槽位。再次排队复用原槽位，不能在满载时偷偷增加溢出集合。队尾轮转避免一个已接纳 Job 连续独占工作协程，但不承诺持续超载时所有被拒 Job 都能在固定时间内获得处理。

#### 队满、写库失败与恢复

拒收提示本身不写 `Job.next_trigger_at`，也不创建失败或取消的 Instance。后续 Cron 回调或既有[每分钟触发恢复](behavior.md#trigger-recovery)重新检查持久化进度，不新增补偿队列、专用扫描或本地 Job 退避重试对象。

恢复检查每次从主库读取最早到期的一批候选，队满或查询失败即结束，下一分钟重新查询，不立即空转重扫。不分页、不保存跨分钟游标，也不保证头部持续失败或反复满载时后面的候选必能轮到；已接纳 Job 的队内去重与队尾轮转保持不变。具体规则见[单批触发恢复](#trigger-recovery-scan)，不将低频恢复变成高频正常调度。

数据库连接获取、锁等待和事务执行均须有超时，自动处理同时受原任期上下文约束。失败不会自行产生下一次检查提示；处理中确实收到的新提示仍按上述合并规则处理。事务明确回滚和提交结果不明沿用触发记账协议，不能仅凭超时认定没有创建成功。

并发许可覆盖实际进行的创建事务操作，不能在操作尚未结束时先释放额度、再用额外协程放任旧操作继续。客户端操作结束也不证明数据库未提交；结果不明仍按后续读取的持久化事实恢复。

#### 手动创建与任期边界

手动执行不进入自动队列，自动和手动入口共用本进程的 Instance 创建并发额度。手动请求没有空位时明确返回系统繁忙，不另建等待队列；取得额度后，仍按[手动触发记账](#manual-trigger-accounting)在提交成功后返回 Instance ID。繁忙仅表示本次请求未获处理，不证明同请求号的此前请求没有成功，重试仍遵守原请求身份规则。

自动队列、合并状态及工作协程属于原 Leader 任期，失主后停止接纳和启动新自动工作，不将旧队列带入新任期。创建并发额度属于进程，不能因同进程重新当选或同时接收手动请求而另起不受约束的创建并发。非 Leader 上的手动入口也受自身进程额度保护；这不是跨节点全局限流，也不是整个数据库所有操作的并发上限。

#### 迟到代价与部署参数

排队时间不冻结错失判定。10:00 收到提示、10:00:06 才取得 Job 行锁，仍按锁后调度进程时间应用固定 5 秒规则，不能因为回调准时就保证创建正常 Instance。每天 10:00 的 Job 若因过载到 10:01 才被恢复发现，默认忽略策略跳过该轮，立即执行一次策略最多补一轮，且仍受阻塞规则约束。

#### 部署初始参数 {#trigger-runtime-defaults}

以下三个配置文件参数采用已确认的实现初始默认值，不增加 Job 页面配置。自动工作协程数直接采用 Instance 创建并发配置，不再提供独立旋钮。

| 参数 | 初始默认值 | 作用范围 |
| --- | --- | --- |
| 待处理 Job 总容量 | 1024 | 排队中与处理中的不同 Job 合计；同一 Job 的后续检查复用槽位，不是启用规则数量上限 |
| Instance 创建并发 | 32 | 自动与手动共用的进程级额度，跨本进程 Leader 任期保留；不是 Task 派发或业务执行并发 |
| 单次触发处理超时 | 3 秒 | 开始处理后的总预算，包含并发额度、数据库连接、Job 行锁等待及事务执行与提交 |

自动工作协程取出 Job 开始处理时计时，不包含此前的自动队列等待；手动请求立即尝试取得额度，没有空位即返回繁忙，不预留手动专用额度。调用方剩余期限更短时采用更短期限，自动处理同时受原任期上下文约束。超时不会冻结固定 5 秒错失判断，也不能证明事务未提交；不得提前释放额度后另起协程继续旧数据库操作。

这三个值是实现起点，不是已验证的性能上限。实现后比较 8、16、32、64 等创建并发档位，同时观察触发延迟、数据库等待、吞吐和资源占用，再校准默认值；不以实现前得出最终最优值作为开工前提。数据库连接池还承接 Task 登记、绑定、结果及其他查询，须一并核算，不能将创建并发直接当作连接池或全集群并发上限。

队列用于吸收短时波动，不以加长队列代替处理能力。Job 恢复采用下节独立的单批读取上限和查询超时，不将其混同为队列容量或触发处理预算。本节不确定 Task 派发或执行器容量，也不承诺 3 万规则同秒及时处理，相关验证见[触发容量验收](verification.md#trigger-capacity-checks)。

### Leader 单批触发恢复 {#trigger-recovery-scan}

仅当前 Leader 在接任时立即检查一次，之后由独立循环每 1 分钟检查一次；不与配置同步合并。循环串行运行，不重叠执行，不累计并补跑错过的周期 tick。

1. 每次读取前取当前调度进程时间，只查询主库中 `deleted_at IS NULL`、已启用、`next_trigger_at` 非空且已到期的 Job，按 `next_trigger_at, id` 升序读取一批，仅返回 `id` 和 `next_trigger_at`。
2. 单次 `LIMIT` 的部署初值为 **1024**，该次查询超时的部署初值为 **5 秒**；不执行后续分页，不跨周期保存游标或本次时间上界。候选查询不加行锁，具体 SQL 见[单批恢复查询](data-contracts.md#trigger-recovery-scan-proposal)。
3. 查询成功后，依次非阻塞 `Offer` 到本任期已有的 Job ID 队列；已接纳的 Job 按原规则合并，拒收新 Job 时立即结束本次，不等待容量、不新增缓冲，也不等待触发事务完成。未投递的候选不跨周期保留。
4. 查询失败或超时则结束本次，不在失败分支重试。下一周期重新读取当时最早到期的候选，不续接旧列表；进度已推进、停用或删除的 Job 按最新事实处理。
5. 查询和提交提示都受 Leader 任期约束，失主即取消查询并停止新投递。查询的短超时上下文只约束这次读取，不能作为已交接工作的父上下文；已入队工作使用原任期上下文和独立的单次 **3 秒**触发处理预算。

**5 秒仅是恢复查询超时，不是本次恢复的总处理预算，也不是固定的错失容忍值。** 每次读取上限与队列容量虽然初值同为 1024，仍是不同作用范围的部署参数。

成功推进后，Job 退出原来最老的积压位置；高频 Job 下次仍可能到期，但按新进度排序。大量头部 Job 持续失败或队列反复满载时，后面的候选可能长期得不到恢复检查。第一版接受这一边界，不承诺严格公平或一分钟恢复完成；不通过恢复扫描自动停用 Job 或改写其进度。此规则只适用于 Job 触发查漏，不替换 Instance／Task 的共同恢复，也不取消已接纳 Job 的队内轮转。

### 手动触发记账 {#manual-trigger-accounting}

手动入口执行管理鉴权与输入校验后，按[手动触发规则](behavior.md#manual-trigger)使用同 Job 的短事务协调，不复用自动触发的计划时间身份：

1. 以 Job 主键等值条件锁定单表单行，读取当前配置与删除状态；Job 不存在或 `deleted_at` 非空时返回不存在，不继续查重。确认未删除后，再用下一条 SELECT 核对同 Job、同 `request_id` 是否已经创建 Instance。
2. 已创建且请求内容一致时，返回原 Instance ID；请求内容冲突则拒绝。不再对原 Instance 重新做创建阻塞检查，也不因原实例已终态或 Job 参数已修改而创建第二轮。
3. 尚未创建时，校验当前创建条件，允许 Job 停用；按当前阻塞策略检查集群中同 Job 的未结束 Instance。被阻塞则明确拒绝，不保存一个等待自动解除的请求。
4. 创建新的待开始 Instance，同事务保存手动请求身份、请求内容比较所需事实和本轮执行配置；当次参数覆盖只作用于本轮，不更新 Job 或 `next_trigger_at`。
5. 收到提交成功确认后返回 Instance ID；后续推进按持久化 Instance 接续，不在创建事务内派发 RPC，也不等待业务执行。

部分唯一索引按 `(job_id, request_id)` 保护手动成功创建，与自动触发约束分开。UUID、覆盖标记及快照参数比较按[字段契约](data-contracts.md#execution-config-field-draft)执行：入口先校验覆盖组合，合法覆盖字符串去首尾空白后用于保存及比较。取得 Job 锁后另发 SELECT 查重；指定手动身份的 INSERT 冲突未返回行时，再用下一条 SELECT 读取原记录并比较，不以无变化 UPDATE 换取旧 ID。冲突后仍查不到原记录时返回可重试的不确定结果，不在事务内无限循环；完整规则见[已确认的触发持久化协议](data-contracts.md#trigger-transaction-proposal)。输入及错误语义按[已定管理契约](data-contracts.md#job-input-query-proposal)落实，不建立独立请求表，也不因请求去重增加 Redis 锁或请求队列。

提交结果不明时保留“不确定”的反馈，调用方用原请求号重入核对，不盲目新建。尚无成功记录时，重试可能按此时的配置及阻塞条件创建；明确拒绝不永久留痕，响应丢失后再次到达也不保证重放第一次拒绝。Job 已逻辑删除时，即使原 Instance 仍保留，创建入口也返回 Job 不存在，原 Instance 仍可按 ID 查询；该响应不证明原请求未执行。历史记录被清理后不保证原号仍能查重，清理与请求重试的实现边界在持久化及管理契约中衔接。

该入口只同步确认创建事实，不改变 Task 回报的异步接收协议，不启动整轮执行倒计时，也不因客户端未收到响应取消已经提交的 Instance。

### Job 逻辑删除事务 {#job-deletion-transaction}

删除管理入口完成鉴权与输入校验后，在一个短事务中执行：

1. 通过 Job 主键等值条件单独锁定一行，读取 `deleted_at` 与启停状态；不存在或已删除的记录不进入后续删除流程，已启用则拒绝删除。
2. 确认未删除且停用后，另发一条 `EXISTS` 查询，检查同 Job 是否存在状态为待开始或运行中的 Instance。复用已有活跃 Instance 部分索引，不拉取历史列表、不锁住全部 Instance，也不按 Task 逐条查询。存在未结束轮次时拒绝。
3. 满足条件时通过 GORM `Delete` 保存 `deleted_at` 删除时间，沿用 System 行为不额外补写 `updated_at`；保留原停用状态及 `next_trigger_at`，不物理移除 Job 行，不改写 Instance／Task。
4. 提交后才按已有机制发送 etcd 配置提示；通知失败仍由分钟核对补齐，不在事务中进行外部 I/O。

删除与手动／自动创建、启用和编辑在同一 Job 行上协调。必须先取得 Job 锁，再发活跃 Instance 查询，以使用 `READ COMMITTED` 下锁后的新语句快照：并发创建先提交时，删除能看到其待开始／运行中 Instance 而拒绝；删除先提交时，后续创建、编辑或启用看到删除标记而拒绝。检查时仍活跃、随后恰好结束的轮次允许使本次删除被保守拒绝，不要求每次 Instance 结束反向锁 Job。

删除只改变定义的可用性，不是停止执行或清理历史。所有 Instance／Task 继续保留；父已终态但子尚未收敛时，沿用原取消和结果处理协议，不能因普通 Job 查询已不可见而丢弃恢复工作。历史查询基于 Instance 快照，显式只读关联已删除 Job 时只能取得删除时的最后定义，不能把它作为本轮执行配置。规则及用户可见边界见[Job 逻辑删除](behavior.md#job-deletion)，验收见[删除专项](verification.md#job-deletion-checks)。

### 切主与配置变更边界 {#leader-config-boundary}

**第一版不增加数据库全局任期锁。发现失主后取消该任期的本地工作；残留触发必须按数据库中的最新 Job 重新判断，接受切主交界处旧任期的合法事务提交。** etcd 选主控制正常触发来源，Job 短事务保护持久化记账；两者不构成“新 Leader 当选后，旧节点一笔事务也不能提交”的保证。

#### 每次选主使用独立的本地上下文

每次当选创建新的 `leaderCtx`，用于该任期的 Cron 触发处理、配置同步、触发恢复和触发记账数据库操作。发现失去 Leader 资格或无法确认资格有效时，取消该上下文并停止安排新工作；待处理工作也不得脱离原任期继续启动。相同进程再次当选时使用新上下文，不能只检查一个重新变为 `true` 的 `isLeader`，让上个任期的工作复活。

停止 robfig 不能终止已经启动的回调；取消 Context 也不能证明在途数据库事务一定回滚。取消信号继续传递至数据库操作，但提交结果仍按持久化事实处理，不因取消而重放旧 INSERT。不承诺从 etcd 租约失效起固定几秒内所有旧动作消失，也不承诺只残留一笔事务。

已有 Instance／Task 的推进、派发与回报属于对等节点职责，不使用 `leaderCtx` 控制其生命周期。失主不取消这些合法工作，仍须满足各自执行权与终态规则。

#### 旧回调只提示检查 Job

触发回调携带 Job ID 作为检查提示，不以旧 Cron、旧启停状态、旧参数或扫描时的 `next_trigger_at` 直接创建 Instance。进入[同 Job 短事务](#trigger-accounting)后，重读最新配置、状态及进度，用锁后读取的调度进程时间应用到期与错失规则，并按当前持久化事实判断阻塞。

例如 A 失主后仍有一笔在途触发事务，B 已当选并检查同一个 Job。A 若按当前数据库事实合法创建本轮 Instance 并推进进度，B 随后取得锁就按新进度处理，不再用旧值重复创建。若 A 的事务最终回滚，B 取得锁后可按原进度判断。接受哪个节点完成这次合法记账，不等于允许旧节点凭过期快照授权触发。

#### 管理变更与触发协调

编辑、启停和删除 Job 与触发记账在同一 Job 行上协调，以成功提交的顺序决定后续处理。编辑只允许未删除且停用，状态检查与保存须和启用协调，不能凭过期快照更新已启用或已删除 Job；启用时依据未删除的当前配置原子保存新触发时间。删除按[单行锁后校验并标记](#job-deletion-transaction)执行；普通更新利用同一行的写入互斥，涉及并发读改写时才按仓库规范使用主键单行显式锁，不把普通 CRUD 全部改成 `FOR UPDATE`。

| 已提交的先后顺序 | 后续行为 |
| --- | --- |
| 停用或删除先提交，触发随后检查 | 看到已停用或已删除，不创建自动触发的 Instance；内存规则尚未移除也不能绕过检查 |
| 触发先提交，随后停用 | 已创建 Instance 保留，停用不追溯取消该轮；如需停止，走 Instance 停止入口 |
| 停用状态完成编辑，尚未重新启用，旧回调随后检查 | 看到停用就不创建 Instance，不能因规则已修改而恢复自动触发 |
| 编辑后重新启用已提交，旧回调随后检查 | 按最新启用状态、当前配置和启用时重算的进度判断，不沿用旧回调携带的规则、参数或时间 |

不在触发事务中查询 etcd 或执行其他外部 I/O，也不增加跨所有 Job 的数据库任期锁。只读一次任期值再比较并不能排除检查后切主；第一版不引入这一额外协调链路，接受上述在途提交边界。

配置通知采用 etcd Watch 加每 1 分钟数据库核对；串行加载、差异应用、监听衔接与任期隔离按下节执行，不要求每次触发携带配置版本作为授权依据。编辑与启用的进度规则已确认，Job 逻辑删除不清理已有 Instance／Task；本轮执行及恢复继续使用创建时保存的配置，不依赖当前 Job 可见。

### Leader 任期生命周期 {#leader-runtime-lifecycle}

**任期资源独立创建、完整退出后再参选；进程资源跨任期复用。** 这条规则防止反复切主累积 Cron、队列和工作协程，不要求其他机器等待旧节点清理完才接任。

| 生命周期 | 管理的资源 | 退出边界 |
| --- | --- | --- |
| 调度进程 | 数据库连接、Instance 创建并发额度、对等 Instance／Task 推进、派发及回报组件 | 不随失主销毁，也不等待业务执行完成才清理本地任期 |
| 一次 Leader 任期 | 独立 `leaderCtx`、Cron、Job 合并队列与自动工作协程、配置工作协程、Watch 及触发恢复循环 | 失主后停止入口、取消并等待本任期工作退出，不复用到下一任期 |

#### 启动与首次装载

先准备好本任期的有界队列与消费能力，再启动配置核对、监听及独立触发恢复。Cron 初始保持未启动；完整读取启用规则后，在未运行的 Cron 中批量注册有效规则，再启动并确认实际初始化完成，最后提交注册后的到期检查。这样避免首次装载大量规则时，边运行边逐条添加导致反复排序。

`Start()` 返回不代表 Cron 已完成全部条目的下一次时间计算。首次启动和后续热更新都须在整批应用完成后确认一次，再提交新增／替换规则的到期检查；具体顺序见[配置加载流程](#job-config-reload)。合法空配置可以启动空 Cron；单条非法规则继续隔离，不阻止其余规则生效。

首次查库失败时 Cron 不启动，但配置入口、分钟核对和独立触发恢复继续运行。后续成功时按同一首次装载路径启动，不把恢复检查串在加载成功之后。整个过程不写入或重置 `Job.next_trigger_at`，也不承诺切主后的所有规则都能在 5 秒内恢复触发。

#### 失主与资源释放

1. 关闭本任期入口，取消 `leaderCtx`，停止接纳和启动新的自动工作。
2. 停止 Cron、Watch、配置核对与恢复等工作来源；丢弃尚未处理的旧提示，不在失主后排空执行旧队列。
3. 等待本任期已启动的短操作、回调和工作协程退出，再释放引用。并发额度仍覆盖实际在途操作，不能先归还额度、再将旧操作留给脱离管理的协程。
4. 本地旧任期清理完成后，才能重新参选；再次当选使用新任期对象，但复用进程级创建额度。

启动、配置应用和停止必须协调，防止加载迟到返回后重新启动已停止的 Cron。robfig 的 `Stop()` 不会取消已经启动的回调，其返回的等待 Context 也不覆盖 DogX 自己的数据库工作协程，不能代替整套任期退出管理。

Go 不能强制终止任意协程。清理异常卡住时，本机保持不重新参选并记录错误，不能通过不断创建新任期掩盖；其他机器仍可接任，必要时由运维重启旧进程。本规则不另设固定清理秒数或自动强杀机制。

取消不证明在途事务回滚，继续接受[旧任期合法提交](#leader-config-boundary)。丢弃提示不推进数据库进度，后续由新 Leader 按持久化事实恢复；对等推进和手动请求不被任期上下文一并取消。对应场景见[任期生命周期验收](verification.md#leader-runtime-checks)。

### etcd 选主与配置通知接入 {#etcd-integration}

**选主采用官方 `concurrency.Session + Election`；配置通知使用一个持久标记，失败由既有分钟核对兜底。** 两者共用 etcd 基础设施，但键空间和生命周期分开，不增加可靠消息队列或每 Job 分布式锁。

#### 选主会话与租约

使用项目当前依赖的 etcd client/v3 v3.5.21。租约 TTL 的部署初值为 **15 秒**，必须校验为正值；这是 DogX 的选择，官方 Session 默认值为 60 秒。续租交给官方组件，等待当选使用候选生命周期上下文，不套触发事务或普通短请求的超时。

会话结束或主动退出后，关闭任期入口并按[生命周期规则](#leader-runtime-lifecycle)清理。旧工作完整退出后才能重新参选；会话建立或竞选失败采用退避，不不断叠加会话或后台协程。普通可恢复网络故障优先由客户端处理，不能将一次请求失败直接等同于租约失效。

`Session.Done()` 表示租约已不再续约、已过期或会话已被孤立；当选返回后仍须检查会话及当前生命周期没有结束，才安装 Leader 运行资源。选主不提供数据库提交硬隔离，旧在途合法事务仍按同 Job 短事务协调。

15 秒不是接任时限，更不保证赶上 5 秒错失容忍。接任还受故障检测、etcd 可用性、选举及规则装载影响；期间遗漏沿用既定忽略或执行一次策略，不因采用租约而承诺每轮都能补跑。

#### 键空间与访问权限

同一逻辑调度集群的副本配置统一前缀，组件集中维护固定后缀。例如：

| 用途 | 键或范围 | 生命周期 |
| --- | --- | --- |
| Leader 选主 | `/dogx/<cluster>/scheduler/election/` | 官方 Election 管理候选键，绑定选主租约 |
| Job 配置变更标记 | `/dogx/<cluster>/scheduler/job-config-changed` | 普通持久键，不挂 Leader 租约，不设置 TTL |

不同环境、不同调度集群隔离前缀，不能让连接不同业务数据库的集群误用同一范围。通知值固定为 `reload`；每次 Put 都会推进 etcd revision 并产生事件，不额外读取、自增或生成随机版本，监听方也不能因为值相同就忽略事件。

选主范围仅允许调度服务访问和维护；通知由负责管理保存的后端写入，Leader 读取和监听。执行器无权操作这些范围，etcd 认证独立于组 Token。部署按实际进程职责授权；etcd 原生写权限也允许删除，不能将其描述成仅允许 Put。

#### 提交后的通知预算

管理事务提交成功后，在当前请求中调用一次标记 Put，最多使用 **1 秒**总预算，并服从更短的上游剩余期限；上游已经取消时可以跳过。应用不另加业务重试，不为每次保存派生后台协程或建立通知队列；客户端自身可能重试，不能把“一次调用”解释成恰好一个网络请求。

通知失败记录日志和指标，不回滚数据库，也不把已提交保存主动改报为保存失败；仍由每分钟配置核对补发现。上游超时或连接断开时，不能保证客户端收到成功响应。通知成功仅说明标记已写入，不证明 Leader 已加载，更不证明首轮已执行。

#### 监听恢复与 I/O 边界

首次或重建时，精确读取标记键，以响应头的 revision 为 `R`，从 `R + 1` Watch，再发出一次配置核对信号；键不存在时也使用响应头 revision，不依赖键自身的版本。Put、Delete 均只表示需要核对，删除标记不等于删除 Job。

可恢复的 Watch 连接故障优先交给官方客户端重连。监听关闭、历史压缩等需要应用重建时，退出旧监听后重建并重新核对；失败采用从 **1 秒增长至最多 30 秒、带随机抖动**的内部退避，不在已有 Watch 仍恢复时再叠加另一套监听。任期结束须取消相关上下文；监听故障不阻断仍有资格的 Leader 的分钟配置核对。

| 操作 | 初始预算 | 约束 |
| --- | --- | --- |
| 主动发起的普通短 etcd 请求 | 5 秒 | 如建租约、读通知位置及主动退选；更短上游期限优先 |
| 配置数据库完整读取 | 5 秒 | 仅该次读取的预算；失败不应用半批结果，不套触发处理的 3 秒预算 |
| 管理提交后的通知写入 | 1 秒 | 上述单次应用调用的总预算，不额外业务重试 |
| 等待当选、持续续租、Watch | 生命周期上下文 | 不套 3 秒或 5 秒短超时；退出由相应生命周期取消 |

这些是实现初值，不增加 Job 页面字段，也不是整个组件的固定退出时限。短建租约请求与长会话续租的上下文必须分开，不能把 5 秒上下文直接作为整个 Session 的生命周期；官方 Campaign 内部取消清理同样不能被宣称保证在短请求预算内结束。具体库行为见[接入依据](references.md#etcd-integration-evidence)，故障要求见[etcd 接入验收](verification.md#etcd-integration-checks)。

### 配置加载与重载 {#job-config-reload}

**每个 Leader 任期使用一个串行配置工作协程，完整读取启用 Job 的轻量配置后只应用差异；已有 Cron 正常触发不随加载暂停。** 配置同步不推进 `Job.next_trigger_at`，也不替代独立的每分钟触发恢复。

#### 通知与首次加载

一个调度集群维护一个 etcd 配置变更标记，管理事务提交后更新标记，提示 Leader 重新核对 PostgreSQL。不保存完整 Job 配置，不为每个 Job 创建监听，也不增加配置版本表；键、权限、发布失败反馈与预算按[etcd 接入约定](#etcd-integration)执行。

新任期按[任期生命周期](#leader-runtime-lifecycle)创建独立资源，Cron 初始不运行；配置工作协程及一个待核对信号先就绪。接任、etcd 通知、每分钟核对和 Watch 重建完成都使用同一配置入口。分钟核对从任期开始运行，不能以首次加载成功为启动前提。

首次建立或重建监听时，先读取 etcd 当前 revision `R`，从 `R + 1` 衔接 Watch，再安排一次数据库核对。读取与监听之间发生的标记变更可在历史仍保留时被接收；历史压缩导致无法续接时，重新取得当前位置、建立监听并重新核对，不要求逐条回放全部旧配置。revision 只表示 etcd 监听位置，不是 PostgreSQL 的 Job 版本，也不改变数据库与通知之间的双写窗口。

Watch 故障不能单独阻塞配置工作协程及分钟核对；是否还允许运行，由已有 Leader 资格控制决定。确认失主或无法确认资格有效时，按任期边界停止新工作，不因配置兜底而绕过选主。

#### 串行核对与差异应用

待核对信号容量为 1，只表示“还需核对”，不是变更事件历史。工作协程先取走信号，再读库和应用；处理期间的新提示可以留下下一轮信号，结束时不能将它清掉。连续提示可以合并，但不通过不断延长等待来推迟已经安排的核对，也不为每条通知新建协程或排队项。

每次从 PostgreSQL 主库用一次查询读取全部未删除且启用 Job 的 ID、Cron 等定时注册字段，明确包含 `deleted_at IS NULL`，不逐 Job 补查，不读取业务参数、Instance 或 Task。只在查询完整成功后应用结果，不能把读取失败或半批结果当成“剩余 Job 已删除”。合法空结果则表示当前没有有效启用规则。

| 数据库与当前内存的差异 | 应用动作 |
| --- | --- |
| 新出现且规则有效 | 注册新规则 |
| 同一 Job 的 Cron 等定时字段变化 | 解析新规则后替换旧规则 |
| 已停用或删除，不再出现在完整结果中 | 移除该 Job 的内存规则 |
| 定时注册字段未变化 | 保持原规则，不删除再注册 |
| 单个 Job 的 Cron 解析无效 | 移除该 Job 残留的旧规则并记录错误，继续处理其他有效 Job；不自动修改数据库启停状态 |

`next_trigger_at` 是运行进度，不参与规则差异比较，不能因每轮进度推进而重建 Cron。只修改名称等非定时字段也不要求重建；触发时仍在同 Job 事务中读取当前配置。核对成本随启用规则数量增长，当前按几百条规则采用全量轻量读取与内存比较，容量由既定基准验证。

同一任期不并发执行多次配置加载，因此不会出现新加载先应用、旧加载后返回覆盖它的顺序倒置。读库期间又有配置提交仍可能产生短暂延迟，后续提示或分钟核对继续收敛；内存快照不是数据库触发授权。

#### 注册后检查到期

首次装载时，完整读取启用规则，在未启动的 Cron 中注册全部有效规则，再启动 Cron；热加载时则向已运行的 Cron 应用本次差异。两条路径都在整批应用后确认 Cron 已完成初始化或接收新增／替换条目，再将这些 Job ID 提交给[统一触发入口](#trigger-accounting)检查一次。未变化的规则不额外检查。

robfig v3.0.1 的 `Start()` 只启动运行协程；热加载的添加调用返回，也可能早于接收方完成该条目的下一次时间计算。因此，仅等待调用返回不能充当初始化确认。例如检查时还是 09:59:59.9，而 Cron 在 10:00:00.1 才计算未来时间，首轮可能要等分钟恢复才发现。

适配层可在协调好生命周期的前提下，使用运行中 `Entries()` 的一次快照往返确认本批已处理；每批一次，不逐条复制全量条目。这是利用运行循环的同步行为，不是库提供了独立就绪接口。确认过程与停止须协调，不能把停止后直接读取内存条目当成运行就绪；不修改第三方库，不增加零值 `Next` 巡检或自动重建。

例如首轮是 10:00，读取配置时为 09:59:59，注册完成时已到 10:00:01。robfig 新规则从注册时刻向后计算，不能依靠它补回过去的 10:00；注册后的检查读取原 `next_trigger_at`，此时迟到 1 秒，按正常规则处理。若已超过 5 秒，则应用错失策略。尚未到期就退出，不表示启用后强制立即执行，也不重新初始化首轮时间。

检查与正常 Cron 回调、恢复检查并发时，共用同 Job 短事务与自动触发身份。配置工作协程不逐个等待触发事务，提交检查受统一触发入口的容量限制；无法及时接纳或处理时仍由独立的恢复检查兜底，不增加专用无界队列。首次加载可能产生一批新增规则，不能承诺所有注册后检查都在 5 秒内完成；接纳、合并及队满处理遵守[触发容量与过载](#trigger-capacity)，采用[1024／32／3 秒部署初值](#trigger-runtime-defaults)。

#### 失败与任期退出

| 情况 | 处理规则 |
| --- | --- |
| 整次查询失败 | 保留已有规则，记录错误，等待下一次通知或分钟核对；不因失败立即自行唤醒形成重试空转 |
| 首次加载失败 | Cron 保持未启动，保留后续核对入口与分钟周期；独立的触发恢复继续，不停止整个加载流程 |
| Watch 中断或历史不可续接 | 可恢复连接故障由客户端处理；需要应用重建时退避重建并核对数据库，不叠加活跃监听，不将通知缺口解释为没有配置变化 |
| 加载尚未返回时失主 | 取消原任期工作，丢弃迟到加载结果，不再安装新规则或发起注册后检查 |
| 同一进程再次当选 | 本地旧任期清理完成后才重新参选；当选后使用新任期运行对象，旧工作不复用新任期的 Cron 或规则映射 |

停止旧任期 Cron 仍不证明已发起回调或数据库事务全部撤销，继续遵守[合法在途提交边界](#leader-config-boundary)。对等 Instance／Task 推进不随配置工作协程退出而取消。

本节确认的是 Job 规则同步流程，不将它扩展为执行器组、Token 缓存的同步协议。Cron 异常按[已定简化规则](behavior.md#cron-errors)处理，不增加检查内存零值 `Next` 并自动重建的分支。通知键、权限、I/O 预算及重连遵守[etcd 接入约定](#etcd-integration)；触发处理采用[已定部署初值](#trigger-runtime-defaults)，其 3 秒预算不直接套用于配置加载。异常时钟遵守[运维边界](operations.md#scheduler-timezone)。对应验证见[配置同步验收](verification.md#job-config-sync-checks)。

## 5.2 对等节点与推进执行权 {#advancement}

Leader 负责长期规则触发，以及接任时和每 1 分钟的 Job 触发进度恢复检查，不负责全局所有 Task 的逐个派发。已经创建的 Instance／Task 由包括 Leader 在内的所有调度节点按自身空闲容量取得必要执行权并推进，不向 Leader 请求分配。准备推进、结果接收和收尾创建可以发生在不同节点。

例如 A 为 Leader 并创建 I1，B 取得准备推进权、派发准备 Task，并在结果持久化后生成分片；分片结果可以由 C 接收，满足条件时由候选节点唯一创建 PostTask。后续步骤不要求返回 B。A 故障后重新选主接替触发职责，执行协调则按持久化工作和执行尝试恢复，不接管一个持续到终态的 Instance 负责人。

“对等、无状态”表示持久化状态与恢复不绑定某个固定节点，不是没有连接、缓存、在途 RPC 或临时回报队列，也不是承诺内存结果不会丢失。结果尚未落库时，进程退出可能丢失其唯一副本；恢复结算不能依赖原节点的本地文件。各节点仍须识别：

- 当前获准进行的推进或派发动作。
- 仍然有效的远端执行尝试。
- 已失效的协调动作与迟到结果。
- 可以恢复的平台步骤，以及成功结果已持久化、不能因平台推进失败再次调用的业务步骤。

取得推进权不代表可以重跑本轮全部 Task。etcd 选主只解决触发 Leader 的范围，不能替代生成、派发和收尾创建的防重。Task 发送前通过 PostgreSQL 条件写入登记当前尝试，不增加每 Task 的 Redis 或 etcd 锁。新尝试登记与父 Instance 终态通过下述单行短事务协调，结果回报不统一锁父；生成及其他推进权的持久化和恢复协议仍待设计。

## 5.3 有界本地派发与持续补充 {#bounded-dispatch}

Task 先保存；分片确认完整生成后，由生成节点直接启动本地有界派发。节点已经知道刚生成的 Task，不需要再次扫描发现它们，也不等待其他节点领取。较大 Instance 按小批量补充，必要时按 Instance 分页读取剩余工作，不把全部 Task 无限制装入内存。准备结果不要求返回原派发节点；完成生成的节点负责当前本地派发，不因此取得整轮固定归属。

节点只在有容量时取得工作，空闲且无工作时退避，避免大量预领后长期排队。本地派发队列、并发派发数、同时准备的 Instance 数量都必须有界；队列满时暂停补充，已提交工作仍留在共享持久化状态中。

公平性需要覆盖两个维度：

- 多个 Instance 之间，避免一个大实例长期占满派发能力。
- 同一 Task 模型的不同阶段之间，避免海量分片长期挤占准备和收尾。

统一 Task 不强制所有类型使用无差别的同一队列。具体公平性算法和容量值尚未决定，不能靠统一建模宣称已经解决负载均衡。单个大 Instance 的初始派发仍受当前派发节点能力限制；其他节点可安全取得待处理工作继续补充，但这不等于单轮派发可以无限横向扩展。

派发 RPC 等待的是**接收确认**，不是业务执行结束；接收确认返回后可以释放本地派发槽位并补充下一批，不必等业务完成。执行器必须维护自身执行并发和队列上限，接收失败、超时及重试不能形成无界堆积。调度器有界派发不能替代执行器容量保护。

### 发送前的尝试登记 {#attempt-registration}

正常派发和恢复接续共用以下规则，适用于普通、准备、分片及收尾 Task：

1. 先取得本地派发容量，再处理容量范围内的一小批候选 Task；没有槽位时不提前登记执行尝试。
2. 候选按 Instance 组织。每个短事务仅以主键等值条件锁定一条 Instance 记录，锁内按当前数据库时间校验本轮仍允许执行、未到截止时间，再对该轮的有界一批 Task 做条件更新：Task 仍可派发、已到最早可派发时间、当前尝试未被其他节点推进且预算允许。当前尝试标识、机会记账及进入执行中状态必须原子保存，不逐条先查再改。
3. 数据库返回本次成功登记的 Task；本次收到明确提交成功确认后，只对这些 Task 发送对应尝试的 RPC。提交结果不明则按[恢复规则](#commit-unknown)放弃本次本地发送；条件未满足的条目也不发送，事务中不包含 RPC。
4. 派发槽位释放后继续补充；积压仍保存在数据库，不把整轮分片提前标为执行中后长期排在内存里。

正常节点与恢复节点同时处理同一 Task 时，共享条件写入约束同一次尝试的登记；失败的一方不得凭旧信息发送。该机制保护平台授权和记账，不保证业务恰好执行一次，也不增加整轮负责人。

有界检查补充遗漏、积压和到期重试，不是每条新 Task 的正常必经步骤。已经登记为执行中的 Task 不能直接被恢复节点重新发送；没有绑定及结果时遵守[有限观察与条件结算](#missing-binding)，已有绑定但结果不明或执行器失联时遵守[等待整轮超时](#bound-result-wait)，不据此提前重派。

### 记账时点与写入成本 {#dispatch-accounting}

**尝试登记提交成功就占用一次执行机会。** 仅在本地排队、尚无派发槽位或登记事务确定未提交，不占用机会。明确未接单的 [BUSY](#busy-backpressure) 可条件返还本次已占机会，但不能扩展到通信结果不明。登记已提交、节点却在实际 RPC 前宕机时，恢复节点不能据此免费重发；平台无法可靠区分“没有发送”与“已发送但确认丢失”。重试次数为 `0` 时，可能业务实际尚未执行，Task 最终却失败。通信故障处理继续遵守[统一预算](behavior.md#retry)，不额外叠加通信重派额度。

记账以数据库实际提交为准，不以调度进程是否收到确认决定是否占机会；只有发送资格要求本次获得明确提交成功确认。确认不明时的保守处理见[提交结果不明恢复](#commit-unknown)。

已保存为待派发的 Task 通常需要一次条件更新。批量操作减少数据库往返，不消除每条记录的行更新、WAL、相关索引维护及行锁竞争。例如 1,000 条 Task 每批 20 条，登记环节约为 50 次批量更新，但仍修改 1,000 条记录；这只是成本示例，不是批次默认值，也不包含后续确认和结果保存的写入。

每个 Instance 的登记批次还增加一次父行加锁和状态／截止校验。同一轮的这些短事务串行，不同轮可并行，提交后的 RPC 与业务执行不占父锁。跨 Instance 不用 `IN` 一次锁多条父记录；这一按轮协调成本已单独接受，处理数量和批次必须有界。大量单 Task 的小 Instance 难以摊薄这部分成本，不能把批量称为消除所有逐轮往返；容量验证必须覆盖该场景。

新建 Task 只有在本地容量与全部派发前提都具备时，才可能合并插入和尝试登记；具体适用路径留到事务实现设计，不能为了省一次写入提前授权全部分片。正常路径仍是持久化后本地直接派发，不改为全节点高频扫描抢任务。

### 新尝试登记与整轮终止协调 {#authorization-terminal}

**新尝试的执行许可必须与父 Instance 的停止、超时和正常结束互斥；保存结果不统一取得这把父行锁。** 新尝试登记和各 Instance 终态入口，都在短事务中按主键等值锁定同一条 Instance 记录。显式锁只针对单表单行，不使用范围、多行、跨表或 advisory lock；事务采用默认 `READ COMMITTED`，不包含 RPC、Redis 等外部 I/O。

| 竞争顺序 | 持久化结果与执行边界 |
| --- | --- |
| 停止或其他终态先提交 | 后续登记取得锁后看到终态，不能再授权新尝试 |
| 登记先提交，随后停止 | 已登记尝试可能正在发送或运行，只能尽力取消；后续新尝试仍被禁止 |
| 等待父锁期间超过截止时间 | 取得锁后用当前数据库时间复核，不用事务开始时的旧时间继续授权 |
| 正常结束与人工停止竞争 | 同一父行协调，按锁内终态及截止检查裁决；正常结束还须满足有效最终结果条件 |

时间判断的边界是**取得父锁后的受保护决策点**，不是事务开始时间、执行器自报时间或本地缓存时间。决策在截止前有效，随后事务成功提交，并不保证物理 COMMIT 或 RPC 到达也发生在同一截止毫秒之前；不能把该协议解释成精确的墙钟截断。若锁内判断时已到期，则不得登记新尝试，Instance 按既定超时规则终止；具体 SQL 与首次开始计时的衔接留到实现协议。

**等待重试只是候选状态，不是再次执行的许可。** 失败结果、明确 BUSY 或未知结算按当前 Task 的尝试、旧状态及预算条件写入，不要求每条处理都锁父。它们与父终态交错时，子 Task 可以短暂进入或留在等待重试，BUSY 的条件记账修正也可以交错完成；这不恢复父状态，不授予新尝试，也不能覆盖子 Task 已有终态。真正再派发必须经过上述父行登记关口。若已观察到父终止，则走取消收敛，不能把“可以短暂交错”用作继续推进的理由。

Instance 终态提交后，子 Task 的分批取消和定向取消 RPC 在父事务之外进行。共同恢复检查必须覆盖**父 Instance 已终态但仍有未终态子 Task**，包括结果处理刚写入的等待重试；不能只扫描活跃父实例，也不新增专用轮询。未终态子 Task 通过条件取消收敛，期间先形成有效终态的仍保留；平台终态不证明业务已经退出。

该协议不恢复整轮固定负责人，不把所有结果写入串到父行上。接收 ACK、结果落库和新执行授权仍是不同事实；登记、BUSY 返还及结果写入的[提交结果不明](#commit-unknown)按已确认规则恢复，不按普通回滚处理。

## 5.4 延迟派发能力复用 {#deferred-dispatch}

失败重试需要持久化“最早可派发时间”，BUSY 延后复用这一能力：Task 在派发前已经入库，收到 BUSY 后需要延后时，更新原 Task 的最早派发时间，由既有待处理检查在到期后继续处理。不新建 BUSY 专属表、队列、扫描器或另一套延迟调度系统。

本地直接派发和恢复检查都遵守这一时间，避免其他节点提前重派。本地计时器可以加速，但不能成为到期工作的唯一依据。保存时间是为了共享派发时机，并不是因为没有时间字段就会丢失 Task；它也不解决执行器负载不均的问题。

### 明确未接单的 BUSY 处理 {#busy-backpressure}

**BUSY 专指执行器明确回复容量已满，本次未接单、未入队且未开始业务执行。** 这是可确认的容量拒绝，不是普通业务失败或不确定的通信失败。执行器已经接受任务后，不得再用 BUSY 表示内部执行失败。

| 情况 | 已确认处理 |
| --- | --- |
| 收到当前尝试明确未接单的 BUSY | 条件返还本次已占执行机会，关闭本次尝试并延期；不消耗 Task 执行重试预算 |
| Job 执行重试次数为 `0` | 仍允许 BUSY 延期再派发，不把未运行的容量拒绝当作一次业务失败 |
| RPC 超时、断连或通用不可用响应 | 不能推断为 BUSY，不能返还；遵守原有通信不确定性和绑定规则 |
| BUSY 响应丢失，或返还事务失败／提交结果不明 | 不凭推测免费重派；持有原响应时仅做有界有限的条件记账重试，不建立长期待返还队列 |
| 持续 BUSY 直至整轮到期或手动停止 | 按整轮终止规则结束，不延长期限，不再正常派发 |

返还、关闭当前尝试及设置最早可派发时间必须原子提交，并校验当前尝试身份及允许的旧状态；重复或迟到 BUSY 不能重复返还、覆盖已有有效结果或恢复子 Task 终态。该记账修正不统一锁父，可以与父终态交错；延期仅产生候选，下一次新尝试仍须经过[父行授权检查](#authorization-terminal)，父终止后子 Task 由恢复取消收敛。数据库事务不包含 RPC，具体字段及 SQL 留在实现协议中明确。

后续派发登记新的尝试身份，不因返还预算而复用旧 ID；已关闭尝试的迟到消息不得重新生效。不增加 Attempt 历史表，尝试身份也不能仅由可增可减的预算计数推导。实际派发次数可以超过原始执行加配置重试次数，但已占且未返还的执行机会仍受统一预算约束。

BUSY 延期复用原 Task 的最早可派发时间、既有有界检查和派发容量控制；必须退避，不能立即循环发送。不新建专用表、队列、扫描器或独立 BUSY 次数池。BUSY 等待包含在本轮时间预算内，具体退避间隔及容量参数尚未确定。

BUSY 记账失败或提交结果不明时，只对原 Task、原尝试和尚未结算的旧状态做**有界有限重试**，不套用执行结果的长期保留规则。原响应释放、进程退出，或未知结算／取消先提交后，不能凭“业务其实没有执行”补返机会；实际未执行也可能消耗一次预算。已落库的返还仍有效，不因本地处理报错撤销。具体次数、间隔或处理时限属于内部实现参数，见[提交结果不明恢复](#commit-unknown)。

再次派发继续使用原生 go-zero 负载均衡，不自行排除上次节点，也不保证下一次换节点或一定能执行成功。容量持续不足仍可能导致整轮超时；本规则避免把明确未运行的容量拒绝直接耗成业务失败，不承诺消除集群负载不均。

## 5.5 派发路由与执行入口 {#dispatch-routing}

首次派发和重试均复用 go-zero 原生服务发现与负载均衡。etcd 提供服务地址发现及更新，RPC 客户端选择可用连接；请求不经过 etcd 转发。调度器不自行挑选执行器，不按 Task 排除上次节点，也不保证重试更换实例。

go-zero 当前默认 `p2c_ewma` 依据 RPC 时延和在途调用等信息选择连接，不掌握异步业务 Task 的剩余执行容量。接收确认很快返回后，业务仍可能运行很久，因此派发 RPC 并发不等于业务执行并发，也不能保证各执行器的业务负载均匀。容量保护与两端背压仍是独立设计内容。

执行器通过统一 RPC 入口接收工作，按处理器名称定位本地注册业务代码，由 Task 类型区分普通执行、准备、分片和收尾。公共执行组件负责容量保护、异步执行、执行上下文、取消协作和结果回报；业务处理器返回结果，不手写回报 RPC，不直接维护调度表。

服务发现解决“发给哪个执行器实例”，处理器名称解决“执行哪段代码”。统一入口是多个执行器共同实现的协议，不是单点转发服务。具体分组、部署和信任边界归入[总体架构](./architecture.md)，消息字段与处理器签名归入[数据与接口](./data-contracts.md)，不通过本节默认决定。

### 接单后的执行器身份绑定 {#executor-binding}

第一版保留 go-zero 原生服务发现和组内负载均衡，不改为调度业务代码先选执行器。执行器每次启动生成新的进程实例标识 `executorInstanceId`，用于区分同一地址上的不同启动进程，不替代组 Token 认证。

正常派发沿用以下顺序：

1. 取得本地容量，条件登记当前尝试及执行机会，事务提交后发送 RPC。
2. 原生负载均衡选择接收执行器；执行器在接单响应中提供本次进程实例标识，不等待业务完成。
3. 调度端取得本次调用的实际对端地址，将进程实例标识与地址条件保存到当前尝试。已有结果或后续尝试不能被迟到的绑定更新覆盖。
4. 后续取消通过已保存的地址定向调用，并校验预期进程实例标识，不再随机负载均衡到同组其他节点。第一版不为已接单 Task 新增活动查询或心跳核对。

执行器直连部署下，可以通过 gRPC 的 `Peer` 取得实际连接地址；它在调用完成后提供，不等于派发前已知目标，也不能从地址推导启动身份。引入代理后，对端地址可能不是执行器，不得直接沿用该假设；可定向寻址是接入契约的要求。

注册描述可选节点，接单响应关联本次实际受理者，两者不是重复注册。Task 仍在发送前登记时进入执行中，不为绑定另加生命周期状态；接单确认不代表业务结果。定向客户端按需创建并有界复用，缓存移除与在途请求处理留待实现契约，不为每个 Task 新建连接。

正常接单后通常增加一次绑定行更新，可以小批量提交但不能为凑批长期拖延。合批降低往返次数，不消除行更新、WAL 和索引成本；该成本纳入容量验证，不宣称本路线比先选址更快。保留此路线是为了复用已有发现、连接可用性筛选和负载均衡，减少第一版自研目录与路由的维护范围。

接单 ACK 丢失，或调度节点收到 ACK 后、绑定提交前退出，可能留下已在执行但没有持久化目标的尝试；不能假定总能定向查询或取消。该窗口按下面已确认的规则处理，不增加 Task 级心跳、执行租约、广播寻找或免费重派机会。

### 绑定缺失的观察与条件结算 {#missing-binding}

本规则适用于当前尝试已经登记提交，但没有持久化执行器绑定，也没有已提交执行结果或结算的情况。它同时覆盖登记后未发送、执行器接单但 ACK 丢失，以及 ACK 已收到但绑定未提交；没有绑定不能证明业务尚未开始。已有绑定但最终结果未落库属于另一条恢复路径，不能直接套用本规则。

#### 有限观察与正常补齐

观察期从当前尝试登记时保存的数据库时间开始计算；换调度节点、重复扫描或重试保存绑定都不重置起点。它是平台内部的派发确认观察期，不是业务执行超时，不随整轮超时时长延长；整轮先到期时服从终止规则。具体秒数须在实现前结合派发 RPC 超时及绑定写入重试节奏确定，当前不设数值默认值。

观察期间，有效接单 ACK 可触发条件保存绑定；保存失败只重试元数据持久化，不重新派发业务。有效执行结果可以先于绑定提交，不能仅因绑定缺失而拒绝当前有效尝试的结果。内存中收到 ACK 或结果成功进入异步队列，都不是持久化证据，不能替代数据库条件。

#### 到期后的持久化裁决

观察期到期只取得条件结算资格，不立即使尝试作废。恢复节点必须再次确认仍是当前有效尝试、处于允许结算的旧状态、未绑定且未有结果或结算。结算本身不授权新执行，父终态与下一次登记按[统一协调规则](#authorization-terminal)处理。绑定保存、有效结果和未知结算通过持久化协议竞争：

| 先成功生效的数据库操作 | 后续处理 |
| --- | --- |
| 保存执行器绑定 | 不再按绑定缺失结算，转入已知执行器处理路径 |
| 保存有效执行结果 | 按结果处理，未知结算条件不再成立 |
| 将当前尝试结算为结果不确定 | 关闭本次尝试，迟到绑定及结果不得恢复它 |

以数据库条件写入成功提交为准，不以某节点内存中的消息到达顺序裁决。尝试标识与允许的更新前状态必须共同校验：即使下一次尝试还未创建，已经结算并进入等待重试的旧尝试也不能再接受迟到结果。迟到绑定不能覆盖有效结果、新尝试或终态，也不能静默替换一个冲突的已有执行器身份。

上述竞争语义已经确认；具体 SQL 与观察期时间比较仍需落实。Task 条件更新保护当前尝试，新执行许可另外经过父行授权关口，不能把未知结算成功当作再次发送许可。

#### 预算与终止优先

当前尝试登记提交时已占用一次执行机会，未知结算不再重复扣减。有剩余预算时，Task 可条件进入等待重试，沿用既定重试间隔，默认 `10 秒`；这只是候选，真正重试须在父仍允许执行时登记新尝试并占用下一次机会。预算耗尽则 Task 条件转为失败，原因注明执行结果不确定；不免费重发，也不广播寻找旧执行。

Instance 已停止或到期，不再授权新尝试或允许迟到消息恢复执行；并发结算留下的重试候选按父终态取消收敛。未知目标可能无法定向取消。数据库不可用时，不能仅凭本地计时器宣布结算成功；数据库恢复后再做条件处理，因此观察期不是保证完成恢复的 SLA。

**明确接受的代价：原业务可能仍在运行，甚至已经成功；若绑定和结果均未落库，平台仍可能重试，或将 Task 标记为结果不确定的失败。** 有限观察不能证明旧业务已停止；平台失败不等于业务一定失败，拒绝旧回报也不能撤销副作用，重复执行仍由业务幂等性兜底。

## 5.6 派发不确定性与业务幂等 {#idempotency}

第一版允许有界重试或恢复造成重复业务执行。派发超时、确认丢失或绑定缺失条件结算时，旧执行可能已经产生副作用，甚至仍在运行；平台不承诺业务恰好执行一次，也不承诺任何故障下必达或必定成功。已有绑定的失联执行不因此提前重派，按[等待整轮超时](#bound-result-wait)处理。

| 责任边界 | 已确认要求 |
| --- | --- |
| 是否先核实旧执行 | 不强制每次超时先查询原执行器，不以证明旧任务绝未执行为重派条件 |
| 执行器严格防重 | 不为此引入本地磁盘记录、跨重启去重或完整生命周期结果缓存；轻量接收防重是否值得采用留到协议设计 |
| 平台状态正确性 | 保留执行尝试与更新前状态条件校验；旧尝试不得覆盖新尝试，重复回报不得重复推进，终止 Instance 不得复活 |
| Task 创建 | 各阶段仍需创建防重；PostTask 每轮唯一，不因接受业务重复就放松持久化防重 |
| 业务副作用 | 准备、分片、收尾只要会产生副作用，业务方都要保证幂等；平台拒绝旧回报不能撤销旧业务副作用 |
| 重派范围 | 必须服从[统一预算](./behavior.md#retry)和整轮终止规则，不以通信恢复名义无限重跑 |

业务幂等依据应匹配实际操作，例如商户日报按“商户 ID＋统计日期”保证唯一或允许覆盖重算。仅用 Task ID 或执行尝试标识可能无法保护跨 Instance 重跑。

允许重复业务执行不取消结果持久化时的尝试与状态校验、本地合并检查、Post 唯一创建及有界恢复。接收 ACK 不承诺结果持久化，框架仍对已保存数据和后续推进的一致性负责。

## 5.7 结果回报与确认边界 {#result-report}

执行器通过 go-zero RPC 回报结果，使用 etcd 发现的调度服务地址，由 RPC 客户端负载均衡选择可用接收节点。回报无须经 Leader 中转，也不要求返回原派发节点；Leader 作为对等副本仍可接收回报。执行器不直接写调度表，数据所有权及状态推进集中在调度服务。

**第一版固定采用双端异步、有界内存缓冲，不提供同步／异步切换开关，不使用本地回报文件、持久化消息队列或跨重启结果缓存。回报 ACK 只表示调度端成功接收进内存队列，不表示已落库，也不表示该结果已被状态机采纳。** Task 状态和后续推进仍以有效结果的持久化提交为准。

### 执行器的独立回报队列 {#executor-result-queue}

业务处理器返回结果后，公共组件将结果交给独立有界队列，由固定数量的回报工作协程取出已有结果、按上限组成小批发送；不为凑批引入长时间等待，也不为每条结果创建一个无约束并发调用。

业务侧异步提交，回报工作协程同步等待 RPC 的接收 ACK，两者不矛盾。收到明确接收确认后释放对应结果；请求失败、超时或调度端无容量时，只在独立的有限回报重试额度内保留并重传。额度耗尽后释放本地结果，记录错误及丢弃指标，不无限等待 ACK。

回报积压严重时降低或暂停新任务接收；队列确实满时，完成结果的提交也接受背压，不能无限堆积或静默丢弃。容量覆盖队列、工作协程持有及在途结果，并与业务执行并发联动；待处理条数、固定工作协程和批量上限在容量设计中落实，结果报文复用 RPC 层大小限制，不额外设置业务结果长度或队列总字节配额。不能把已耗尽回报额度的结果重新入队并重置计数，变相恢复无限等待；入队等待和退出期间的具体清理边界仍需闭合。

### 回报重试预算与清理 {#report-retry}

**结果回报重试与 Task 执行重试独立。** 回报只是重发同一 Task、同一次执行尝试的已有结果，不重新调用业务处理器、不登记新执行尝试，也不消耗 Job 配置的 Task 执行重试次数。Job 执行重试次数为 `0` 时，仍允许按回报规则重传。

第一版用框架内部独立常量控制回报重试次数、间隔和单次 RPC 超时，不进入 Job 配置页面；具体数值尚未确定，也不沿用 Task 默认的 3 次额外重试和 10 秒间隔。普通、准备、分片及收尾结果共用这套回报规则。

收到接收 ACK 后结束对应结果的回报；没有收到 ACK 时，在有限额度内重发相同结果，由调度端幂等处理。重试耗尽后释放本地结果并记录错误及丢弃指标，即使原业务实际成功，也不为保住结果无限占用内存。批次部分接收、永久非法请求、过期结果及错误分类的具体契约仍需细化，不能把一个批次 ACK 当作所有条目已被接收。

本地释放结果不直接把数据库 Task 改成失败，不自行触发业务重跑，也不能撤销调度端可能已经接收或保存的同一结果。若后续恢复协议允许重新执行业务，仍按原 Task 执行预算及整轮终止规则记账。整轮超时用于未结束任务的兜底，不因回报重试延长期限。

这一取舍优先保证执行器长期运行，接受结果因有限重试耗尽而丢失，不仅限于进程退出导致的丢失。调度端采用不同的[写库故障保留规则](#scheduler-result-retention)，不套用执行器回报耗尽后的释放策略。

### 调度端入队与后台落库 {#scheduler-result-queue}

1. 按[内部信任边界](architecture.md#internal-trust)完成组 Token 认证及报文格式等基础校验，报文大小复用 RPC 接收上限，保留已认证的组上下文。
2. 成功进入有界结果队列才返回接收 ACK；容量不足时拒绝本次回报，不能丢弃结果却回复成功。
3. 固定后台消费者校验持久化 Task 所属组、当前有效尝试及更新前状态条件，幂等保存有效结果，采用有界小批量提交；组归属按本轮保存的配置／Task 关联判断，不以当前 Job 的组覆盖。
4. 事务提交后，通知本节点进行对应阶段的推进检查；不因入队或 ACK 提前生成分片、创建 PostTask 或结束 Instance。

认证和接收不能代替持久化授权校验。重复入队、旧尝试或跨组 Task 引用不能覆盖有效状态；批量落库也不能省略每条 Task 的条件校验。批量减少往返，不消除逐行写入、WAL 和索引成本。数据库暂时异常时，消费者保留当前有界批次并退避重试，积压向入口传导；不因已经 ACK 就把写库错误仅记录日志后丢弃。

两侧容量、工作协程数和批量上限属于部署参数，不进入 Job 页面；具体默认值、退出处理、批次错误隔离、确认粒度及重传退避在详细契约和压测中确定，不在此增加新的数值规则。

### 调度端写库故障与容量边界 {#scheduler-result-retention}

**调度端已经接收的结果遇到可恢复的数据库故障时，有界保留、退避重试，容量满后拒收新结果；不按固定重试次数或保留 TTL 主动丢弃。** 写库重试不占 Task 执行预算，也不重新调用业务处理器。

| 情况 | 已确认处理 |
| --- | --- |
| 可恢复的数据库故障持续存在 | 固定消费者保留已有结果并退避重试，不因失败次数或等待时间达到阈值就丢弃，不高频空转 |
| 待处理容量已满 | 拒收新回报，不对未接收结果返回成功 ACK，不另建无界等待队列或为每条结果新增等待协程 |
| 数据库恢复 | 重新按 Task 归属、当前尝试、状态及整轮终止规则处理；有效结果提交后才推进，不因曾经 ACK 就无条件写入 |
| 重复、旧尝试或永久无效数据 | 按有效性规则结束处理，不无限重试拖住正常记录；不能把数据库暂时不可用误判为结果无效，具体错误分类和批次隔离仍需设计 |
| 接收节点落库前退出 | 接受内存结果丢失，不依赖本地文件、持久化队列或执行器必然重报来补回 |

容量按**待处理结果总条数**控制，包含排队、消费者持有及等待重试的结果；从队列取出后仍占用待处理容量。重试保留原结果，不以不断复制结果或创建协程绕过上限。结合固定消费并发和 RPC 报文大小上限估算内存规模，第一版不做队列总字节配额，不实时累计内存占用后按 MB 准入，也不增加独立的业务结果长度限制或 Job 页面参数。

这些约束不等于整个 Go 进程的内存硬上限：业务结果构造、序列化、RPC、对象和 GC 仍有额外开销，需通过容量验证确认。具体队列条数、批次、并发、RPC 报文上限和退避参数尚未确定；准备工作项数组的生成和暂存仍按其独立契约设计。

数据库是调度端推进的必要依赖，故障期间保留固定容量的积压不等于无界增长；丢弃结果也不能替代恢复数据库。执行器有限重报与调度端保留因此采用不同规则。内存保留不延长整轮截止时间，也不使已停止或超时的 Instance 复活；退出处理与错误隔离的具体协议仍需在实现前闭合。

### 易失结果与恢复边界 {#volatile-results}

| 故障位置 | 已确认的处理边界 |
| --- | --- |
| 调度端未接收，或执行器未收到 ACK | 在独立回报额度内重传同一尝试；不占执行重试预算，重复回报不得重复推进 |
| 回报重试耗尽 | 释放执行器本地结果，记录错误及丢弃指标；不直接修改 Task 状态或重新运行业务，原结果可能已在调度端接收或落库 |
| 执行器在结果有效落库前退出 | 内存结果可能丢失，不依赖原机文件或持久卷重放 |
| 调度端 ACK 已收到、执行器已释放结果，接收节点落库前退出 | 唯一结果副本可能丢失，执行器重传不能保证补回；执行器甚至仍然在线 |
| 有效结果已提交，后续检查提示丢失 | 按持久化事实恢复平台推进，不重新执行已确认成功的业务步骤 |

平台不保证每条业务执行结果跨进程故障无损保存，也不能从“节点仍在线”推断当前尝试仍在运行。没有绑定及结果时按[绑定缺失规则](#missing-binding)有限观察并条件结算；已有绑定但无有效结果时按下述规则等待整轮终止，不再因失联或结果丢失提前重派。任何路径都不能承诺重建原来的真实成功结果。

### 已绑定但无结果时等待整轮超时 {#bound-result-wait}

**当前尝试已有持久化执行器绑定，但没有有效落库结果时，第一版不因执行器失联、重启或回报丢失而提前结算重派，统一由有限整轮超时兜底。** 执行器仍在线但回报重试耗尽、调度端已 ACK 却在落库前退出，也遵守同一规则。

| 事件 | 已确认处理 |
| --- | --- |
| 有效成功结果落库 | 按正常规则推进，不因为曾经失联而拒绝仍有效的结果 |
| 有效失败结果落库 | 有剩余预算时可形成重试候选，下一次执行仍须经过父行授权检查；不因处理结果而统一锁父 |
| 无有效结果，包括已知执行器退出 | 当前尝试保持执行中，不创建新尝试、不返还已占机会，不凭节点离线提前重派 |
| 有效手动停止 | 按既定取消规则终止，不必等到超时 |
| 整轮到期 | Instance 以失败及超时原因结束，未结束 Task 按既有取消规则收敛；即使有剩余执行次数，也不再重派 |

“等待结果”只是对执行中状态的描述，不新增状态、独立 Task TTL、活动探测或心跳，也不在某个调度节点持续保留一个等待对象。首次开始及截止时间持久化，由既有有界超时检查恢复推进；重试、换节点或丢失回报均不延长期限。整轮超时不允许 `0` 或无限时长；新增表单预填 900 秒，实际执行使用本轮已保存的配置，不在恢复时补默认值。

接受的代价是故障恢复不够及时：例如整轮预算 15 分钟、第 1 分钟执行器宕机，可能还需等待剩余 14 分钟才结束，而不使用剩余次数换节点重跑。一个分片永久丢失结果也可能拖到整轮超时，阻止正常 Post，并按既定阻塞策略影响后续触发。已成功 Task 不改为失败，不将缺少回报当作业务明确失败。

这一规则保证未结束尝试有整轮终止边界，不保证每轮自动恢复成功；平台超时不证明业务代码已经退出，数据库不可用时也不能保证准时提交终态。已持久化的有效结果仍可恢复平台推进；没有绑定的尝试仍按独立观察与条件结算处理。具体截止比较、父子条件写入及迟到结果竞争在实现协议中闭合，不改变上述已通过选择。

普通回报只条件更新自己的 Task，不逐条锁定 Instance，也不为每条回报更新 Instance 完成计数。回报用于保存执行结果，不另存一份重复业务日志。详细日志位置见[管理与运维](./operations.md)。

Instance 终止和各 Task 的取消、结果落库不承诺一次原子变更。各 Task 按自身终态条件收敛，任何有效子结果都不得恢复父终态、授予新执行尝试或启动正常收尾；短暂重试候选不等于获准执行，已取消 Task 不能被迟到成功覆盖。具体条件写入、回报应答与恢复实现仍须落实[已确认的收敛语义](behavior.md#task-convergence)。

结果回报与 `Notify` 不是同一个方向：前者由执行器向调度服务提交，后者是平台向业务处理器发送的整体进度回调。第一版保留结果回报，不提供业务内部实时进度和 Notify，见[目标与范围](./scope.md)。

## 5.8 分片完成检查与本地合并 {#completion-check}

正常路径为：**结果提交 → 本节点按 Instance 合并检查 → 查询未结束分片 → 候选收尾原子推进**。不增加 Redis 完成计数器、MQ 或整轮固定负责人。

### 事件来源与合并边界

- 分片进入最终状态的有效回报先提交，再发出本地待检查提示；不能在提交前判断整轮完成。
- 失败后还有重试的分片保持未终态，不能把重试等待当作分片已完成；准备与收尾结果按各自阶段推进，不一律执行分片汇总查询。
- 分片生成完整的持久化事实提交后也通知检查，不能仅依赖结果回报；合法空数组同样走该路径。生成完成后集合固定，最终分片状态不得被普通迟到回报逆转；生成封口字段及原子协议仍待设计。
- 每个节点维护按 Instance ID 去重、有容量上限的待检查集合，由固定数量工作协程处理。同一节点、同一 Instance 同时最多运行一个检查。
- `100ms` 是短合并窗口的初始测试值，不做页面配置，也不是已经锁定的运行常量；新事件不能不断推迟检查，造成始终无法执行。
- 检查期间若又有结果提交，必须标记重查并在本轮检查后重新安排。标记清理和新事件登记须协调，不能因“已有检查在运行”直接丢弃后续事件；具体内存结构待设计。

合并只在接收节点内部生效。同一 Instance 回报分散到多个节点时仍可能分别检查，大量不同 Instance 的稀疏回报也不容易合并。不能宣称全局只查一次；验证需要同时观察完成延迟、查询次数和数据库负载。

### 查询最小必要事实

普通检查依次判断：

1. Instance 仍允许推进，且没有停止或超时。
2. 分片已经完整生成。
3. 是否还存在未结束分片。

第三项使用适配索引的 `EXISTS`，只判断业务分片 Task 的待执行、执行中、等待重试三类未终态，不逐条回报读取全部 Task 列表，也不每次统计整个批次的成功／失败数量。具体状态编码、索引与查询条件需在数据设计中明确并验证执行计划；使用 `EXISTS` 本身不保证必然避免大量扫描。

真正推进时才读取必要汇总信息，业务收尾所需结果集合也在对应阶段获取，不在每条回报时反复加载。本地集合只是加速提示，不是完成数量或状态的权威来源。

### 通知丢失与容量耗尽

集合满、数据库暂时异常、节点退出或提交后未通知，都不能丢失已提交结果。复用共同的有索引、有界恢复检查，公平轮转活跃 Instance 和待派发 Task，补上“结果已齐但未推进”和“Post 已保存但未派发”。不新增独立的全表汇总轮询，也不永远只检查最老一批。容量、协程数、轮转与退避参数在实现及压测中确认。

## 5.9 原子创建收尾与并发终止 {#post-creation}

多个节点可以重复判断“可能已完成”，但只有通过持久化协议才能创建已配置的业务收尾。该机制已经确认，不使用额外 Redis 分布式锁或专门的数据库锁表；未配置 Post 时直接进行平台终态推进，不为套用本流程创建空 Post。

候选推进者按以下顺序处理：

1. 开启 PostgreSQL 默认 `READ COMMITTED` 事务，以 Instance **主键等值条件**执行 `SELECT … FOR UPDATE`，只锁单表的一条记录。
2. 锁内重新检查本轮仍允许推进、没有停止或超时；已存在 PostTask 则结束创建尝试，不能把事务外检查当作写入许可。
3. 复核分片生成完整，且不存在未结束或待重试分片。该判断依赖已固定的分片集合和不回退的最终状态；Instance 行锁不会自动锁住所有 Task。
4. 按 Instance 保存的收尾选项及本轮执行配置创建 PostTask，提交事务并释放行锁；不改读编辑后的 Job。PostTask 记录本身表示收尾工作已创建，不为这把锁额外增加一个独立阶段字段。
5. 本次成功创建者提交后执行正常路径的本地有界派发；已有但未派发的 PostTask 由共同恢复协议接续，不绑定创建节点。

数据库同时保证**同一 Instance 最多一条 PostTask**，兜底防止其他入口或遗漏检查造成重复创建。约束不能扩展成“每类 Task 每轮只有一条”从而禁止多个分片；具体类型字段与唯一约束 DDL 留到数据设计。Post 重试仍复用原记录。

同一 Instance 的两个候选者依次取得锁，后取得者看到已有 PostTask 后退出；不同 Instance 锁不同记录，可并行推进。锁只保护少量数据库校验与插入，不读取和组装整批业务结果，不包含 RPC、Redis 等外部 I/O，也不持有到执行器完成。这是短事务并发保护，不是整轮归属。

停止、超时和收尾创建通过同一 Instance 状态协议协调：

| 竞争顺序 | 必须保持的结果 |
| --- | --- |
| 停止或超时先提交 | 收尾事务复核后不再创建 PostTask |
| PostTask 先提交，随后停止或超时 | 阻止后续正常派发和重试，对在途及运行中执行尽力取消 |
| 终止后收到成功回报 | 不得把 Instance 改回成功，也不得恢复后续派发 |

提交与实际 RPC 之间仍有竞争窗口，行锁不保证停止后绝无 RPC 或业务副作用；沿用[尽力取消、不等待实际退出](./behavior.md#stop-semantics)的规则。PostTask 记录唯一也不等于 Post 业务恰好执行一次。

## 5.10 Instance 汇总归属 {#instance-finalization}

平台完成检查、结果统计和 Instance 状态更新由**调度服务内部推进逻辑**负责，不放进业务 Post 处理器，也不另建“平台汇总 Task”。PostTask 只承载业务收尾，其执行结果与分片结果一起成为平台终态判断的输入。

Post 最终结果持久化后，平台依据分片和收尾最终结果更新 Instance；仍可重试的 Post 失败不是最终结果，不能提前完成正常终态汇总。没有 Post 时，分片完整生成且全部最终结束后直接由平台汇总。所有终态入口使用[同一父行协调协议](#authorization-terminal)，遵守[已有终态不覆盖、锁内决策时到期按超时、未到期有效终态竞争](behavior.md#terminal-order)的顺序，也不抹除分片最终失败。

Post 成功已持久化、Instance 更新失败时，只恢复平台推进，不重新调用 Post；恢复时若父行保护决策点看到 Instance 尚未终止且已到截止时间，仍按超时失败结束。正常推进不要求由原派发或原接收节点完成；普通任务由平台根据唯一普通 Task 的有效结果结束本轮。各路径共用已定父行协调，具体条件更新、汇总查询和首次计时衔接在[数据与接口](./data-contracts.md)设计中落实。

## 5.11 待处理检查与恢复边界 {#recovery}

有界检查不仅在节点宕机后运行，也承接正常积压、队列满和到期工作。覆盖待派发、到期重试、绑定缺失观察、整轮超时、结果齐备但漏推进，以及父终态下未终态子 Task 的取消收敛；不能只检查活跃父实例。已绑定无结果的失联执行依整轮超时处理，不增加独立失联重派扫描或专用取消轮询。查询需有索引、批次上限、退避与公平轮转，不扫描整个历史表。

派发与推进队列、回调及计时用于加速处理，已持久化的待处理事实不能随它们丢失。结果回报队列则容许持有未落库的唯一易失副本，丢失后需要结算原执行尝试，不能宣称从数据库恢复原结果。不为派发或回报增加 MQ、本地文件，也不依赖跨节点额外唤醒保证恢复；这不影响管理配置变更后的主动通知。

| 故障交界 | 已确定的不变量 | 尚需完成的协议 |
| --- | --- | --- |
| Task 已保存，尝试尚未登记 | 持久化工作可被重新发现；有容量后复用批量条件登记，不依赖原节点存活 | 条件写入的具体字段与 SQL、恢复检查覆盖范围 |
| 尝试登记已提交，尚未发 RPC 或发送情况不明 | 已占一次机会，不免费重发同一尝试；无绑定及结果时按有限观察与条件结算处理，零重试可能未执行业务就失败 | 观察期秒数及已定条件写入的具体实现 |
| 登记提交返回超时或断连，结果不明 | 撤销本地发送计划、释放槽位；事后看到已登记也不补发，交既有观察与结算；真未提交且仍合格则普通条件登记 | 错误分类、撤销本地发送与恢复路径的实现验证 |
| BUSY 返还写库失败或提交结果不明 | 有界有限重试同一条件事务；不重复返还，响应释放或失效后不猜测补返 | 内部重试参数、原子条件 SQL 与清理实现 |
| 执行器已接收，RPC 确认丢失或绑定尚未提交 | 从登记的数据库时间有限观察；到期仅获结算资格，绑定／结果／未知结算持久化竞争；不重置、不重复扣预算、不恢复旧尝试 | 观察期秒数与时间比较、已定父行协调的具体 SQL 及恢复实现 |
| 已绑定执行器失联或重启，无有效结果 | 不提前重派；等待有效结果、手动停止或整轮截止，终态不得复活 | 截止比较、父子条件写入及迟到结果处理 |
| 回报 ACK 丢失，执行器仍保留结果 | 独立有限重试，不占执行重试预算；耗尽后释放并记录错误及丢弃指标，重复入队不能重复推进 | 内部常量的具体值、批次确认粒度、错误分类及入队等待边界 |
| 回报已 ACK，数据库持续发生可恢复故障 | 保留已有结果并退避重试，不按次数或保留 TTL 丢弃；总待处理条数有界，满后拒收，不做队列总字节配额 | 容量参数、RPC 报文上限、错误分类与批次隔离、恢复时的条件写入 |
| 回报已 ACK，但接收节点在落库前退出 | 允许原结果丢失；已有绑定则等待整轮终止，无绑定则适用独立观察规则，均不依赖本地文件 | 对应路径的条件写入、迟到结果及终止竞争 |
| 有效 Pre 结果已提交，生成未完成 | 只恢复平台生成，不重跑 Pre，不另造分片集合 | 生成执行权、分批持久化、完整封口和部分生成恢复 |
| 最后一个分片已提交，检查提示丢失 | 共同检查恢复推进，不依赖内存计数 | 活跃查询索引、公平轮转和退避 |
| Post 已创建，派发尚未完成 | 每轮唯一 Post，恢复复用同一 Task | 通用派发／尝试恢复协议 |
| Post 成功已提交，Instance 未结束 | 只恢复平台终态推进，不重跑 Post；父行保护决策点仍未终止且到期时按超时失败 | 已确认优先顺序与时间比较的具体 SQL 及恢复实现 |
| Instance 终态已提交，子 Task 仍待执行、执行中或等待重试 | 不再授予新尝试；已有子终态保留，未终态按自身条件取消，在父事务外尽力发送取消 RPC | 复用共同恢复的索引、公平批次及定向取消契约，覆盖并发写入的重试候选 |

### 数据库提交结果不明的恢复 {#commit-unknown}

数据库可能已经提交成功，但调度端因确认丢失而收到超时或断连。**提交报错不等于事务回滚，普通查询没有看到改动也不证明原事务已经结束。** 本规则复用当前尝试、允许的旧状态、既有缓冲和恢复检查，不增加新状态、历史表、发送凭证或补偿队列。

| 不确定的写入 | 已确认恢复规则 | 接受的代价 |
| --- | --- | --- |
| 新尝试登记 | 不发 RPC，撤掉本次本地发送计划并释放派发槽位；即使事后看到该尝试已登记也不补发。已提交的按既有观察、结算与预算恢复；实际未提交且仍可执行的 Task 由普通流程重新竞争登记 | 业务可能没运行，却占用一次执行机会；零重试可能最终失败 |
| BUSY 关闭与返还 | 持有原响应时，在有界有限处理重试内，重做原 Task、原尝试且尚未结算状态下的原子关闭、一次返还及延期；已经生效或失效则不再修改 | 原响应释放或随进程丢失后不能猜测补返；未知结算或取消先提交时，迟到 BUSY 也不能返还，可能消耗实际未执行的机会 |
| 执行结果保存 | 保留原结果，按已有有界结果保留规则退避重做同一次条件写入；未生效且仍有效则保存，已生效则不重复修改，已失效则不覆盖当前状态 | 可恢复数据库故障期间占用固定待处理容量，满后拒收；进程退出仍可能丢失未落库结果 |

登记进入不明分支后，不因迟到确认或读回状态恢复原发送计划，也不另外退款。没有登记的候选仍须重新经过本地容量、父状态与截止、Task 状态和预算条件；不能凭一次查询“没看到”就直接发送。释放本地槽位不等于原数据库事务或锁已释放，未决事务仍可能使后续条件写入等待或超时，沿用数据库操作超时与退避处理。

BUSY 只检查尝试 ID 不够，还必须检查**尚未结算的旧状态**；否则在下一次尝试尚未创建时，同一消息仍可能重复返还。关闭、返还与延期在同一事务中原子完成，不能单独重试减计数。BUSY 的有限记账重试不是重新派发业务，不占执行重试额度，也不建立常驻等待对象；具体内部参数在派发模块明确。

结果保存继续采用[已确认的有界保留](#scheduler-result-retention)，可恢复错误不按次数或 TTL 丢弃，不能混用 BUSY 的有限处理策略。结果重做后即使没有再次修改记录，也可以重新发出本地 Instance 检查提示；提示只促使按数据库当前事实检查，不拿原消息直接再生成分片、Post 或结束本轮。重复提示通过既有合并、条件推进与恢复处理，不重复产生业务工作。

正常成功路径不额外增加一次写后查询。异常路径需要核对时，以 PostgreSQL 主库为准，按有界批次读取，不用缓存或延迟副本作恢复裁决；读回只是判断依据，不能替代后续条件写入。批量重做仍逐条校验原尝试与旧状态，不把提交报错当成整批条目都未生效。具体 SQL、错误分类和批次契约在对应模块落实。

本节 Instance／Task 恢复的具体检查间隔、批量大小、索引、容量和公平性实现依赖状态机与压测，不凭空设定吞吐承诺；不将 Leader 已定的每分钟 Job 触发恢复周期直接套用于这些检查。重点验证提交交界故障、单轮大任务、密集回报、跨节点分散回报、稀疏小 Instance 及重试洪峰，见[验证与交付](./verification.md)。

依赖故障时哪些能力暂停、继续或拒绝请求，见[管理与运维](operations.md#dependency-boundaries)。数据库前置步骤未提交不能凭内存越过授权派发；失去 Leader 资格不自动停止其他满足执行权条件的推进。回报成功入队可确认接收，数据库故障时有界保留并背压；两侧内存结果均不保证跨进程退出保存。依赖恢复后的处理仍服从预算与终止规则，具体重连、重传和未知结果结算协议继续设计。

## 5.12 本章待决事项与完成条件 {#chapter-exit}

本章已确认的本地直接派发、父行授权与终态协调、绑定、回报、结果保留、提交结果不明恢复及完成推进规则继续有效。B2 [闭环总审](progress.md#b2-review)和[触发模块开工总审](trigger-readiness-review.md)均已通过，当前按用户要求暂不编码，等待明确开始实现指示。以下为全章剩余事项，在对应模块实现前闭合，不全部作为触发模块的开工前置条件：

- 已定 etcd 官方选主、15 秒租约初值、键空间、通知反馈、I/O 预算及重连的具体接入，实现任期资源管理、首次批量装载与整批初始化确认。落实触发容量初值、并发控制、每分钟从头限量读取的单批恢复，统一 Cron 计算及已定单 Job 错误隔离的实现。触发事务、锁后分语句查询、两个部分唯一索引、身份结构 CHECK、历史冲突处理及本批五条触发索引已确认，连同按组管理索引、仅停用可编辑及启用重算的管理 SQL，均已汇入已通过的 [SQL 对照稿](trigger-sql-review.md)，迁移与数据库验证待实现。不重选已确认的串行差异同步、注册后检查、六字段与服务器时区、时钟运维边界、每分钟兜底、合法在途提交及进度原子提交规则。
- 已确认的 Instance 字段及 JSONB v1 的批量读取、RPC 传递和未来结构兼容实现，不重选字段分工、创建时固定和整轮沿用规则。
- PreTask 创建、分片生成权、分批保存和生成完整性封口。
- 已确认尝试登记、父行协调、预算记账及绑定缺失结算的字段与条件写入实现、观察期秒数，以及已绑定无结果等待整轮终止的条件写入。
- 两端容量保护、已定 BUSY 条件返还与延期的事务实现及退避参数、取消的定向路由与上下文契约。
- 已绑定无结果等待整轮终止的超时检查、父子收敛及迟到结果验证；不重新引入独立活动探测或失联提前重派。
- 回报重传的错误分类、批次确认粒度、批次错误隔离与退出处理；本地检查期间事件合并、待处理查询索引、公平轮转及退避。
