# 4 调度与执行规则

本章规定系统在触发、重叠执行、失败、超时和停止时应呈现的行为，作为状态机、接口和测试的共同依据。对象定义见[第 3 章：任务模型](./task-model.md)，实现这些行为的协作协议见[第 5 章：执行流程与可靠性](./execution.md)。

**设计成熟度：本章行为规则、状态与生命周期语义及终态竞争顺序已经确认；持久化原子协议、通信故障处理及部分接入契约尚未闭合。** 规则确认不等于实现完成，也不表示所列待决事项已有默认答案。

## 4.1 规则总览 {#rule-overview}

| 关注点 | 已确认规则 | 详细定义 |
| --- | --- | --- |
| 正常触发 | 有效 Leader 维护长期 Job 规则，由 robfig 到点回调；正常触发不依赖到期 Job 轮询 | [触发与配置同步](#trigger-sync) |
| 触发容量 | 自动入口按 Job 合并、有界排队，固定协程处理；满时拒绝提示，不因此推进进度，沿用恢复与错失规则；手动创建共享本进程并发额度 | [触发容量与过载](execution.md#trigger-capacity) |
| Cron 与时区 | 固定六字段，采用 robfig 语义；统一使用调度服务器／容器的进程默认时区，不配置 Job 独立时区 | [Cron 格式与时区](#cron-contract) |
| 触发时间来源 | 到期、5 秒错失判定及下一次时间计算使用调度进程时间，不另取数据库当前时间；锁后取值，不沿用回调时刻 | [Job 触发时间来源](#trigger-clock) |
| 首轮计划 | 首次启用与第一轮计划时间同事务保存，提交后再通知注册；不等待首次回调初始化 | [首轮计划初始化](#first-trigger-initialization) |
| 触发恢复 | Leader 接任时立即检查，任期内每 1 分钟按持久化触发进度查漏；不增加本地 Job 退避补试机制 | [低频触发恢复](#trigger-recovery) |
| 配置编辑与启用 | 已有 Job 仅停用时可编辑；编辑不重设持久化触发进度，启用时统一计算下一次、不补旧轮次 | [编辑与重新启用](#job-edit-enable) |
| Job 删除 | 仅停用且无待开始／运行中 Instance 时逻辑删除；保留定义及执行历史，不提供恢复站，不级联删除 | [Job 逻辑删除](#job-deletion) |
| 执行器组删除 | 第一版无组启停，仅逻辑删除；未删除 Job、旧组未结束 Instance 和未收敛 Task 阻止删除，不级联停止或删除历史 | [组生命周期与依赖](data-contracts.md#executor-group-lifecycle) |
| 本轮执行配置 | Instance 创建时保存必要执行配置，本轮各阶段、重试和恢复沿用；Job 编辑只影响新建 Instance | [Instance 执行配置](#instance-execution-config) |
| 配置同步 | etcd 通知加每分钟核对；任期内串行读取、差异更新，不重建未变规则；新注册后检查到期，不重置触发进度 | [触发与配置同步](#trigger-sync)、[加载流程](execution.md#job-config-reload) |
| 切主与旧回调 | 每次任期使用独立上下文，失主取消本地触发工作；残留事务按最新 Job 校验，接受合法提交，不做全局任期硬拦截 | [切主与配置变更边界](execution.md#leader-config-boundary) |
| 触发身份与进度 | 自动触发按 Job 与原计划时间识别；每次到期处理最多创建一轮，统一推进到判定时间之后，包括 5 秒内的多轮积压 | [触发身份与到期处理](#trigger-identity) |
| 手动触发 | 未删除 Job 无论启用或停用均可手动执行，沿用集群阻塞规则，不改定时进度；仅允许当次业务参数覆盖，同请求号防重复创建 | [手动触发规则](#manual-trigger) |
| 错失触发 | 忽略为默认选项，也可选择立即执行一次；相对旧进度的迟到容忍固定 5 秒 | [错失策略](#misfire) |
| 同 Job 重叠 | 丢弃为默认选项，也可选择并行；判断集群中的整个 Instance | [阻塞策略](#blocking) |
| 失败重试 | Job 统一配置，各 Task 独立使用执行预算；通信与业务执行失败共用预算 | [自动重试](#retry) |
| 分片最终失败 | 其他分片继续；全部分片结束后仍执行已配置的收尾；整轮不判为部分成功 | [阶段结局](#stage-outcomes) |
| 执行超时 | 整个 Instance 共用有限正数时间预算，不允许 `0` 或无限时长；新增表单预填 900 秒，API 必填，不提供 Task 单次超时配置 | [整轮超时](#instance-timeout) |
| 停止与取消 | 尽力取消，不以业务实际退出作为平台终态前提；不得用迟到结果恢复执行 | [停止语义](#stop-semantics) |

## 4.2 触发与配置同步 {#trigger-sync}

有效 Leader 将未删除且启用的 Job 长期规则注册到 `github.com/robfig/cron/v3`，由其计算、等待并触发下一次执行。注册对象是 Job 规则，不是每个分片 Task。正常路径不提前数秒查询到期 Job，也不自行实现时间轮、堆或 Timer 调度器。

robfig v3.0.1 内部采用规则排序和每轮等待的 `time.Timer`，并非时间轮。几百条规则是当前容量预期，触发密集时的承载能力仍需按[验证计划](./verification.md)确认，不将库的工作方式等同于本系统已经通过容量验证。

到点回调只提交 Job ID，不等待数据库或业务完成。Cron、注册后检查和分钟恢复共用按 Job 合并的有界待处理队列，由固定工作协程执行触发短事务；容量包含排队及处理中 Job，队满拒绝新提示并记录指标和限频日志，不因此推进数据库进度。后续按持久化事实补查，仍服从 5 秒错失规则，不保证每轮都执行；手动创建不入该队列，但共享本进程创建并发额度。完整规则见[触发容量与过载](execution.md#trigger-capacity)。

数据库是 Job 配置的权威来源，内存规则按下列方式同步：

1. Leader 启动或接任时加载启用规则。
2. 管理变更事务提交后，通过 etcd 变更通知推动 Leader 核对数据库最新状态：Leader 使用 Watch 接收变更提示，再读取 PostgreSQL；启用则注册当前规则，停用或删除则移除。Job 只能停用后编辑；重新启用时应用当前配置，不支持启用中的直接编辑。
3. 每 1 分钟兜底核对一次，弥补通知丢失。

**采用 etcd 通知加每 1 分钟核对，不采用每 10 秒仅轮询配置的方案。** etcd 只传递变更提示，不成为 Job 配置或触发进度的权威来源；通知不直接授权创建 Instance，也不重置 `Job.next_trigger_at`。

PostgreSQL 提交与 etcd 通知不是同一个事务：提交后进程退出、通知写入失败或 Watch 中断，都可能使配置没有及时应用。通知发出不等于 Leader 已应用，1 分钟也不是生效时限保证；依赖故障或处理积压仍可能延迟。错过计划时间后继续按固定 5 秒及既定错失策略判断，不能因使用通知就承诺首轮绝不遗漏。

管理变更与触发在同一 Job 行上协调；停用先提交，后续自动触发检查就不能创建 Instance；触发先提交，随后停用不取消已创建的 Instance。旧回调只提示检查 Job，不能凭旧配置创建，完整规则见[切主与配置变更边界](execution.md#leader-config-boundary)。

配置加载与重载采用单个集群变更标记、任期内串行工作协程和一个合并信号；一次读取主库轻量配置，仅注册、替换或移除变化的规则。查询失败保留旧规则，单条坏 Cron 隔离处理；Watch 按 revision 衔接，重建后主动核对。新注册或替换成功后，通过统一入口检查一次是否已经到期，避免只依赖下一次 Cron 回调；它不是立即执行命令，不重置首轮时间，也不改变 5 秒错失规则。完整流程与故障边界见[配置加载与重载](execution.md#job-config-reload)。

正常触发依靠 Cron 保证及时性，遗漏触发通过下述低频数据库检查发现；不是运行期间完全不扫描 Job。正常回调、恢复与注册后检查共用[同 Job 短事务入口](execution.md#trigger-accounting)。发现失主后取消该任期的本地工作，但不承诺旧在途事务全部回滚；残留事务仍须按最新 Job 合法记账。

### Cron 格式与时区 {#cron-contract}

**第一版固定使用六字段 Cron：秒、分、时、日、月、周。解析和下一次时间计算复用 `robfig/cron/v3`，不自行兼容 Quartz。**

| 输入约定 | 已确认规则 |
| --- | --- |
| 字段数量 | 只接受六字段，不接收五字段或额外年份字段 |
| 基础语法 | 使用 robfig 的数字、列表、范围、步长、英文月份和星期名称；`?` 沿用库的通配含义 |
| 星期数字 | `0 = SUN`，`6 = SAT`，不接受 `7`；页面样例优先使用 `MON` 等名称 |
| 日期与星期 | 两者都具体限制时沿用库的“或”语义，不自行改成“且” |
| 不支持的输入 | Quartz 的 `L/W/#`，`@daily`、`@every` 等描述符，以及表达式内的 `TZ=`、`CRON_TZ=` |

`0 */5 * * * *` 表示每五分钟；`0 0 0 * * *` 表示每天零点；`0 0 9 * * MON-FRI` 表示周一至周五九点。`0 0 9 1 * MON` 表示每月一号或每周一九点，不是每月第一个周一。六字段相同不等于兼容 Quartz，尤其不能照搬其星期数字或特殊字符语义。

**时区使用调度服务所在服务器／容器的进程默认时区，不在 Job 增加 `timezone` 字段，也不提供页面时区选择。** 所有调度节点的部署时区必须一致；不是按执行器、浏览器或数据库连接的显示时区解释 Cron。不将 `Asia/Shanghai` 写死为产品默认值，部署采用哪个时区就按哪个时区计算。

校验、执行时间预览、首次启用、`Job.next_trigger_at` 计算及 Leader 注册使用同一套解析规则与调度进程时区，当前时间取自执行计算的调度后端进程，见下节。数据库读回的持久化时间点可能携带 UTC 或其他显示时区，不能因此让直接调用 `Next` 与 Cron 回调采用不同的时区解释。不能仅给运行器设置时区而忽略其他计算入口。

保存及启用时不仅校验语法，还要确认库能够求出下一次时间；在库的搜索范围内找不到时明确报错，不能把零值当有效进度。停用状态保存时的试算仅用于有效性校验，**不写入或重置 `Job.next_trigger_at`**；首次启用及重新启用仍按各自受保护决策点计算并持久化。运行时解析失败或 `Next` 为零，按[简化异常处理](#cron-errors)结束该 Job 本次自动触发，不将零值写成成功推进结果。

采用有夏令时的部署时区时，沿用库和时区规则，不另造补偿算法；当地不存在的时间可能不触发，不能承诺当地每天严格执行一次。部署负责系统校时，异常时钟沿用既有触发判断，时区变更走维护流程，见[时钟与时区运维边界](operations.md#scheduler-timezone)。语法及竞品差异依据见[参考资料](references.md#cron-contract-evidence)。

### Job 触发时间来源 {#trigger-clock}

**Job 触发使用调度服务器的系统时间，与 robfig 的时间来源保持一致；不另取 PostgreSQL 服务器的当前时间判断是否到点。** 数据库保存的 `Job.next_trigger_at` 仍是下一轮触发进度的权威事实，统一时钟来源不改变行锁、唯一身份或事务记账规则。

正常回调、注册后检查与低频恢复进入同 Job 短事务后，取得 Job 行锁，再读取一次调度进程的 `time.Now()`，作为本次到期判断、5 秒错失判断及 `Next` 计算的共同基点。不沿用回调、入队、扫描或事务开始时的旧时间，也不在同一次决策中反复取时。恢复查询的候选截止时间同样由 Leader 进程提供；候选只是提示，最终判定仍在取得行锁后重新取时。

校验、预览、首次启用与重新启用也使用执行该计算的调度后端进程时间，并按统一部署时区解释 Cron；启用在各自受保护决策点取时，预览不授权触发。所有承担这些计算的服务器需要系统校时。相同时间来源消除了同一触发路径中调度机与数据库机的时钟混用，但不保证多台服务器绝对同步；异常时钟和部署时区变更遵守[运维边界](operations.md#scheduler-timezone)，不增加应用层校时或自动迁移机制。

本规则只修改 Job 触发时间来源。Instance／Task 的执行截止判断、尝试登记及绑定观察期继续沿用既定数据库时间，不将整个系统的时间来源一并替换。

### Cron 异常处理 {#cron-errors}

**保存和启用校验是主要防线；运行时只隔离异常 Job，不自动停用，不新增异常状态或专门修复机制。** 语法能解析但在库的搜索范围内找不到下一次时间，同样属于校验失败。绕过管理入口修改数据库等异常不作为正常调度路径设计。

| 发现位置 | 处理规则 |
| --- | --- |
| 保存或启用 | 解析失败或求不出下一次时间时拒绝操作，不保存无效规则或零值触发时间 |
| 自动触发短事务 | 该 Job 本次处理失败，不创建 Instance、不推进 `next_trigger_at`；不创建一条失败 Instance 代替报错，也不清空原进度 |
| 配置加载 | 非法 Cron 不注册，并移除该 Job 残留的旧内存规则；保留数据库启停状态，继续处理其他有效 Job |

触发处理或配置加载发现异常时，记录包含 Job ID 与原因的限频错误日志；错误处理按 Job 隔离，不因一条坏规则中断其他 Job。已有 Instance 不被取消，手动执行仍按原管理与阻塞规则处理，不依赖 Cron 求下一次时间。

不为这类异常增加字段、扫描、重试队列或内存规则自动修复。既有核对与恢复可能再次校验该 Job，但不额外检查 robfig 内存条目的零值 `Next` 并自动重建，也不改变“配置未变则保留原规则”的差异加载原则。

接受 Job 仍显示启用、但异常期间自动触发无法继续的情况。管理员根据日志修正原因，必要时在修正后重启相关调度进程恢复内存规则；不承诺自动自愈，也不把简单停用再启用视为必然重建内存规则的保证。错误处理或仅恢复内存规则不重置持久化进度；管理员停用、编辑、重新启用仍遵守既有[启用重算规则](#job-edit-enable)。自动入口按当前进度及原错失策略处理，不承诺补齐遗漏。竞品取舍与 robfig 行为见[异常处理依据](references.md#cron-error-evidence)，验收见[Cron 异常场景](verification.md#cron-error-checks)。

### 首轮计划初始化 {#first-trigger-initialization}

**Job 首次启用成功时，第一轮计划时间必须已经持久化，不能等第一次 Cron 回调才初始化。** `next_trigger_at` 表示下一次尚未完成触发记账的计划时间，不是本轮业务完成时间。

- 新建时直接启用：创建 Job 的同一事务内，按规则计算并保存第一轮 `next_trigger_at`。
- 新建时停用：首次启用的同一事务内，保存启用状态和第一轮 `next_trigger_at`；不能出现已启用但尚无首轮有效计划的已提交状态。
- 事务提交后，才通知 Leader 注册 robfig 规则；不在数据库事务中等待通知或内存注册。

启用提交后、通知或注册完成前宕机，数据库仍保存第一轮计划；注册延迟不能成为按恢复时刻重新初始化、跳过原计划的理由。初始化事务明确回滚时，启用状态和首轮计划均不生效；提交确认丢失不等于回滚，不能仅凭报错重新初始化。

例如 09:58 首次启用时已保存 `next_trigger_at = 10:00`。10:00 创建 Instance 和推进进度的事务失败且未提交，首轮计划仍保留为 10:00，后续可以按持久化进度发现遗漏。发现时若已超过 5 秒容忍，仍按[错失策略](#misfire)忽略或补执行一次，不承诺所有遗漏都会补跑。

本项确认首次启用的初始化时点与原子性；后续记账、低频恢复及切主边界见对应协议，自动触发身份见[触发身份](#trigger-identity)，内存同步见[配置加载与重载](execution.md#job-config-reload)。时间存储采用已定 `TIMESTAMPTZ` 字段契约，具体 SQL 仍须落实。修改 Cron 或停用后再次启用遵守下节规则；新建默认停用，允许显式启用，未曾启用的进度为 NULL。

### 编辑与重新启用 {#job-edit-enable}

**第一版只允许编辑未删除且停用状态的 Job。编辑保存不重设持久化触发进度，从停用切换为启用时，按当前配置统一计算 `Job.next_trigger_at`，不补旧轮次。** 名称、描述等普通配置也遵守同一限制，不再区分启用中哪些字段可以编辑。保存时可为校验 Cron 有效性试算下一次，但不以试算结果初始化或推进进度；已删除 Job 不能编辑或重新启用。

| 操作 | 已确认规则 |
| --- | --- |
| 编辑已有 Job | 仅停用状态允许；后端保存时校验真实状态，不能只限制页面按钮 |
| 停用状态保存配置 | 校验并保存当前规则及其他配置，不更新 `next_trigger_at`；试算只用于有效性校验 |
| 从停用切换为启用 | 按当前规则计算启用时刻之后的下一次触发时间，与启用状态原子保存；不表示立即执行一次 |
| 对已启用 Job 重复启用 | 不重置 `next_trigger_at`，避免重复请求不断推后触发时间 |
| 服务重启、Leader 切换或配置重载 | 沿用持久化触发进度，不按加载时刻重新初始化；遗漏仍按错失策略处理 |

启用在同 Job 的短事务协调内，依据当前配置与受保护决策点读取的调度后端进程时间计算下一次，提交后再通知内存规则同步。编辑使用未删除且停用的条件更新，只写完整可编辑配置，不带回启停或进度；启用按 Job 主键单行短事务重读并计算，停用只更新状态并保留进度。第一版不设编辑版本号，允许停用 Job 的并发完整编辑按提交顺序覆盖；条件更新不承诺防止编辑互相覆盖。请求、零值及事务边界见[管理契约](data-contracts.md#job-management-proposal)，最终 SQL 仍须实现验证。

例如每小时整点执行的 Job，09:50 停用、12:20 重新启用，下一次为 13:00，不补 10、11、12 点。重新启用放弃的是全部尚未创建 Instance 的旧轮次，包括停用前因故障积欠的触发；即使错失策略选择立即执行一次，也不借启用补旧账。Job 始终启用、仅服务故障后恢复则不同：保留原 `next_trigger_at`，仍按错失策略处理。

停用不取消已有 Instance，也不要求等全部 Instance 结束才能编辑。已有 Instance 继续参与同 Job 阻塞判断，执行配置沿用创建时保存的本轮配置，不跟随 Job 后续编辑。停用时保留 `next_trigger_at`；停用期间不以旧值授权自动触发，也不在页面将它显示为仍将执行的计划，重新启用时统一重算。

管理入口还须遵守[组引用与离线配置校验](data-contracts.md#job-group-reference-proposal)：新增、编辑保存、启用校验目标组存在且允许引用，不要求组内执行器在线，也不远程探测处理器。停用和删除不受组故障阻碍，已有轮次继续使用本轮快照。

### Job 逻辑删除 {#job-deletion}

**Job 沿用项目的 `deleted_at TIMESTAMPTZ` 逻辑删除约定：未删除为 NULL，删除后保存删除时间。仅未删除、已停用且没有待开始或运行中 Instance 的 Job 可以删除。** 检查与标记删除在同一个 Job 主键单行短事务中完成，与启停、手动及自动创建协调；取得 Job 锁后另发 `EXISTS` 查询，不能依赖锁等待前的活跃状态快照。具体顺序见[删除事务](execution.md#job-deletion-transaction)。

普通列表与详情、配置装载、恢复候选、编辑启停和手动／自动创建都排除已删除 Job。创建入口锁后先检查删除状态，再处理请求查重或新建；已有内存规则、已入队提示及旧扫描结果不能绕过这一检查。删除提交后沿用 etcd 配置提示和分钟核对，不在事务中等待通知。

Job／Instance／Task 三者中仅 Job 采用逻辑删除，不给 Instance／Task 增加软删除字段，不级联、不清理执行记录，也不通过删除自动停止执行；执行器组另按[组生命周期](data-contracts.md#executor-group-lifecycle)维护删除标记。第一版不提供恢复站或恢复已删除 Job 的入口。删除时已终态的 Instance 可能仍有尚未收敛的子 Task；这些历史和恢复依据继续保留，取消收敛、结果处理不依赖一个有效的 Job，父终态不证明业务进程已经退出。

执行历史按 Instance 自身快照查询，不要求关联未删除 Job 才可见。必要时可显式只读关联已删除 Job，但保留的是删除时的最后定义，不是每轮执行时的完整 Job 历史，不能用它覆盖 Instance 的执行快照。Job 删除后，旧手动创建请求返回 Job 不存在；原 Instance 仍可按 ID 查询，不承诺跨 Job 删除重放原创建请求。

### Instance 执行配置 {#instance-execution-config}

**Instance 创建时，保存一份本轮必要的执行配置。之后编辑 Job，只影响新建的 Instance。** 固定时点是创建，不是首次派发；已创建但尚未开始的轮次也适用。

| 配置 | 本轮使用规则 |
| --- | --- |
| 执行目标 | 保存稳定的执行器组标识与处理器标识；不保存当时的节点地址列表 |
| 执行模式与收尾选项 | 固定普通／分片模式及 Post 选项，后续生成分片或收尾不能改读当前 Job |
| 业务参数 | 默认保存创建时的 Job 业务参数；手动指定当次参数时保存覆盖后的实际参数，不改 Job；分片工作项仍由本轮准备结果产生 |
| 执行重试 | 保存重试次数和间隔；普通、准备、分片及收尾 Task 共用配置、各自计数 |
| 整轮超时 | 保存有限正数时长；仍从首次有效开始计时，不从 Instance 创建时计时 |

本轮后续的 Task 创建、派发、重试及跨节点恢复都使用这份配置，不混用编辑后的 Job。例如 I1 创建时参数为 A、重试 3 次、超时 15 分钟；Job 停用后改为 B、1 次、30 分钟，I1 仍用原配置，重新启用后新建的 I2 才用新配置。新增表单初值为 15 分钟，但每轮使用实际保存的配置，不在恢复时重新套默认值。

这不是复制整条 Job：Cron、启停、错失和阻塞策略用于决定是否创建新一轮，不作为存量 Instance 的执行策略快照。节点地址与服务发现结果、组 Token、队列容量也不冻结。保存组标识不等于冻结组的发现目标；组删除和发现目标变更对存量执行的影响仍按组生命周期协议设计。

共享执行配置在 Instance 级保存一份，不为每个 Task 重复复制完整 Job，也不增加配置版本历史表。创建事务可复用已经读取的 Job，随 Instance 一起写入；仍有存储字节和序列化成本。后续按 Instance 复用或批量加载，避免按每条 Task 查询 Job。组标识与运行数据使用独立列，其余必要执行配置放入 `execution_config` JSONB，并由 Go 明确结构体承载；[字段与 JSON v1 成员](data-contracts.md#trigger-field-draft)已确认，DDL 和读取／传递协议继续细化。

配置固定不等于冻结业务代码或业务数据。处理器同名升级仍须兼容在途轮次的参数和行为；本规则不提供代码版本锁定。

### 低频触发恢复 {#trigger-recovery}

**正常触发依靠 Cron；Leader 每 1 分钟查询 Job 的持久化触发进度，只做遗漏恢复，不承担正常触发的及时性。** 恢复循环位于当选的调度进程内，不另外部署恢复服务。

| 时机或角色 | 处理职责 |
| --- | --- |
| 启动后选主成功，或接替旧 Leader | 立即检查一次 Job 触发进度，发现停机、切主期间未处理的触发 |
| 正常担任 Leader | 每 1 分钟按索引、小批量检查已启用且触发时间已到的 Job，交给统一触发入口重新判断 |
| 发现失去 Leader 身份 | 取消该任期上下文，停止安排新的 Job 触发恢复检查；已按最新 Job 合法记账的在途事务仍可能提交 |
| 普通非 Leader 调度节点 | 不扫描 Job 做遗漏触发恢复；继续参与已经创建的 Instance／Task 的推进与恢复 |

持久化依据是 **`Job.next_trigger_at`**，不是另建一张“计划表”或重试队列。创建 Instance 与推进该字段的事务确定未提交时，字段保持原值；后续正常回调或恢复检查仍可据此发现未处理的触发。提交确认不明不能推断字段未变，必须按最新持久化事实处理。

配置同步与触发恢复是同一个 Leader 进程内的两个独立后台循环，各自每 1 分钟运行，共同受 Leader 任期控制；失去 Leader 身份后，两个循环都停止安排新工作。配置同步另由管理变更通知推动，触发恢复在接任时立即检查一次。不要求两个循环同时运行，也不要求使用同一条 SQL。

每分钟配置同步检查规则有没有修改；每分钟触发恢复检查 `Job.next_trigger_at` 有没有到期未处理。配置内容未变化不能成为跳过触发恢复的理由，也不把“配置加载成功”作为恢复循环运行的前置条件。配置同步变慢或失败时，恢复循环仍独立安排检查；二者仍共享进程及数据库资源，恢复必须满足数据库可用、Job 规则有效和触发授权等条件，不承诺完全故障隔离。周期检查仍有数据库成本；候选批次与处理并发必须有界，按索引查找候选，不加载全部历史 Instance／Task。在途事务适用[已确认的切主边界](execution.md#leader-config-boundary)，不以停止循环证明数据库硬隔离。

第一版不增加本地 Job 退避补试机制。触发写库失败或本地触发提示未被处理时，后续恢复检查按数据库事实重新进入触发入口；数据库仍不可用时等待后续检查，不保留无限等待的本地 Job 重试对象。此规则不改变 Task 执行重试、BUSY 记账和两端结果回报的既定机制。

每次从主库按 `next_trigger_at, id` 读取最早到期的一批未删除且启用的 Job，只取 ID 与计划时间。单次 `LIMIT` 的部署初值为 **1024**，查询超时初值为 **5 秒**；不分页，也不保存跨分钟游标或上一轮时间上界。候选通过非阻塞方式提交到已有触发队列，队满即结束本次，不等待空位或另建缓存；下分钟重新查询当时的数据库事实。恢复循环串行、不重叠，不补跑积压的周期 tick。具体查询与上下文边界见[单批触发恢复](execution.md#trigger-recovery-scan)。

第一版不保证 Job 恢复候选的严格公平轮转：大量最早到期的 Job 持续失败或队列反复满载时，后面的候选可能长期得不到恢复检查。此取舍不取消已接纳 Job 在队列内部的去重与队尾轮转，也不改变 Instance／Task 恢复的既定公平性要求。

1 分钟是检查周期，不是恢复完成时限；数据库故障、上述头部阻塞及处理耗时可能使恢复更晚。恢复进入触发事务后，仍按取得 Job 行锁后的调度进程时间判断是否超过固定 5 秒容忍：超出后按错失策略忽略或最多补执行一次，不承诺所有遗漏都会补跑。已有 Instance 的故障恢复原 Instance，不因 Job 查漏再创建同一轮。

## 4.3 错失策略与触发进度 {#misfire}

页面提供两种错失策略：

| 选项 | 行为 |
| --- | --- |
| 忽略（默认） | 跳过错过的周期，继续未来的正常计划 |
| 立即执行一次 | 无论错过多少个周期，最多补一次，然后恢复正常计划；不逐周期补跑 |

相对本次计划触发时间，迟到不超过固定 **5 秒**时按正常触发处理，超过 5 秒才应用错失策略。该容忍值不开放页面或配置文件设置。

错失处理的对象是**尚未形成 Instance 的计划触发**。已经存在的 Instance 出现故障，应恢复原 Instance，不能再按错失策略补建一轮；补执行也必须服从[阻塞策略](#blocking)。

系统持久化 `Job.next_trigger_at`。robfig 本身不提供持久化错失恢复，普通回调也不直接传入本次计划时间；回调只是提示检查 Job，处理哪一轮以锁内读取的数据库进度为准。

### 自动触发身份 {#trigger-identity}

**自动触发按 `(job_id, scheduled_at)` 唯一识别，`Instance.scheduled_at` 保存本次处理前、锁内读取的 `Job.next_trigger_at`。** `Instance.id` 标识实际创建的一轮执行；原计划时间、创建时间和首次有效开始时间分别表达不同事实，不能相互替代。

正常 Cron 回调与恢复检查使用同一种自动触发身份。正常／错失是本次判定结果，不能作为区分唯一身份的维度，让同一 Job 的同一原计划时间各创建一轮。主要保证是[Job 单行短事务](execution.md#trigger-accounting)内创建 Instance 与推进进度原子提交，自动触发唯一约束作为兜底；不据此承诺业务恰好执行一次。

补执行也保留旧进度作为 `scheduled_at`。例如原定 `2026-10-15 10:00:00+08:00`，到 `2026-10-15 10:03:00+08:00` 才补建，原计划时间仍保存前者，而不是创建时间；业务尚未开始时，不提前填写开始时间。计划身份包含完整时间点，不把不同日期的同一钟点视为同一轮。已有 Instance 的故障恢复沿用原 Instance，不重新补建。

手动执行使用独立于自动触发的请求身份，不占用上述自动唯一身份，也不推进 Cron 进度；启停条件、当次参数及请求防重复创建按[手动触发规则](#manual-trigger)处理。两个部分唯一索引及冲突处理按[已确认的触发持久化协议](data-contracts.md#trigger-transaction-proposal)执行：校时后重新启用若重遇已保留的自动身份，不覆盖或重新执行旧 Instance，仍推进当前 Job。历史清理移除身份后不保证永久防重，具体清理衔接继续设计。

### 到期区间与下一次时间 {#trigger-advancement}

在同 Job 短事务内，用旧 `Job.next_trigger_at` 作为原计划时间，用取得行锁后读取一次的调度进程时间作为本次判定时间。未启用、已删除或不存在的 Job 不授权自动触发；有效 Job 按下表处理：

| 原计划时间与判定时间的关系 | 本次动作 | 进度处理 |
| --- | --- | --- |
| 原计划时间尚未到 | 不创建 Instance，不允许提前执行 | 保持原值 |
| 已到期，迟到不超过 5 秒，包括恰好 5 秒 | 尝试创建一个正常 Instance | 推进到严格晚于本次判定时间的第一个 Cron 时刻 |
| 迟到超过 5 秒，错失策略为忽略 | 不创建执行 Instance | 同上 |
| 迟到超过 5 秒，错失策略为立即执行一次 | 尝试创建一个补执行 Instance | 同上 |

创建仍受[阻塞策略](#blocking)约束；因已有未结束 Instance 而丢弃时，也推进到上述下一次时间，不等待前一轮结束再补。需要执行时，Instance、本轮配置与进度在同一事务中保存；忽略或丢弃也必须提交进度，不按本地判定结果直接跳过数据库记账。

**每次到期处理最多创建一个 Instance，包括 5 秒容忍内的多轮积压。** 本次处理的区间从旧进度开始，包含截至本次判定时间的全部 Cron 时间点；不逐轮追赶。下一次时间通过当前 Cron 规则求得，不用“当前时间加固定周期”代替；也不循环刷新当前时间、追赶到事务物理提交时刻。

迟到分类只比较旧进度与本次判定时间。旧进度已迟到超过 5 秒且选择忽略时，会跳过整段到期时间点，不再从其中筛出最近 5 秒的时间点单独执行。5 秒表示本次处理是否应用错失策略，不是保证该窗口内每个周期都执行。

### 时间示例 {#trigger-time-examples}

以下假设 Job 已启用、未被阻塞，规则使用[六字段 Cron](#cron-contract)，时间均按同一调度时区解释：

| 规则与旧进度 | 锁后调度进程判定时间 | 结果 | 新 `next_trigger_at` |
| --- | --- | --- | --- |
| 每分钟，10:01:00 | 10:01:05.000 | 正常创建一个，`scheduled_at = 10:01:00` | 10:02:00 |
| 每分钟，10:01:00 | 10:01:05.001 | 按错失策略忽略或补一个 | 10:02:00 |
| 每分钟，10:01:00 | 10:05:20 | 将 10:01 至 10:05 五个时间点一起处理；忽略或最多补一个，补执行仍保存原计划时间 10:01:00 | 10:06:00 |
| 每秒，10:00:00 | 10:00:04 | 正常创建一个，不创建五个，原计划时间为 10:00:00 | 10:00:05 |
| 每秒，10:00:00 | 10:00:10，选择忽略 | 整段跳过，不另执行最近 5 秒的时间点 | 10:00:11 |

补执行表示对本段遗漏提供一次执行机会，不承诺自动补齐所有遗漏周期的业务工作。此规则控制积压后的触发数量，不适用于要求每个秒级周期必达的场景。对照依据见[参考资料](references.md#trigger-identity-evidence)。

## 4.4 阻塞策略 {#blocking}

页面提供两种同 Job 重叠执行策略：

| 选项 | 行为 |
| --- | --- |
| 丢弃（默认） | 同一 Job 已有未结束 Instance 时跳过本次触发并记录原因；不排队，也不在上一轮结束后补跑 |
| 并行 | 上一轮未结束时仍可创建独立 Instance，同时运行 |

判断范围是同一 Job 在**整个集群中的未结束 Instance**，包括开始前等待、准备、分片执行、重试等待和收尾，不是单个执行器上的某个分片。第一版不提供串行排队、覆盖旧实例或额外的“恢复”阻塞选项。

定时、恢复和手动创建入口共用[Job 主键单行短事务](execution.md#trigger-accounting)：取得同一 Job 行锁后，用适配索引的 `EXISTS` 检查未结束 Instance，再决定是否创建。手动触发不推进 Cron 的 `Job.next_trigger_at`，重复请求先识别已有 Instance，避免被自己的执行记录阻塞；具体见[手动触发规则](#manual-trigger)。

阻塞判断以检查时的数据库事实为准。检查时存在未结束 Instance、随后它恰好结束，允许本次仍按丢弃处理；不承诺业务线程物理上绝不重叠。Instance 终态不可逆，结束操作只会减少未结束数量，不要求每次 Instance 结束也锁 Job。自动错失忽略及阻塞丢弃在进度提交确认后仅写结构化服务日志，不另建数据库记录；管理页无跳过明细，日志不保证完整审计，见[跳过留痕](data-contracts.md#trigger-skip-record-proposal)。手动触发的交付边界见[目标与范围](./scope.md)。

### 手动触发规则 {#manual-trigger}

**手动执行创建新的一轮 Instance，不改变 Job 的启停状态、Cron 或 `next_trigger_at`。未删除的 Job 无论启用或停用均可手动执行；停用只关闭自动触发，不代表禁止一切执行。** 管理权限、输入及执行配置校验仍然适用。

| 事项 | 已确认规则 |
| --- | --- |
| 与定时的关系 | 不要求 Cron 到期，不占用自动触发身份，不推进定时进度，也不自动启用 Job |
| 与已有执行的关系 | 遵守同 Job 的集群级阻塞策略，不提供强制绕过；丢弃策略下已有未结束 Instance 时明确拒绝，不排队补跑 |
| 当次业务参数 | 默认沿用已保存参数；允许仅替换本轮业务参数，实际参数固定进 Instance 的 `execution_config`，不修改 Job |
| 其他配置 | 不临时改写执行器组、处理器、重试、超时、阻塞策略或节点地址；其余执行配置沿用创建时读取的 Job |
| 成功响应 | Instance 及本轮配置提交成功后返回 Instance ID，不等待开始或完成业务；页面提示“已创建执行记录” |
| 再执行与重发 | 用户明确再执行一次使用新 `request_id`；同一次操作的网络重发沿用原号，不重开原 Instance |

例如补算某一天的报表时，只覆盖本轮日期参数，不必先修改 Job、执行后再改回。分片仍按正常路径运行准备、分片和可选收尾，不把手动执行变成选择失败分片重跑。

**原请求重发只在 Job 未删除且执行记录仍保留时，按同一 Job、同一 `request_id` 返回成功创建结果，不是永久保存每次请求结果。** 请求号随 Instance 保存，由唯一约束兜底；不增加 Redis 锁、请求队列或独立请求记录表。已删除 Job 先返回不存在，不借旧请求绕过删除状态；已创建的原 Instance 仍可按 ID 查询。

- 相同请求号和相同请求内容再次到达时，已经创建的直接返回原 Instance ID，即使它已成功、失败或取消，也不另建一轮；查重在新建所需的阻塞判断之前完成。
- 同一请求号不能换参数后复用，应返回冲突。请求号采用 UUID；按 `params_overridden` 区分沿用与覆盖，覆盖字符串去首尾空白后与原快照参数精确比较，内部空白和 JSON 键序仍影响比较；沿用时不比较后来 Job 的参数。覆盖空串或 trim 后为空均不同于沿用，规则见[字段契约](data-contracts.md#execution-config-field-draft)，HTTP／RPC 表达仍需落实。
- 阻塞拒绝等未成功创建的请求不永久留痕；收到明确拒绝后，客户端结束本次操作，不后台等待补跑。若拒绝响应丢失，稍后同号重试时条件已满足，可以创建；没有已创建记录时按重试时的配置和条件判断。
- 提交确认丢失不能宣称“肯定未创建”，重发沿用原号核对；不能自动换新号重试。Instance 被清理后，旧号的防重证据随之消失，不承诺跨历史清理永久防重。

这是低频管理入口的创建确认，不改变 Task 结果回报“入队即 ACK、异步落库”的既定规则，也不代替业务幂等。创建顺序见[手动触发记账](execution.md#manual-trigger-accounting)，竞品对照见[参考资料](references.md#manual-trigger-evidence)，验证场景见[手动触发验收](verification.md#manual-trigger-checks)。

## 4.5 自动重试 {#retry}

本节是重试行为的完整定义。普通业务执行 Task、准备 PreTask、各分片 Task 和收尾 PostTask 共用 Instance 创建时从 Job 保存的重试配置，**每个 Task 独立计数**，不是整轮共享一个次数池，也不随 Job 后续编辑改变。

### 配置与执行预算

| 参数 | 已确认语义 |
| --- | --- |
| 重试次数 | 默认额外重试 **3 次**；设置为 `0` 时不对失败或结果不明自动重派，但允许明确未接单的 BUSY 延期再派发 |
| 重试间隔 | 默认固定 **10 秒** |
| 配置位置 | 只在 Job 上配置一份；第一版不增加准备、分片或收尾专属重试参数 |

每个 Task 默认具有原始执行加三次重试、共 **4 次执行机会**的预算；明确 BUSY 可以条件返还本次已占机会，因此实际派发请求次数可能超过四次。PreTask 消耗自己的额度，不扣减分片或 PostTask 的额度，也不因存在多个阶段而累加成另一份阶段预算。预算不是精确确认业务实际运行了多少次；故障后的旧执行可能仍在运行，BUSY 返还也不允许复用旧尝试身份。

执行机会在**当前尝试登记提交成功时**占用，与新尝试身份及进入执行中状态原子保存。没有派发槽位、仅在本地排队或登记事务确定未提交，不占用机会。明确未接单的 BUSY 是条件返还例外，只有持久化返还与延期成功后才重新获得该机会。登记提交后、实际发送 RPC 前宕机仍不能免费重发，因此零重试时可能业务实际尚未执行就最终失败。发送顺序与成本见[尝试登记](execution.md#attempt-registration)、[记账边界](execution.md#dispatch-accounting)及[BUSY 规则](execution.md#busy-backpressure)。

除明确未接单的 BUSY 外，派发失败、RPC 派发超时和明确业务执行失败，需要重新发起业务执行时，消耗当前 Task 的**同一个预算**。以默认额外重试 3 次为例：首次派发超时且没有持久化绑定或有效结果，先完成有限观察及结果不确定的条件结算，再等待默认 10 秒；有剩余预算且父 Instance 仍允许执行时，登记第二次尝试后派发。若第二次业务失败，还剩两次执行机会，后续仍须遵守重试间隔并重新取得父实例授权；若第四次也失败且期间没有 BUSY 返还，则额度耗尽，不再登记第五次尝试。通信超时本身不直接授权 10 秒后重发，也不额外保留一份业务专用额度。

### 身份、边界与非执行重试

- 重试沿用原 Instance ID、Task ID，更新重试计数并区分执行尝试；不创建新 Instance，不重跑已成功 Task。
- 等待重试只是候选状态，不证明 Instance 仍未结束；下一次登记必须重新取得父实例授权。仍可重试的分片不能先进入最终失败，再异步改回可执行状态。
- RPC 层不额外叠加可能重复调用业务处理器的自动重试，底层通信重发不能绕过平台执行预算。
- 数据库操作重试、结果回报重传、本地等待派发槽位不属于重新执行业务，不消耗本预算。执行器结果回报使用独立内部常量控制有限重试，耗尽后释放并记录错误及丢弃指标，见[回报重试与清理](execution.md#report-retry)；调度端可恢复的写库故障则按[有界保留与背压规则](execution.md#scheduler-result-retention)处理，不套用耗尽释放。错误分类、批次及具体参数仍需设计。
- 派发结果不明并不额外产生重试机会。次数为 `0` 时，结果不明也不能自动获得重新派发额度。
- 首次派发与重试均使用 go-zero 原生负载均衡，不保证更换执行器实例；不以先查询原进程、证明旧执行绝未发生为重派前置条件。
- 重试仅能在本轮仍允许执行且整轮时间预算未耗尽时进行。停止或整轮超时后取消后续重试，不借失败或结果不明创建新一轮补跑。

本规则不免除业务幂等责任；平台与业务的职责边界见[派发与业务幂等](./execution.md#idempotency)。登记、绑定、等待结果及 BUSY 条件返还规则已确认。BUSY 返还须持久化生效才恢复机会；记账只做有界有限重试，响应丢失或结算先提交时，不保证实际未执行的机会一定返还。登记提交不明则放弃本次本地发送，不免费补发；统一边界见[提交结果不明恢复](execution.md#commit-unknown)。具体退避与 SQL 在对应模块细化，不把通用 RPC 错误当 BUSY。

回报链路固定为双端异步、调度端入队即 ACK。重传未确认的同一结果不等于业务重试；ACK 本身不改变 Task 或 Instance 状态，不是生成分片或开始收尾的许可。已有持久化执行器绑定而无有效结果时，不因失联或回报丢失提前重派，由整轮超时兜底；明确失败结果仍可按预算重试。没有绑定及结果的尝试适用独立观察规则，详见[无结果处理](execution.md#bound-result-wait)。

## 4.6 阶段结局与分片失败处理 {#stage-outcomes}

未被停止或整轮超时终止的正常流程按下表推进。各阶段只重试原 Task，不重跑整轮。

| 阶段 | 重试范围 | 最终失败后的处理 |
| --- | --- | --- |
| 普通执行 Task | 原普通 Task | 整轮失败，不组合准备或收尾阶段 |
| 准备 PreTask | 原准备 Task | 没有有效准备结果时，不生成分片，整轮失败，不进入正常 Post 流程 |
| 分片 Task | 当前分片，保留其他分片结果 | 其他分片继续；所有分片结束后仍进入已配置的 Post |
| 收尾 PostTask | 原 PostTask，不重跑分片、不新建第二条 PostTask | 整轮失败；Post 成功也不能抹除已有分片最终失败 |

某个分片重试耗尽或没有配置重试后最终失败，不立即停止其他分片。等待所有分片以及已配置的 Post 最终结束后，平台汇总时只要存在最终失败分片，Instance 即判为失败，不判为“部分成功”；已成功分片保留成功状态。某次尝试失败、后续重试成功，不属于最终失败。未配置 Post 时，平台直接根据分片最终结果结束本轮，不额外创建收尾 Task。

准备成功且工作项为合法空数组时，按零分片生成完成推进：有 Post 则创建唯一 PostTask 并按统一重试规则执行，没有 Post 则成功结束。非法或缺失结果不按空数组放行；语义及范围见[状态与生命周期](task-model.md#lifecycle)。

部分分片失败仍需进入已配置的业务收尾，处理本轮成功和失败结果，例如汇总错误、生成报告。PostProcess 不是仅针对成功分片进行计算的 Reduce，也不是任何失败场景都必定执行的 `finally`。其成功不能改写已有分片的最终失败，且仍受整轮剩余时间约束。准备和收尾同样可能因重试重复产生副作用，业务方必须保证幂等。

业务执行失败与平台推进失败必须分开：

- 准备成功结果已有效持久化，后续生成分片失败时，只恢复平台生成，不重新执行 Pre；旧尝试或重复回报不得替换已接受的准备结果，也不得生成另一批分片。
- Post 成功结果已有效持久化，更新 Instance 失败时，只恢复平台终态推进，不重新执行 Post。
- 上述平台推进恢复不消耗业务执行预算，也不能借此重新调用业务处理器。

状态集合与主转换见[任务模型](task-model.md#lifecycle)，终态竞争按[本章统一顺序](#terminal-order)处理。具体条件更新与通信故障协议继续在[数据与接口](./data-contracts.md)中闭合；终止后的正常流程不得因收尾而复活或延长预算。

## 4.7 整轮执行超时 {#instance-timeout}

执行超时限制**整个 Instance 的总执行时间**，使使用者能够安排“一轮任务最多允许运行多久”。必须使用有限正数，不允许 `0`，不提供无限时长选项；第一版不另设 Task 单次执行超时参数。

**新增表单预填 900 秒，即 15 分钟，用户可按业务修改。** API 仍须显式提供超时，数据库不设 SQL 默认，不改已有 Job 或 Instance。该初值不是最大上限，不增加其他业务最小／最大秒数；详见[默认值契约](data-contracts.md#timeout-default-proposal)。整轮作用范围和终止语义不变；已有执行器绑定但无有效结果时，不因失联或结果丢失提前重派，见[等待整轮超时](execution.md#bound-result-wait)。

有限整轮超时不保证卡住的业务代码实际退出，也不能代替 RPC 通信超时。整轮耗时受数据量、分片数量及并发资源影响，这一语义不保证每个分片各获得完整预算。

计时从“首次有效开始准备／执行”开始，Instance 创建后等待开始调度的时间不计入。开始后，准备、Task 生成、派发、分片执行、重试等待、平台汇总和业务收尾共用同一预算。没有准备处理器的普通任务也从开始推进本轮执行时计时，不延后到某个 Task 实际运行才开始。

例如配置 30 分钟，10:00 创建 Instance，10:02 开始准备，截止时间即为 10:32。Task 重试、推进节点变化和故障恢复等待都不延长截止时间。首次开始与截止时间需要持久化；首次开始的原子判定及其与派发的衔接待详细协议明确，不依赖整轮负责人或本地计时器保存。

整轮超时使用 **Instance 失败＋超时原因**，不增加独立超时状态。超时后：

1. 未派发 Task 不再派发，等待重试的 Task 取消后续重试。
2. 对正在执行的 Task 发出取消请求，但不等待业务实际退出才推进平台状态。
3. 已成功 Task 保留结果，不自动回滚业务操作。
4. 不自动重试整轮，不新建 Instance 补跑；未来正常定时触发仍按触发和阻塞策略判断。
5. 迟到成功回报不得把超时 Instance 改为成功，也不得恢复后续派发。

## 4.8 停止与取消语义 {#stop-semantics}

停用 Job、停止某个 Instance 和业务代码实际退出是三个不同事实。Job 停用只影响后续自动计划触发，仍允许按[手动触发规则](#manual-trigger)新建执行；有效手动停止将未终止且未到期的 Instance 置为取消，阻止后续正常派发和重试，对在途及运行中的执行尽力取消。平台推进终止状态，不以所有业务代码实际退出为前提。

第一版不增加停止确认宽限期，不增加为等待退出而设的“停止未确认”状态，也不无限等待退出上报。取消 RPC 仍需通信超时和有界失败处理；通信应答只说明取消请求的处理结果，不是业务已经退出的证明。

执行器使用协作式取消，处理器需要配合。不响应取消的代码可能继续运行或产生副作用。因此，“平台已停止”不保证旧执行与未来新一轮在物理执行上绝不重叠，业务方仍需按场景保证幂等或互斥。具体取消路由、上下文契约和条件更新协议待设计，不改变本节已经确认的停止边界。

### 停止、超时与正常结束竞争 {#terminal-order}

所有 Instance 终态入口遵守同一优先顺序，不由哪个后台检查先醒来决定超时是否有效：

1. 已经持久化终态时，保留成功、失败或取消，不接受后续请求覆盖或复活。
2. 取得 Instance 父行锁后，在受保护决策点按当前数据库时间判断：尚未终止且已经达到有效整轮截止时间时，按失败及超时原因结束；不能用事务开始时的旧时间绕过截止，也不能因超时检查迟到而写成功或手动取消。
3. 该决策点尚未开始整轮计时或未到截止时间时，正常结束与手动停止通过同一父行协调，先完成有效判定并成功提交的终态生效；正常结束仍须满足各阶段最终结果的条件。

预算包含平台汇总。因此，即使 Post 成功结果已落库，平台恢复推进时在父行保护下看到 Instance 尚未终止且已到期，仍按超时失败结束，不重新执行 Post，也不按执行器自报的结束时间倒改本轮为成功。截止前已完成有效决策的短事务随后成功提交，不因物理 COMMIT 稍后越过截止毫秒就倒改为超时；本协议不承诺物理提交或 RPC 到达的精确墙钟时限。协调规则见[新尝试登记与整轮终止](execution.md#authorization-terminal)，首次开始及具体 SQL 在实现协议中补齐。

### 终止后的子任务收敛 {#task-convergence}

不承诺 Instance 终止与全部 Task 状态在一个事务中同时完成。父终态先阻止后续正常推进，各子 Task 通过自身条件更新收敛：已有成功、失败或取消不变；尚未结束的 Task 取消后续执行并尽力请求业务退出。

有效结果回报与 Task 取消仍可能竞争。取消先落库时，迟到成功不能把该 Task 改回成功；有效终态结果先落库时保留结果。失败、BUSY 或未知结算可以与父终态交错，使未终态子 Task 短暂进入或留在等待重试，记账修正也可交错完成；这不授予新尝试，不改变父终态，也不能启动正常收尾。共同恢复必须覆盖父已终态但子未终态的情况，分批取消与取消 RPC 在父事务外完成。结果处理不统一锁父，具体条件写入和恢复索引仍需实现验证。

执行记录与详细日志分别存储：Instance、Task 保存查询所需状态和简短诊断；详细过程进入服务日志，不建立独立 Attempt 表或数据库过程日志表。详见[数据与接口](./data-contracts.md)和[管理与运维](./operations.md)。
