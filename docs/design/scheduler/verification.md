# 8 验证与交付

本章将设计边界转为可检查的交付依据。下列场景来自已确认的行为与可靠性要求，是后续验证清单，不是已运行的测试结果。基准测试规模和质量方向已经通过；首批实现单元已确定为触发闭环，调度功能尚未实现，测试部署、具体性能门槛、恢复时限及各批具体交付接口仍需细化。

## 8.1 验证原则

设计协议时同步补充正常和故障用例，不能在实现后根据观察到的表现反推产品承诺。分别验证平台持久化状态、调度推进和业务副作用，不能以“状态显示成功”代替业务执行正确，也不能以一次正常跑通证明故障恢复成立。

单元测试适合规则和局部状态转换；涉及事务、唯一约束和执行计划的行为需要真实 PostgreSQL 验证；多节点、选主及通信故障需要集成或端到端环境。最终测试组织沿用仓库[测试规范](../../development/testing.md)。

## 8.2 行为与故障检查清单

| 场景 | 必须验证的设计边界 | 实施前仍需明确 |
| --- | --- | --- |
| 正常普通任务与分片任务 | 普通单 Task；分片必需 Pre、可选 Post；从触发到记录、回报和终态形成闭环 | 处理器接口、持久化协议、测试业务处理器 |
| Leader 切换与配置竞争 | 每任期独立取消与串行配置加载；残留触发按最新 Job 判断，接受合法在途提交，不按旧快照重复创建 | 已定任期、加载与容量协议的实现、自动唯一约束及进度 SQL |
| 自动触发过载与依赖失败 | 三种自动来源共用有界 Job ID 队列及固定工作协程；队满可观测且不改进度，恢复每分钟从头限量读取，不保证候选严格公平，失败不自循环 | 已定容量与超时的实现、单批恢复及指标 |
| 错失与同 Job 重叠 | 相对旧进度固定 5 秒容忍，5 秒内多轮也只创建一轮并推进未来；各创建入口共用 Job 单行短事务，补执行也受集群阻塞策略约束；历史身份冲突保留旧轮、推进当前进度；跳过仅服务日志 | 已定触发事务、五索引和跳过日志的实现验证、统一 Cron 计算实现及历史清理衔接 |
| 准备成功后生成中断 | 恢复平台生成，不重跑已成功准备；不派发未完成生成的分片集合 | 生成执行权、分批写入、封口与恢复协议 |
| Task 保存后尚未登记尝试 | 数据库待处理事实可被其他节点接续；按本地容量登记，不依赖原节点存活 | 登记字段与 SQL、恢复检查覆盖范围 |
| 尝试登记后尚未发送或发送情况不明 | 已提交登记占用机会，不能免费重发；无绑定及结果时按有限观察与条件结算处理，零重试可能尚未执行业务就失败 | 登记提交结果不明的核对、观察秒数与具体条件写入 |
| RPC 接收确认丢失 | 无绑定及结果时有限观察，条件结算后才按预算重试，接受业务可能重复，不另加通信层执行额度 | 具体观察期、SQL 与父终态协调 |
| 重复、乱序及旧尝试回报 | 成功入队只确认接收；后台旧结果不覆盖新结果，重复回报不重复推进，提交后才进行阶段推进 | 批次确认、重传、校验及错误契约 |
| 密集回报与生成完成通知 | 本地合并不无限延后；检查期间新事件不丢失；待执行、执行中、等待重试都属于未结束分片 | 合并结构、状态编码及查询索引 |
| 多节点同时创建 PostTask | 单行短事务复核和唯一约束保证每轮至多一条 PostTask | 具体 DDL、并发测试与事务实现 |
| 部分失败和收尾失败 | 分片最终失败不立即停止其他分片；等待其他分片及已配置 Post 结束，Post 成功不能抹除分片失败 | 结果汇总字段及终态条件更新 |
| 收尾成功后终态更新失败 | 只恢复平台推进，不重跑已成功 Post；Instance 尚未终止却到期时按超时失败 | 条件更新、时间比较与恢复协议 |
| 停止／超时与派发、回报竞争 | 不恢复正常派发与重试，迟到成功不使父终态恢复；子 Task 条件收敛，不等待业务实际退出 | 定向取消、有效开始原子性、父子收敛及终态条件更新 |
| Instance／Task 本地集合满、节点退出或提交后通知丢失 | 既有有界检查补齐未推进和未派发工作，不另建全表汇总扫描 | 对应推进模块的退避、公平轮转及扫描进度 |
| BUSY、执行器变慢或失联 | 明确未接单的 BUSY 原子返还一次机会并延期，遵守最早可派发时间；已绑定无结果不因失联提前重派 | BUSY 条件写入与退避参数、两端容量及整轮超时条件写入 |

上述故障应覆盖准备、业务分片和收尾，不只验证普通业务 Task。停止测试应使用配合取消和不配合取消的处理器，验证平台声明的“尽力取消”与实际副作用边界。

### 持久化交接与最小组依赖验收 {#trigger-handoff-checks}

以下对应已通过的[持久化交接](data-contracts.md#trigger-durable-handoff)与[正式最小组依赖](data-contracts.md#executor-group-lifecycle)，是后续实现的验收要求，不是已运行的功能测试。

| 场景 | 预期结果 |
| --- | --- |
| 自动或手动创建确认提交 | WAITING Instance 和完整本轮配置同事务保存；开始、截止、结束时间为空，自动进度及手动请求身份分别遵守原事务规则 |
| 提交后尚未通知即退出，或本地 ID 提示队满、丢失 | 不回滚已保存事实，不额外创建一轮；执行模块的既有恢复可重新发现待推进 Instance |
| 提交确认不明 | 不声称回滚或凭推测通知；沿用现有查重和恢复，提示不是提交凭据 |
| 多节点读取同一候选 | 读取不表示已获执行权；后续首次开始与首 Task 创建仍须按执行模块的原子协议协调 |
| 候选较多，或创建后 Job 参数、组发生编辑 | 有界候选与配置批量读取，无 N+1；使用 Instance 快照，不用当前 Job 重建配置 |
| 较小 ID 的事务晚于较大 ID 提交 | 不因永久 ID 消费水位漏掉前者；恢复再次覆盖未推进状态 |
| 首批尚无业务推进消费者 | 保留 WAITING，继续参与同 Job 阻塞判断；不补假 Task、假成功或临时超时来伪造完整闭环 |
| 正式组记录存在、已删或不存在 | 使用 `job_executor_group` 的真实模型、主键行锁和未删除校验；不存在或已删拒绝新引用，未删除但无在线执行器允许引用 |
| Job 列表读取组名称 | 保持批量 LEFT JOIN，不逐条查询，不因组侧过滤意外丢失 Job 行，不读取凭据或实例目录 |

本批测试覆盖交接事实和组依赖；实际接续执行、恢复扫描参数、完整删组及凭据失效在相应模块验证，不能用测试夹具代替这些功能。

### etcd 选主与通知接入验收 {#etcd-integration-checks}

以下验证[已确认的 etcd 接入约定](execution.md#etcd-integration)，不是已运行的功能测试。

| 场景 | 预期结果 |
| --- | --- |
| 多副本正常竞争，或等待当选超过 5 秒 | 使用官方 Session＋Election；候选等待不被短请求预算取消，不自行实现第二套选主 |
| 使用缺省租约配置，或配置为零／负值 | DogX 默认 TTL 为 15 秒；非法值明确拒绝，不静默退回库的 60 秒默认值 |
| 建租约请求成功后超过 5 秒，进程继续健康运行 | 长会话仍正常续租，不因误用短请求上下文而结束 |
| Session 结束或当选返回时生命周期已取消 | 不启动新的任期工作；关闭入口并清理，完整退出前本机不再次参选或叠加会话 |
| etcd 故障期间取消竞选或停止运行 | 验证库内部清理及本地资源退出；不把短请求预算当成固定退出保证，不以脱离旧协程再开新竞选规避阻塞 |
| 不同调度集群共用 etcd，或执行器尝试操作控制键 | 前缀隔离；执行器无权操作选主及通知范围，组 Token 不能替代 etcd 认证 |
| Leader 更换，已有配置通知标记存在 | 标记不随选主租约消失，不挂 TTL；新 Leader 按最新监听位置及主库核对接续 |
| 连续写入同样的 `reload` 值 | 每次 Put 仍形成事件；监听方不按值相同过滤，多个事件可合并成核对信号 |
| 通知键尚不存在、被删除或历史被压缩 | 使用 Get 响应头 revision 衔接，必要时重建并核对；Delete 只是核对提示，不删除数据库 Job |
| 数据库已提交，但通知写入失败或上游已取消 | 应用调用至多一次 Put、总预算最多 1 秒且更短期限优先；不主动改报保存失败，不建立后台通知队列，分钟核对兜底 |
| 通知失败同时客户端断线 | 数据库提交仍有效，但不保证客户端收到成功响应；通知不是配置已应用确认 |
| Watch 可恢复断线、关闭或反复重建失败 | 可恢复故障交给客户端；应用重建前结束旧监听，按 1 秒至最多 30 秒带抖动退避，不叠加活跃 Watch，不阻断有效任期的分钟核对 |
| 短 etcd 请求或配置数据库读取变慢 | 初值分别为 5 秒、5 秒，更短上游期限优先；配置失败保留旧规则，不应用半批结果，不与触发 3 秒预算混用 |
| 故障接任耗时超过 5 秒或 15 秒 | 按原进度及错失策略判断；不以 TTL 推导接任时限或每轮补跑保证，仍接受合法旧事务提交 |

### Job 配置通知与核对验收 {#job-config-sync-checks}

以下对应已确认的 [etcd 通知与每分钟核对](behavior.md#trigger-sync)及[配置加载与重载流程](execution.md#job-config-reload)，是待实现的验证要求。

| 场景 | 预期结果 |
| --- | --- |
| 管理变更事务提交并成功发送 etcd 通知 | 更新集群级单个变更标记，Leader 收到提示后读主库；不在 etcd 保存完整 Job 配置，不建立逐 Job 监听，不把提示当作触发授权 |
| PostgreSQL 已提交，进程在发送通知前退出或 etcd 写入失败 | 数据库保存仍有效；每 1 分钟配置核对补发现，不把保存成功解释为已应用 |
| 接任首次加载、通知、分钟核对及 Watch 重建同时到达 | 共用本任期唯一串行工作协程，不并发查询和应用配置；连续提示只合并成一个待核对信号，不随通知数无限积压 |
| 数据库查询或差异应用期间又收到通知 | 本轮结束后再次核对；不得清掉处理中到达的新提示，也不产生两次加载结果乱序覆盖 |
| 首次监听或重建监听时，配置刚好再次变化 | 通过 etcd revision 衔接读取与监听；遗漏不能由简单“先查库、后开始监听”的窗口造成。revision 只用于通知流，不作为数据库 Job 版本 |
| Watch 断线或历史已压缩 | 可恢复连接故障先交客户端处理；需要应用重建时按接入约定退避重建并核对最新主库，不要求重放全部历史，也不只等待新变更 |
| Watch 暂时不可用，但 Leader 资格仍有效 | 分钟配置核对不等待 Watch 恢复；一旦失主或无法确认资格有效，按任期规则停止，不因核对可运行而继续触发 |
| 批量核对启用 Job | 一次从主库完整读取定时注册所需的轻量投影，不逐 Job 查询，不加载业务参数、Instance 或 Task；不把查询错误或不完整结果当成空配置应用 |
| 新增、Cron 改变、停用或删除，与未变化规则同时存在 | 分别注册、替换、移除相应内存规则；未变化的条目保持原注册，不每分钟全删重建；原有有效 Cron 触发继续运行 |
| Job 仅推进 `next_trigger_at` 或发生非定时注册字段变化 | 不视为 Cron 注册差异，不因此重建规则；配置核对不写入或重算持久化进度 |
| 新增或替换规则时，读取到注册之间跨过首轮时间 | 完成注册并确认本批已由 Cron 初始化后，再向有界统一触发入口提交一次该 Job 的到期检查；按原持久化时间判断，不依赖已过去的 robfig 回调 |
| 注册后的检查到达时尚未到期 | 不创建 Instance、不推进进度；该检查不是“启用就立即执行” |
| 注册后检查与 Cron 回调或触发恢复同时处理同一轮 | 共用同 Job 短事务及自动身份约束，不重复创建；取得行锁后读取调度进程时间，继续适用 5 秒规则 |
| 新注册较多或注册后到期检查入口已满 | 配置加载不逐个等待触发事务，不启动无限补试；入口拒绝新提示并记录指标与限频日志，保留进度供独立触发恢复补查，仍按 5 秒及错失策略判断；未变化规则不额外提交检查 |
| 整次配置查询失败 | 保留已注册规则并记录错误；等下一次通知或分钟核对，不由失败分支立即自循环重试 |
| 接任后的首次配置查询失败 | Cron 保持未启动，但分钟核对及独立触发恢复仍运行；后续成功加载不能被首次失败永久阻断 |
| 单个 Job 的 Cron 无效，其他 Job 正常 | 仅不注册该 Job 并移除其旧规则，记录错误；其他有效规则照常应用，不自动修改数据库启停状态 |
| 加载未结束便失主，随后同进程再次当选 | 取消旧任期监听及加载、停止旧 Cron；本地清理完成后才重新参选，新任期使用新运行对象，旧结果不能写入新任期，旧待处理信号不复活 |
| 配置加载期间失主，但节点仍在推进已有 Instance／Task | 只停止任期内的自动触发与配置工作，不取消对等节点职责；已在途的合法触发提交沿用切主边界 |
| 通知或配置核对延迟，发现时首轮已超过 5 秒 | 保留原 `next_trigger_at`，按既定错失策略处理；通知渠道不提供零遗漏或固定生效时限保证 |
| 没有配置变更通知 | 配置核对仍每 1 分钟运行；独立的触发进度恢复仍按自身周期运行，不因配置未变而跳过 |

触发入口有界承载及过载行为按[容量验收](#trigger-capacity-checks)检查，采用[已确认的实现初值](execution.md#trigger-runtime-defaults)；配置加载 I/O 采用[etcd 接入约定](execution.md#etcd-integration)，恢复查询采用[单批恢复协议](execution.md#trigger-recovery-scan)的 1024 条上限和 5 秒查询超时初值。异常时钟按[已定运维边界](operations.md#scheduler-timezone)及[验收场景](#clock-operations-checks)检查。不以注册后检查代替低频恢复，也不把上述流程解释成跨 PostgreSQL 与 etcd 的原子提交。

### Leader 任期生命周期验收 {#leader-runtime-checks}

以下对应[任期生命周期](execution.md#leader-runtime-lifecycle)与整批初始化确认，是实现后的验收要求。文档渲染检查不代表这些功能测试已经运行。

| 场景 | 预期结果 |
| --- | --- |
| 首次装载大量有效规则 | 有界队列与消费能力先就绪；在尚未启动的 Cron 中批量注册，再启动，不进行首次运行中逐条添加所产生的反复排序 |
| `Start()` 已返回，但运行循环尚未完成初始化 | 不提前提交注册后检查；整批确认一次，不按每条规则读取全量快照 |
| 热更新最后一条添加调用已返回，但接收方尚未完成其下一次时间计算 | 等待整批确认后再提交新增／替换规则检查；未变化规则不重建、不额外检查 |
| 初始化确认期间跨过首轮时间 | 检查原 `next_trigger_at`，按实际处理时间及 5 秒规则决定，不重算进度或保证所有检查都能及时接纳 |
| 首次查询得到合法空配置，或部分规则非法 | 空配置可启动空 Cron；坏规则隔离，不阻止其余有效规则，不增加零值 `Next` 巡检 |
| 首次加载失败，随后数据库恢复 | Cron 暂不启动，后续核对与独立触发恢复继续；成功后走首次批量装载路径 |
| 加载、启动或整批确认期间失主 | 关闭入口并取消任期；迟到结果不能重新启动已停止的 Cron 或继续提交旧检查；停止后的快照不能冒充初始化确认 |
| 失主时队列仍有提示，另有正在执行的触发短事务 | 丢弃未处理提示，不排空执行旧队列、不推进其进度；等待在途操作退出，合法旧提交仍按原边界处理 |
| Cron 停止，但 DogX 数据库工作协程尚未退出 | 不把 `Stop()` 的回调等待等同于完整清理，不提前释放并发许可或允许本机重新参选 |
| 持续多次失主和重新当选 | 旧任期全部退出后才重新参选；新建任期资源，复用进程创建额度，不累积旧队列、规则和协程 |
| 本地清理异常卡住 | 本机不叠加新任期，记录错误供运维处理；其他机器可接任，不等待旧机清理或业务执行完成 |
| 任期退出时另有手动创建及对等 Instance／Task 工作 | 不被任期上下文一并取消，继续受进程容量、执行权及终态规则约束 |

不新增固定清理超时或强杀保证，不把取消当作回滚证明。实现应覆盖竞争交界及反复切主的资源占用，而不只验证单次正常启动。

### 触发容量与过载验收 {#trigger-capacity-checks}

以下对应已确认的[触发容量与过载协议](execution.md#trigger-capacity)，验证自动提示的有界接纳、恢复和创建事务并发。实现初值为待处理 Job 总容量 1024、创建并发 32、单次处理超时 3 秒；下列场景是验收要求，不是已运行的测试结果。

| 场景 | 预期结果 |
| --- | --- |
| 使用默认配置，自动及手动请求同时到达 | 排队和处理中唯一 Job 合计不超过 1024；自动工作协程数为 32，自动与手动实际创建共用进程级 32 份额度，不另建手动等待队列或专用预留额度 |
| 覆盖创建并发配置 | 自动工作协程数随同一配置调整，不出现第二个独立并发参数；待处理总容量仍按配置分别约束 |
| 自动排队后处理，或手动调用方只剩更短期限 | 自动取出 Job 后启动 3 秒处理预算，覆盖额度、连接、锁等待和提交；采用更短的上游期限。此前排队虽不计入处理预算，仍影响 5 秒错失判断 |
| Cron 回调、注册后检查和 Leader 恢复同时提交提示 | 三者共用本任期同一个有界 Job ID 队列和固定工作协程，不按来源增设旁路；触发授权仍来自同 Job 短事务内的最新数据库事实 |
| 同一 Job 已排队，又连续收到提示 | 合并为一项，不因重复提示增加占用或不断推迟已安排的检查 |
| 同一 Job 处理中收到多个新提示 | 只保留一次后续检查，当前处理结束后复用原槽位回队尾；同一任期内不同时启动该 Job 的另一项本地处理，不按提示数累积工作 |
| 新提示与当前处理结束同时发生 | 状态转换不能清掉已保留的新提示；后续检查进入队尾，不在当前工作协程内连续追赶 |
| 队列、处理中 Job 及后续检查同时存在 | 本任期总容量覆盖排队和处理中的唯一 Job ID；取出队列不释放该 Job 的占用，回队尾不增加槽位，不产生无界待入队集合或等待协程 |
| 总容量已满，继续提交已有 Job 和新 Job 的提示 | 已有 Job 按排队合并或处理中保留一次处理；拒绝新的 Job 提示，不等待空位或无限新开协程，不写 `next_trigger_at`，不创建失败 Instance；拒绝有指标和限频日志 |
| 热点 Job 持续产生提示，其他 Job 已获接纳 | 热点 Job 的后续检查排到队尾，不一直占住工作协程立即重跑；持续超载时不据此承诺所有新 Job 都能及时获接纳 |
| 恢复候选超过一批，最早到期的 Job 持续失败或反复队满 | 每次仅读取一批，队满即结束，不分页或保留跨分钟游标；允许后面的候选长期未被恢复检查，不把队内轮转误当成候选严格公平，不增加本地补试或立即重扫 |
| 提示准时到达，排队或锁等待后已超过 5 秒 | 仍按取得 Job 锁后的调度进程时间判断。例如原计划 10:00:00、判定时间 10:00:06，按错失策略忽略或最多补一次；入队时间不冻结正常触发资格 |
| 数据库连接获取、Job 行锁等待或事务操作变慢 | 等待及操作受超时和相应上下文约束，不无限占用工作协程，不借额外协程绕过创建并发额度；超时不自动证明事务回滚 |
| 触发处理失败，期间有或没有新提示 | 失败本身不制造下一次检查；没有新提示时结束本次处理，等待后续 Cron 或分钟恢复。有真实新提示时仅保留既定的一次后续检查 |
| 提交响应丢失、断连或取消导致结果不明 | 不凭报错修改进度或盲目重放旧 INSERT；后续进入统一事务，依据最新进度及自动身份处理，已有 Instance 由原恢复路径接续 |
| 手动创建遇到本进程创建额度已满，或取得额度 | 手动请求不进自动队列；无额度直接返回忙，不增加请求队列。有额度时与自动创建共用同一进程额度和 Job 阻塞协调，提交成功后同步返回 Instance ID，不推进 Cron 进度 |
| 旧任期仍有在途创建，同进程手动入口发起创建 | 共用本进程并发上限，不能提前释放旧操作额度；旧待处理工作随原上下文取消，旧在途合法提交仍按既定切主边界处理；本机此时不得重新参选 |
| 本地旧任期已清理，再次当选并接收自动及手动创建 | 新任期复用同一进程级创建额度，不因重新当选另开一份额度，不恢复旧待处理提示 |

恢复每分钟从头读取当前最早到期的一批 Job，不保证候选严格公平，也不把检查周期解释成恢复完成时限或所有遗漏都会补跑。单批上限初值 1024、查询超时初值 5 秒，详细场景见[低频恢复验收](#trigger-recovery-checks)；已接纳 Job 的去重与队尾轮转仍须验证。进程级额度只限制本进程的 Instance 创建事务，不是全数据库或全集群的并发上限。

实现后比较 8、16、32、64 等并发档位，结合数据库连接池观察有效 Instance 创建吞吐、触发长尾延迟、队列积压及数据库等待，不仅统计入队提示。100 条同秒到期仍是下文已确认的基准场景；更大规模对标需明确负载分布与持续时长，不把分钟平均吞吐等同于全部规则同秒触发，也不把队满拒绝或错失跳过算作正常执行。Task 端到端执行与结果落库性能由后续模块验证，不能由本批创建性能代替。

### 字符串字段类型与容量验收 {#string-field-type-checks}

对应[字段重设计](data-contracts.md#string-field-types)，是后续实现的验证要求，不表示调度表已经建立。

| 场景 | 预期结果 |
| --- | --- |
| 核对模型、迁移及字段注释 | Job.name／processor_name／cron_expr 为 VARCHAR(128)，remark 为 VARCHAR(500)；Instance.job_name 为 VARCHAR(128)，end_reason 为 VARCHAR(64)。params／result_summary 为 TEXT，execution_config 为 JSONB，其他原生类型与原设计一致 |

### Job 输入查询与错误契约验收 {#job-input-query-checks}

以下对应已通过的[输入查询与错误契约](data-contracts.md#job-input-query-proposal)，是后续真实接口及数据库验证要求，不表示功能测试已经执行。

- 用生成后的真实解析路径覆盖普通新增／编辑的 remark、params：缺失、null、空串均归为空串，编辑会清空旧值，不是 PATCH；固定字段 map 更新不得忽略空串。对其他必需配置、创建默认值及状态筛选验证必要的存在性，新增零重试不得变成默认 3，省略状态不得误筛停用。
- 手动覆盖单独验收：false 时 null／省略合法，任意字符串包括空串和全空白均非法；true 时必须提供字符串，null／省略非法，空串及 trim 后为空均表示明确覆盖。确认必要存在性跨 API／RPC 保留，先校验组合再规范化。
- 验证 params 在普通新增／编辑及手动覆盖中统一 `strings.TrimSpace`，仅去字符串首尾空白，不改变内部空格、换行或 JSON 键序；同请求号的 `" abc "` 与 `"abc"` 返回原 ID，内部文本变化则冲突。沿用请求不比较当前 Job 参数，不重新改写旧快照。
- 验证短字段 Unicode 长度与 VARCHAR(n) 容量一致、去首尾空白范围、解析后字段 NUL／非法 UTF-8 拒绝、数值类型及时间运算边界；不新增可调业务数值范围 CHECK，不承诺替换默认解析器严格检查原始 HTTP 字节。
- 分别验证 HTTP 请求体和内部 RPC 报文限制，超限不能部分保存；参数 JSON 转义后体积不能等同于原字符串大小。详情及手动覆盖也须覆盖大参数，不把“请求被接收”当作所有后续链路都可承载。
- 名称筛选覆盖中文、大小写、空白和字面 `%/_/!`；省略状态不筛选，0 则只查停用；分页及总数使用同一过滤条件。
- 检查列表不加载业务参数、说明、历史统计或在线节点；总数与本页查询加组名关联维持固定两次 SQL，组缺失不丢 Job 行；并发变更允许总数与分页短暂不一致。
- 验证按组分页／引用 EXISTS 的索引与实际执行计划，不要求普通 B-tree 加速包含搜索；不因小表顺序扫描直接判失败。超出部署数据库类型容量或分页偏移溢出应拒绝，不生成错误 LIMIT/OFFSET。
- 停用 Job 的响应计划时间为 null，但数据库原进度不变；详情完整配置可原样编辑，其他可空时间不伪造为零时间。
- 覆盖不存在、状态不允许、活跃阻止删除、阻塞拒绝触发、组不可引用、请求冲突、容量忙和技术失败；提交不明不能声称已回滚，普通新增不自动重发，手动重试不换请求号。

以下对应已通过的[Job 逻辑删除](behavior.md#job-deletion)及[删除事务](execution.md#job-deletion-transaction)，是后续真实数据库与接口验收要求，不是已执行的测试结果。

| 场景 | 预期结果 |
| --- | --- |
| 启用中的 Job 请求删除，或停用 Job 尚有待开始／运行中 Instance | 拒绝删除，不自动停用、不停止执行、不写删除标记；两种未终态 Instance 都必须覆盖 |

| 手动创建先取得 Job 锁并提交，删除随后取得锁 | 删除使用锁后的下一条 `EXISTS` 看到新建待开始 Instance 而拒绝；不得把活跃检查放进等锁前的同语句快照 |
| 删除先提交，随后手动／自动创建、编辑或启用 | 创建入口锁后先检查删除标记，不继续查重或新建；编辑和启用在同一行协调中拒绝已删除记录，不因此统一增加普通 CRUD 的显式锁。已有内存提示、旧候选及回调不能绕过删除状态 |
| 检查活跃 Instance 后，该轮恰好结束 | 允许本次保守拒绝删除，不为保证立即可删反向锁 Job 或引入全局协调 |
| 普通列表、详情、规则加载和恢复查询面对已删除记录 | 普通有效 Job 路径均排除 `deleted_at` 非空记录；配置与恢复 SQL 包含 `deleted_at IS NULL`，已有内存规则在核对后移除 |
| 删除已提交但 etcd 通知失败或进程退出 | 标记仍有效，旧触发入口拒绝创建；分钟配置核对最终按现有机制移除规则，不依赖通知即刻成功，不在数据库事务中发送通知 |
| 已删除 Job 的原手动请求号重发，原 Instance 仍保留 | 创建入口返回 Job 不存在，不返回旧创建成功或新建；原 Instance 可按 ID 查询，错误不被解释为原业务未执行 |
| Job 删除后查询执行历史，或显式只读关联已删除定义 | Instance／Task 历史仍可查询，不要求 JOIN 有效 Job；快照不被覆盖，关联的最后定义不能冒充本轮完整历史配置 |
| 父 Instance 已终态但子 Task 尚未收敛，随后删除 Job | 所有子记录及恢复依据保留，原取消／回报协议继续；不因 Job 不可见而丢弃工作，也不宣称删除或父终态证明业务退出 |
| 删除事务明确回滚或提交确认丢失 | 回滚不留下删除标记；确认不明不能推断未删除，以后续持久化状态判断，不自动清除标记或追加历史清理 |

本项不扩展为执行器组删除或历史清理协议，不提供恢复站。删除的并发保护只锁单条 Job、查询必要的活跃存在性，不加载全部历史 Instance／Task。

### Job 组引用与离线配置验收 {#job-group-reference-checks}

以下对应已通过的[组引用校验](data-contracts.md#job-group-reference-proposal)，是后续接口与数据库测试要求，不表示功能已实现或测试已运行。

| 场景 | 预期结果 |
| --- | --- |
| 新增、编辑保存、启用引用不存在或已逻辑删除的组 | 拒绝操作，不保存坏引用或启用状态；有效组要求存在且 `deleted_at IS NULL`，不另查组启停状态 |
| 组存在，但无在线执行器 | 允许保存、启用和手动创建 Instance；成功不表示业务执行成功，不隐含无限等待或自动取消策略 |
| 处理器名称为空、本地格式不合法，或符合格式但实际未注册 | 前两者由输入校验拒绝；最后一种不在保存时远程探测，在实际执行入口按执行协议反馈 |
| 手动新建一轮，与相同请求号重发已创建轮次 | 新建校验组引用；Job 未删除且请求匹配时，重发返回原 Instance，不按当前组可用性重判旧成功请求 |
| 组已缺失或离线，管理员停用或删除 Job | 不因组故障拒绝管理；删除仍要求停用且没有待开始／运行中 Instance，不顺带删除组或历史 |
| Job 编辑后，旧 Instance 继续执行或恢复 | 仍使用该轮快照中的组及配置，不用最新 Job 覆盖 |
| Cron 触发、Task 派发及管理事务 | Cron 和 Task 派发不因本规则新增逐次组表查询；管理入口仍执行已定组引用校验，数据库事务内不调用执行器 RPC，不引入处理器注册表或同步机制 |

组删除与新增引用的并发用例见下节；本项不以一次存在性查询代替并发保护，也不放开组删除。

### 组引用与删除并发验收 {#group-reference-concurrency-checks}

以下对应已通过的[组生命周期](data-contracts.md#executor-group-lifecycle)与[引用协调协议](data-contracts.md#group-reference-concurrency-proposal)。新增／编辑侧在本批验证；完整删除侧随组模块交付，不能把组表测试夹具当作删除功能已完成。

| 场景 | 预期结果 |
| --- | --- |
| 新增或完整编辑先锁目标组并提交，删组随后取得锁 | 锁后独立引用查询看到未删除 Job，拒绝删组；停用 Job 同样阻挡 |
| 删除先锁组并提交，新建或改入该组随后取得锁 | 读取到非空 `deleted_at` 并拒绝保存；不能形成悬空的新引用 |
| Job 从 A 改为 B，同时有人删除 A 或 B | 编辑只锁 B，再条件更新 Job；不锁 A。删组持组锁后普通查询引用，不反向逐条锁 Job，不形成 Job→Group 的反向锁序 |
| 旧组 Instance 创建先提交，随后 Job 改组 | Job 行协调保证改组等待创建提交；删旧组在确认没有有效 Job 后，后续查询仍看到旧快照的活跃 Instance 并拒绝 |
| 改组先提交，随后创建 Instance | 新轮次读取新组；不会在删除检查之后凭陈旧 Job 再创建旧组轮次 |
| Job 已逻辑删除或父 Instance 已终态，仍有未结束 Task | 已删除 Job 本身不阻挡；原组运行／恢复依赖仍阻挡，不能仅查当前 Job 或父状态就允许删组 |
| 仅剩无恢复依赖的已结束历史 | 历史不永久阻挡删组；保留记录，ID 不复用，历史读取不要求关联当前有效组 |
| 无引用及运行／恢复依赖，逻辑删除成功 | 同事务使用 GORM `Delete` 写入 `deleted_at`，不额外补写 `updated_at`；保留组行及全部 Job／Instance／Task 历史，不发送停止任务或关闭进程指令 |
| 删除后普通读取、新引用及历史查询 | 普通组读取和新引用排除已删组，历史查询不依赖当前有效组；不借普通入口隐式恢复组 |
| 第一版组管理及表结构 | 无组启停入口或 `status` 列；不能用停用 Job 代替解除引用，也不把删除包装成组级暂停 |
| 等锁期间引用事务提交、事务回滚或请求取消 | 取得锁后另发引用查询，不能复用等锁前快照；回滚不留下半套引用，等待受 Context 限制 |
| 自动触发、Task 派发、回报、启用及手动创建 | 不因本项新增组锁；自动触发、派发、回报不新增逐次组查询；管理存在性校验仍保留 |

组删除完整交付还须验证运行依赖索引、取消恢复、凭据和连接缓存清理顺序。所有 Task 已终态不证明业务线程退出，也不证明所有尽力取消 RPC 已发送；本节不承诺零在途通信。

### 本轮执行配置验收 {#instance-execution-config-checks}

以下对应已通过的 [Instance 执行配置规则](behavior.md#instance-execution-config)，是待实现的验证要求，不是已运行的测试。

| 场景 | 预期结果 |
| --- | --- |
| Instance 已创建但尚未开始，Job 停用并编辑 | 该轮仍使用创建时的执行目标、模式、参数、重试及超时配置，不推迟到首次派发才取值 |
| 编辑后重新启用并创建下一轮 | 新轮使用新配置，旧轮配置不被覆盖；创建及配置保存原子完成 |
| Pre 执行期间修改 Job，之后生成分片或 Post | 后续 Task 仍沿用本轮配置；工作项来自本轮有效准备结果，不混用当前 Job 参数或 Post 开关 |
| 原 Task 失败后，Job 的重试次数或间隔改变 | 本轮重试仍使用保存的次数与间隔，各 Task 独立计数，不因编辑增加或收回预算 |
| Instance 创建后等待一段时间才首次有效开始 | 保存的超时时长不变，倒计时从首次有效开始计算；重试、恢复及 Job 编辑不延长截止时间 |
| 生成节点宕机，由其他节点恢复 | 读取已保存的本轮执行配置，不依赖原节点缓存，不从当前 Job 重建旧轮配置 |
| Job 从组 A 改为组 B，旧轮仍有回报 | 旧轮按已保存的组 A 归属校验，不误拒旧轮合法结果或允许组 B 覆盖；凭据仍按独立认证规则处理 |
| 同轮大量 Task 创建及派发 | 共享配置在 Instance 级保存，不逐 Task 复制完整 Job；查询采用复用或批量加载，验证存储字节与读取成本 |
| Instance 配置保存与读取 | 组标识、状态和运行时间保留独立列，执行配置存入 JSONB；Go 结构体往返序列化保留配置含义，不把运行计数写入共享配置 |
| Job 配置与业务参数存储 | 平台配置保存为普通列，业务参数去首尾空白后保存为 TEXT，内部内容不变；商户范围等业务字段不扩展平台表，JSON 文本不强制转为对象 |
| 触发事务创建本轮配置 | 复用事务中已经读取的 Job，不为构造快照额外查询一次 Job；本轮配置与 Instance 同时提交 |
| 配置结构版本与旧 Instance 恢复 | v1 按明确成员解析；未知版本不得默默改读当前 Job 或套新默认值。未来演进按相应兼容契约验证，不改变已冻结配置 |

存储分工见[Instance 执行配置存储](data-contracts.md#instance-config-storage)。组删除、发现目标变更、凭据轮换及同名处理器升级按各自生命周期和兼容契约补测试，不把配置固定当作冻结资源、凭据或业务代码。

### 触发字段契约验收 {#trigger-field-checks}

以下对应[已通过字段契约](data-contracts.md#trigger-field-draft)，是待实现验证，不是数据库测试结果。

| 场景 | 预期结果 |
| --- | --- |
| 新建时未指定启用 | 默认停用，`next_trigger_at` 与 `deleted_at` 均为 NULL；显式启用则同事务保存未来时间，仍为未删除 |
| 停用并编辑后再次启用 | 停用及编辑保留原进度，再启用重算；停用旧值不是自动触发许可 |
| 仅推进触发进度 | 更新 Job 审计字段 `updated_at`，不将它用作配置版本 |
| 时间持久化往返 | TIMESTAMPTZ 保持相同时间点，显示时区不改变 Cron 解释；非计划运行时间不强制截为秒 |
| 自动与手动身份 | 自动计划时间非空、UUID 为空；手动反之。正常与错失共用自动身份，不按类型拆分 |
| 手动沿用参数后 Job 参数改变，再用原号重发 | 按沿用标记返回原 ID，不拿新 Job 参数比较；覆盖与沿用标记不同则冲突 |
| 同号明确覆盖空串或不同文本 | 覆盖空串不是沿用，全空白规范化为空串；覆盖内容 trim 后精确比较，仅首尾空白不同视为相同，内部空白或 JSON 键序不同仍冲突 |
| 配置 JSONB 往返 | `schema_version=1`，所有成员显式保存；零重试、false、空参数不被省略，参数 JSON 文本仍为字符串 |
| Instance 创建与待开始取消 | 创建时开始／截止／结束时间均为 NULL；待开始取消可只写结束时间，不能强制先开始 |
| 保存历史名称及操作者 | 名称取锁内已读 Job，手动操作者 ID 取认证上下文，不为保存额外查询用户名 |

Job 逻辑删除按[专项验收](#job-deletion-checks)落实，超时初值按[默认值验收](#timeout-default-checks)验证，短字段长度按[容量验收](#string-field-type-checks)验证，输入／查询／错误按[已定契约验收](#job-input-query-checks)；结束原因字典及历史清理策略仍待对应模块设计。

### 触发事务与索引验收 {#trigger-persistence-checks}

以下对应[已确认的触发事务与五个索引](data-contracts.md#trigger-transaction-proposal)，使用真实 PostgreSQL 验证；当前尚未执行。

| 场景 | 预期结果 |
| --- | --- |
| 两个自动入口，或自动与手动入口竞争同 Job | 丢弃策略下先取得 Job 锁的创建成功后，后续独立 SELECT 能看到其活跃 Instance，不按等锁前快照再创建；并行策略允许不同身份并存 |
| 正常定时与错失补执行重复同一身份 | 共用自动部分唯一索引；手动记录不进入该索引，自动记录不进入手动部分唯一索引，不另建同列普通索引 |
| 自动／手动身份字段组合不合法 | 身份结构 CHECK 拒绝不匹配的计划时间、请求号、操作者及自动参数覆盖标记；不增加重试、间隔或超时范围 CHECK |
| 校时回拨后，Job 42 再次算到 `2026-10-15 10:00:00+08:00`，该身份已有历史记录 | 保留原 Instance 的配置、触发类型和终态，推进当前 Job；不通过修改毫秒绕过身份，不重新通知旧 Instance 执行 |
| Instance 插入后、Job 进度更新前失败 | 同一事务全部回滚；进度更新影响行数不是 1 时也不能留下半套记录 |
| INSERT 指定身份冲突、普通写入错误或确认不明 | 只有指定冲突的语句成功且未返回行才按重复处理；超时及其他错误不能伪装成功，确认不明沿用持久化恢复规则 |
| 手动 INSERT 冲突后读取原记录 | 使用下一条 SELECT 取得新快照并比较参数，不用无变化 UPDATE 取旧 ID；记录仍不可见时返回可重试的不确定结果，不在事务中无限循环 |
| 五个索引及实际驱动查询 | 两个身份部分唯一索引、到期 Job、同 Job 活跃 Instance、待开始 Instance 索引与对应谓词匹配；验证预编译执行计划，不把非唯一活跃索引改成限制并行的唯一索引 |

索引验证采用有代表性的历史存量和活跃比例；小表选择顺序扫描不直接判为失败。运行中数据变化和并行清理的成本按[历史存量与持续写入验证](#history-load-checks)检查，不以索引存在或一次查询命中代替持续负载验证。

### 触发记账与低频恢复验收 {#trigger-recovery-checks}

以下场景对应已确认的[同 Job 短事务](execution.md#trigger-accounting)和 [Leader 低频恢复](behavior.md#trigger-recovery)，是待实现的验证要求，不是已运行的测试。

| 场景 | 预期结果 |
| --- | --- |
| Cron 与恢复同时发现同一 Job 的同一触发时刻 | 共用 Job 主键单行协调，后取得锁的一方重读进度，不按旧快照重复创建 Instance |
| 等待 Job 锁期间跨过到期或 5 秒容忍边界 | 使用取得锁后读取的调度进程时间，正常与恢复来源适用相同错失规则 |
| 创建 Instance 与推进进度明确回滚 | 两者均不生效，保留原 `Job.next_trigger_at`；后续回调或恢复可重新判断 |
| 创建和推进已提交，但提交响应丢失 | 不把错误当作回滚，重入后按最新进度及触发身份判断，已有 Instance 走原恢复路径 |
| 启用 Job 的触发提示丢失或本地容量满 | 持久化进度仍留在后续到期候选中；不依赖长期本地补试对象，不静默跳过进度，也不承诺在持续头部阻塞下必能被恢复检查接纳 |
| Leader 接任与普通节点运行 | 新 Leader 立即检查 Job 进度，并每 1 分钟查漏；非 Leader 不执行 Job 触发恢复扫描，仍可恢复已有 Instance／Task |
| 到期候选超过 1024 条，或计划时间相同 | 默认单次主库查询最多返回 1024 条，仅取 `id,next_trigger_at`，按 `next_trigger_at,id` 排序；不执行第二页、不加载历史 Instance／Task、不锁候选行 |
| 本次候选被推进、停用或删除，下一分钟又有新到期 Job | 每次按当时的调度进程时间和数据库事实重新查询；不保存旧列表、跨分钟游标或旧时间上界，实际处理仍锁后重读 Job |
| 非阻塞提交遇到已有 Job，随后新 Job 被队列拒收 | 已有 Job 按原规则合并；首次拒收后结束本次，不等待空位、不尝试保留剩余列表或增设缓冲，下一分钟重新查询 |
| 候选查询失败、超时或运行中错过周期 tick | 查询使用独立 5 秒初始超时，失败结束本次；循环不重叠，不积累或补跑历史 tick，不立即重查 |
| 查询结束后短上下文取消，但已有提示交接给工作协程 | 不取消已交接工作；其使用原 Leader 任期上下文和取出后的 3 秒处理预算，不沿用候选查询的 5 秒上下文 |
| 最早到期的一整批 Job 长期失败，后面仍有到期 Job | 可以持续读到同一批，显式验证这一已接受的公平性边界；不要求遍历全部候选，也不自动停用异常 Job 或推进其进度来制造公平 |
| 发现 Leader 失效时仍有在途处理 | 取消该任期上下文并停止安排新的 Job 恢复检查；允许按最新 Job 合法记账的在途事务提交，不能以停止循环证明其已回滚 |
| 配置未修改但触发记账遗漏 | 每分钟触发恢复仍检查进度，不能因配置内容未变而跳过 |
| 配置同步变慢或单独失败 | 触发恢复由独立后台循环安排，不以配置加载成功为前置条件；仍须读取有效 Job 规则并满足数据库及授权条件，不承诺共享资源完全故障隔离 |
| 两个后台循环运行或发现失去 Leader 身份 | 配置同步与触发恢复各每 1 分钟，不要求同相位或同一 SQL；发现失主后均停止安排新工作，在途提交按已定边界验证 |
| 数据库故障后恢复 | 未提交的进度可由后续检查发现，不增加本地 Job 退避补试；Task、BUSY 和结果回报的既定重试不受影响 |
| 分钟级查漏发现已迟到超过 5 秒 | 按错失策略忽略或最多补一次，并服从阻塞策略；不保证所有遗漏补跑或一分钟内完成恢复 |
| 手动与自动触发竞争，阻塞策略为丢弃 | 创建入口共用 Job 协调，不能均按旧的“无未结束 Instance”结论创建；手动不推进 Cron 进度 |
| 阻塞检查后原 Instance 恰好结束 | 允许仍按检查时未结束的事实丢弃本次，不要求 Instance 结束反向锁 Job |
| 忽略或阻塞丢弃某次自动触发 | 同事务按策略推进进度，不被每轮检查重复处理；确认提交后仅写服务日志，不创建 Instance、跳过表记录或额外 Job 字段 |
| 多个 Job 到期或存在较长遗漏区间 | 候选批次与并发有界，同 Job 短暂串行、不同 Job 可并行；不逐周期无限补建，不按每个 Task 查 Job |

选主生命周期、配置加载、统一 Cron 计算及已定触发事务、索引、单批恢复和跳过日志仍须实现和验证。触发约束与冲突处理按[事务专项验收](#trigger-persistence-checks)检查，容量、过载和队内轮转按[触发容量验收](#trigger-capacity-checks)检查。Job 恢复的周期和非严格公平边界不能直接套用为 Instance／Task 恢复规则。已定语法、时区及身份／区间规则按下列各节验证。

| 跳过事务回滚或提交结果不明 | 不输出已成功跳过的日志；提交不明保留技术不确定信息，不能凭本地判断认定进度已推进 |
| 一次判断折叠多个错失时刻，随后重复提示 | 本次确认提交只输出一条决策日志，不枚举历史 Cron 时刻；重复提示未再次形成跳过决策时不重复输出 |

| 管理端查询实例及成功率 | 实例历史不含跳过明细，不能用其成功率代表全部计划机会；追溯跳过原因依赖服务日志 |

| --- | --- |
| 原计划 10:00:00，调度进程已到点，数据库服务器当前时间为 09:59:59.900 | 到期判断使用锁后调度进程时间；不因数据库服务器稍慢判为未到期，仍须满足最新配置、阻塞及记账条件 |
| 锁后调度进程时间尚未到原计划，数据库服务器时间已超过原计划 | 不按数据库服务器时间提前创建 Instance 或推进进度 |

| Job 触发与 Instance／Task 执行时间规则同时验证 | Job 使用进程时间；执行截止、尝试登记和绑定观察期保留既定数据库时间，不因共用辅助组件误替换 |

统一来源不等于多节点时钟绝对一致。时钟跳变与部署时区变更按下节已定运维边界验证，不增加应用层自动校时。

### 时钟与时区运维验收 {#clock-operations-checks}

以下对应[已定运维边界](operations.md#scheduler-timezone)，包含部署检查和待实现的功能测试要求，不是已经执行的结果。

| 场景 | 预期结果 |
| --- | --- |
| 调度与管理后端多节点部署 | 系统校时由部署保障，所有承担 Cron 计算的进程使用同一时区；不依赖应用层探测时差、修正系统时钟或自动隔离节点 |
| 系统时间向前跳，原计划已逾期 | 下一次实际检查时按固定 5 秒容忍和原错失策略处理，最多补一轮；不承诺跳变瞬间唤醒 Timer、立即检查或补齐全部遗漏 |
| Job 持续启用，`next_trigger_at` 已推进到 10:15，系统时间回到 09:45 | 保留 10:15，不倒退进度；本机时间尚未到点时不创建 Instance，不重新生成已消费的旧轮次 |
| 运维纠正明显时钟故障并重启相关调度进程，Job 始终启用 | 重建内存规则但不重置持久化进度，后续按现有触发及恢复规则判断；异常期间不保证准点或不漏跑 |
| 在维护窗口改变部署时区 | 停用受影响 Job、处理在途执行，退出旧时区计算进程并结束在途计算与事务后，统一改时区、重启、重新启用；不支持混用新旧时区进行启用或触发计算 |
| 按维护流程重新启用，已有历史 Instance | 按新时区计算未来下一次，不补停用期间轮次；不改写历史计划时间、已保存的绝对截止时间或历史执行记录，不增加在线迁移机制 |

显式重新启用沿用启用重算规则，不套用持续启用的“不倒退进度”保证。校时后重算若遇到仍保留的相同自动身份，按已定协议保留旧记录并推进当前 Job，不重新执行旧 Instance，见[事务专项验收](#trigger-persistence-checks)。清理后的身份保留边界仍须衔接，不能由这些运维约定推导任意时钟故障下永久防重。

### Cron 格式与服务器时区验收 {#cron-contract-checks}

以下是[已定 Cron 契约](behavior.md#cron-contract)的测试计划，不是已执行的功能测试。部署时区值是测试输入，不是产品默认值。

| 场景 | 预期结果 |
| --- | --- |
| 六字段数字、列表、范围、步长及英文月份／星期 | 保存、预览、启用和注册使用相同 robfig 语义；例如 `0 */5 * * * *` 按每五分钟计算 |
| 五字段、年份字段、`L/W/#`、`@daily`、`@every`、`TZ=` 或 `CRON_TZ=` | 拒绝不支持的输入，不因底层库支持部分扩展而放行 |
| 星期 `0`、`SUN`、`6`、`SAT` 和 `7` | 前四项分别匹配周日、周六，`7` 不合法；不使用 Quartz 的 1 至 7 编号 |
| 日期／星期使用 `?` 或均指定具体限制 | `?` 沿用 robfig 通配语义；`0 0 9 1 * MON` 为每月一号或每周一九点，不误作“且” |
| 语法可解析但库在搜索范围内找不到下一次时间 | 保存及启用明确报错，不保存零值进度；不把“库未找到”表述为对无限未来的证明 |
| 停用状态保存有效 Cron | 可试算验证，不初始化或推进持久化 `next_trigger_at`；正式值仍由启用事务计算 |
| 多个调度节点采用同一部署时区并切换 Leader | 相同表达式与时间基点计算出同一时间点；无 Job `timezone` 字段和页面时区选择 |
| 调度时区为 Asia/Shanghai，数据库以 UTC 返回持久化的 `next_trigger_at` | 持久化值仍表示同一时间点；预览、注册和直接求下一次都按调度时区解释，例如每日零点对应前一 UTC 日 16:00；不照搬数据库值的 Location，也不改用数据库当前时间 |
| 整个调度部署改用 UTC 的独立测试环境 | 同一每日零点表达式按 UTC 零点计算，证明没有硬编码北京时间；此用例不是现存进度的在线迁移测试 |
| 浏览器或执行器采用不同于调度端的时区 | 不改变调度规则的解释和触发时间点 |
| 部署时区存在夏令时跳时或重复当地时间 | 与 robfig 及该时区规则一致，不额外补造不存在的当地时刻；按实际时间点比较，不承诺当地每天严格一次 |

运行中无下一次时间按下节已定异常处理验收；时钟跳变及部署时区变更按[运维专项验收](#clock-operations-checks)验证，不增加自动迁移或应用层校时。

### Cron 异常处理验收 {#cron-error-checks}

以下对应[简化异常处理](behavior.md#cron-errors)，是待实现的测试要求，不是已运行的功能测试。

| 场景 | 预期结果 |
| --- | --- |
| 保存或启用时语法无效，或语法合法但无可求得的下一次时间 | 拒绝操作；例如每年 2 月 31 日不能因字段数值合法就通过，不保存零值触发时间 |
| 绕过校验写入异常规则，自动触发事务解析或求下一次失败 | 本次不创建 Instance、不推进或清空原进度，不额外创建失败 Instance，不自动改变 Job 启停状态 |
| 同批候选中一条 Job 异常，其余正常 | 按 Job 隔离错误，其他 Job 继续处理；限频错误日志包含异常 Job ID 与原因 |
| 配置加载发现单条非法 Cron，原内存规则仍存在 | 移除该 Job 残留规则，不注册非法规则；数据库启停状态保持不变，其他有效规则继续加载 |
| 同一异常被既有配置核对或恢复再次发现 | 沿用原有处理与限频日志，不追加立即重试、专用队列或扫描；不新增异常状态 |
| robfig 内存条目的 `Next` 已为零，配置投影未变化 | 不要求分钟核对自动重建该条目；不承诺简单停启必然修复，管理员修正原因，必要时重启相关调度进程恢复内存规则 |
| 异常 Job 已有 Instance，或收到合法手动执行请求 | 不取消已有 Instance；手动入口不依赖 Cron 下一次计算，仍执行原鉴权、阻塞及请求身份规则 |

错误处理或仅恢复内存规则不重置持久化进度；若管理员停用、编辑并重新启用，则按既有启用规则重算进度。自动入口仍按当前进度及原错失策略处理，不把这一组验证解释为异常自动自愈或遗漏全部补跑保证。

### 自动触发身份与区间处理验收 {#trigger-identity-checks}

以下是[已通过规则](behavior.md#trigger-identity)的测试计划，不是已执行的测试。除专门验证阻塞的场景外，假设 Job 已启用且允许创建；规则按已定六字段和调度时区解释，持久化采用已定 TIMESTAMPTZ 默认微秒精度，示例未显示的精度不意味着截断。

| 场景 | 预期结果 |
| --- | --- |
| 锁后调度进程时间仍早于 `Job.next_trigger_at` | 不创建 Instance、不推进进度；5 秒容忍不变成提前执行窗口 |
| 迟到恰好 5 秒，错失策略为忽略 | 正常创建一轮，不按错失忽略 |
| 迟到 5 秒再多一个受支持的最小时间单位 | 进入错失策略；比较不通过向下取整将其误判为 5 秒 |
| 每秒一次，旧进度 10:00:00，判定时间 10:00:04 | 只创建一个正常 Instance，`scheduled_at = 10:00:00`，新进度为 10:00:05；不创建五个，不推进到 10:00:01 |
| 每分钟一次，旧进度 10:01，10:05:20 恢复，选择补一次 | 最多创建一轮，`scheduled_at = 10:01`，新进度 10:06；不逐个补五轮，也不把 10:05:20 存为原计划时间 |
| 同上，选择忽略 | 不创建执行 Instance，仍推进到 10:06 |
| 每秒一次，旧进度 10:00:00，10:00:10 检查，选择忽略 | 整段跳过并推进到 10:00:11，不从尾部挑出最近 5 秒再创建 |
| 正常触发或补执行被同 Job 阻塞丢弃 | 不创建执行 Instance，仍推进到判定时间之后首个 Cron 时刻；前轮结束后不补本次 |
| Cron 与恢复分别处理 Job 42 的 `2026-10-15 10:00:00+08:00` 自动身份 | 来源及正常／错失分类不允许绕过 `(job_id, scheduled_at)` 部分唯一索引；重入先重读最新进度，不将其他日期的同一钟点视为该身份 |
| 创建与推进回滚或提交确认不明 | 回滚则两者均不生效；确认不明按最新持久化事实重入，不重放内存旧进度的 INSERT |
| 新进度在事务提交前又到期 | 只要求新进度晚于本次锁后判定时间，不在锁内循环追赶；后续入口按新进度判断 |
| 自动与手动触发发生在同一时刻 | 手动不占用自动唯一身份、不推进 Cron；双方仍共用 Job 阻塞协调，手动请求按下节规则去重 |

时钟异常按既有触发规则及[运维边界](operations.md#scheduler-timezone)处理；校时后重新启用重遇已有历史自动身份时，按[已定冲突协议](data-contracts.md#trigger-transaction-proposal)保留旧记录并推进当前进度。历史清理后的防重衔接仍须明确，不能仅凭保留期间的唯一索引声称无限期防重。

### 手动触发验收 {#manual-trigger-checks}

以下对应已通过的[手动触发规则](behavior.md#manual-trigger)及[手动创建与请求去重](execution.md#manual-trigger-accounting)，是待实现的验证场景。

| 场景 | 预期结果 |
| --- | --- |
| 分别手动执行未删除且启用／停用的 Job | 两种状态均可创建；不修改启停状态或 `next_trigger_at`，不因手动执行补跑自动遗漏 |
| 沿用参数或仅覆盖当次业务参数 | 本轮 `execution_config` 保存实际参数，Job 不变；拒绝临时修改组、处理器、重试及超时配置 |
| 手动创建与停用状态下的编辑并发 | 通过同 Job 协调取得完整配置，不混合修改前后字段；创建后的旧轮快照不因后续编辑或请求重发而变化 |
| 多节点并发提交同一 `job_id`、`request_id` 和请求内容 | 只创建一个 Instance，返回同一 ID；即使阻塞策略为并行，也不能重复创建 |
| 同一请求重发时，原 Instance 仍待开始或运行中 | 先识别已有成功创建，不被自己创建的活跃 Instance 阻塞，不再创建新轮 |
| Job 未删除，原 Instance 已成功、失败或取消，再重发原请求 | 记录保留期间仍返回原 ID，不复活原轮；用户明确再次执行时须使用新请求号，并重新遵守阻塞策略 |
| Job 已逻辑删除，原 Instance 仍保留，再重发原请求 | 先返回 Job 不存在，不继续查重或返回原创建成功；原 Instance 仍可按 ID 查询，不承诺跨 Job 删除重放创建请求 |
| 同一 Job 和请求号携带不同参数再次提交 | 拒绝请求内容冲突，不覆盖原快照，也不另建 Instance |
| 创建事务明确回滚、提交确认不明或成功响应丢失 | 明确回滚不留下半套 Instance 与配置；确认不明及响应丢失沿用原请求号，依据持久化事实处理，不能凭一次未查到就认定回滚 |
| 创建提交与后续业务执行 | 仅在 Instance 和配置提交成功后返回 ID，不等待业务执行；提示“已创建执行记录”，不提示“执行成功” |
| 手动、自动或不同手动请求竞争，阻塞策略为丢弃 | 共用 Job 主键单行短事务和集群未结束 Instance 判断；不提供强制绕过，手动拒绝不推进 Cron 进度 |
| 阻塞拒绝响应丢失，之后同号重试且阻塞已消失 | 拒绝不永久留痕，可以按当时条件创建；客户端收到明确拒绝则结束本次操作，不后台等待补跑 |
| Job 未删除，手动执行记录仍保留或已按规则清理 | 保留期间验证成功创建去重；清理后不承诺旧请求号仍被识别，不能依赖旧 ID 无限期防重 |

请求身份及部分唯一索引存于 Instance，不增加 Redis 锁、独立请求记录表或手动请求队列。参数比较、锁后独立查询及冲突后重读按已确认契约执行，并由[事务专项验收](#trigger-persistence-checks)验证；错误语义按[输入查询契约验收](#job-input-query-checks)，清理协议仍待对应模块补齐。这里的低频创建事务不改变 Task 结果异步回报规则。

### 切主与配置变更验收 {#leader-config-checks}

以下验证[已确认的切主边界](execution.md#leader-config-boundary)，是实现后的验收要求，不是已运行的测试。

| 场景 | 预期结果 |
| --- | --- |
| 同一进程失主后再次当选 | 本地清理完成后才重新参选，新任期使用新 `leaderCtx`；旧上下文保持取消，旧待处理工作不能因 `isLeader` 恢复而重新启动 |
| 发现失主时存在 Cron 回调、配置加载及恢复工作 | 取消原任期上下文，不再安排新工作；取消信号传递到相应数据库操作，不以 Cron Stop 或 Cancel 证明所有在途事务回滚 |
| 新 Leader 当选时，旧 Leader 的触发事务仍在途 | 允许旧事务按最新 Job 合法提交；随后取得 Job 锁的一方按最新进度判断，不凭旧扫描值再建同一轮 |
| 取消或断连导致触发提交确认不明 | 按持久化事实重入，不重放旧 INSERT，不因旧进程已失主就否定已提交 Instance |
| 停用先提交，旧回调仍到达 | 读取到停用，不创建自动触发 Instance，不依赖内存规则已被移除 |
| 触发先提交，随后停用 | 保留已创建 Instance；停用不替代人工停止，也不取消对等节点合法推进 |
| 停用后完成编辑，旧规则回调仍到达 | 尚未启用则不创建；重新启用已提交则按当前规则和新进度判断，不按旧回调携带的时间创建 |
| 逻辑删除先提交，触发随后检查 | 看到 `deleted_at` 非空便不创建，不把仍保留的 Job 行当成有效定义；原 Instance／Task 保留，按[删除专项](#job-deletion-checks)验证 |
| 节点失主，但仍有 Instance／Task 推进、派发或回报 | 不被 `leaderCtx` 一并取消，继续按各自执行权、容量和终态规则处理 |

验收不要求“新 Leader 当选后旧节点零提交”，也不设定尚未批准的残留笔数或固定退出秒数。etcd 选主与 PostgreSQL 提交不是跨系统原子操作；管理变更同一行协调的 SQL、选主参数及已定串行加载与任期隔离仍需对应实现测试。

### 状态与生命周期验收 {#lifecycle-checks}

以下检查对应已通过的状态语义，不代表执行权或事务协议已经完成，也不是已运行的测试结果。

| 场景 | 预期结果 |
| --- | --- |
| 普通任务成功、最终失败 | 只存在一个普通 Task，不生成 Pre 或 Post；平台按有效结果结束 Instance |
| 分片成功／失败且未配置 Post | 等待分片完整生成并全部最终结束，直接由平台汇总；存在最终失败则 Instance 失败，不创建空 Post |
| 合法空数组，配置或未配置 Post | 零分片生成完成事件触发推进；有 Post 则创建唯一 PostTask、传递空结果集合并按统一重试规则执行，无 Post 则在未终止、未到期条件下成功结束 |
| 缺失或非法准备结果 | 不按合法空数组成功，不据此生成成功本轮；校验应答按后续契约验证 |
| 准备最终失败 | 不生成业务分片，不执行正常 Post，Instance 失败 |
| 分片或 Post 尚可重试 | Task 为等待重试，Instance 仍运行中；不能提前汇总为最终失败或创建下一阶段 |
| 分片失败但 Post 成功，或分片成功但 Post 最终失败 | Instance 均失败；阶段间不能抹除已有最终失败 |
| Instance 待开始与首次开始 | 待开始不消耗整轮预算，首次有效开始后预算包含全部推进及业务阶段；重试或换节点不重置期限 |
| 整轮超时配置为 0、负数或无限时长 | 拒绝非法配置；必须使用有限正数，新增表单初值为 900 秒，但不把它作为最大上限或唯一合法值 |
| 手动停止发生在未开始或运行期间 | 未终止且未到期的 Instance 变为取消，后续正常派发、重试及收尾被阻止；不等待所有业务退出 |
| 截止前正常结束与手动停止竞争 | 共用同一父行保护，锁内有效判定并成功提交的终态生效，后者不能覆盖 |
| 取得父锁后的决策点已到截止，超时检查尚未运行 | 尚未终止的 Instance 按超时失败，不因检查延迟写成功或手动取消；原有终态不覆盖 |
| Post 成功已落库，平台汇总中断直至到期 | 保留 Post 成功；恢复在父行保护决策点看到未终止且已到期时按超时失败，不重跑 Post |
| 父终态与子结果／取消竞争 | 不要求父子同事务更新；已有子终态保留，取消先落库则拒绝迟到成功，结果先形成有效终态则保留；均不得复活父 Instance |
| 阶段展示及重复恢复 | 不依赖第二套 Instance 阶段权威字段；生成事实及 Task 可恢复，成功／失败／取消不回退 |

涉及准确截止时刻的用例需在时间来源与事务协议确定后覆盖边界，不能只靠本地定时器触发时刻判断。自动跳过按[留痕验收](#trigger-skip-record-checks)检查；无可用执行器的事件分类仍按后续协议补充。明确 BUSY 的分类及返还规则已经确认，响应编码和事务实现待细化。已绑定无结果的失联执行等待整轮终止，不从节点离线推导提前重派。

### 本地派发与尝试登记验收 {#dispatch-registration-checks}

以下对应已通过的发送前登记与记账规则，是待实现验证的清单，不表示完整执行协议或测试已完成。

| 场景 | 预期结果 |
| --- | --- |
| 完整生成后暂不运行恢复扫描 | 生成节点利用已知 Task 直接启动本地派发，不等待全节点扫描发现新工作 |
| 本地无槽位或整轮分片多于容量 | 不提前登记全部积压，不因本地排队消耗执行机会；容量释放后有界补充 |
| 正常节点与恢复节点同时登记同一 Task | 同一次尝试只有成功条件写入的一方发送，另一方不得凭旧信息发送 |
| 批次中仅部分条目满足条件 | 事务提交后只派发本次成功登记的条目，不能发送整批旧候选 |
| 登记事务回滚或确定未提交 | 不发送 RPC，不占用机会；提交结果不明按已定恢复规则处理，不等同于回滚 |
| 登记已提交、实际 RPC 前节点退出 | 恢复不免费重发；无绑定及结果时从登记的数据库时间有限观察，条件结算后遵守剩余预算；零重试可能业务尚未执行就最终失败 |
| 恢复发现 Task 已执行中 | 不直接抢过来重发，先按确认、结果不明或失联协议处理当前尝试 |
| 登记与 Instance 停止／截止竞争 | 共用单 Instance 主键行锁和锁内当前时间判定，按下述授权与终态清单验证，不凭 Task 条件更新代替父行协调 |

### 新授权与整轮终止验收 {#authorization-terminal-checks}

以下是[已通过协调规则](execution.md#authorization-terminal)的待实现验收要求，不是已经运行的并发测试。

| 场景 | 必须验证的边界 |
| --- | --- |
| 停止先提交，随后登记初次或重试尝试 | 登记取得父锁后拒绝新授权，不发送未经登记的 RPC |
| 登记先提交，停止随后提交 | 已授权 RPC 可能在途或稍后到达，只能尽力取消；后续新尝试被禁止 |
| 同轮多节点登记，不同轮同时登记 | 同轮短登记事务串行，不同轮可并行；每事务只显式锁单表主键单行，任务批次和数量有界 |
| 登记事务等待父锁期间跨过截止 | 锁内使用当前数据库时间，不以事务开始时间继续授权 |
| 截止前完成有效决策，提交或 RPC 到达稍后越过截止 | 不按物理 COMMIT 毫秒倒改已有效提交的决定；不宣称 RPC 或业务副作用的精确时间隔离 |
| 失败回报、BUSY 或未知结算与父终态交错 | 不统一锁父；允许短暂候选态和条件记账修正，但不能覆盖子终态、恢复父状态或授予新尝试 |
| 父终态提交后节点退出，或并发写入重试候选 | 共同恢复覆盖父已终态而子未终态，按子条件取消；不能仅扫描活跃父实例 |
| 子取消与有效终态结果竞争 | 已有子终态保留，取消先提交则旧成功不可覆盖；不把所有父终止后的子结果一律拒绝 |
| 父终态事务与取消 RPC | 子分批取消、RPC 均在父事务之外，不等待全部业务退出后才提交父终态 |
| 稀疏单 Task Instance 与同轮大批派发 | 分别测父行检查次数、锁等待、事务时长及吞吐；不把批量减少往返等同于消除逐轮协调成本 |

SQL、批次大小、首次开始计时的衔接及恢复查询索引在对应模块明确；提交结果不明按下面已通过规则验收。

### 提交结果不明恢复验收 {#commit-unknown-checks}

以下对应[已通过的三类恢复规则](execution.md#commit-unknown)，用于后续故障注入；当前未实施这些测试。

| 场景 | 必须验证的边界 |
| --- | --- |
| 登记已提交但提交确认丢失 | 撤销本次本地发送并释放派发槽位；机会按实际提交占用，事后查询看到已登记也不补发 |
| 登记实际未提交，或原事务仍未决 | 合格 Task 仍经普通父行授权与条件登记；不能凭普通查询没看到改动就宣布回滚或直接发 RPC |
| 登记进入不明分支后迟到确认到达 | 不能恢复已撤销的本地发送计划；已提交尝试复用原登记时间观察与结算，不获得免费重派 |
| 原数据库事务仍持有锁 | 释放本地槽位不宣称数据库锁已释放；后续条件写入允许等待或超时，使用既有超时与退避，不无界堆积 |
| BUSY 返还已提交但确认丢失 | 重做同一条件事务不重复返还，不重复关闭或刷新延期；只比尝试 ID 不够，还须校验未结算旧状态 |
| BUSY 返还未提交、取消或未知结算抢先 | 仅仍有效的原尝试允许原子关闭、一次返还及延期；已经结算则不返还，不能越过终态补账 |
| BUSY 有限记账重试耗尽或进程退出 | 不保留常驻待返还对象，不从数据库猜测丢失的 BUSY 证据；原已提交返还保留，未提交可能占用实际未执行的机会 |
| 结果保存已提交、未提交或期间已失效 | 有界保留原结果并退避条件重做；分别不重复修改、有效时写入、失效时拒绝覆盖，不重复消费执行预算 |
| 结果重做没有再次修改记录 | 可再次提示 Instance 检查，但只依据当前持久化事实推进；不凭旧消息重复生成分片或 Post，不重跑已成功步骤 |
| 可恢复错误持续存在 | 执行结果沿用有界保留且不按次数或 TTL 丢弃；BUSY 元数据使用有限处理，不能混同两种清理规则 |
| 正常成功路径和异常批次核对 | 正常路径不增加写后查询；必要异常核对按批读主库，不用缓存或延迟副本裁决，不把整批提交报错当作每条都未生效 |

本清单不引入新状态、新表或专用队列；具体内部重试参数、驱动错误分类及 SQL 由对应模块实现验证。

### BUSY 返还与延期验收 {#busy-checks}

| 场景 | 必须验证的边界 |
| --- | --- |
| 执行器容量满，明确未接单 | 返还本次已占机会、关闭当前尝试及延期原子提交，不消耗执行重试预算 |
| 执行重试配置为 0，连续明确 BUSY | 可继续按最早派发时间延期，允许请求次数超过原始执行加配置重试次数；不复用旧尝试 ID |
| 超时、断连、通用不可用或 BUSY 响应丢失 | 不推断未接单，不返还机会，按原有不确定结果规则处理 |
| 同一 BUSY 重复处理、旧尝试 BUSY 迟到 | 不能多次返还、覆盖有效结果或让旧尝试重新生效 |
| 返还、关闭和延期事务失败／提交结果不明 | 不出现只返还但仍允许旧尝试推进的中间态，不凭内存确认重复返还或派发 |
| BUSY 元数据有限处理结束 | 原响应释放后不保证恢复返还；不把执行结果的有界长期保留规则套到 BUSY，也不凭推断免费补返 |
| BUSY 与手动停止或整轮截止竞争 | 条件记账修正可交错完成，延期只产生候选；不重置截止，下一次登记必须检查父状态与当前时间，未终态子任务由恢复取消收敛 |
| 多节点恢复处理到期 BUSY Task | 继续使用同一条件登记协议，不额外建队列或扫描；有退避和派发容量约束，不热循环 |
| 原生负载均衡再次选中繁忙节点 | 可以再次明确 BUSY，不能假设每次都换节点或保证最终成功 |

具体状态与响应编码、返还事务 SQL、退避秒数及队列容量仍需实现前明确；本清单不代表实现或故障测试已经完成。

### 接单后执行器绑定验收 {#executor-binding-checks}

以下对应已通过的原生路由、条件绑定及[绑定缺失规则](execution.md#missing-binding)。这些是实施验收要求，不是已运行测试；具体观察期秒数及 SQL 在实现前确定，新授权与父终态协调使用上节已定边界。

| 场景 | 必须验证的边界 |
| --- | --- |
| 原生负载均衡派发并正常接单 | 接收响应提供当前启动实例标识，调度端结合实际地址条件保存本次尝试的执行器绑定 |
| 相同 IP、端口上的执行器重启 | 新进程标识不同；定向取消及核对不能将新进程当作旧尝试的执行器 |
| 定向控制与连接复用 | 不负载均衡到同组其他节点，不为每个 Task 新建连接；代理场景不得盲用 Peer 地址 |
| 有效结果先于绑定保存 | 结果不因缺少绑定被拒绝；有效结果提交后，未知结算失败，迟到绑定不得覆盖结果 |
| 接单 ACK 丢失或绑定提交前调度节点退出 | 从当前尝试登记的数据库时间有限观察；不能假定可定向查询／取消，不广播寻找旧执行 |
| 换调度节点、重复扫描或重试保存绑定 | 不重置观察起点；不随整轮超时时长延长观察期，整轮先到期则服从终止规则 |
| 保存绑定失败，但 ACK 已收到 | 仅重试元数据持久化，不重发业务；内存 ACK 不能当成持久化绑定 |
| 观察期到期但尚未结算 | 仅取得条件结算资格，不自动使当前尝试作废；此时仍可由有效绑定或结果先提交而阻止未知结算 |
| 绑定、有效结果与未知结算并发提交 | 按当前尝试和允许旧状态裁决；绑定先有效则转已知目标路径，结果先有效则按结果处理，结算先有效则拒绝旧绑定／结果；新执行另经父行授权 |
| 结果已经入队，但未知结算先提交 | 入队 ACK 不算有效结果落库，后台不得用旧结果恢复已关闭尝试 |
| 已进入等待重试，下一次尝试尚未创建 | 即使尝试 ID 未变，迟到绑定／结果也不得恢复已关闭尝试，不能只比对 ID |
| 迟到绑定指向不同进程 | 不静默替换已有冲突身份，不覆盖新尝试或终态 |
| 未知结算后预算剩余或耗尽 | 当前机会不重复扣减；剩余预算进入等待重试，沿用默认 10 秒间隔，新登记占下一次机会；耗尽则以结果不确定原因失败 |
| Instance 停止或到期与未知结算竞争 | 可短暂形成重试候选，但不授予新尝试、不恢复父终态；共同恢复包含终态父实例下的未终态子 Task |
| 观察到期时数据库不可用 | 不凭本地计时器宣布结算成功，恢复后条件处理；观察期不被当作恢复完成 SLA |
| 原业务仍在执行或实际已成功，但无绑定及结果落库 | 平台仍可能按预算重试或结果不确定失败；终态不证明业务停止，业务幂等性保护重复副作用 |
| 小批量保存绑定 | 校验每条当前尝试及旧状态，不因合批长时间拖延；统计额外行更新、WAL 与绑定持久化延迟 |

### 异步回报与易失结果验收 {#result-report-checks}

以下对应已通过的双端有界异步、入队 ACK 与后台落库方案；无绑定及结果时按上述窗口规则验收，已有绑定无结果时按等待整轮终止规则验收。具体条件写入尚需实现验证，不表示恢复已经实现。

| 场景 | 必须验证的边界 |
| --- | --- |
| 业务完成后正常回报 | 公共组件入独立有界队列，固定工作协程小批发送并等待 ACK；业务处理器不手写回报，不为每条结果无限创建并发调用 |
| 调度端入队成功、暂停后台消费 | 可以返回接收 ACK，但 Task 仍未形成结果终态，不生成分片、不创建 Post、不结束 Instance |
| 调度端队满或基础鉴权失败 | 不对未接收结果返回成功；未确认的可重传结果仅在独立有限额度内保留，永久错误按最终契约处理 |
| ACK 丢失、重复入队或回报乱序 | 重传沿用同一尝试，不扣执行重试次数；幂等更新不重复推进，旧尝试不能覆盖新尝试 |
| Job 执行重试次数为 0 | 仍允许独立的结果回报重试，发送同一 Task 和尝试的已有结果，不新建尝试、不调用业务处理器 |
| 回报重试耗尽或重新入队 | 释放本地结果并记录错误及丢弃指标；不因重新入队重置额度，不直接改 Task 状态或触发业务重跑 |
| 回报 ACK 丢失，但原结果已被接收或保存 | 本地耗尽后释放不撤销调度端结果，后台仍按尝试及状态条件处理，不由回报失败推断业务失败 |
| 回报重试参数及阻塞请求 | 使用独立内部常量，不沿用 Job 执行次数或间隔；单次 RPC 有超时，具体值及入队等待、退出边界在实施前明确 |
| 认证组有效但引用其他组 Task | 即使基础接收校验已通过，后台仍拒绝越权更新；入队 ACK 不成为数据修改许可 |
| 数据库暂时故障及恢复 | 保留消费者持有的有界批次、退避重试，积压传导至拒收；不把已 ACK 结果仅记日志后丢弃，恢复后提交才通知检查 |
| 执行器回报积压或网络长期中断 | 容量覆盖排队、持有及在途结果；降低／暂停新任务接收，完成结果提交必要时接受背压；耗尽结果可释放，不因无限等 ACK 长期占用结果槽位 |
| 执行器在结果持久化前退出 | 允许未落库结果丢失；不依赖本地文件或跨重启结果缓存，有绑定等待整轮终止，无绑定按独立观察规则处理 |
| ACK 已收到、调度端落库前退出 | 允许丢失唯一结果副本；覆盖执行器仍在线的情况，不能以重传或节点在线假定结果可恢复；有限整轮超时仍有效 |
| 结果已提交、完成检查通知丢失 | 持久化事实支持恢复推进，不因通知丢失重新执行已确认成功的业务 |
| 小批量中混有无效、重复或旧结果 | 每条结果仍受归属、尝试和状态约束；部分接收、确认释放及批次错误隔离按最终契约验证 |

测试覆盖普通、Pre、分片和 Post；特别区分“业务成功但结果未持久化”与“成功结果已持久化、平台推进中断”。前者按有无绑定适用不同规则，不能一律重跑；后者只恢复平台推进。

### 调度端写库故障与容量验收 {#scheduler-result-retention-checks}

以下验证[已确认的保留和背压规则](execution.md#scheduler-result-retention)，不是已经完成的故障测试。

| 场景 | 必须验证的边界 |
| --- | --- |
| 已 ACK 后发生持续可恢复写库故障 | 保留已有结果并退避重试，不按次数或保留 TTL 丢弃；不消费 Task 执行预算或重新运行业务 |
| 队列、消费者及等待重试共同积压 | 三者合计受待处理结果数量上限约束；取出队列不释放待处理容量，不能转入无界旁路缓存或新增等待协程 |
| 容量耗尽后继续回报 | 拒收新结果，不回复成功 ACK；不通过丢弃已接收结果循环腾空并继续 ACK |
| 大报文及批量回报 | 复用 RPC 报文上限，结合条数和固定消费并发验证内存规模；不引入队列总字节配额，不把约束等同于进程 RSS 硬上限 |
| 数据库恢复、提交结果不明或重复结果再次处理 | 依持久化事实幂等处理，不重复推进；重新校验当前尝试、状态和整轮终止规则 |
| 批次含永久无效或过期结果 | 不无限重试坏记录堵住正常结果，也不将短暂数据库错误当作永久无效；错误分类及批次隔离按最终契约验证 |
| 保留期间停止、整轮超时或节点退出 | 不延长截止时间、不复活终态；退出仍可能丢失已 ACK 但未落库结果，不宣称跨重启可靠保存 |

具体容量、RPC 报文上限、退避参数及退出处理留到对应协议和容量验证，不新增未经评审的默认值。

### 整轮超时默认值验收 {#timeout-default-checks}

以下对应已通过的[900 秒默认值](data-contracts.md#timeout-default-proposal)，是待实现验证的要求。管理输入和快照属于本批契约；真实计时、重试和终态推进随执行模块验收，不以文档检查代替功能测试。

| 场景 | 预期结果 |
| --- | --- |
| 打开新增 Job 表单并保存未修改的超时 | 预填 900 秒，提交显式值，Job 保存 900；后续新 Instance 快照为 900 |
| API 未传超时、传 0 或负数 | 拒绝，不由后端或 SQL 静默补成 900；不以 Go 零值代替字段存在性语义 |
| 用户显式改为其他有限合法正数 | 保存实际值，不把 900 当作上限，也不覆盖成默认值 |
| Instance 创建后等待，之后首次有效开始 | 等待期间不启动倒计时；首次有效开始后按本轮时长建立截止，准备、派发、重试等待和 Post 共用预算 |
| 已有 Job 或 Instance 的超时不是 900，随后编辑其他配置或恢复执行 | 不因默认值确定而覆盖旧值；编辑提交实际配置，恢复始终读取本轮快照 |
| 默认 900 秒的轮次，已有绑定的执行器在开始后第 1 分钟宕机且无结果 | 沿用等待剩余整轮时间的规则，不因为默认值改变而提前重派；到期按现有超时及取消语义收敛 |

### 已绑定无结果的整轮超时验收 {#bound-result-wait-checks}

| 场景 | 必须验证的边界 |
| --- | --- |
| 已保存绑定，执行器退出、地址消失或同地址重启 | 不自动提前重派，当前尝试仍执行中；不额外轮询 Task 活动或创建等待结果状态 |
| 执行器在线但回报耗尽，或 ACK 后结果丢失 | 同样等待有效结果、手动停止或整轮到期，不因节点在线假设结果可找回 |
| 截止前有效成功或明确失败落库 | 成功正常推进；明确失败仅在父允许且有预算时重试，不把无结果与失败回报混同 |
| 整轮到期时尚有执行重试额度 | Instance 失败并记录超时原因，未结束 Task 按取消规则收敛，不返还机会、不延长截止、不再重派 |
| 其他分片已成功，仅一个结果永久丢失 | 保留已成功结果；允许整轮等待至超时而不运行正常 Post，不把全部子任务改成业务失败 |
| 调度节点切换或超时提示丢失 | 从持久化截止时间和既有有界检查恢复终止，不依赖原节点内存等待对象 |
| 无执行器绑定或成功结果已有效保存 | 分别沿用绑定缺失观察、已保存结果推进规则，不因本节改变为一律等超时 |

### 内部信任与依赖故障验收 {#trust-dependency-checks}

以下来自 A3 已通过的架构边界及 B2 对回报确认的修订，具体认证、恢复及探针协议仍须在实现前补齐，不表示这些场景已经测试通过。

| 场景 | 必须验证的边界 |
| --- | --- |
| 单进程单组与组内扩容 | 一个执行器进程配置一个组，可提供多个处理器；同组兼容副本共享 Token，不因每个 Job 新增组或凭据 |
| Token 为空、错误、跨组或回报旧尝试 | 不进入未授权业务处理，不跨组修改 Task，不覆盖有效新尝试；无法取得凭据也不得免认证放行 |
| 凭据生成、暴露与缓存 | 后端安全随机生成，无公开默认；日志与普通组列表不泄露凭据；热路径不逐条查组表，更新和撤销按后续明确的时效验证 |
| etcd 注册权限与组 Token 分离 | 禁止越权写发现及选主范围；etcd 授权通过但组 Token 错误时不能成功执行任务 RPC；发现陌生实例不自动创建组 |
| PostgreSQL 故障及恢复 | 前置写入失败不越过持久化授权派发；有容量时可确认回报入队、满后拒收，未提交不推进；恢复服从预算、停止和超时，不假设在途业务已停 |
| Leader 失权与 etcd 发现中断 | 发现失主或无法确认资格后取消该任期，不安排新的自动触发；接受按最新 Job 合法提交的在途事务。非 Leader 身份不阻断合法回报；已有连接可用性与新实例发现分别验证 |
| 单组不可用与业务依赖故障 | 不拖垮其他组或调度全局健康判断；不叠加无限故障重派预算 |
| 回报断连、缓冲耗尽及两侧节点退出 | 回报重传有界，内存接收 ACK 不算落库成功；已 ACK 未落库结果也可能丢失，恢复不绕过幂等、尝试和终态保护 |
| 冷启动、热运行及能力就绪 | 基础配置错误明确失败，短暂故障按能力暴露就绪；不要求所有组在线或每个节点当选 Leader；验证 go-zero 首次注册／发现依赖 etcd 的实际行为 |
| 嵌入业务 RPC | 调度服务暂不可达不单独拖垮原业务接口；原业务自身基础设施依赖照常验证 |

Token 轮换、缓存失效、回报保留、具体恢复时限与 etcd 授权配置，均按后续详细设计补测试输入，不在此设定未经评审的默认值。组 Token 不提供传输加密或单实例强身份隔离，不将这两项作为现有方案已经满足的安全承诺。

## 8.3 容量与性能验证

### 基准场景与负载形态

采用[第 1 章已确认基线](scope.md#_1-6-质量目标与容量前提)：500 条启用规则、其中 100 条同秒到期、单个 Instance 的 1,000 个业务分片，以及 100 个 Instance 各 10 个业务分片。这些是待执行的基准场景，不是已取得的成绩；各场景分别验证，不将数字相乘组成一项叠加承诺，也不据此设置产品最大值。

| 负载形态 | 重点观察 |
| --- | --- |
| 多条规则同一时刻触发 | 回调承载、排队与处理中 Job 总占用、创建事务并发、触发迟到及积压；队满拒绝可观测，持久化进度保留供恢复，排队后仍按锁后调度进程时间应用错失策略 |
| 单个大 Instance | 准备数组内存峰值、Task 插入、尝试登记及接单后绑定的批次数和实际行写／WAL 成本、初始派发节点上限与本地队列占用 |
| 多个小 Instance 同时执行，含大量单 Task 实例 | 实例间公平性、每轮每批父行检查成本、数据库写入与恢复检查竞争，不能按单轮批量收益外推 |
| 同轮密集回报及回报分散到多节点 | 本地合并收益、检查次数、完成延迟和候选推进行锁竞争 |
| 回报峰值与数据库短暂变慢 | 双端队列及在途结果容量、小批处理收益、背压传播、接收与实际落库速率，不能仅按 ACK 吞吐声称数据库承载能力 |
| 大量不同 Instance 的稀疏回报 | 合并收益下降时的持续数据库压力，不能按单轮密集回报成绩外推 |
| 长短任务混合及海量分片 | 准备／收尾是否被挤占，执行器容量、长尾与慢 RPC 槽位占用 |
| 执行器掉线、恢复及重试集中到期 | 重试洪峰、背压、退避、公平轮转和平台资源上限 |
| 大历史存量、持续状态更新与并行清理 | 活跃查询和待处理索引的执行计划、部分索引成员变化及维护成本，清理对在线任务和数据库资源的影响 |

### 历史存量与持续写入验证 {#history-load-checks}

在有代表性的大量已结束 Instance／Task 历史数据上，保持新记录插入和活跃状态更新，再按最终清理协议加入并行清理。分别记录仅历史存量、持续写入、叠加清理三种负载下的触发与回报延迟、吞吐、恢复查询耗时、锁等待、WAL、死元组及 VACUUM 开销，检查五索引及后续执行索引的计划和维护成本。

历史量、活跃比例、持续时间和通过阈值在正式压测前明确；清理算法、批次与保留期限按后续生命周期设计选定，不在这里预设。当前不采用月分区不等于已经证明大表性能满足要求，也不以空表或一次短时查询代替这组持续验证；本组测试尚未执行。

### 指标口径与确认时点

| 指标 | 测量边界 |
| --- | --- |
| 触发延迟 | 计划时刻到对应 Instance 有效落库，不等同于业务开始执行 |
| 回报接收 ACK 延迟 | 调度服务收到回报到成功入队并返回接收确认，不代表持久化完成 |
| 回报持久化延迟 | 调度服务收到回报到有效结果提交，不等待整轮检查或业务 Post |
| 后续推进延迟 | 最后一个业务分片最终结束后，到 PostTask 就绪或适用的平台终态推进；准备完整性等前提必须成立，不混入 Post 业务耗时 |
| 故障恢复耗时 | 按故障类型记录恢复持久化工作或完成应有终止处理的时间，不能只用 RPC 恢复连通代表执行已恢复 |
| 吞吐与资源占用 | 记录对应负载下的持续处理速率、积压和平台内存／并发峰值，区分平台与业务执行器的资源成本 |

测试方案需明确规则数、触发密度、活跃实例数、分片数量与字节体积、执行时长分布、回报速率及部署资源。具体毫秒数、吞吐和恢复时限，在部署资源明确后、正式压测前评审确认；不得测试后按成绩倒定验收标准，也不以 robfig 能管理几百条规则推导整个系统的吞吐。

验收同时检查已持久化工作不因节点退出或通知丢失而静默遗失、旧回报隔离、终态保护、PostTask 唯一创建，以及平台内存结构与并发有界。恢复遵守已批准的预算和终止规则，不代表业务必然成功；进程内有界也不表示数据库积压量天然受限。

固定 5 秒是错失分类边界；配置同步与 Leader 触发恢复各有每分钟检查职责，但都不是执行或恢复 SLA。整轮超时必须有限，不允许 `0`；截止时间约束终态判定，不承诺业务实际退出时间，也不能在数据库不可用时保证准时完成终态提交。
