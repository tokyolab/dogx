# ADR-0004：单租户 RBAC、菜单与接口权限模型

- 状态：已接受
- 日期：2026-08-25

## 背景

DogX 是面向通用后台管理场景的单租户骨架。系统需要同时处理三类含义不同的权限：

- 页面入口权限：决定用户在不同前端应用中能看到哪些目录和页面；
- 页面元素权限：决定页面中的按钮、Tab、操作列等元素是否显示或启用；
- 后端接口权限：决定请求是否允许执行，是系统的安全边界。

PC 管理后台使用动态树形菜单。独立移动管理端可以使用不同的页面入口，但移动端布局、TabBar 和宫格仍由客户端代码维护，后端只控制已有页面入口的显示与隐藏。

权限模型还必须遵守既有认证与架构边界：

- 不引入 `tenant_id` 或 Casbin Domain；
- JWT 保存认证标识和角色 ID，Redis Session 只保存会话信息；两者都不保存菜单、页面元素或具体接口权限；
- PostgreSQL 业务数据由 `system-rpc` 管理，`system-api` 不直接访问业务数据库；
- Redis 中禁止使用 `KEYS` 命令。

## 决策

### 菜单和接口独立授权

角色的菜单权限与接口权限分别配置、分别持久化：

```text
用户 -> 角色 -> sys_role_menu -> sys_menu
             -> casbin_rule  -> path + method
```

两套权限职责固定如下：

- `sys_menu` 控制目录、页面入口和页面元素的显示，不是后端安全边界；
- `casbin_rule` 保存角色的接口策略，后端请求必须通过 Casbin 判定；
- 拥有菜单不自动获得相关接口，拥有接口也不自动获得菜单；
- 后端始终默认拒绝没有匹配策略的受保护请求。

不建立菜单与 API 的强绑定关系。`sys_menu.permission` 只表示前端页面元素权限码，不作为菜单与 API 的关联键，也不参与后端接口放行。这样可以让 PC、移动端和未来其他客户端拥有不同的页面与元素结构，同时共享一套接口权限。

### 多应用菜单

PC 和移动管理端共用 `sys_menu` 与 `sys_role_menu`。`sys_menu.app_code` 标识菜单所属应用，例如：

```text
admin_web
admin_mobile
```

菜单类型包括：

- `1`：目录，仅用于组织页面；
- `2`：页面，代表客户端中可以显示或隐藏的页面入口。
- `3`：页面元素，代表页面中的按钮、Tab、操作列或其他可控制元素。

同一应用中的 `route_name` 和非空 `path` 必须唯一。父子菜单必须属于同一个 `app_code`。

PC 前端根据目录和页面节点生成动态路由与侧边栏，并从已授权的页面元素节点提取 `permission` 集合。页面元素没有路由和组件，通过权限码控制前端元素显示或启用。

移动端可以只配置目录和页面节点，把获得授权的页面标识映射为本地已经编译的 Tab、宫格或页面入口；需要细粒度显示控制时，也可以增加移动端自己的页面元素节点。移动端不要求按树形菜单渲染，也不在 `sys_menu` 中维护客户端布局。

角色配置界面保持两类授权：

```text
[菜单权限] [接口权限]
```

“菜单权限”内部按 `app_code` 切换应用，而不是为 PC、移动端硬编码多个顶级 Tab。

### API 资源目录与 Casbin 持久化

`sys_api` 是接口资源目录，保存：

- 所属服务与业务分组；
- 接口名称；
- HTTP 路径与方法；
- 是否为角色必需接口；
- 启停状态。

`(method, path)` 在未软删除的数据中唯一。接口授权页面读取 `sys_api`，按服务和业务分组展示，并把角色最终选择的策略通过官方 GORM Adapter 写入 `casbin_rule`。

`casbin_rule` 使用官方 GORM Adapter 的标准结构：`ptype`、`v0` 至 `v5`，以及七列唯一索引。DogX 不再维护一份内容重复的 `sys_role_api`，避免角色接口权限出现两个事实源。

角色接口策略约定为：

```text
p, r:<roleId>, <path>, <method>
```

用户与角色关系仍以 `sys_user_role` 为事实源。登录时把用户拥有的全部启用角色 ID 写入 JWT，API 使用这些角色主体批量执行 Casbin 判定；任意角色允许即可放行。修改用户角色、停用角色或删除角色时必须撤销受影响用户的全部 Session。完整加载与多实例生效方案见 [ADR-0005](0005-casbin-runtime-and-policy-sync.md)。

### 页面元素权限

页面元素作为 `sys_menu` 中的第 `3` 类节点，由 `sys_role_menu` 和页面节点一起授权。页面元素必须属于同一个 `app_code` 下的父节点，并填写非空 `permission` 权限码；目录和页面节点不填写该字段。

前端只接收当前角色获授页面元素的权限码集合，并据此控制按钮、Tab、操作列等元素。页面元素权限与 API 权限不自动互相授予，也不要求权限码与 HTTP 路径建立固定映射。

无论页面元素是否隐藏，都不得把前端显示状态作为安全判定依据；后端接口权限始终由 Casbin 保证。

### 运行时边界

Casbin 保护面向客户端的 HTTP 接口。业务 RPC 不重复执行同一份 HTTP RBAC；RPC 端口不得直接暴露到公网，RPC Logic 仍必须验证资源状态、数据归属和业务不变量。

需要接口权限的 HTTP 路由必须显式启用认证和权限中间件。登录、刷新令牌、健康检查等公开接口不进入接口策略；所有登录用户都应具备的自助接口可以只要求有效 Session。

权限不足返回 HTTP 403。Casbin Enforcer、JWT 角色快照、多实例失效通知、串行周期重载和失败关闭规则按 [ADR-0005](0005-casbin-runtime-and-policy-sync.md) 执行。

## 后果

- 菜单和接口权限边界清晰，适合多个前端应用共享同一套后端服务；
- 角色管理员需要分别配置页面入口和接口权限，可能出现有菜单但接口返回 403，或有接口但没有页面入口；
- API 授权树必须提供分组、搜索、整组勾选、必需接口和角色复制等能力，降低人工配置成本；
- 页面元素显示与后端安全解耦，可以独立控制前端交互体验；
- API 路径或方法变化时，权限管理服务必须同步更新相应 Casbin Policy，不能遗留旧路径策略。

## 不采用的方案

- 不让菜单直接打包或自动授予 API：会把不同客户端的页面结构与后端接口绑定；
- 不增加 `sys_role_api`：接口策略只在 `casbin_rule` 中持久化；
- 不使用 `sys_menu.permission` 判定 API 权限：页面元素权限码只供前端显示控制；
- 不把具体菜单或 API 权限写入 JWT；JWT 只携带角色 ID，角色变化通过撤销 Session 处理；
- 不引入多租户 Domain：部门、岗位、门店等业务概念不是租户。

## 测试要求

实现 RBAC 时至少覆盖：

- 同一角色的菜单权限与接口权限互不自动影响；
- `app_code` 正确隔离不同前端应用的菜单，同一菜单树不能跨应用引用父节点；
- 页面元素权限随角色菜单授权正确返回，不生成路由，也不能代替 API 权限；
- 无角色用户默认拒绝受保护接口；
- 单角色允许和拒绝，多角色任一允许即放行；
- HTTP 路径、方法和角色策略正确匹配；
- 必需 API 不能从普通角色策略中遗漏；
- 停用用户、角色或 API 后旧权限在约定时间内失效；
- 权限不足返回 HTTP 403。
