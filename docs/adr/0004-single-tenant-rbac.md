# ADR-0004：单租户 RBAC、菜单与接口权限模型

- 状态：已接受
- 日期：2026-08-25

## 背景

DogX 是面向通用后台管理场景的单租户骨架。系统需要同时处理三类含义不同的权限：

- 页面入口权限：决定用户在不同前端应用中能看到哪些目录和页面；
- 页面元素权限：决定页面中的按钮、Tab、操作列等元素是否显示或启用；
- 后端接口权限：决定请求是否允许执行，是系统的安全边界。

PC 管理后台使用动态树形菜单。独立移动管理端可以使用不同的页面入口，但移动端布局、TabBar 和宫格仍由客户端代码维护，后端只控制已有页面入口的显示与隐藏。

权限模型还必须遵守既有认证与架构边界：

- 不引入 `tenant_id` 或 Casbin Domain；
- JWT 保存认证标识、角色 ID 和服务端派生的 `isSuperAdmin`，Redis Session 只保存会话信息；两者都不保存菜单、页面元素或具体接口权限；
- PostgreSQL 业务数据由 `system-rpc` 管理，`system-api` 不直接访问业务数据库；
- Redis 中禁止使用 `KEYS` 命令。

## 决策

### 菜单和接口独立授权

角色的菜单权限与接口权限分别配置、分别持久化：

```text
用户 -> 角色 -> sys_role_menu -> sys_menu
             -> casbin_rule  -> path + method
```

两套权限职责固定如下：

- `sys_menu` 控制目录、页面入口和页面元素的显示，不是后端安全边界；
- `casbin_rule` 保存普通角色的接口策略，普通用户的受保护请求必须通过 Casbin 判定；
- 拥有菜单不自动获得相关接口，拥有接口也不自动获得菜单；
- 普通用户没有匹配策略时，后端始终默认拒绝受保护请求；拥有有效 `super_admin` 角色的用户按下述系统内置角色规则旁路 Casbin。

不建立菜单与 API 的强绑定关系。`sys_menu.permission` 只表示前端页面元素权限码，不作为菜单与 API 的关联键，也不参与后端接口放行。这样可以让 PC、移动端和未来其他客户端拥有不同的页面与元素结构，同时共享一套接口权限。

### 多应用菜单

PC 和移动管理端共用 `sys_menu` 与 `sys_role_menu`。`sys_menu.app_code` 标识菜单所属应用，例如：

```text
admin_web
admin_mobile
```

菜单类型包括：

- `1`：目录，仅用于组织页面；
- `2`：页面，代表客户端中可以显示或隐藏的页面入口。
- `3`：页面元素，代表页面中的按钮、Tab、操作列或其他可控制元素。

同一应用中的 `route_name` 和非空 `path` 必须唯一。父子菜单必须属于同一个 `app_code`。

PC 前端根据目录和页面节点生成动态路由与侧边栏，并从已授权的页面元素节点提取 `permission` 集合。页面元素没有路由和组件，通过权限码控制前端元素显示或启用。

移动端可以只配置目录和页面节点，把获得授权的页面标识映射为本地已经编译的 Tab、宫格或页面入口；需要细粒度显示控制时，也可以增加移动端自己的页面元素节点。移动端不要求按树形菜单渲染，也不在 `sys_menu` 中维护客户端布局。

角色配置界面保持两类授权：

```text
[菜单权限] [接口权限]
```

“菜单权限”内部按 `app_code` 切换应用，而不是为 PC、移动端硬编码多个顶级 Tab。

### API 资源目录与 Casbin 持久化

`sys_api` 是接口资源目录，保存：

- 所属服务与业务分组；
- 接口名称；
- HTTP 路径与方法；
- 是否为角色必需接口；
- 启停状态。

`(method, path)` 在未软删除的数据中唯一。接口授权页面读取 `sys_api`，按服务和业务分组展示，并把角色最终选择的策略通过官方 GORM Adapter 写入 `casbin_rule`。

`casbin_rule` 使用官方 GORM Adapter 的标准结构：`ptype`、`v0` 至 `v5`，以及七列唯一索引。DogX 不再维护一份内容重复的 `sys_role_api`，避免角色接口权限出现两个事实源。

角色接口策略约定为：

```text
p, r:<roleId>, <path>, <method>
```

用户与角色关系仍以 `sys_user_role` 为事实源。登录时把用户拥有的全部启用角色 ID 写入 JWT；普通用户由 API 使用这些角色主体批量执行 Casbin 判定，任意角色允许即可放行。修改用户所属角色时必须撤销该用户的全部 Session；停用或重新启用角色不撤销关联用户 Session，在下一次登录或刷新令牌时进入新的 JWT 角色快照。仍被未软删除用户引用的角色禁止删除。完整加载与多实例生效方案见 [ADR-0005](0005-casbin-runtime-and-policy-sync.md)。

`sys_role.is_system` 标记系统内置角色，但不表示该角色天然拥有超级管理员权限；未来增加的其他系统内置角色仍按普通角色的 Casbin 策略鉴权。超级管理员只由固定角色编码 `super_admin` 表示，不依赖固定数据库 ID。

`super_admin` 是不可配置接口权限和菜单权限的内置角色。用户拥有未停用的 `super_admin` 角色时，登录和刷新 Token 会得到服务端签名的 `isSuperAdmin = true`；JWT 与 Redis Session 校验通过后，后端直接放行该用户的受保护接口，不依赖 `casbin_rule`，新增接口也不需要逐条授予超级管理员。角色管理前端应显示“全部权限（系统内置）”并禁止编辑接口权限树，后端也必须拒绝针对 `super_admin` 的接口授权请求，不能只依赖前端限制。

同样地，超级管理员取得菜单时始终由后端返回全部未软删除且已启用的目录、页面和页面元素，不依赖 `sys_role_menu`，新菜单也不需要逐条授权。角色管理前端对其菜单权限显示“全部菜单（系统内置）”并禁止编辑菜单树，后端菜单授权接口必须拒绝针对 `super_admin` 的写入。前端仍消费后端返回的菜单树和页面元素权限码，不在客户端硬编码或自行拼装超级管理员菜单。

初始化的 `super_admin` 角色不可停用、删除或修改编码，避免后台通过普通角色管理接口破坏首次授权和恢复入口；名称、描述和排序仍可按展示需要修改。用户与角色管理还必须保证系统始终至少存在一名未软删除、已启用且持有启用 `super_admin` 角色的用户，不能通过停用用户、移除角色等操作删除最后一个有效超级管理员。普通角色使用软删除；删除前只检查未软删除用户的引用，存在引用时整个操作失败且保持角色、关联和策略原样。没有引用时，删除事务同时硬删除软删除用户遗留的 `sys_user_role`、`sys_role_menu` 关联，并通过官方 Casbin Adapter 删除该角色的全部 `p` 策略。

### 页面元素权限

页面元素作为 `sys_menu` 中的第 `3` 类节点，由 `sys_role_menu` 和页面节点一起授权。页面元素必须属于同一个 `app_code` 下的父节点，并填写非空 `permission` 权限码；目录和页面节点不填写该字段。

前端只接收当前角色获授页面元素的权限码集合，并据此控制按钮、Tab、操作列等元素。页面元素权限与 API 权限不自动互相授予，也不要求权限码与 HTTP 路径建立固定映射。

无论页面元素是否隐藏，都不得把前端显示状态作为安全判定依据；后端安全边界始终由授权中间件保证，普通用户的接口权限由 Casbin 判定。

### 运行时边界

Casbin 保护普通用户访问的面向客户端 HTTP 接口；超级管理员在 JWT 与 Redis Session 校验后先按签名 Claim 旁路 Casbin。业务 RPC 不重复执行同一份 HTTP RBAC；RPC 端口不得直接暴露到公网，RPC Logic 仍必须验证资源状态、数据归属和业务不变量。

需要接口权限的 HTTP 路由必须显式启用认证和权限中间件。登录、刷新令牌、健康检查等公开接口不进入接口策略；所有登录用户都应具备的自助接口可以只要求有效 Session。

权限不足返回 HTTP 403。Casbin Enforcer、JWT 角色快照、多实例失效通知、串行周期重载和失败关闭规则按 [ADR-0005](0005-casbin-runtime-and-policy-sync.md) 执行。

## 后果

- 菜单和接口权限边界清晰，适合多个前端应用共享同一套后端服务；
- 角色管理员需要分别配置页面入口和接口权限，可能出现有菜单但接口返回 403，或有接口但没有页面入口；
- API 授权树必须提供分组、搜索、整组勾选、必需接口和角色复制等能力，降低人工配置成本；
- 页面元素显示与后端安全解耦，可以独立控制前端交互体验；
- API 路径或方法变化时，权限管理服务必须同步更新相应 Casbin Policy，不能遗留旧路径策略。
- 超级管理员不依赖逐条 API Policy 或 `sys_role_menu`，不会因误清空接口权限树、菜单权限树或新增资源未授权而锁死管理入口；该能力只由服务端签名 Claim、有效 Session 和受保护的内置角色关系共同决定。

## 不采用的方案

- 不让菜单直接打包或自动授予 API：会把不同客户端的页面结构与后端接口绑定；
- 不增加 `sys_role_api`：接口策略只在 `casbin_rule` 中持久化；
- 不使用 `sys_menu.permission` 判定 API 权限：页面元素权限码只供前端显示控制；
- 不把具体菜单或 API 权限写入 JWT；JWT 只携带角色 ID 和派生的 `isSuperAdmin`，用户所属角色变化通过撤销 Session 处理，角色启停在下一次登录或刷新令牌时生成的新快照中生效；
- 不引入多租户 Domain：部门、岗位、门店等业务概念不是租户。

## 测试要求

实现 RBAC 时至少覆盖：

- 同一角色的菜单权限与接口权限互不自动影响；
- `app_code` 正确隔离不同前端应用的菜单，同一菜单树不能跨应用引用父节点；
- 页面元素权限随角色菜单授权正确返回，不生成路由，也不能代替 API 权限；
- 无角色用户默认拒绝受保护接口；
- 单角色允许和拒绝，多角色任一允许即放行；
- 有效超级管理员在 JWT 与 Session 校验后不进入 Casbin；伪造或篡改 `isSuperAdmin` 的 JWT 无法通过验签；
- HTTP 路径、方法和角色策略正确匹配；
- 必需 API 不能从普通角色策略中遗漏；
- 停用用户、角色或 API 后旧权限在约定时间内失效；
- `super_admin` 不能停用、删除、修改编码或配置接口与菜单权限，其他 `is_system` 角色不会自动获得超级管理员权限；
- 超级管理员即使没有任何 `sys_role_menu` 记录，也能取得全部有效菜单和页面元素；普通角色仍严格按 `sys_role_menu` 返回；
- 停用用户或修改用户角色时不能移除最后一名有效超级管理员；被未软删除用户引用的普通角色不能删除，拒绝时所有数据保持原样；可删除角色成功后不残留用户、菜单关联或 Casbin 策略；
- 权限不足返回 HTTP 403。
