# ADR-0001：DogX v0.1 架构

- 状态：已接受
- 日期：2026-08-21

## 决策

### 后端仓库与服务边界

DogX 后端使用一个 Git 仓库和一个 Go Module。可独立部署的进程放在 `apps` 下，首个服务域为 `system`，包含两个进程：

- `system-api`：面向客户端的 REST API/BFF。
- `system-rpc`：面向内部调用的 gRPC 服务，承载业务逻辑和数据访问。

当前固定调用链为：

```text
client → system-api → system-rpc → PostgreSQL / Redis
                 └─ 只读认证 Session → Redis
                 └─ 只读权限快照 → PostgreSQL 授权表
```

API 与 RPC 分别构建、配置和部署。后续只有出现清晰的业务边界、独立伸缩需求或独立数据所有权时，才在 `apps` 下新增服务域；不会仅按数据表拆分服务。

### go-zero 范式

API 保留 goctl 可识别的 `.api` 契约和官方生成式结构：

```text
.api definition → handler → logic → svc.ServiceContext → zrpc client
```

RPC 保留 Protobuf 契约和 goctl 生成式结构：

```text
.proto definition → gRPC server → logic → svc.ServiceContext → GORM / Redis
```

- API Handler 只负责 HTTP 参数解析和响应。
- API Logic 负责 BFF 层的调用编排和协议错误转换，不直接访问数据库。
- HTTP 契约以 `system.api` 作为唯一生成入口，业务类型和路由按资源拆分到 `desc/*.api`；公共基础类型集中在 `desc/base.api`。
- RPC Logic 承载业务用例并通过仓储或数据访问层读写数据。
- 两个进程的 `ServiceContext` 都显式持有各自依赖，不使用包级可变全局数据库或 Redis 实例。
- API 的 `ServiceContext` 持有 zrpc 客户端、只读认证 Session 依赖，以及 RBAC 阶段的 Casbin Enforcer 和权限专用只读 PostgreSQL 连接；RPC 的 `ServiceContext` 持有 GORM、Redis 和后续的仓储、领域服务。
- 可使用 goctl 生成重复代码，但生成器不是架构边界，也不是测试替代品。

当前不在 API 前增加独立的 go-zero Gateway。生产部署可由负载均衡或反向代理将外部流量转发给多个 `system-api` 实例。

### 数据访问

- API/BFF 不初始化通用业务 Repository，也不直接访问普通业务表。RBAC 阶段允许 `system-api` 使用权限专用只读 GORM 连接加载 `casbin_rule` 中的 Casbin `p` 策略；该例外只服务于本地 Casbin 判定，完整边界见 [ADR-0005](0005-casbin-runtime-and-policy-sync.md)。
- 普通业务数据库访问仍由 `system-rpc` 负责；未来同属 System 域且确需直接访问数据库的 MQ、Job 进程可以复用 System 域数据层。
- API 只通过窄接口精确读取认证 Session，不通过 Redis 写入会话或保存普通 CRUD 缓存。
- ORM 使用 GORM，不使用 go-zero `sqlx/model` 自动缓存模板。
- 数据库结构以 Goose 管理的版本化 SQL 迁移为准，不在 RPC 启动时执行 GORM `AutoMigrate`。
- 迁移版本采用 Goose 官方混合策略：开发阶段使用时间戳，正式发布前转换成连续版本。
- GORM 模型及与模型字段直接绑定的类型和常量放在 `apps/system/internal/model`，数据库操作通过 `apps/system/internal/repository` 中的窄接口封装；迁移、数据库配置和连接工厂也由 System 域统一持有。
- RPC Logic 不直接调用 GORM、手写 SQL 或解析 PostgreSQL 驱动错误。Repository 隔离数据库查询、事务、锁和约束错误，使业务 Logic 单元测试不依赖数据库；真实 PostgreSQL 行为由 Repository 集成测试验证。
- Repository 默认按聚合或业务资源提供一个包含必要读写能力的内聚接口，不仅为了测试替身而拆分 Reader、Writer、Store，也不建立机械转发 ORM 的通用 BaseRepository。跨聚合、Casbin、Session 或事件发布的业务事务由显式业务服务负责。
- 其他业务域不得导入 System 域的 Model、Repository 或直接访问其数据表；跨域读取和操作通过 RPC 或事件完成。
- 需要跨业务域理解的字段、枚举和消息定义在 Protobuf 或版本化事件契约中，不通过 GORM Model 共享。
- 唯一支持的关系型数据库是 PostgreSQL；当前主版本使用 PostgreSQL 18，数据库迁移尽量保持 PostgreSQL 17 兼容。不为 MySQL、SQLite 或其他数据库保留运行时适配层，也不为了跨数据库兼容放弃合理的 PostgreSQL 能力。
- Redis 只用于会话、验证码和其他明确的分布式状态；Casbin `p` 通过 Redis Watcher 失效通知和 PostgreSQL 周期重载保持多实例最终一致。
- 不为普通用户、角色、菜单 CRUD 默认增加缓存。

### API 风格

- 业务接口采用 Action 风格并默认统一使用 `POST`，包括查询、详情、列表、新增、修改和删除，例如 `POST /user/get`、`POST /user/list`、`POST /user/create`。
- 普通业务 CRUD 默认不使用 `GET`、`PUT`、`PATCH` 或 `DELETE`；只有协议、浏览器或工具生态明确要求时才使用其他 HTTP Method。
- 健康检查、就绪检查、指标等基础设施端点遵循工具生态约定，使用 `GET`。
- 成功响应使用 HTTP 200 和数字 `code=0`；业务错误使用 HTTP 200 和 `100000+` 数字业务码。
- 参数错误和技术错误使用真实 HTTP 4xx/5xx，内部错误细节只写日志。
- 统一响应与内部 RPC 错误传输的完整约定见 [ADR-0002](0002-http-response-and-rpc-errors.md)。

### 配置与密钥

- 仓库只提交 `*.example.yaml`。
- 同目录真实 `*.yaml` / `*.yml` 被 `.gitignore` 忽略。
- go-zero `conf.UseEnv()` 展开 `${ENV_NAME}`，部署环境可从环境变量或未来的配置中心注入密钥。
- API 配置保存 REST、应用信息、RPC 客户端配置、只读认证 Redis 连接，以及 RBAC 阶段的权限专用只读 PostgreSQL 配置。
- RPC 配置保存 gRPC 服务、PostgreSQL 和 Redis 配置。
- 代码、示例配置、测试和日志不得包含真实密码或令牌。

### 健康检查

- `GET /health` 是 API 存活检查，不访问 RPC、PostgreSQL 或 Redis。
- `GET /ready` 是整条服务链的就绪检查：API 检查认证 Redis、权限只读 PostgreSQL 和 Casbin 初始快照，再调用 RPC 检查 PostgreSQL 与 Redis。
- RPC 依赖异常时返回 gRPC `Unavailable`；API 对外转换为 HTTP 503，且不泄漏内部错误细节。

### 测试

- 每个首要用例同步编写 Logic 单元测试。
- API Handler 使用 `httptest` 验证 HTTP 契约。
- PostgreSQL、Redis 和 RPC 客户端等外部依赖通过窄接口隔离，普通单元测试不访问公网开发环境。
- 数据库迁移和仓储层后续增加独立集成测试。

## 暂不采用

- 在 `system-api` 前增加独立的 go-zero Gateway。
- goctl model/sqlx 自动缓存。
- 使用 GORM `AutoMigrate` 替代版本化迁移。
- 多租户数据模型。
- 将 PC 管理端和移动端放入后端仓库。
