# ADR-0007：字典使用边界、管理与缓存

- 状态：已接受
- 日期：2026-09-28

## 背景

DogX 需要支持业务人员维护分类和表单选项，并供列表、详情和表单复用。字典不应替代代码枚举、业务实体或系统参数。一个页面可能使用多个字典，因此首版同时提供批量读取和 Redis 缓存，不照搬逐个请求字典的方式。

## 决策

### 使用边界

- 字典用于可配置的分类选项，例如客户来源、客户行业。新增选项后，程序仍执行相同的保存、展示、筛选逻辑，不需要增加代码分支。
- 用户启停、菜单节点类型、订单支付状态等决定程序行为或状态流转的值使用固定枚举，不交给字典管理。前端集中维护这些枚举的文案、颜色和国际化映射，后端负责合法性及状态流转校验。
- 部门、角色、门店等有独立关联关系或业务行为的数据独立建模；登录有效期、上传大小等属于系统参数，不放入字典。
- 业务表保存稳定的字典值，前端根据字典映射显示标签，不把显示标签当作关联依据。
- 字典选项不是权限。公开访问、业务接口权限和业务数据权限分别判断。
- 前端选项不能代替后端校验。业务要求从字典中选择时，后端校验取值；是否允许保留已有的停用值由业务用例明确处理。

### 模型与交互

- 使用字典、字典项两张表，首版为平铺结构，不支持父子层级、扩展值、默认项、导入导出。
- 字典包含名称、编码、备注、状态、是否公开；是否公开默认关闭。
- 字典项包含所属字典、标签、值、排序、备注、状态。字典值统一使用字符串。
- 字典编码全局唯一，同一字典内的值唯一，由数据库唯一约束兜底；编码和字典项值创建后不可修改，标签可以修改。
- ID、排序和状态类型遵守现有跨层类型规范；字段长度、编码格式和批量上限在实现契约时明确，并同步前后端校验，不使用无界批量请求。
- 左侧选择字典，右侧管理字典项；新增编辑使用现有弹窗和表单风格，列表、状态开关和操作反馈沿用已定的角色管理规范，不引入行内编辑。
- 管理界面固定文案支持国际化；字典名称和标签填什么显示什么，不配置国际化 key，也不在后端翻译文件中维护字典内容。切换界面语言不会翻译管理员填写的数据。

### 停用、删除与历史展示

- 字典或字典项停用后，不再作为新增选择项；不修改、清空已保存的业务值。
- 停用项仍可参与历史值的标签映射。编辑历史数据时必须保留原值，不能因其不在可选列表中而自动清空；能否原样保存由业务用例决定。
- 有字典项时禁止删除字典；允许删除字典项，不提供扫描所有业务表或登记所有业务引用的通用检查机制。
- 已使用但不再需要选择的项优先停用，删除用于清理误建项。删除确认沿用现有简短文案，不增加长篇风险提示。
- 已删除或无法识别的值显示原始值，不显示空白，不改写业务字段；不承诺删除后仍能显示原标签。

### 读取与权限

- 管理列表、管理详情和维护操作需要对应接口权限，直接查数据库，不使用业务字典缓存。
- 业务读取按编码数组批量获取，单个字典也使用同一接口；普通后台用户需要有效登录，但不要求拥有字典维护权限。
- 提供无需 Token 的公开批量读取接口。服务端对每个请求编码检查公开属性，不允许通过混入非公开编码读取内部字典。
- 公开属性由数据库中的字典配置控制，不维护代码白名单。非公开字典不因未来增加 App 而自动开放；App 的非公开读取需求届时接入对应身份体系，不复用后台 Token。
- 业务读取区分可选性和历史展示：返回字典、字典项状态，只有两者均启用时才可新增选择；标签映射保留停用项。公开读取对历史映射同样执行公开性检查。
- 一个请求中的多个字典使用批量数据访问，禁止逐个编码查询数据库；列表的每一行也不得单独请求字典。

### Redis 数据结构与旁路缓存

- 首版加入 Redis 缓存。一个字典对应一个 String Key，JSON 同时保存字典状态、公开属性和整组未删除字典项，包含停用项。
- 字典项缓存只含业务读取需要的标签、值、状态、排序；不缓存管理用的 ID、时间戳和备注。不将公开状态拆成另一个独立缓存键。
- Key 由集中定义统一生成，业务代码不散落拼接魔法值。示意结构如下，字段状态值遵守现有枚举：

```text
dogx:system:{dict}:customer_source
```

```json
{
  "status": 1,
  "isPublic": false,
  "items": [
    { "label": "官网", "value": "website", "status": 1, "sort": 0 },
    { "label": "展会", "value": "exhibition", "status": 0, "sort": 10 }
  ]
}
```

- 使用旁路缓存：批量读取 Redis，命中则使用；未命中的编码批量查库，按字典回填，再返回。命中缓存后仍检查公开属性和状态，不能直接将内部缓存原样作为公开响应。
- Redis TTL 固定为 24 小时，从写入时计时，不因读取续期。首版不添加随机 TTL、进程内回填请求合并或分布式锁。
- 字典存在但没有字典项时，缓存空列表，空列表不是缓存未命中。数据库查询失败时不把错误伪装成空列表并缓存。
- Redis 读取失败时可以回源数据库；数据库查询成功但回填 Redis 失败时，返回数据库结果并记录错误，不因缓存写入失败使正常读取失败。
- 保持现有 API → RPC 分层，数据库访问和字典缓存协调留在 System RPC 侧；API 不新增普通业务数据库访问，不增加 Service 层。

### 自动失效与手动刷新

- 正常新增、修改、删除、启停字典项：数据库操作成功后，删除所属字典的整组 Redis 缓存，不立即重建。
- 字典属性变化、公开属性变化或删除字典，同样失效对应编码的缓存；新建字典也清理同编码可能残留的旧缓存。
- Redis 操作在数据库事务外执行，不修改 PostgreSQL 默认隔离级别，不增加数据库显式锁。
- “刷新缓存”是有独立接口权限的管理操作，用于直接修改数据库或异常后的修复；只清理全部字典 Redis 缓存，不全量查库写入、不做预热、不退出登录。
- 全部清理必须覆盖数据库中已经不存在、但 Redis 尚残留的字典。按现有 Redis 规范维护显式缓存键索引并分批清理，不使用 `KEYS`、不使用 `FLUSHDB`，也不靠键名通配扫描实现该业务操作。索引不是第二份字典内容缓存。
- 失效失败必须记录并向调用方明确反馈，不能报告缓存刷新成功，也不能声称已提交的数据库修改被回滚；不得通过无条件重放新增、删除等业务写入来重试缓存失效。

### 前端缓存

- 前端按字典编码保存内存缓存，不设 TTL，不持久化到 localStorage 或 sessionStorage。
- 正常字典维护和手动“刷新缓存”均不主动清理当前窗口或其他窗口的业务字典缓存，不增加跨窗口、跨用户通知。
- 管理页面保存后重新查询管理数据；已经加载字典的业务页面可能继续显示旧标签或选项，这是明确接受的行为。
- 用户刷新浏览器后清空内存并重新请求；仅切换系统页签不保证更新。重新请求后，Redis 未命中时自动查库回填。
- 前端缓存不作为服务端校验或权限判断依据。

## 首版实现约定

- 编码为 1～64 位，以小写字母开头，只允许小写字母、数字、下划线和短划线。名称、标签和值最多 128 个字符，备注最多 500 个字符；排序为非负 int32。
- 单次业务读取接受 1～50 个编码，服务端去重后按请求顺序返回。不存在的字典不返回、不做负缓存；公开读取也省略非公开字典。
- HTTP 管理接口使用 `/dictionary/*`，字典项使用 `/dictionary/item/*`；登录读取为 `/dictionary/read`，匿名读取为 `/dictionary/public/read`，均接受编码数组。匿名入口由 API 固定设置 RPC 的公开读取标志，不信任请求体提供的标志。
- 全量清理接口为 `/dictionary/cache/clear`。缓存索引为 `dogx:system:{dict}:_index` Set；内容写入和索引登记使用 Lua，删除内容和移除索引也使用 Lua。共享 Redis hash tag 保证这些键在 Cluster 下位于同一槽，这不是分布式锁。
- 全量清理使用 SSCAN 遍历显式索引，每批最多删除 200 个内容键；同时存在的在途回填仍遵守下文的最终一致性取舍。索引中的过期内容键会在清理时一并移除。
- 前端 `loadDictionaries` 批量复用内存缓存；`dictionaryChoices` 用于新增选项，`dictionaryLabel` 用于历史标签与原值回退，`dictionaryEditChoices` 保留不可再选的历史值。业务提交时仍需执行自身后端校验。

## 取舍与限制

- 采用简单旁路缓存，不承诺数据库、Redis 和所有已打开页面之间的强一致性。删除缓存失败，或并发旧查询在删除后回填，均可能使 Redis 暂时保留旧值；TTL 和手动刷新提供恢复途径，不代表每次刷新都能阻止在途请求的旧值回填。
- 24 小时是后端缓存兜底过期时间，不是前端内容的最长陈旧时间。前端不设 TTL，已打开页面可以持续使用旧值，直到用户刷新浏览器。
- 公开属性也位于缓存中，因此从公开改为非公开不承诺瞬时撤回所有已发出的数据或旧缓存；公开字典只放允许公开的信息，不存放秘密，也不把该开关当作敏感数据的紧急撤权机制。
- 不做全量预热。批量过期或手动清理后存在集中回源的可能，批量查询仅减少每个请求的数据库访问次数，不消除不同并发请求之间的重复查询；出现实际压力后再评估请求合并等措施。
- 删除、改标签都不是历史快照功能。需要保留交易发生时原始名称的业务，应自行保存相应业务快照，不能依赖当前字典标签。

## 验证

- 覆盖编码和值的唯一约束、禁止改值、字典有项时禁止删除、停用与历史标签映射、删除后原值回退。
- 覆盖普通登录读取、管理权限、公开读取和混合编码请求不能泄露非公开字典，包括缓存命中与回源两条路径。
- 覆盖全命中、部分命中、全未命中、空字典、固定 TTL、批量查询次数，以及 Redis 读写故障降级。
- 覆盖数据库成功后才失效缓存、失败反馈、手动全部清理包含残留键且不影响其他业务缓存。
- 使用真实 Redis 验证存储和失效，前端验证管理列表更新与业务缓存保留、刷新浏览器重新加载；保持既有单元测试、集成测试和覆盖率检查。
